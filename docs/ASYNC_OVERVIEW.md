# 非同期タスク・イベントキュー機能の概要

作成日：2026-11-13  
状態：企画案・詳細未定  
管理タスク：tque **613**（親121 ForthSigma、未着手、進捗auto）

## 目的

GUIやゲームの入力・描画を継続しながら、計算やデータ処理をバックグラウンドで実行できる機構を検討する。将来は複数CPUコアによる並列計算にも対応する。

対象プラットフォームはWindows / Linux / macOS。既存VMと既存プログラムへの影響を抑え、必要な機能から段階的に追加する。本書は利用者が提示した企画・基本設計案と、その後の検討事項をまとめたもの。現行コードの調査結果や実装済み機能を示す文書ではない。

## 構成案

メインVMは対話・コンパイル・アプリケーション状態の管理・GUI操作を担当する。バックグラウンド処理は独立したワーカーVMで実行し、結果やエラーをメインVMへ通知する。

|構成要素|役割の案|
|---|---|
|メインVM|入力とイベントの処理、GUI・描画、ゲーム状態の更新、タスク管理|
|ホスト入力管理|OSからの入力取得と、既存API・新イベントAPIへの提供|
|イベントループ／キュー|入力・タイマー・タスク通知の受信、待機、メインVMへの配信|
|ワーカープール|独立したワーカーVMを再利用し、投入された計算を実行|
|既存音声処理|既存の実行方式との整合と影響を調査|

ワーカーのスタックと論理メモリーはメインVMから分離する案とする。GUI操作とゲームの主要状態の変更はメインVMへ集約する。ホスト資源やグローバル状態を含めて分離できるかは、実装調査で確認する。

## 実装前に検討する3点

### ワーカーVMの初期化・同期コスト

タスク投入のたびに辞書とメモリーを丸ごと複製すると、短い計算を大量に処理する用途で複製コストが問題になる。

ワーカープール起動時にVMを生成し、辞書が更新された場合だけ同期する方式を検討する。生成・辞書同期・タスク間の状態初期化のコストを区別して評価する。辞書更新の検出方法、実行中タスクとの関係、タスク間で保持／初期化する状態は未定。

### 既存入力APIとの統合

MOUSE-EVENTやINKEYと新しいイベントAPIが同じ入力を取り合う構造を避ける。ホスト側で入力イベントを一元管理し、既存APIと新APIの両方へ提供する方式を検討する。

両APIへの配信方法、同じ入力を両方で参照した場合の扱い、入力状態の整合、キュー満杯時の処理は未定。既存APIの意味を維持することを目指す。

### 非同期処理と並列計算の分離

GUIの応答性を確保する非同期処理と、複数CPUコアを使う並列計算では、適したスケジューリングが異なる。

イベントループとワーカープールを独立したサブシステムとして設計する。イベント待機・通知と計算の実行を分離し、将来それぞれを拡張できる構成を検討する。ブロッキングI/Oをどこで実行するかも未定。

## 機能の候補

- タスクの投入、終了判定、結果取得、キャンセル要求、ハンドル解放。
- ユーザー・タイマー・入力・タスク完了／エラーを扱うイベントキュー。
- セル値やコピーしたデータによるVM間の受け渡し。
- GUI・ゲームループへの完了通知と、古い計算結果の識別。
- エラー情報、ログ、実行時間やメモリー使用量の確認。

提案されたREQUIRE-ASYNC、SPAWN、TASK-*、EVENT-*等の名称・スタック効果は候補であり、確定APIではない。ワーカー数、キュー容量、タイムアウト、性能目標の具体値も本書では確定しない。

## 調査・設計で決める事項

- State・Storage・辞書・ホストAPIの依存とスレッド境界、ワーカーで許可する機能。
- 辞書スナップショット、実行トークンの解決、メモリー上限、VMの再利用方法。
- 引数と結果の規約、バイト列転送、ハンドルの所有権と寿命。
- イベントの順序、あふれ時の処理、通知とタスク状態の整合。
- キャンセル確認地点、待機中I/O、アプリケーション終了時の停止・回収。
- GUI処理中の同期待機の制限、既存音声処理への影響。
- SAVE / SAVESYS / LOAD-DICTIONARY / FORGET / MARKERとの関係。
- 単一VM性能、初期化・同期コスト、並列性能、各OSでの検証方法。

辞書イメージについては、既存の[P00方針](GFORTH_P00_SPEC.md)に「旧イメージ互換を要求せず、安全に拒否する」という決定がある。今回の企画案にある互換性維持の目標との関係は、設計時に整理する。本書によって既存方針を変更しない。

## 段階的な進め方の案

既存実装の調査 → イベント基盤 → 独立ワーカーVM → タスク完了・エラー通知 → GUI・ゲーム連携 → 安定化・性能評価を候補とする。ワーカー再利用と辞書同期は初期設計で検討する。

詳細な工程、依存関係、完了条件、子タスクはまだ作成しない。現在のGforth対応計画との実施順序も未定。

初期段階では、共有辞書への同時書込み、任意の既存ワードのスレッドセーフ化、プリエンプティブなVM切替、実行中タスクのイメージ保存、分散処理、ハードリアルタイム保証を対象に含めない案とする。
