# 非同期・TUI実行基盤とエディタ拡張の企画

作成日：2026-11-13  
状態：仕様案・未確定（実装未着手）

管理タスク：tque **613**（親121 ForthSigma、未着手、進捗auto）

## 目的

GUIやゲームの入力・描画を継続しながら、計算やデータ処理をバックグラウンドで実行できる機構を検討する。将来は複数CPUコアによる並列計算にも対応する。追加企画として、Vimライクなターミナルエディタと、その基盤を再利用するTUIツール向けの16項目を含める。

対象プラットフォームはWindows / Linux / macOS。既存VMと既存プログラムへの影響を抑え、必要な機能から段階的に追加する。本書は利用者が提示した企画・基本設計案と、その後の検討事項をまとめたもの。現行コードの調査結果や実装済み機能を示す文書ではない。

## 構成案

メインVMは対話・コンパイル・アプリケーション状態の管理・GUI操作を担当する。バックグラウンド処理は独立したワーカーVMで実行し、結果やエラーをメインVMへ通知する。

|構成要素|役割の案|
|---|---|
|メインVM|入力とイベントの処理、GUI・描画、ゲーム状態の更新、タスク管理|
|ホスト入力管理|OSからの入力取得と、既存API・新イベントAPIへの提供|
|イベントループ／キュー|入力・タイマー・タスク通知の受信、待機、メインVMへの配信|
|ワーカープール|独立したワーカーVMを再利用し、投入された計算を実行|
|既存音声処理|既存の実行方式との整合と影響を調査|

ワーカーのスタックと論理メモリーはメインVMから分離する案とする。GUI操作とゲームの主要状態の変更はメインVMへ集約する。ホスト資源やグローバル状態を含めて分離できるかは、実装調査で確認する。

## 実装前に検討する3点

### ワーカーVMの初期化・同期コスト

タスク投入のたびに辞書とメモリーを丸ごと複製すると、短い計算を大量に処理する用途で複製コストが問題になる。

ワーカープール起動時にVMを生成し、辞書が更新された場合だけ同期する方式を検討する。生成・辞書同期・タスク間の状態初期化のコストを区別して評価する。辞書更新の検出方法、実行中タスクとの関係、タスク間で保持／初期化する状態は未定。

### 既存入力APIとの統合

MOUSE-EVENTやINKEYと新しいイベントAPIが同じ入力を取り合う構造を避ける。ホスト側で入力イベントを一元管理し、既存APIと新APIの両方へ提供する方式を検討する。

両APIへの配信方法、同じ入力を両方で参照した場合の扱い、入力状態の整合、キュー満杯時の処理は未定。既存APIの意味を維持することを目指す。

### 非同期処理と並列計算の分離

GUIの応答性を確保する非同期処理と、複数CPUコアを使う並列計算では、適したスケジューリングが異なる。

イベントループとワーカープールを独立したサブシステムとして設計する。イベント待機・通知と計算の実行を分離し、将来それぞれを拡張できる構成を検討する。ブロッキングI/Oをどこで実行するかも未定。

## 機能の候補

- タスクの投入、終了判定、結果取得、キャンセル要求、ハンドル解放。
- ユーザー・タイマー・入力・タスク完了／エラーを扱うイベントキュー。
- セル値やコピーしたデータによるVM間の受け渡し。
- GUI・ゲームループへの完了通知と、古い計算結果の識別。
- エラー情報、ログ、実行時間やメモリー使用量の確認。

提案されたREQUIRE-ASYNC、SPAWN、TASK-*、EVENT-*等の名称・スタック効果は候補であり、確定APIではない。ワーカー数、キュー容量、タイムアウト、性能目標の具体値も本書では確定しない。

- State・Storage・辞書・ホストAPIの依存とスレッド境界、ワーカーで許可する機能。
- 辞書スナップショット、実行トークンの解決、メモリー上限、VMの再利用方法。
- 引数と結果の規約、バイト列転送、ハンドルの所有権と寿命。
- イベントの順序、あふれ時の処理、通知とタスク状態の整合。
- キャンセル確認地点、待機中I/O、アプリケーション終了時の停止・回収。

- SAVE / SAVESYS / LOAD-DICTIONARY / FORGET / MARKERとの関係。
- 単一VM性能、初期化・同期コスト、並列性能、各OSでの検証方法。

辞書イメージについては、既存の[P00方針](GFORTH_P00_SPEC.md)に「旧イメージ互換を要求せず、安全に拒否する」という決定がある。今回の企画案にある互換性維持の目標との関係は、設計時に整理する。本書によって既存方針を変更しない。

## 段階的な進め方の案

既存実装の調査 → イベント基盤 → 独立ワーカーVM → タスク完了・エラー通知 → GUI・ゲーム連携 → 安定化・性能評価を候補とする。ワーカー再利用と辞書同期は初期設計で検討する。

初期段階では、共有辞書への同時書込み、任意の既存ワードのスレッドセーフ化、プリエンプティブなVM切替、実行中タスクのイメージ保存、分散処理、ハードリアルタイム保証を対象に含めない案とする。

### 既存の非同期案との調整事項

- 従来案の独立ワーカーVMと、今回案の「初期版はZigネイティブジョブのみ、Forthはメインスレッドで実行」を区別する。両案の段階・適用範囲は未確定で、今回の登録で従来案を削除しない。
- イベントループとワーカープールは独立サブシステムとする案を保ち、ホスト入力の一元管理によってINKEY/MOUSE-EVENT等と新APIが入力を取り合わない構成を検討する。
- 従来提案の `EVENT-WAIT ( -- event )` / `EVENT-WAIT-MS` と、今回の `EVENT-WAIT ( timeout-ms -- event flag )` は異なる。`EVENT-FREE` / `EVENT-RELEASE`、TASK-* / JOB-*の関係も含め、統合時に名称・スタック効果・資源解放規約を確定する。
- 以下のキー入力とTEXT入力の分離は目標仕様。実際に取得できる情報、IME確定文字列・修飾キー・キー解放通知等の端末能力差は調査事項として残す。
- 正規表現・Unicodeテーブル・Tree-sitter等の採用実装、バージョンとライセンスは選定時に確認する。以下の候補を採用決定とは扱わない。
- モジュールIDによる再結合は候補であり、現在の画像ABI照合・旧形式を安全に拒否する方針を変更しない。

### 1. ターミナル制御（637、必須）

全画面TUI向けに、既存の文字出力やグラフィックス表示から独立した文字セル管理を追加する案。

- Raw mode切替・復元（行単位処理とエコーの停止）、Alternate Screen Buffer。
- カーソル移動・表示／非表示・形状、全画面・行・矩形の消去／再描画。
- 16色・256色・True Colorと能力別フォールバック。
- 文字セル単位のバックバッファと差分描画、Bracketed Paste、端末サイズ取得。

| API案 | スタック効果 | 機能 |
|---|---|---|
| TERM-OPEN | `( -- handle ior )` | セッション開始 |
| TERM-CLOSE | `( handle -- ior )` | 状態復元 |
| TERM-SIZE | `( handle -- cols rows ior )` | サイズ取得 |
| TERM-CLEAR | `( handle -- ior )` | 描画バッファ消去 |
| TERM-MOVE | `( x y handle -- ior )` | 0始まり座標へ移動 |
| TERM-STYLE | `( fg bg attrs handle -- ior )` | スタイル指定 |
| TERM-WRITE | `( addr len handle -- ior )` | UTF-8をバックバッファへ描画 |
| TERM-PRESENT | `( handle -- ior )` | 前画面との差分を出力 |

正常終了・処理可能なエラー・中断時に端末状態を復元し、Bracketed Pasteも無効化する。非対応機能は無効化して基本表示を保つ。リサイズ時は描画バッファを再構築する。

### 2. イベントキュー（638、必須）

入力・タイマー・外部プロセス等を単一イベントループへ集約する案。

| イベント案 | 内容 |
|---|---|
| KEY | キーコード、修飾キー、押下状態 |
| TEXT | UTF-8テキスト入力 |
| PASTE | Bracketed Paste |
| MOUSE | クリック・移動・ドラッグ・ホイール |
| RESIZE | 端末サイズ変更 |
| TIMER | タイマー満了 |
| PROCESS | 子プロセス終了 |
| STREAM | プロセスからのデータ受信 |
| JOB | ジョブ完了・失敗 |
| CANCEL | 中断・終了要求 |

| API案 | スタック効果 | 機能 |
|---|---|---|
| EVENT-POLL | `( -- event flag )` | 非待機取得 |
| EVENT-WAIT | `( timeout-ms -- event flag )` | 時間指定待機 |
| EVENT-TYPE | `( event -- type )` | 種別 |
| EVENT-KEY | `( event -- key mods )` | キー情報 |
| EVENT-TEXT | `( event -- addr len )` | 入力文字列 |
| EVENT-RELEASE | `( event -- )` | 資源解放 |

Ctrl+S等のキー操作と、IME確定日本語等のTEXT入力を分離する目標。原則として単一の編集スレッドで消費する。有界キューとし、移動・リサイズは集約を許すが、キー・テキストを無断で破棄しない。イベント文字列の所有権と有効期間を明示する。

### 3. 非ブロッキングI/O（639、必須）

標準入力・パイプの非ブロッキング読取、書込可能待機、複数対象監視、部分読書き、EOF・切断・タイムアウトの区別、監視登録／解除を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| IO-WATCH | `( handle flags -- watch-id ior )` | 監視登録 |
| IO-UNWATCH | `( watch-id -- ior )` | 監視解除 |
| IO-READ | `( handle addr len -- n status )` | 非ブロッキング読取 |
| IO-WRITE | `( handle addr len -- n status )` | 非ブロッキング書込 |

statusは成功・再試行可能・EOF・エラーを区別し、要求より少ない読書きも正常とする。epoll・kqueue・Windowsイベント機構等のOS差をZig層へ隠蔽し、Forthには共通ハンドルとイベントを公開する。

### 4. Unicode処理（640、必須）

UTF-8検証・エンコード／デコード、コードポイント移動、拡張書記素クラスタ境界、全角／半角・結合文字・絵文字の表示幅、タブを含む表示列、単語境界、不正UTF-8の安全な取扱い、Unicodeテーブルのバージョン管理を追加する案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| UTF8-DECODE | `( addr len -- codepoint bytes status )` | 先頭文字解析 |
| UTF8-VALID? | `( addr len -- flag )` | 妥当性判定 |
| UTF8-NEXT | `( addr len offset -- next-offset )` | 次コードポイント |
| GRAPHEME-NEXT | `( addr len offset -- next-offset )` | 次書記素クラスタ |
| UNICODE-WIDTH | `( addr len -- cells )` | セル幅 |
| UNICODE-WORD-NEXT | `( addr len offset -- next-offset )` | 次単語境界 |

位置は原則バイトオフセットとし、画面列とは別管理する。「あ」の3バイト／通常2セルのような違いに加え、結合文字・複合絵文字はバイト数やコードポイント数だけで幅を決めない。端末差に対応する表示幅ポリシーを設定可能にする。

### 5. 高速テキストバッファ（641、必須）

通常のForth文字列とは別の編集用バッファを導入する案。複数バッファの生成／破棄、任意位置の挿入・削除・置換、範囲取得、行番号とバイト位置の双方向変換、変更世代、ファイル入出力、大規模ファイルの部分アクセス、カーソル／マーカーの位置追跡を扱う。

| 候補 | 長所 | 短所 |
|---|---|---|
| Gap Buffer | 単純、カーソル付近の編集が速い | 離れた編集に不利 |
| Piece Table | 元データ保持、履歴と好相性 | 断片管理が必要 |
| Rope | 大規模ファイル・多数の編集に適する | 複雑 |

本格的エディタではPiece TableまたはRopeを優先するという提案を保持し、採用方式は未確定とする。

| API案 | スタック効果 | 機能 |
|---|---|---|
| BUF-NEW | `( -- buf ior )` | 生成 |
| BUF-FREE | `( buf -- ior )` | 破棄 |
| BUF-LOAD | `( addr len -- buf ior )` | ファイル読込 |
| BUF-LENGTH | `( buf -- bytes )` | バイト長 |
| BUF-LINES | `( buf -- lines )` | 行数 |
| BUF-INSERT | `( buf pos addr len -- ior )` | 挿入 |
| BUF-DELETE | `( buf pos len -- ior )` | 削除 |
| BUF-REPLACE | `( buf pos len addr n -- ior )` | 置換 |
| BUF-SLICE | `( buf pos len -- addr n ior )` | 範囲参照 |
| BUF-LINE-START | `( buf line -- pos ior )` | 行頭位置 |
| BUF-REVISION | `( buf -- revision )` | 世代 |

BUF-SLICEの借用範囲は変更後も有効とは限らない。寿命を明示するか、呼出側所有領域へコピーするAPIを別途設ける。元バイト列を原則保持し、LF・CRLF・CRに対応して保存時の意図しない改行変換を避ける。

### 6. 編集トランザクション（642、必須）

編集開始・確定・ロールバック、複数変更の一括記録、Undo/Redo、保存済み状態との識別、カーソル／選択範囲復元、直前変更の再実行、履歴メモリー上限を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| EDIT-BEGIN | `( buf -- tx ior )` | 開始 |
| EDIT-COMMIT | `( tx -- ior )` | 確定 |
| EDIT-ROLLBACK | `( tx -- ior )` | 取消 |
| EDIT-UNDO | `( buf -- ior )` | Undo |
| EDIT-REDO | `( buf -- ior )` | Redo |
| EDIT-CAN-UNDO? | `( buf -- flag )` | Undo可否 |
| EDIT-CAN-REDO? | `( buf -- flag )` | Redo可否 |

Insertモードの連続入力を1回のUndoへまとめる。履歴再生中は新しい履歴を生成しない。Vimの`.`は変更コマンドの再実行であり、Undo/Redoの履歴とは分離して記録する。

実行ファイル・引数・作業ディレクトリ・環境変数、標準3ストリームのパイプ、実行状態・終了コード、キャンセル／強制終了、起動失敗通知と終了後回収を扱う案。LSP・Git・フォーマッター・検索ツール等へ利用する。

| PROC-ARG | `( addr len proc -- ior )` | 引数追加 |
| PROC-CWD | `( addr len proc -- ior )` | 作業ディレクトリ |
| PROC-START | `( proc -- ior )` | 起動 |
| PROC-STDIN | `( proc -- stream ior )` | 標準入力 |
| PROC-STDOUT | `( proc -- stream ior )` | 標準出力 |
| PROC-STDERR | `( proc -- stream ior )` | 標準エラー |

### 8. 非同期ジョブ管理（644、高優先度）

検索・構文解析・ファイル走査を入力処理から独立して実行する案。生成・開始・終了、実行待ちキュー／ワーカー、状態・進捗、キャンセル、完了／失敗イベント、優先順位、同時実行数・メモリー上限を扱う。

| API案 | スタック効果 | 機能 |
|---|---|---|
| JOB-SUBMIT | `( task data -- job ior )` | 投入 |
| JOB-STATUS | `( job -- state )` | 状態 |
| JOB-CANCEL | `( job -- ior )` | キャンセル |
| JOB-RESULT | `( job -- result ior )` | 結果 |
| JOB-FREE | `( job -- ior )` | 破棄 |

今回案の初期版ではワーカーはZigネイティブ処理のみを実行し、結果をイベントへ返す。辞書・スタック・VM状態を複数スレッドで同時操作せず、Forthはメインスレッドで実行する。Forth並列実行はVM／スタック分離を別途設計する。従来の独立ワーカーVM案との段階整理は調整事項。

### 9. タイマー機能（645、高優先度）

単発・周期、ミリ秒指定、取消、満了イベントと単調増加時計を扱う案。`g`等の複数キー待ち、検索候補更新の遅延、ファイル監視間隔等へ利用する。

| API案 | スタック効果 | 機能 |
|---|---|---|
| TIMER-START | `( ms -- timer ior )` | 単発開始 |
| TIMER-REPEAT | `( ms -- timer ior )` | 周期開始 |
| TIMER-STOP | `( timer -- ior )` | 停止 |
| CLOCK-MS | `( -- ms )` | 単調増加時計 |

高速ポーリングで入力を待たず、次のタイマー満了またはI/Oイベントまで効率的に待機する。

### 10. ファイルシステム拡張（646、高優先度）

ディレクトリ列挙／再帰走査、ファイル種別・サイズ・更新日時・権限、絶対／相対パス変換と正規化、シンボリックリンク、変更監視、一時ファイル・安全な置換、親ディレクトリ参照によるプロジェクトルート探索を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| DIR-OPEN | `( addr len -- dir ior )` | 開く |
| DIR-NEXT | `( dir -- entry flag ior )` | 次のエントリ |
| DIR-CLOSE | `( dir -- ior )` | 閉じる |
| FS-STAT | `( addr len -- stat ior )` | 情報 |
| FS-REALPATH | `( addr len -- path ior )` | 正規化パス |
| FS-WATCH | `( addr len flags -- watch ior )` | 監視 |
| FS-UNWATCH | `( watch -- ior )` | 監視解除 |
| FS-REPLACE | `( src slen dst dlen -- ior )` | 置換 |

entryに名前・種別・識別情報等を含める。OSのパス表現／通知方式を吸収する。監視通知は再確認の契機として使い、実際の状態を再取得する。安全な保存では元の権限、リンクの扱い、ディスク永続化保証も検討する。

### 11. 正規表現エンジン（647、高優先度）

コンパイル、前方／全件検索、キャプチャ、大小文字無視、複数行、置換、キャンセル、不正パターンのエラー報告を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| REGEX-COMPILE | `( addr len flags -- regex ior )` | コンパイル |
| REGEX-FIND | `( regex addr len start -- match flag ior )` | 次の一致 |
| REGEX-GROUP | `( match index -- start len ior )` | キャプチャ範囲 |
| REGEX-REPLACE | `( regex src slen repl rlen -- result ior )` | 置換 |
| REGEX-FREE | `( regex -- )` | 解放 |

初期版はPCRE等の完全互換より一般的検索・置換を優先する。大量ファイル検索はファイル走査とジョブ管理を組み合わせる。

### 12. JSON処理（648、高優先度）

LSPのJSON-RPCと構造化設定を想定し、解析、オブジェクト／配列生成、数値・真偽値・文字列・null取得、キー検索、配列アクセス、シリアライズ、不正JSONとエラー位置、所有権／解放を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| JSON-PARSE | `( addr len -- json ior )` | 解析 |
| JSON-TYPE | `( json -- type )` | 種別 |
| JSON-GET | `( json key-addr key-len -- value flag )` | キー検索 |
| JSON-AT | `( json index -- value ior )` | 配列要素 |
| JSON-STRING | `( json -- addr len ior )` | 文字列値 |
| JSON-SERIALIZE | `( json -- addr len ior )` | JSON生成 |
| JSON-FREE | `( json -- )` | 解放 |

全データをスタックへ展開せず、不透明ハンドルとする。LSPのContent-Lengthによるメッセージ境界はJSONパーサーから独立したストリームプロトコル層で扱う。

### 13. ファジーマッチング（649、中優先度）

部分列一致、スコア付け、大小文字、単語境界／パス区切りへの加点、候補ランキング、上位抽出、条件変更時の再計算、キャンセルを扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| FUZZY-NEW | `( -- matcher ior )` | 検索器 |
| FUZZY-ADD | `( matcher addr len id -- ior )` | 候補追加 |
| FUZZY-SEARCH | `( matcher addr len limit -- results ior )` | 検索 |
| FUZZY-COUNT | `( results -- count )` | 件数 |
| FUZZY-GET | `( results index -- id score ior )` | 結果 |
| FUZZY-FREE | `( matcher -- )` | 検索器解放 |

数万件以上でも入力応答を妨げず、候補更新と結果計算を分離し、必要ならジョブ化する。毎回文字列をコピーせず、候補IDと文字列バッファ参照を保持する方式を優先候補とする。

### 14. 構文解析インターフェース（650、中優先度）

Tree-sitter等について言語定義の読込、パーサー生成、解析、差分再解析、ノード種別／範囲、構文クエリ、解析エラー、パーサー／構文木の管理を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| SYNTAX-LOAD | `( addr len -- lang ior )` | 言語定義 |
| SYNTAX-NEW | `( lang -- parser ior )` | パーサー |
| SYNTAX-PARSE | `( parser buf -- tree ior )` | 解析 |
| SYNTAX-EDIT | `( tree change -- ior )` | 変更反映 |
| SYNTAX-NODE | `( tree pos -- node ior )` | ノード |
| SYNTAX-KIND | `( node -- kind )` | 種別 |
| SYNTAX-RANGE | `( node -- start end )` | 範囲 |
| SYNTAX-FREE | `( parser -- )` | 解放 |

ソースと特定の変更世代を対応させ、バックグラウンド解析後の古い結果を現在の画面へ誤適用しない。Tree-sitterの本体への静的リンクは必須とせず、エディタ用ビルドで選択可能にする。

### 15. ネイティブワード登録API（651、中優先度）

Zig機能のワード登録、名前／実装対応、所属モジュール、初期化／終了、重複名検出、スタック効果／引数検証支援、Forthへのエラー伝達、画像内の参照管理を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| MODULE-LOAD | `( addr len -- module ior )` | 登録済みモジュール有効化 |
| MODULE-UNLOAD | `( module -- ior )` | 終了 |
| MODULE-WORDS | `( module -- )` | ワード一覧 |
| MODULE-AVAILABLE? | `( addr len -- flag )` | 存在確認 |

Zig側の概念例（現行State等に合わせて設計し直す。実装コードではない）：

```zig
pub const NativeWord = struct {
    name: []const u8,
    function: *const fn (*Vm) anyerror!void,
};

pub fn registerNativeWord(vm: *Vm, word: NativeWord) !void {
    // 辞書または拡張ワード表に登録する概念例
}
```

既存組込ワード番号を不用意に変更しない。安定したモジュールID／ワードIDを画像読込時に関数へ再結合する方式が候補。ネイティブ関数のアドレス自体は保存しない。既存画像方針との関係は調整事項に残す。

### 16. 実行制御・キャンセル（652、中優先度）

ステップ数／時間制限、キャンセル受付、安全な中断、エラー時のスタック／実行状態復元、中断後の再開可否、確実な資源解放を扱う案。

| API案 | スタック効果 | 機能 |
|---|---|---|
| EXEC-LIMIT | `( steps -- )` | ステップ上限 |
| EXEC-DEADLINE | `( ms -- )` | 時間上限 |
| EXEC-CANCEL | `( task -- ior )` | キャンセル |
| EXEC-CANCELLED? | `( -- flag )` | 状態 |
| EXEC-YIELD | `( -- )` | 協調的制御 |
| EXEC-RESET | `( -- )` | 制限初期化 |

機械語命令の任意地点で強制停止せず、安全な境界で確認する協調方式を基本候補とする。停止しないネイティブ処理／外部プロセスには個別タイムアウトと終了処理を設ける。EXEC-YIELDでは継続状態・リターンスタックの保持を検討し、初期版は完全なコルーチンより小さなジョブへの分割でもよい。

### 17. モジュール構成案と資源の寿命

| 層 | モジュール案 |
|---|---|
| Runtime Extensions | terminal、events、async_io、unicode、process、jobs、timer、filesystem、native_words、execution_control |
| Editor Libraries | text_buffer、transactions、regex、json、fuzzy、syntax |

ビルド時に各モジュールの有効／無効を選択する案。非同期I/Oとイベント、構文解析とテキスト変更情報等の依存を整理する。VMの実行状態とZig管理の外部資源の寿命を分離し、辞書画像の保存、終了、エラー、モジュール解放のいずれでも無効なハンドルを残さない。
