# メモリーアクセス検査の調査（#792）

**今回の判断：確認したLinux +!経路の重複検査は統合済み。実例6ケースでは計測対象内の登録あり通知は0。範囲検査削除や登録探索の書換えは選ばず、C!の登録0時の呼出し省略は予備案として残す。本体未変更・速度改善未実証。以下は各段階の記録。**

2026-11-16。[実例6ケースの頻度](VM_WORKLOAD_OPERATION_PROFILE.md)でメモリーprimitiveの実行を確認したため、実装を読んだ。新しいVM変更や時間比較は行っていない。

State.memoryAddressは負アドレス・memory長超過と、lengthが残り範囲に収まることを検査する。readCellはこの検査後little-endianのセルを読み、writeCellは検査後に書き込む。writeCellはaddresses.count!=0のときだけaddress_registry.writtenを呼ぶ。従って通常の読込みに常に登録アドレス全件走査がある、とは言えない。

C!はアドレス検査後に値をpopして書き込み、writtenを呼ぶ。written側はlength==0または登録0で即returnする。一方!はアドレスと値のpop後にwriteCellで範囲を検査する。検査とpopの順が違うため、容量/範囲の失敗を含む実装変更でこの順序をそろえることはしない。

+!と1+!/1-!はreadCellとwriteCellの両方を呼ぶ。ソース上ではmemoryAddressが2回になるが、最適化後の実際の検査分岐数は未確認。ソースの呼出し数から費用を推定しない。

address_registry.writtenは登録がある場合も常に全件走査とは限らない。index_dirtyかつstable_writes<32では線形通知、その後はensureIndexとmemory_orderの探索へ進む。登録更新の頻度・件数・通知範囲が費用を左右し得るが、実例での動的回数は未計測。

次は#792で、代表的な@/!/+!/C!の基準生成コード、登録0/非0の分布、実際の検査・通知回数を確認する。範囲外・unaligned・重なり書込み・typed slotの破損/修復、失敗時のstackと出力エラー優先を維持する。検査や通知を省略する試作はまだ選んでいない。

根拠はsrc/forth.zigのmemoryAddress/readCell/writeCell、src/core/words_memory.zig、src/core/address_registry.zig。原文SHAは[測定根拠](measurements/2026-11-16-memory-access-source.json)に保存した。本体は変更していない。


## 基準版の生成コード確認（#837）

採用ソースと同じLinux fast/baseline CPU・シンボル付き実行体を再利用した。forth.zig/words_memory.zig/address_registry.zigを現在の基準とハッシュ照合し一致。各カーネル100/200反復のCallgrind差分とobjdumpの命令位置・ソース注釈を照合した。これは命令計数で、CPU時間やWindows/count付き生成コードの結果ではない。

| 語 | 範囲検査の条件分岐（正しいアドレスを使う確認経路） | 登録0のIr/反復 | 登録1のIr/反復 |
| --- | --- | --- | --- |
| @ | 負値、上端、残り8バイトの1組（3分岐） | 152 | 152 |
| ! | 同じく1組（3分岐） | 146 | 219 |
| +! | 読み書きを通して1組（3分岐） | 140 | 213 |
| C! | 負値とbyte上端（2分岐） | 172 | 211 |

+!は1組の検査後のadd [memory],valueに畳み込まれ、ソース上のreadCell/writeCellの2呼出しから検査2組が残ると考えるのは誤りだった。今回の経路で重複検査削除の試作は見送る。表のカーネルは異なるため、語同士の速さの順位表ではない。登録1は別のAVARIABLEを用意し、対象外の通常セル/byteへ書く条件。差分は定常側の費用で、初期の線形通知費用を代表しない。

登録0の!/+!にはwrittenの呼出しがなく、C!には1回/反復残った。C!のwritten自身は登録0で23命令/反復を実行して即復帰する。呼出し元に同様のgateを置く案は考えられるが、実際の削減量と時間効果は試作・測定していない。[生成コード・計数・入力・命令位置](measurements/2026-11-16-memory-access-generated-code.json)。

## 通知の動的回数（#838）

作業用コピーに、memoryAddress/readCell/writeCellのsource-level入口とwritten/notifyRecordの分岐カウンターを追加した。in_counted内だけを対象にしたが、index再構築だけはreset後のglobal計数なので範囲外の再構築が混じり得る。計測用コードが最適化を変え得るため、この入口回数を基準版の実際の検査分岐数と同一視しない。特に+!の入口は読み/書きの2回でも、上記基準生成物の検査は1組である。

登録0のセル書込み・byte書込み、登録1の対象外書込み・完全セル書込み・部分書込み・+!の6対照を実行。各対照の基準版出力と計測版2回の出力が一致し、計測版のカウンターも一致した。登録0の!は通知呼出し0、C!は100回呼んで全て即復帰。登録セルへの100回通知は完全/部分をそれぞれ区別できた。

3つのregistered-store対照では線形通知が0、索引通知100、reset後の索引構築1だった。registered-add-storeは索引構築0だった。線形段階は終了していたが、索引まで事前構築済みとは言えない。index再構築カウンターはVM外も含むため、構築がWORKLOADのどの位置で起きたかは特定していない。追加の測定専用unit testではin_counted=trueとcold indexを明示し、100通知のうち線形32・索引68・索引構築1、全体セル通知によるvalid→部分通知のdamaged→全体セル通知のvalid復帰を確認した。これはメモリー自体を書き換えずwrittenを直接呼び、内部状態を設定した制御試験で、実利用の頻度を表さない。CLI対照ではstatus値を観測していない。

計測版の初回フル試験では、profile出力に関する既存テスト2件が失敗した。1件目は追加行による出力不一致がログに明示されている（core 1,010成功/5skip/2失敗）。期待値を変更せずログを保存し、counter専用core rootに絞った確認を別に実行した。後者はcore 3件成功、host/CLI/freestandingのbuildステップも成功。この初回を全回帰通過とは扱わない。2件目のNEW末尾照合は失敗したが、actual出力の差分が記録されていないため直接原因の特定には至っていない。テスト用stderr捕捉には512byteの上限があり、初回found出力は途中で切れていた。初回の計測コードの型/reflect API修正と失敗ログも保存した。

前回と同じ6実例で、基準版と計測版の出力が一致、計測版2回のカウンターが一致した。compiled PCの回数も前の計測版と全て一致した。自己整合・出力の確認であり、全状態の同一性や一般的な精度の保証ではない。

全ケースのwriteCell経由の書込みは登録0のgateを通り、writtenは全て早期復帰した。早期復帰カウンターはlength=0と登録0を区別しないため、その内訳を断定しない。初期/終了の登録数だけで全期間一定とは証明していない。今回の通知入口のカウンターから、対象範囲のwritten内の線形/索引走査が起きていないことを確認した。他のregistry関数の走査全般を計数したものではない。登録を多用する入力、初期化/資産生成/コンパイル/I/O、表示付き操作などは範囲外であり、#836に残す。

## 対策の選定

- +!の重複検査削減：確認したLinux経路は既に統合されており試作しない。
- 登録探索の高速化：この6実例には登録あり通知がなく、現在の対象入力での優先対策には選ばない。登録多用の入力を確認した場合は再検討する。
- C!の登録0時gate：安全な通知条件を維持する局所案として予備へ残す。compiled C!は今回klondike-logicで28回、klondike-renderで5回、他は0。written入口28〜140等の全数をC!の回数とは扱わない。他の書込み経路も含むためである。時間効果は未判定。
- 一般の範囲検査省略：不正/境界アドレスの動作を変える根拠はなく選ばない。unsigned化や事前検査の移動も、負値、length=0、memory末端、過大length、失敗時stackの同等性を確認せず実装しない。

#792は第1調査と今回の選定を記録する。共通VM全体を高速化する小変更が見つかったとは結論しない。次の既定候補#793はビルド最適化の利用可能性の調査で、配布CPU互換性を変更する判断とは分ける。残る実例範囲の調査は#836、全候補の再順位付けは#806で未完了のまま。


## レビュー対応と最終確認

[レビュー原文](VM_MEMORY_ACCESS_CLAUDE_REVIEW.md)の索引状態の記述を訂正した。3対照のindex再構築1は記録にあるが、global計数のため最初のWORKLOAD通知で起きたとまでは断定しない。+!以外の1+!/1-!生成コードは未確認。MOVE/CMOVEの登録0時はwriteCell/writtenを通らず、char localや別幅書込み等もwriteCell入口に含まれないため、全書込みや全検査を数えたとは扱わない。

初回テストでは診断global値の持越しが出力に見えていたが、CLI計測は各別プロセスとresetで区切っている。レビュー後、追加profile行を専用reset引数使用時だけに出すgateを追加し、core全体を戻してWindows Debugフル試験を実行。core 1,012成功/5skip、host 59/5skip、全21/21ステップが成功した（計1,071成功/10skip）。新しいgateを含むバイナリで6対照・6実例を再実行し、全ての出力・命令別回数・nativeカウンターが前版と一致した。元の失敗記録、counter-only 3テストの直接実行名、両バイナリSHAも保存している。

計測版への出力gate追加は静的レビュー後の修正で、フル試験と再計数で確認した。再静的レビューは行っていない。一般的なC!の時間効果は計測していないため「効果が出ない」と断定せず、今回の頻度を根拠に予備とする。[指摘への対応](VM_MEMORY_ACCESS_REVIEW_RESPONSE.md)。
