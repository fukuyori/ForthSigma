# 全項目比較の実行経路と限界

2026-11-15。Claude CodeのB-1〜B-3への対応。これは計測処理の欠落を新たに修正した記録ではなく、実際に実行した親driverとworkerの役割・ハッシュ・出力の対応を明示する記録である。VMコード・測定結果・判定値は変更していない。

## 実際の処理

親`all-driver-v2.py`は`run(..., 7)`で比較の最低回数を渡す。Windowsの`focused.py`、Linuxの`focused-linux.py`が`accepted-aa.json`を読み、次の処理で実回数を確定してからループを開始する。

```python
if a.stage == 'compare':
    accepted = json.loads((out / 'accepted-aa.json').read_text())
    slug = a.config.removesuffix('-config.json')
    a.rounds = max(a.rounds, accepted[slug]['rounds'])
```

このためcommands.jsonのCLI引数7は最低値であり、実際の回数は各系列JSONの`rounds`と各エンジンの`samples_us`の要素数に記録される。全29追加条件で実回数≥max(7,採用A/A回数)を照合済み。重点5条件も、その校正・比較の実回数を個別に保持する。最終比較前にworker側へ実装したもので、実行後に親driverを書き換えて帳尻を合わせてはいない。

## 計時本体benchmark-runtime.pyの同一性

workerが実行時に読み込むscripts/benchmark-runtime.pyは、前段の重点項目記録（今回の追加29条件の測定前）、今回の全項目記録、現在のファイルでSHA-256が一致した。方法監査JSONに実バイト列とハッシュも保存した。workerに実行ごとの同ファイルのハッシュ検査はなく、これを実施済みとは主張しない。これは前後の保存記録と現ファイルの照合であり、各プロセス起動時の暗号学的証明ではない。

## Windowsの時間刻みと境界の余裕

保存されたWindows比較CPU時間はすべて15.625ms刻みだった。これは今回の観測値であり、APIが常にこの分解能だと一般化しない。1.1〜1.3秒程度の試行では、1刻みが約1.2〜1.4%に当たる。中央値差が0の項目も、揺らぎが存在しないという意味ではない。

Windows LOOPの短縮が小さい系列は約10.12%で、最低10%に対する余裕は約0.119ポイント。この系列の基準中央値に対する1刻みは約0.595ポイントで、余裕は1刻み未満である。既定条件は点推定として満たしたが、「十分な余裕を持って通過」とは扱わない。

Windows THROWの最大悪化は約7.79%。上限10%までの余裕は約2.21ポイントであり、別環境・再測定でも上限を超えない保証ではない。A/A δは信頼区間でも候補の最大ばらつきの上限でもない。SYNONYMなどには系列差と広い試行範囲があり、全CATCHが改善したとは主張しない。CPU内部の原因は未特定。

## 再実行の前提

保存workerは測定当時の基準版src/forth.zigのSHA-256も検査する。本体反映後に元の作業ツリーで起動すれば、この検査で拒否するのが意図した動作。再測定は、基準版ソース・保存実行体・設定・benchmark-runtime.pyを備えた別コピーで、commands.jsonの個別workerコマンドを使う。accepted-aa.jsonも必要。現在の作業ツリーを巻き戻したり、tqueを更新する親driverをそのまま再実行したりしない。別コピーでの再測定手順自体を今回追加実行したとは主張しない。
