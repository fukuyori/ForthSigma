# セル型local・標準条件の継続評価結果（#881）

2026-11-17。[継続方針](VM_PARTIAL_ADOPTION_CONTINUATION_PLAN.md)の凍結protocolで、セル型localの標準条件を計時した。**標準15条件を比較し、14条件は悪化上限を通過した。Windows catch-nested-256の比較が系列1で上限5%を超えたため、停止規則どおり終了した。追加採用は保留、製品VMは変更していない。**

## 停止した条件

Windows catch-nested-256（N=600,772）の標本（CPU秒）は次のとおり。

| 群 | 基準版 | 候補版 |
| --- | --- | --- |
| A/A 系列1（A1 / A2） | 5.422 / 6.000 / 6.000 / 5.312 / 5.328 | 5.469 / 5.391 / 6.016 / 5.344 / 5.359 |
| A/A 系列2（A1 / A2） | 5.469 / 5.453 / 5.344 / 5.906 / 5.953 | 5.406 / 5.359 / 5.344 / 6.000 / 5.375 |
| 比較 系列1 | 5.359 / 5.469 / 5.438 / 5.969 / 5.375 / 5.391 / 5.469 | 6.141 / 6.125 / 5.906 / 5.562 / 5.969 / 5.984 / 5.484 |
| 比較 系列2 | 5.500 / 5.484 / 5.766 / 5.469 / 5.438 / 5.969 / 5.953 | 6.016 / 5.672 / 5.500 / 6.000 / 5.547 / 6.875 / 5.578 |

A/Aの行は、どちらの列も基準版である。基準版だけの標本でも、5.3～5.5秒付近と5.9～6.0秒付近の両方の値が出ている。比較では系列1が+9.770%で上限5%を超え、系列2は+3.125%で上限内だった。両系列とも上限内という条件を満たさないため、判定は不通過である。

候補の変更箇所は`.local_fetch`のセル型分岐だけで、CATCHの処理は変更していない。この増加が候補の性質によるものか、この条件の標本のばらつきによるものかは、この記録からは区別できない。

## 監査

完成した62群（A/A32群・比較30群）を生標本から再計算した。標本数、warmupの除外、checksum、中央値、δ、変化率、先後順、親と生存中の子のaffinity[2]、校正・比較の判定が保存記録と一致した。保存記録上の子実行はwarmupを含めて864件。入力301件・実行体4件・過去の証拠・worker・controller・protocolのSHAは、監査時点で凍結値と一致した。

A/Aは時計精度の証明や信頼区間ではない。背景負荷を独立に監視した記録はない。ハッシュはworker起動時と監査時の照合であり、全期間の連続的な不変証明ではない。今回、新しい製品build・テストは実施していない。

## 判断

承認済みの採用条件は「標準の全条件が両OSで悪化上限を通過すること」である。Windows catch-nested-256が不通過となったため、セル型localの追加採用は行わない。実例18条件での短縮（資産生成−8.0～−12.2%など）と、今回通過した標準14条件の記録は保持する。

同じ条件を取り直して通過扱いにすること、上限や標本数を変えて判定をやり直すことはしていない。
