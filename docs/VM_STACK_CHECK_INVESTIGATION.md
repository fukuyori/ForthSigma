# スタック深さ検査の調査

2026-11-16。tque #791の予備的なソース調査。削減可能性は未確定で、実装・生成コード比較・性能測定は未実施。

State.requireDepthは必要深さを一度確認する。popとpeekは個別にunderflowを確認し、pushは容量を確認する。ソース上で連続していても、最適化後の機械語に検査が残るとは限らない。重複の有無は基準版の生成コードで確認する必要がある。

| 箇所 | 現在の処理と境界 | 調査上の扱い |
| --- | --- | --- |
| State.popDouble | requireDepth(2)の後にpopを2回。深さ不足なら取り出し前に失敗 | 局所的な検査統合の候補。ただし生成コードに検査が残るか未確認 |
| 2R@ | return深さを確認し、data空き2を確認した後にpushを2回 | 両スタックのエラー順序を維持する必要。残存検査の確認候補 |
| NIP | popを2回、その後push。深さ1なら最初のpopで深さ0になってから失敗 | 先頭requireDepth(2)への置換は失敗時の途中状態を変えるため、単純な統合対象から外す |
| 2DUP / 2OVER | peekを2回後、pushを2回。空き1なら最初のpush後に2回目がoverflow | 先頭で空き2を検査すると失敗時状態が変わる。一括成功条件だけでは互換性を確認できない |

これらはソースの制御フローから確認した点であり、新たな実行プローブによる検証結果ではない。CATCHの復元だけで途中状態の差を無視せず、直接呼出し・compiled、counted、出力エラー優先・失敗PCも確認する。

次はpopDouble/2R@に対象を絞り、最適化済み基準生成物で残存分岐と呼出しを確認する。残存がなければ、その箇所の検査削減試作は見送る。残存する場合だけ、同一状態とエラー順序を守れる単独試作を選定する。命令数から実時間を推定せず、試作後は別途校正と対比較を行う。
