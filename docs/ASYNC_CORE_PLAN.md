## 共通の方針

1. **Gforthにある語は、Gforthの名前と動作に合わせる。** Gforthにない機能だけ、Sigma独自の語にする。独自の語の名前は企画書のAPI案を候補とする。
2. **既存のホスト層を広げる。** 端末の入力は `host_input.zig` が1か所で扱っている。別の入力経路を並べて作らない。
3. **通常の実行速度を変えない。** 通常の実行ループに確認の処理を足さない。上限や中断の確認は、`--max-steps` と同じ「数える実行ループ」の中だけで行う。
4. **端末の状態を、決めた終了経路で戻す。** 行入力の前、`SYSTEM` の前、通常の終了、捕捉されなかったエラーによる終了で、端末を元の状態へ戻す。OSによる強制終了では戻せないので、保証する経路を設計で列挙する。戻す仕組みは項目1で述べる。
5. **語群としてビルド時に外せるようにする。** 既存の `-D<群>=false` の仕組みを使う。組み込み語を足すと辞書のABIが変わり、以前の辞書イメージは読めなくなる。
6. **資源を残さない。** 子プロセスや監視は、終了時にまとめて回収する。ディレクトリの `closeAll` と同じ形にする。資源ごとに、だれが持ち、だれが閉じるかを表にしてから実装する。
7. **待機・期限・中断の取り決めを、項目をまたいで1つにする。** 項目2、3、5、7は、どれも「時間を区切って待つ」「途中でやめる」を扱う。期限の数え方（単調時計）、タイムアウト・終端・エラーの区別、中断の伝え方を、段階Aの実装の前に共通の仕様として決める。

## 1. ターミナル制御（637）

### 現状

`host_input.zig` は、`INKEY` や `EKEY` が最初に端末を読んだときにRaw modeへ切り替え、行入力・`KEY`・`SYSTEM`・終了の前に `leave` で戻す。マウスの報告（`ESC [ ? 1003 h` と `1006 h`）の開始と停止、カーソル位置の問合せ（`ESC [ 6 n`）もここにある。Windowsでは、コンソールの入力レコードをここで復号する。VT出力は起動時に有効化している（`src/main.zig`）。

`leave` はRaw modeでないときは何もしないで戻る（`src/host_input.zig:142`）。復元に失敗しても呼出し側には伝えない。終了時の復元は `src/main.zig` の `defer` で行っている。WindowsのRaw modeは、コンソールのVT入力（`ENABLE_VIRTUAL_TERMINAL_INPUT`）を外して、`ReadConsoleInputW` の入力レコードで読む（`src/host_input.zig:367`、451）。

### 対応方法

- **本体が覚える端末の状態を増やす。** 代替画面（`ESC [ ? 1049 h`）、貼り付けモード（`ESC [ ? 2004 h`）、カーソルの表示（`ESC [ ? 25 l`）を、マウス報告と同じ扱いにする。本体が状態を覚えて戻す。
- **表示の状態とRaw modeを分けて管理する。** いまの `leave` はRaw modeでなければ何もしないので、入力を読む前に代替画面へ切り替えると戻らない。表示の状態（代替画面、貼り付け、カーソル、マウス）は、Raw modeとは別の変数で持ち、別に戻す。アプリが求めた状態と、実際に端末へ送った状態を分けて覚える。解除は何度呼んでも同じ結果になるようにする。設定の途中で失敗したら、送った分を戻す。
- **`SYSTEM` と行入力の前後**：前で一時的に解除し、後で求められた状態へ戻す。
- **戻す経路**：通常の終了、捕捉されなかったエラーによる終了、`BYE`。`CATCH` で捕捉された `THROW` では戻さない（アプリが続くため）。OSによる強制終了は対象外とする。
- **語は「状態の組を設定する語」1つと「読む語」1つを候補とする。** 例：`TERM-MODE! ( mask -- ior )`、`TERM-MODE@ ( -- mask )`。ビットは代替画面、貼り付け、カーソル非表示、マウス。企画書の `TERM-OPEN`、`TERM-CLOSE` はハンドルを返す形だが、端末は1つなので、ハンドルなしを第1候補とする。
- **Gforthに合わせる語**：`COLS`、`ROWS` を `FORM` の上に足す。
- **アプリ側に任せるもの**：カーソル移動、色、消去、文字セルのバッファと差分描画。これらはエスケープ列の出力で書ける。

### 実装場所

`host_input.zig` の `report` と `leave` を広げる。Windowsでは、代替画面とカーソルの表示は、VT出力が有効なら同じエスケープ列を送れる見込みである（実機で確認する）。

貼り付けモードはこれと別である。貼り付けの開始と終了の印は入力として届くので、Windowsでは印を受け取るためにVT入力の有効化が必要になる（Microsoft Terminalの開発者による説明：<https://github.com/microsoft/terminal/issues/12385>。この説明は、今回は実機で確かめていない）。いまのRaw modeはVT入力を外して入力レコードで読んでいる。

**初期版では、Windowsは入力レコードのまま読み、貼り付けの印を出さない（決定）。** 貼り付けモードを求められても設定せず、`TERM-MODE@` で設定されていないと分かるようにする。貼り付けた文字は、通常の文字のイベントとして届く。いまの入力レコード方式はキーと修飾キーを取れており、VT入力へ切り替えたときにその情報が変わらないかを確かめていないためである。

実機で確かめて情報が変わらないと分かった場合の候補は、貼り付けモードの間だけVT入力に切り替えてキーをエスケープ列から復号する方式（Linux・macOSと同じ復号を使う）である。入力をすべてVT入力へ移す方式は採らない。

### 未決の点

- 端末がエスケープ列に対応しない場合の扱い（何もしないか、エラーを返すか）。
- Raw modeに入る契機。いまは最初の読取りで暗黙に入る。全画面のアプリが明示的に入る語を足すかどうか。
- VT入力に切り替えたときに、キーと修飾キーの情報が変わるかどうか（実機での確認）。
- `COLS`、`ROWS` のスタック効果。`FORM ( -- rows cols )` の戻り値と同じ値を返す形にし、Gforthと照合する。

## 2. イベントキュー（638）

### 現状

`EKEY` はすでに、キー、修飾キー（`K-SHIFT-MASK` など）、端末の大きさの変更（`K-WINCH`）を1つのセルで返す。`event_input.zig` の内部の読取りは待ち時間の引数を持っているが、時間を指定して待つ語はない。マウスはGRAPHICSの `MOUSE-EVENT` と `INKEY` の側にあり、`EKEY` には来ない。`EKEY` と `INKEY` はどちらも `host_input.zig` から読む。Raw modeを出るとき、標準入力の経路（`standard_keyboard`）で読んでいた場合は読み残しを保ち、そうでない場合は捨てる（`src/host_input.zig:146`、219、375〜376）。

`EKEY` の読取り（`src/core/event_input.zig` の `read`）は、最初の1バイトを期限なしで待ち、ESCに続く列を50msまで待ち、UTF-8の続きのバイトを期限なしで待つ。`EKEY?`（同 `ready`）は、入力を実際に1つ取り出して保留に置く。機能キーかどうかの判定（`src/core/standard_keys.zig` の `isFunction`）は、いまある値の範囲で決めている。端末から読んだ値3（Ctrl+C）は、割込みのエラーになる（`src/main.zig` の `if (event == 3) return error.UserInterrupt`）。

### 対応方法

- **イベントは `EKEY` のセルのまま扱う。** 企画書の「イベントのハンドルと解放」は導入しない。既存の `EKEY>CHAR`、`EKEY>FKEY`、`EKEY>XCHAR` がそのまま使え、所有権の問題が起きない。
- **時間を指定して待つ語を1つ足す。** 例：`EKEY-WAIT ( ms -- event true | false )`。Gforthには同じ形の語がない（Gforthの `stop-ns` はタスクを止める語）ので、Sigma独自とする。期限は「完成したイベントが得られるまで」に対して数える。呼出しの全体で1つの単調時計の期限を使い、ESCの列やUTF-8の列の途中で期限が来たら、読んだ分を保留して次の呼出しへ持ち越す。いまの読取りは続きのバイトを期限なしで待つので、内部の引数を語にするだけでは足りず、読取りの作りを変える。タイムアウト、入力の終端、入力のエラーは、戻り値で区別できるようにする（スタック効果は共通の取り決めで決める）。
- **マウスを `EKEY` に出す。** 新しいイベントの値 `K-MOUSE` と、マウスの位置とボタンを返す語を足す。位置とボタンは、キューの要素ごとに持たせ、「`EKEY` が最後に取り出したイベントのもの」を返す。`EKEY?` は先読みをするので、参照される情報を `EKEY?` では更新しない。GRAPHICSの `MOUSE-EVENT` の意味は変えない。
- **新しいイベントの値の範囲を決める。** `K-MOUSE` と貼り付けの印の値を置く範囲を予約し、`EKEY>FKEY` と名前の表示がそれらをどう扱うかを決める。いまの `isFunction` は値の範囲を固定しているので、変更が要る。
- **貼り付けは印のイベントで挟む。** 貼り付けの開始と終了を `K-PASTE-BEGIN`、`K-PASTE-END` で知らせ、その間の文字は文字のイベントとして1つずつ渡す。文字列をまとめて渡さないので、バッファの寿命を決めずに済む。
- **貼り付けの間は、キーとしての解釈をしない。** 終了の印以外のESCの列は機能キーに変えず、文字として渡す。Ctrl+Cに当たる値3も割込みにしない。改行とタブの渡し方、UTF-8として正しくないバイト、終了の印が来ない場合（打切りの条件）を仕様で決める。
- **複数の入力源の待機は項目3の上に作る。** 子プロセスの出力と端末の入力を同時に待つ機能は、項目3の待機の語で実現する。キュー用の別スレッドは初期版では作らない。

### 未決の点

- `EKEY` と `INKEY` を同じプログラムで混ぜたときの規則。いまの読み残しの扱い（経路により保つか捨てる）を保つか。
- キューがあふれたときの扱い。キーと文字は捨てない方針（企画書）を、どの大きさのキューで実現するか。
- IMEで確定した文字列がどう届くか。端末による違いは実機で調べる。

## 3. 非ブロッキングI/O（639）

### 現状

`KEY?`、`KEY-FILE`、`KEY?-FILE` がある。複数の対象をまとめて待つ手段はない。`READ-FILE` は要求した長さまで待つ。

ファイルの読取りはCのストリーム（`fread`）を使う。`KEY?-FILE` の準備の確認（`src/main.zig` の `fileReady`）は、Cのストリームから1バイトを読んで `ungetc` で戻し、ファイルIDごとの `file_peeked` と `file_eof` に状態を持つ。Windowsのパイプでは、その前に `PeekNamedPipe` で調べている。Cのストリームは先読みをするので、OSの側だけを調べると、すでに取り込まれたデータを見落とす。`CLOSE-FILE` は、パイプのファイルIDを受け付けない（`fileClose`。パイプは `CLOSE-PIPE` で閉じる）。Tcl用の書込み（`src/host_process.zig` の `writeProgram`）は、全部を書き終えるまで戻らない。

### 対応方法

- **待機の語を1つ足す。** 例：`WAIT-FILES ( addr n ms -- index ior )`。ファイルIDの並びと待ち時間を受け取り、読める状態になった最初のものの番号を返す。端末の入力も対象に含められるようにする。タイムアウトのときの番号（例：-1）、終端や切断になった対象を「読める」として知らせるか、無効なファイルID、対象が0個の場合を仕様で決める。
- **読める分だけ読む語を1つ足す。** 例：`READ-AVAILABLE ( c-addr u fid -- u2 eof? ior )`。待たずに、いま読める分だけを返す。「いまはデータがないが続く」（u2が0、eof?が偽）と終端（eof?が真）を、フラグで区別する。
- **ファイルIDごとの状態を1か所で管理する。** OSのハンドル、Cのストリームの先読み、受信のキュー、終端、エラー、閉じ方を、ファイルIDごとにまとめて持つ。待機の語は、OSの側を調べる前に、先読みと受信のキューに残りがあるかを見る。待機の対象にするファイルIDは、Cのストリームを通さずにOSのハンドルから直接読む形にする案を第1候補とする。
- **書込みの側も扱う。** 子プロセスの標準入力へ書きながら、その標準出力を読む使い方では、書込みが詰まると両方が止まる。書けた分だけ書いて戻る語（部分書込み）と、書込み可能の待機を段階Bに含める（決定）。
- 企画書の `IO-WATCH`、`IO-UNWATCH`（監視の登録と解除）は、初期版では作らない。待機のたびに並びを渡す形のほうが、資源の寿命が単純になる。

### 実装場所とOSごとの方法

- Linux・macOS：`poll` を使う。
- Windows：コンソールの入力は待機できるが、無名パイプは待機の対象にできない。パイプごとに読取りスレッドを置き、届いたデータをキューに入れてイベントで知らせる方式とする（決定）。音声とウィンドウですでにスレッドを使っている。`PeekNamedPipe` で短い間隔で調べる方式は、待ち時間の精度と負荷が下がるので採らない。
- 読取りスレッド方式では、次を先に設計する。受信のキューの容量と、満杯のときに読取りを止める方法（逆圧）。読取りスレッドと既存の `READ-FILE` が同じパイプを同時に読まない構造。待機中に閉じられた場合の扱い。スレッドの停止と `join` の順序。

### 未決の点

- 1回の待機で、端末の保留中の入力（`EKEY` の保留、読み残し）とパイプをまとめて扱う方法。

## 4. Unicode処理（640）

### 現状

文字の幅は `char_width.zig` の表で求める。表は `scripts/make-width-table.py` がUnicode Character Databaseから作り、全コードポイントでGforthと同じ幅になることを確かめてある。書記素クラスタの境界を求める手段はない。Gforthにも書記素の語は見当たらなかった。

### 対応方法

- **境界を求める語を足す。** 例：`X-GRAPHEME ( xc-addr u -- u1 )`（先頭の書記素クラスタのバイト数）と、末尾側の語。
- **規則はUnicodeのUAX #29に従う。** 表は `GraphemeBreakProperty.txt`、`emoji-data.txt`（Extended_Pictographic）、`DerivedCoreProperties.txt`（インド系文字の結合の規則が使う `Indic_Conjunct_Break`）から、幅の表と同じ方法で生成する。Unicodeの版と、対応するUAX #29の改訂を1つに固定し、使うファイルを一覧にする。
- **末尾側の語には、文字列の先頭を渡す。** 境界は前の文字に依存するので、現在の位置だけでは決まらない。
- **端の場合を仕様で決める。** 空の文字列、UTF-8として正しくないバイト、境界でない位置から始めた場合、長い結合列での計算量。
- **検証にはUnicodeが配る試験データ（`GraphemeBreakTest.txt`）を使う。**
- 単語境界と、タブを含む表示列の計算はアプリ側とする。

### 未決の点

- クラスタ全体の幅の決め方。結合した絵文字を2列とするか、端末の実際の表示に合わせる設定を持つか。
- Unicodeの版。幅の表の生成スクリプトは15.1.0を使っている。同じ版にそろえるか。
- `THIRD_PARTY_NOTICES.md` には、すでにUnicode Character Databaseの記載がある。使うファイルを追記する。

## 5. 子プロセス管理（643）

### 現状

`SYSTEM`、`SH`、`OPEN-PIPE` はシェルの文字列を渡す形で、パイプは単方向である。一方、Tcl用の `host_process.zig` には、Windowsの `CreateProcessW` と無名パイプ、Linux・macOSの `fork` と `exec` で、標準入力と標準出力の両方をパイプにつないで起動する処理がすでにある。

この処理は、子プロセス1個とそのパイプをグローバル変数で持つ。POSIX側は、`exec` に失敗すると子が終了コード127で終わる形で、起動の失敗を起動時に知らせない。停止の処理も1個のプロセスを対象にしている。

### 対応方法

- **`host_process.zig` の起動処理を、Tcl専用から一般の形に広げる。** 実行ファイル、引数の並び、作業ディレクトリ、標準3ストリームの扱いを指定できるようにする。
- **語は企画書の `PROC-*` を候補とする。** Gforthの `fork+exec` はLinux向けで、Windowsを含む共通の語がGforthにないためである。
- **複数のプロセスを扱える形にする。** グローバル変数1組から、プロセスごとの表に変える。
- **起動の失敗を起動時に知らせる。** POSIXでは、`exec` の失敗を親へ伝えるパイプ（close-on-exec）を使う方法を候補とする。
- **終了状態を保つ。** 終了したプロセスの終了コードを、アプリが読むまで表に残す。POSIXでは `waitpid` で回収する。孫プロセスの扱い（プロセスグループごと止めるか）を決める。
- **ストリームはファイルIDで返す。** そのために既存の語の側に要る変更は次のとおり。`CLOSE-FILE` がこの種類のファイルIDを閉じられるようにする（いまはパイプを拒む）。`READ-FILE` と項目3の語が同じ入力を取り合わないようにする（項目3の「ファイルIDごとの状態」）。プロセスとファイルIDのどちらが閉じるかを決め、二重に閉じないようにする。ストリームの終端とプロセスの終了は別々に知らせる。
- **終了要求**：Windowsは `TerminateProcess`、Linux・macOSは `SIGTERM` の後に `SIGKILL`。Gforthの `kill` はタスクを止める語なので、同じ名前は使わない。
- **回収**：Sigmaの終了時に、残っている子プロセスとパイプと読取りスレッドをまとめて片付ける。通常のエラー（`QUIT` へ戻る場合）では止めない。

### 未決の点

- Windowsの引数の渡し方。`CreateProcessW` は1本の文字列を受け取るので、引数の並びから文字列を組み立てる引用の規則を本体に持つ必要がある。
- 環境変数の指定を初期版に入れるかどうか。
- 標準エラーを別のパイプにするか、標準出力にまとめる指定を持つか。

## 6. ファイルシステム（646）

### 現状

ディレクトリの一覧、状態の取得、名前の照合、名前の変更はそろっている。`FILE-STATUS` が返すのは読み書きの可否（fam）だけで、更新時刻、大きさ、ファイルの識別子は返さない（`src/main.zig` の `fileStatus`）。`FLUSH-FILE` はCのバッファを書き出す（`fflush`）だけで、ディスクへの同期はしない。Windowsの名前の変更は `MoveFileExW` に「既存を置換」と「コピーを許す」を指定しており、別のボリュームへも移せる。パスの文字列だけの整理（`.` と `..` の除去）は、内部の処理として `src/core/paths.zig` の `normalize` にある。`FILE>PATH` は検索パスを探してファイルを開く語で、正規化の語ではない。`RENAME-FILE` は、移動先のファイルがある場合も成功して置き換える。WindowsとWSLのLinux版で実行し、どちらも結果は0（成功）で、移動先の中身が入れ替わり、移動元がなくなった。

### 対応方法

- **上書き置換**：`RENAME-FILE` がすでに置き換えるので、置換のための新しい語は足さない。ただし、実行で確かめたのは「成功して置き換わる」ことだけで、途中の状態を見せないこと（原子性）と、障害の後に残ること（永続性）は確かめていない。安全な保存を本体で支えるなら、次の3つを分けて扱う。Cのバッファの書出し（`FLUSH-FILE`）、同じディレクトリに作った一時ファイルからの置換（同じファイルシステムの中での名前の変更）、OSへの同期（`fsync`、`FlushFileBuffers`）。同期の語を足すかどうかは未決とする。
- **パスの正規化**：
  - 文字列だけの整理（`.` や `..` の除去）は、Gforthの `compact-filename` に合わせて足す。内部の `normalize` を語として公開する形になる。Gforthとの照合では、名前だけでなく、渡した領域を書き換えるか、戻り値、末尾の `.` と `..`、ルートの扱いを比べる。
  - リンクをたどった実パスは、Gforthに語がないのでSigma独自の語を足す。例：`FILE>REALPATH ( c-addr u -- c-addr2 u2 ior )`。Linux・macOSは `realpath`、Windowsは `GetFinalPathNameByHandleW`。
- **変更の監視**：初期版では本体に入れない（決定）。OSごとに仕組みが大きく違う（Linuxはinotify、macOSはkqueueまたはFSEvents、Windowsは `ReadDirectoryChangesW`）。アプリ側が一定の間隔で調べる方法を使うには、更新時刻と大きさを取る手段が要る。いまの `FILE-STATUS` はそれを返さないので、更新時刻と大きさを返す語を1つ本体に足す（名前とスタック効果は未決）。それで足りないと分かった時点で、OSの監視の仕組みの追加を検討する。

### 未決の点

- 実パスの語が返す文字列の置き場所。
- 同期の語と、更新時刻・大きさの語の、名前とスタック効果。

## 7. 実行制御（652）

### 現状

`--max-steps` は、実行数に上限を付ける。数える対象は、コンパイル済みコードの実行と、ネイティブの処理の中の反復（256回ごとに1。`src/core/words_numeric.zig` の `checkWorkBlock`）である。次の性質がある。

- 上限があるときは「数える実行ループ」を使い、通常の実行ループには確認の処理がない。どちらを使うかは、実行ループに入るときに決まる（`src/forth.zig:1809`）。ループの中では種類がコンパイル時の定数なので、実行中に上限を設定しても、すでに走っている通常の実行ループは数えるループに変わらない。
- この仕組みはデバッグ機能のビルド（`debug_enabled`）のときだけある。
- 上限に達したときのエラー（`StepLimit`）は、`CATCH` に渡さずに外へ返す（`src/forth.zig:1830`）。

割込みのエラー（-28）は定義されている。Raw modeでは、Ctrl+Cは信号ではなくキーとしてホストに届く（POSIXは `ISIG` を外し、Windowsはprocessed inputを外す）。`EKEY` の経路では、読んだ値3を割込みのエラー（-28）に変える。したがって、Raw modeでキーを読まずに計算を続けている間は、Ctrl+Cを押しても割込みは起きない。`NS` の待機（`src/host_wait.zig`）は、待つ間だけ信号のハンドラーと端末の設定を変えて、Ctrl+Cで待機をやめられるようにしている。

### 対応方法

- **数える実行に入る入口を、語として明示する。** 実行中に上限を変えてもループの種類は変わらないので、「上限を設定する語」だけでは働かない。実行トークンと上限を受け取り、数える実行ループでその語を実行する形を第1候補とする。例：`EXEC-LIMITED ( i*x xt u -- j*x ior )`。上限に達したら、その入口まで戻ってiorで知らせる。いまの `StepLimit` は `CATCH` に渡らないので、入口で受ける形にすれば既存の動作を変えずに済む。入れ子にしたときの予算の扱いを決める。
- **実行制御の語群は、デバッグ機能のビルドにだけ入れる（決定）。** 数える仕組みは `debug_enabled` のときだけある。デバッグ機能を外したビルド（`-Ddebug=false`）では、実行制御の語群ごと外す。数えるループだけを別の条件で残す形は、ビルドの組合せが増えるので採らない。
- **中断の確認は、数える実行ループの中だけで行う。** 数える実行ループが印を確認して-28を `THROW` する。通常の実行ループには手を入れない。中断できるようにしたいアプリは、上の入口から実行する。
- **中断の要求の出どころを分けて設計する。** (1) Raw modeのCtrl+C：キーとして届くので、読まなければ気づけない。数える実行ループの確認のときに端末の入力をのぞくか、計算の間だけ `NS` と同じように信号を有効にするかを決める。(2) OSの信号とコンソールの制御ハンドラー：印を立てる。`NS` が待機の間だけ置くハンドラーと、だれがハンドラーを持つかをそろえる。(3) プログラムからの要求（別スレッドなど）：初期版では扱わない。
- **入力の待機とネイティブの処理の中断は別に扱う。** 数える実行ループの確認は、待機の語の中やOSの呼出しの中では働かない。待機の語は、共通の取り決めに従って自分で中断を確認する。
- 企画書の `EXEC-YIELD`（協調的な切替え）と `EXEC-DEADLINE`（時間の上限）は、初期版では作らない。時間の上限は、ステップの上限と時計の組合せでアプリ側が近い動作を作れる。ただし、待機やOSの呼出しで止まっている間は確認が働かないので、時間どおりに止まる保証にはならない。
- **単調時計を読む語を足す。** アプリ側でタイマーと時間の上限を書くには、時刻の変更に影響されない時計が要る。`UTIME` は実時刻を返す。単調時計はホストの内部（`monotonicMilliseconds`）にあるので、これを語として公開する。名前はGforthに同じ働きの語があるかを調べてから決める。段階Aに入れる。

### 未決の点

- 数える実行の入口の語の形（上の例でよいか）と、入れ子のときの予算。
- Raw modeのCtrl+Cを、計算の間にどう受け取るか。
- 数える実行ループの速度の低下。`docs/DEBUGGING.md` に費用の説明があるが、今回は測っていない。
- 上限の単位。ステップ数だけにするか。

|---|---|---|
| 0 | 共通の取り決め（仕様だけ、900） | 待機・期限・中断の取り決め、資源の持ち主の表、実行制御（項目7）の仕様を先に決める。A、B、Cがこれに依存する |

段階Aは、いまの `host_input.zig` と `event_input.zig` を土台にする。ただし、既存の処理の小さな変更では済まない部分がある。`EKEY` の読取りを期限を守る作りに変えること、表示の状態をRaw modeから分けることである（Windowsの貼り付けの印は初期版では出さない）。段階Bには、Windowsのパイプの待機と、Cのストリームの先読みとの統合という論点がある。

## 設計で先に決める横断の事項

- 待機・期限・中断の共通の取り決め（共通の方針7）。
- 1回の待機で、端末の保留中の入力とパイプをまとめて扱う方法。
- キューの容量と、満杯のときの扱い（キーと文字は捨てない。パイプは読取りを止める）。
- 資源の持ち主の表（端末の状態、ファイルID、プロセス、読取りスレッド、キュー）。
- 辞書イメージの保存に含めない実行時の状態（端末の状態、開いているプロセス、キュー）と、イメージを読み込んだ直後の初期値。
- 語群のビルド時の依存関係（子プロセスは待機の語に依存する、実行制御はデバッグ機能に依存する、など）。

## 検証の方法

- 単体テスト：ホストの入力を差し替えて試す既存の方式（`key_fn`、`event_key_fn` などの差替え）で、各語の動作を試す。
- Gforthとの照合：Gforthに合わせる語（`COLS`、`ROWS`、`COMPACT-FILENAME`）は、WSLのGforthと結果を比べる。
- 端末での確認：Windowsのコンソール、WSLの端末で、代替画面・貼り付け・大きさの変更・異常終了時の復元を実際に動かして確かめる。対話的な確認は利用者の操作が必要になる。
- 失敗と境界の場合：設定の途中の失敗、キューの満杯、大量の貼り付け、標準出力と標準エラーの同時の出力、待機中に閉じた場合、子プロセスがすぐ終わる場合、終端、端末の復元の失敗。
- 通常の実行ループへの影響：変更の前後で速度を比べる（時間の計測は利用者に確認してから行う）。各語群を外したビルドが通ることも確かめる。
- macOS：手元に実行環境がない。CIの単体テストで確認できる範囲と、利用者がMacで確かめる範囲を分ける。
