# セル型local・VALUEの部分採用評価案（#870）

2026-11-17 最新結果：[#881の継続評価](VM_PARTIAL_ADOPTION_LOCAL_STANDARD_RESULTS.md)を停止条件まで完了し、#870を終了した。VALUEは未測定38条件を残して評価を終了。セル型localは実例18条件と標準16条件で悪化上限を通過したが、Windows catch-nested-256が上限5%を超え、標準17条件は未比較。両候補とも追加採用は保留、製品VMは採用済み基準版のまま。以下は各時点の履歴である。

実施後追記：[承認済み基準での初回評価結果](VM_PARTIAL_ADOPTION_RESULTS.md)。両候補ともpinball資産生成の必須改善とlogicの悪化検査は通過したが、Windows waterworks logicの短いCPU区間で停止した。残り48比較条件/候補は未測定、追加採用は保留。#870は未完了で、短い入力の計時設計が残る。

2026-11-16。利用者が本案を承認した。部分採用に限り、整数・LOOP各10%短縮の必須条件を、両OSのpinball資産生成でmax(3%, 2δ_i)超の短縮へ置き換える。安全性・悪化上限・サイズ条件は維持する。承認は実装済み・採用済みを意味しない。以下の提案・判断前という表記は承認前の記録であり、追加評価は承認内容に従って進める。[3候補の結果](VM_THREE_CANDIDATES_RESULTS.md)から、VALUE、セル型localの順で検討する。両候補は別々に評価し、組合せ版を作らない。literal→bit_andはWindows専用予備条件で悪化したため対象に含めない。

## 現行条件で確定していること

両候補ともWindows標準整数の10%短縮目標を満たさず、標準34条件の残り33条件は未測定である。専用ケースの短縮（VALUE約42～45%、local約11～18%）から、標準採用や実例全体の速度改善を宣言できない。

[既存基準](VM_PERFORMANCE_PLAN.md#性能サイズの採否基準案)は「条件を自動的に緩めず、効果・サイズ・他項目を示して別の採否判断に回す」としている。現行条件を維持する限り追加採用は保留のままである。残り33条件を調べても、測定済み整数目標の未達が消えるわけではない。

## 評価の優先順位

1. VALUE：両OSで専用短縮が大きく、既存の実例分類でpinball資産生成に9,464,534回のVALUE呼出しを観測した。時間比や直接最適化される呼出しの割合とは異なり、実例の効果は未測定。
2. セル型local：両OSで専用短縮を観測し、実例のlocalが計数範囲で全てcellだった。VALUEより短縮幅は小さく、実例での時間比も未測定。

VALUEが通過するまでlocalを必ず止めるという依存関係ではなく、まず一候補を独立して評価する順序である。

## 部分採用の別判断に向けた提案

変更案は、整数・LOOP各10%短縮を「部分採用の必須改善対象」から外し、**事前指定した実例の改善を必須対象にする**ことだけである。全体の10%目標を達成したとは扱わない。

実例側の提案値は、同じ条件の両OS・2系列で`max(3%, 2δ_i)`を超えるCPU短縮を得ることとする。これは新しい部分採用基準の提案であり、決定済みではない。専用ケースの既知の改善だけを実例改善の代わりにしない。

安全性、全標準項目の悪化上限、CATCH上限、各OSの実行体増加1%以内、State/CallFrame/容量/追加ヒープを増やさない条件は維持する。標準整数・LOOPも悪化検査の対象に残す。通常項目の`max(3%, 2δ_i)`、CATCH成功等5%・THROW系10%の既存上限を使い、今回の結果に合わせて広げない。

**この基準変更を判断する前に、上記の新基準を使った候補比較・部分採用を開始しない。** #870は評価案の作成だけで完了にせず、判断と評価が残るタスクとして維持する。

## 基準変更を認めた場合の追加評価手順案

1. 採用済みruntimeと単独候補のソース・実行体・入力・helperを固定する。最終追補の回帰と同じ候補であることをSHAで照合する。基準変更の承認後に、測定対象と実行順を別の凍結protocolへ具体化する。
2. 実例は既存のpinball/waterworks/klondikeのlogic・renderと3件の資産生成、計9ケースを固定する。候補の計測結果を見て効果の大きいケースだけ選び直さない。VALUEの必須改善対象はpinball資産生成とする。localの必須改善対象もpinball資産生成とする。保存済み9ケース分類でセルlocal取得48,576,540回と最大だったためで、時間効果を証明する数値ではない。
3. 各入力を繰り返す場合の状態初期化、画面・出力・checksum、計時境界を先に設計する。入力準備・コンパイルを除外できる範囲を明示する。renderではnative処理を含む結果とVM部分を混同しない。正しさを確認できる計時入力を作れなければ打ち切る。
4. Windows/Linuxとも既定のprocess CPU、CPU2を使い、baselineのみのpilotで反復数を一度決める。過去のCPU2成立を今回の校正へ流用せず、各条件でA1/A2各5標本×2群、全arm中央値5秒以上・最大δ2%以下を確認する。未達条件のCPU/N/回数探索や同条件再試行はしない。
5. 校正後、各7標本×2系列、warmup除外、先後交替・系列反転で実例比較を行う。全9ケースを個別報告し、必須対象の改善と他実例の既存悪化上限を両OSで確認する。最初の打切り条件に達したら未測定範囲を明記する。
6. 標準34条件を同じ新protocolで検査する。既知の整数目標未達を再挑戦して10%通過に読み替えず、ここでは新しい判断のための悪化検査とする。残り33条件の未測定を過去結果で補わない。A/A条件・比較回数・各悪化上限は維持する。
7. 回帰・保存形式・構成別・両OSサイズの検査を、固定した最終候補で照合する。既存記録と同じ入力・ハッシュなら再利用範囲を明示し、新しい入力やruntime変更があれば必要な再検証を行う。build/test/profileとCPU計時を重ねない。
8. 全結果をレビューし、個別採否を記録する。試作を本体へ反映する場合は別の実装・最終検証タスクで管理する。専用短縮、実例短縮、標準目標達成の有無をそれぞれ報告する。

この段階では、実例計時用の状態初期化と入力をまだ作成しておらず、追加所要時間を確定できない。少なくとも両候補の全条件評価を短時間の追試とは扱わない。

## 変更を認めない場合

現行基準による未達と採用保留を確定結果として残し、この部分採用案の評価は実施せず閉じる。過去の専用ケースの効果や試作記録は保持する。CPU0/API/ETWの残差調査を再開する必要はなく、その調査は[原因未特定で打切り済み](VM_WINDOWS_ETW_CONDITION_INVESTIGATION.md)である。

## 承認後の入力設計

資産生成は画像poolとdictionaryへ確保を行うため、同じprocess内で無条件に繰り返さない。1回ごとに新しい子processへ入力を読み込み、READY後のCPU差だけを合算するbatch方式とする。準備・コンパイル・終了は各子の計時外、BAKE-ALL・状態checksumは計時内。Nはbaselineのみの1batch pilotから約6秒となる子数を一度固定する。校正の5秒以上条件はbatch合計へ適用し、1個の連続kernelを5秒測ったとは扱わない。子ごとのAPI量子化・誤差は相殺を保証せず、全生値を残す。9実例は同じfresh-process方式で入力初期化を揃える。
