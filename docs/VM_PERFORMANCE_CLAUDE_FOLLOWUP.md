**結論:** 重大な残存問題は見つかりませんでした。条件付きで、安全な実験計画として成立します。

**確認範囲:** 計画書の案A、A0、案B、判定基準(53–138行)、`src/forth.zig:1787-1850`、`resumeCatch`と`returnToCaller`(1666-1691)、`words_system.zig:90-135`を読みました。確認は読取りのみで、旧版ソース、テスト本体、生成コード、ベンチ結果は見ていません。

**改訂点の確認結果**
- **1・2(A)は妥当です。**
  - `resumeCatch`は`running.* = self.frames[...]`で全体を上書きします(1670行)。外側の`running`は通常終了、QUIT、StepLimitのいずれでも再利用されません(1804–1806, 1818行)。
  - そのため、外側への通常の書戻しは不要という記述は現行コードと整合します。
  - ループ内の`halted`経路(1831行)で`resumeCatch(running)`が呼ばれる点も、同じローカルに揃える対象として明記されています。
  - 書戻しdeferが復元済みRunningを潰すという初回の指摘は、現行の呼出し寿命では成り立ちません。訂正は妥当です。
- **3(A0)は妥当です。** 新設チェックの除去策とせず、副作用境界と生成コードの根拠を条件にした別案へ格下げしたのは適切です。
- **4(判定基準)は大筋で整合しています。** δ_i>2%なら再測定とし、悪化の許容はmax(3%, 2δ_i)で上限が付きます。
- **5(B)は妥当です。** 偽のRuntimeErrorを使わない方針と、ran、deferred CATCH補正、抑制状態、再入境界を詳細設計の条件にしたのは適切です。

**条件付きの推奨(重大ではありません)**
1. **外側のRunningの用途を確認する。** `traceRunning(running, true)`(1799行)と、catch後の`checkWatches(running.pc -| 1)`(1813行)は外側のRunningを読みます。前者は開始時の値で問題ありません。後者は`resumeCatch`で復元済みのため問題ありません。実装時に、ループから戻った後に外側のRunningを読む箇所が他にないかをgrepで確認してください。
2. **`failed_pc`の記録を検査する。** `errdefer`(1823行)がローカルの`running.pc`を読む前提です。「命令取得後にpcが進んだ値」という既存の意味が保たれていることを、エラー系テストで確認してください。
3. **サイズ基準の揺らぎに備える。** 実行体1%以内という基準は、配置やアライメントだけで揺れる可能性があります。第0段階で同一ソースの再ビルド差も測り、あわせて非countedループのバイト数を主指標にしてください。
4. **CATCHの許容幅を確認する。** 成功・入れ子・動的は+5%以内としていますが、専用カーネルのδ_iが2%近いと実質的な余裕が小さくなります。δ_iを専用カーネルごとに測る方針(128行)は維持してください。

**未確認・未保証:** 機械語レベルの原因は未確定のままです。Aの効果は生成コードを見るまで保証されませんが、計画書もその前提で「保持しない」という撤退条件を置いています。既存テストが列挙どおりの範囲を覆っているかも未確認です。
