# 追加対策の再順位付け（#806・#807）

2026-11-16。現在の基準は7b1295fのPC分離＋データ語経路分離。本体への追加採用はない。#787の小規模候補調査と#805の限定実例調査を受け、次の着手順を更新する。これは改善率の順位ではなく、確認済みの頻度・観測時間・変更の安全性・検証費用に基づく**次の調査の順位**である。各対策の期待改善率は未確定で、数値を補わない。

## 次の着手順

1. **ローカル変数アクセスとcallの内訳を調査する。** local_fetch/local_storeとcall/call_colonの採用版生成コードを両OSで確認する。callの計数全体を関数呼出し数とは扱わず、データ語・inline marker等を分ける。一般メモリーの安全検査を単純削除しない。
2. **資産生成のVM/native内訳を調査する。** BAKE-ALLの約246〜762msという診断値を根拠に、主要生成語・native画像処理の寄与を観測する。計測版の短時間診断を本体の速度差と混同しない。通常操作にも共通する負担があるか確認する。
3. **上記で局所案が得られた場合だけ、一案の実験計画を作る。** 有効な案がなければ命令の隣接頻度の調査へ進む。命令融合の実装を先に始めない。大規模化する案しかなければ見送る。

local_fetchは通常6ケースで47,283〜6,035,002回、資産生成3ケースで13,317,449〜48,576,540回。local_storeも資産生成で4,912,789〜21,030,798回。これらはcompiled-PCの回数であり、アクセス検査・関数呼出し・時間の同数性を意味しない。最適化済みの箇所に変更余地があるとも断定しない。主目標の整数演算・LOOPに直接効くかも未確認で、実例のみの効果を標準目標達成と扱わない。

## 次の実験条件と打切り（#807）

調査1では採用版SHA・source/toolchain/target/CPU/optimizeを固定し、localの各型とcallの内訳が分かる入力を作る。Linuxの命令計数と両OSの逆アセンブルを対応付ける。全localを単なるcellとして扱ったり、call全数をnative呼出しとして数えたりしない。ソース上の検査が消えていれば、その重複削除案は見送る。

調査2では未計測基準の出力・画像の限定チェックと観測版出力を照合し、reset範囲・nativeの重複計上・測定攪乱を明示する。頻度を時間比へ換算せず、部分の和から未観測残余を識別する。短い区間しか取れなければ診断に限定し、速度効果を断定しない。

具体的な局所案が得られた後に、単独試作・回帰・レビュー・時間比較を順に計画する。既存の整数演算/LOOP10%以上かつ2δ超、通常項目悪化上限、CATCH目標、実行体各1%以内、メモリー・意味の維持を変更しない。Windows A/A校正未達では候補を測らず採用保留とし、同一条件の再試行を根拠なしに繰り返さない。実例だけの改善は標準条件達成とせず別の採否判断にする。性能比較とbuild/test/profileは重ねない。

局所案を一つに絞れない、安全性を小規模に示せない、又は生成コードに削減対象がなければ試作を打切り、予備の隣接頻度調査へ進む。その場合もVM融合・大規模cache/JITを自動着手しない。
