## 修正推奨(結論は変わらないが、記述が根拠をやや超える)

1. **プローブはresetを検証していません。**
   - プローブのsetupはコロン定義だけで、reset前にcompiled codeを1命令も実行しません。resetが無効でも結果は同じ214(19命令×10 + 24)になります。
   - reset自体はコード上正しいです。引数境界で`counts.reset()`が呼ばれ、その時点で実行中の語はありません。未認識なら`includeFile`に落ちて終了コード1になり、assertで止まります。
   - 文書とスクリプトのコメントにある「reset後の出力を検証」は、「ラベルと出力経路の検証。resetはコード確認による」が正確です。実証するなら、reset前にコロン語を実行するプローブが要ります。

2. **「全PC合計 = Profile.operations」はほぼ恒等式です。**
   - `countOperation`が両方を同時に加算します(`src/core/profiler.zig:57`)。
   - 不一致になるのは、reset後に`emit`が計数済みPCを0に戻す場合(`src/forth.zig:1435`)、`code_count`より上のPCが落ちる場合、出力の解析漏れの場合だけです。
   - つまり示せるのは「出力と解析の欠落なし」で、計数やラベルの正しさではありません。
   - 2回一致も、同じ実行体・同じ入力での決定性を示すだけです。系統的な誤りは2回とも同じに出ます。

3. **短長診断の「一次CPU値とAPI差の一致」は自己整合です。**
   - `run.py`の`Clock.read_ns`が返す値がそのまま一次値で、同じ呼出しを記録しています。独立した確認ではなく、ログの整合確認です。
   - 意味のある独立情報は主スレッド値との一致ですが、診断側の文書はそれに触れていません。
   - この照合と`summary.json`を作ったスクリプトは`.work`に見当たらず、`docs/measurements`のJSONにも照合結果の項目は見つかりませんでした。

## 項目別の確認結果

### 計数(reset・compile選択・count経路・ラベル)
- **通常compile選択**: `plain_calls`を読むのは`keepsCalls()`だけで、その利用は`src/core/inline_calls.zig:49,73`の2箇所です。パッチでインライン選択は通常どおりになります。ただしこれはコード読解による確認で、基準版と計測版のコンパイル結果を比べた検査はありません。
- **count経路**: `profile != null`ならすべて`runOperations(counted=true)`に入り、dispatchごとに1回数えます(`src/forth.zig:1783, 1884`)。文書の「counted経路で通常速度を表さない」は正確です。
- **ラベル**: `call_builtin`は`words[op.value].builtin`、`builtin`は`@fromBackingInt(op.value)`で、実行側(`src/forth.zig:2021, 2045`)と同じ解釈です。プローブは対象4語が各ちょうど10回で、取り違えはありません。
- **表の数値**: pinball-logicで (fetch 2,984,372 + store 72,967 + add_store 16,058) / 21,332,706 = 14.407%、-ROTは 2,004×2 / 21,332,706 = 0.018788% で一致しました。

### 漏れる経路
- 文書の列挙(native内部、直接解釈、動的呼出し)は妥当です。
- **明記を勧める経路**: SYNONYMやDEFER経由で組込み語に入る場合です。`call`タグのまま`wordInLoop`から実行され(`src/forth.zig:1658`)、ラベルは「-」になります。pinball-logicの`call`は260万回あり、出力からは内訳を分離できません。
- 直接コンパイルされた組込み語は必ず`call_builtin`かprimitiveタグになります(`specializeCall`、`src/forth.zig:1364`)。
- 6ケースの1回目出力では、`execute`と`local_execute`の実行は0件でした。compiled EXECUTE経由の漏れはこの実行にはありません。
- **0の意味**: 3例と`graphics.fs`、`gui.fs`で対象4語を含む行は計3行だけです。うち2行は-ROT(`src/graphics/graphics.fs:170`、`src/graphics/gui.fs:102`)で、残りはpinball.fsの1行です。「0」は動的頻度というより、これらの実例が語彙として使っていないことの反映です。文書の限定記述と矛盾しませんが、一言あると誤読を防げます。

### 短長診断
- **A/A合格扱いはしていません。** 文書34行・36行と`protocol.json`、`complete.json`の`not_adoption`が一貫しています。
- 表の中央値・範囲・系列間差は、`samples.json`の12標本から再計算して全て一致しました。順序も`run.py`と`protocol.json`どおりです。
- **「独立2系列」は強すぎます。** 1回のスクリプト実行内で連続しています(02:42:57〜02:47:11 UTC)。別セッション間の変動は含みません。
- **未記載の観察が2つあります。**
  - CPU値はすべて15.625 msの倍数です。短条件では1刻みが約0.26%で、2%上限は約8刻みに当たります。
  - 経過時間がCPU時間を一貫して約5〜6%上回ります(例: 6,365 ms対6,000 ms)。
  - どちらも原因の断定には使えませんが、予定している「計時境界・affinity照合」に入れる価値があります。
- 絶対範囲は長条件で縮んでいません(系列1は156 msから328 ms、系列2は78 msのまま)。相対値の縮小は分母の増加による分を含みます。「安定性の保証ではない」という記述は適切です。
