共通仕様は[決定事項の#909](DECISIONS.md)、調査範囲は[検討書9章](NATIVE_WINDOW_STUDY.md)。LinuxではlibX11/libxcbを新たにリンクせず、ローカルUnixソケットへの直接通信を先行する。TCP・SSH転送とWayland直接接続は今回の最小試作に含めない。未対応の接続先は失敗として返し、将来の自動選択では既存Tk/端末への候補探索を維持する。

最小試作の素材は`experiments/linux_x11_probe.py`（Python標準ライブラリのみ）。再実行は`python3 experiments/linux_x11_probe.py`。既定のDISPLAYを変える場合は`--display`。ソースと公式規約の照合先は[X11R7.7 protocol](https://xorg.freedesktop.org/archive/X11R7.7/doc/xproto/x11protocol.html)。認証の番号空欄は表示番号のワイルドカードとして扱う。

この試作はForth本体に接続していない。専用スレッド、キーボード/IME、マウス、フォーカス、入力待ち/計算中の応答、実際の閉じるボタンは#911/#923の対象。WM_DELETE_WINDOWは合成SendEventの経路確認であり、物理操作の合格とはしない。pixmap読戻しは画像転送の照合であり、画面上の向きや実描画FPSの目視・測定とは区別する。

### X11レビュー対応と追加試作

初回レビューの対象はMapNotify/Expose等を追加する前の試作だった。その指摘を受け、認証は同順位の最初の項目を選ぶよう修正し、空のXAUTHORITYを既定パスとして扱い、資源IDはmaskの最下位ビットに合わせた。要求サイズをあえて16384 bytes以下に制限し、257×129でも分割送信を通すよう変更した。Xvfbをパッケージから`/tmp`へ展開して16bitと24bitの独立X11サーバーでも実行し、全画素読戻しとライフサイクルが成功した。16bit/pad32では実際の行paddingも検証できた。Xvfbは試験用で、Sigmaの依存ではない。

この試作段階では、XIMは別の成立確認が必要というレビューに従い、本体の自動表示の既定を変更しない。X11実装中の動作確認には実験用ビルドオプション`-Dx11=true`を使う。この段階では、残る受け入れ項目を満たすまで配布版の表示優先順位を変更しない方針だった（後に既定ONへ変更。最終節参照）。現在のデスクトップの`XIM_SERVERS`にはibus（所有者なし）とfcitx（所有者あり）があり、XKEYBOARD拡張も存在する。接続可能なIMサーバーがあることと、確定文字・preeditが使えることは区別する。

### XIMの試作とレビュー対応（#994/#995）

公式の[XIMプロトコル](https://xorg.freedesktop.org/archive/X11R7.7/doc/libX11/XIM/xim.html)を照合し、`experiments/linux_xim_probe.py`でfcitx transport 0.0、UTF8_STRINGの交渉、preedit callbackを使うICの作成/破棄を確認した。Zigでもliveのopen/focus/spotを含む4件が非skipで成功した。IMサーバーの存在やIC作成だけでは、日本語入力・変換・候補位置が正しい証拠にはしない。

XIMの実装レビューではMappingNotifyによる誤切断、IM障害による窓全体の終了、no-string DRAWの削除解釈、遅れた解放、Xフォーカスとの不一致、UTF-8途中切れ、候補位置の再通知、muslスレッドのスタックなどを指摘された。IM用接続の無関係イベントは無視し、障害はIMを閉じてrawキーへ縮退させる。IMはXのフォーカスとGUI入力欄のactiveが両方ある場合だけキーを受ける。非activeのINKEYゲーム操作を変換中の文字列へ吸い込まない。preeditはUnicodeスカラー単位の差分を処理し、GUI側の小さい受信バッファでもUTF-8境界で区切る。確定文字列は残りを保持して有界の入力キューへ順に渡す。候補位置は窓の再作成・ConfigureNotify・前回応答待ちの後も再送する。XIMの初期化予算は750ms、応答の監視は1秒、終了の交渉は100ms以内とする。

Debugで512KiBのスレッドスタックを使った試験では、`Client.open`のスタックプローブでSIGSEGVを再現した。逆アセンブルで同関数だけで0x9b0a8（約620KiB）のフレームがあることを確認し、スレッドスタックを4MiBに明示した。修正後、隔離Xvfbの合成IMサーバーで「日本」から1文字削除し「語」を挿入したpreedit「本語」、確定文字「日本語😀」のUTF-8全13バイト、IC/IM/接続の正常終了が成功した。これはワイヤ経路の合成試験で、物理IMEの合格ではない。

現段階の対象はXIM X-transport 0.xとUTF8_STRINGを交渉できる静的イベントフロー。COMPOUND_TEXTのみのサーバー、REGISTER_TRIGGERKEYSによる動的イベントフローは未対応。preeditの色分けfeedbackや文節カーソルの再現は対象外で、既存GUI-FIELDの下線表示へ文字列を渡す。物理IMEのインライン表示・取消・候補位置・確定・フォーカス移動は、下記の利用者確認で合格した（#995）。この段階では既定の`-Dx11=false`を維持した。後述の最終受け入れ後に既定ONへ変更した。

### 静的muslのゲームパッド（#914/#993）

[Linux inputの状態取得](https://docs.kernel.org/input/event-codes.html)と[gamepad仕様](https://docs.kernel.org/input/gamepad.html)、[新規にはevdevを勧めるjoydev文書](https://docs.kernel.org/input/joydev/joystick-api.html)を参照。Claude Codeの方式レビューを受け、evdevの状態ポーリングを採用した。機種固有のhidraw、動的SDL helperの追加、配布全体のglibc化、SDL静的リンクは今回採らない。動的Linux/Windows/macOSのSDLは維持し、静的Linux muslでのみevdevを使う。

最初の版はrawのみ。`mapped`と`GAMEPAD-MAP`は常に偽で、mapped専用ゲームの操作を保証しない。軸はABSコード昇順で最大16、ボタンは0x100以上のコード昇順で最大32、-1..1のHAT軸は最大4組の帽子へ変換する。アナログ用途のHATコードは通常軸へ回す。SDLのraw番号とも互換とはしない。軸は全範囲を-32768..32767へ正規化し、デッドゾーン補正はなく、トリガーの静止値も-32768になる。GUIDはbus/vendor/product/versionによる独自の32桁hexで、SDLのmapping GUIDではない。

sysfsのmodaliasにBTN_GAMEPAD/BTN_JOYSTICKがある候補だけを開き、キーボード等のイベントを読まない。ioctlで状態を取得し、grab・書込・力覚・LED・センサーは扱わない。対象はevent0〜255、最大8台、走査は1秒間隔。権限設定直前の一時拒否には1走査の猶予を置く。継続して候補が全て拒否されたら-1、一部を開けたらその数、候補なしは0、sysfs/dev/inputがなければ-1。-1からもPOLLで再試行できる。必要なデバイスACLはログインセッションとudev設定に依存し、モード0660だけで可否を判断しない。inputグループへの追加やデバイスの権限変更は行っていない。

スナップショットは複数ioctlの結果であり、同一SYN_REPORTにそろった原子的な観測ではない。POLL間の短い押下は失われる。EINTRは再試行し、一時失敗は前回の全状態を保持、ENODEV等では破棄して再検出する。再接続でIDは変わる。実機接続/切断と実デバイスのioctlは後述の#993で確認した。uinputによる合成試験は未実施。

### 再レビューで残った通常操作の修正

Claude Codeの再レビューで、初回作成期限を閉鎖後のアイドル受信にも流用する不具合を指摘された。期限をメールボックスのフレームと同じロックで保持し、作成時だけ適用するよう修正。private Xvfbで起動6秒後のclose/reopenを確認した。XKBはDetectableAutorepeatだけでなくNewKeyboardNotify/MapNotifyも選択し、コアChangeKeyboardMappingでaをbに変更した後の入力が更新されることを確認した。NumLockの修飾マスクをGetModifierMappingから調べ、グループ2でNoSymbolになる特殊キーのグループ1への復帰、テンキーとControlの変換も追加した。グループ3/4や複雑なXKB key typeは未対応。

IMの生存確認は、forwardごとの応答数の推測をやめた。最初の未応答forwardから1秒待ち、任意のXIM受信を生存の証拠とする。何も届かなければSYNCを送り、さらに1秒応答がない場合だけIMを閉じる。キーを黙って消費しSYNCだけに応答する合成IMでも、その後のpreeditと確定が動く試験を追加した。打鍵の空白が長かった場合でも、最後の受信時刻ではなく最初のforward時刻から猶予を取る。

接続拒否・EOF・setup無応答は、`test-linux-x11-failures.py`で明示SHOWの-265として捕捉できた。正常終了し、SIGPIPEでプロセスが終わることはなかった。無応答は5.052秒。Xvfb切断後、同じSigmaプロセスでSHOWが1回-265になり、Xvfbを再起動した次のSHOWは成功した。表示後にSAVESYSしたファイルには実行権限があり、その実行ファイルからも新たに表示できた。

ゲームパッド再レビューでは、GUIがraw番号をSDL標準配置と誤認する既存の経路を発見し、GUIのパッド入力をmappedだけに制限した。raw無視、押し続けたボタンの1回だけの実行、切断/再接続後の押下が反応する回帰試験を追加した。以前の辞書に保存したGUI定義は自動更新されないため、rawバックエンドを使う場合はGUIをソースから読み直して保存し直す。

再現用スクリプトは`tests/scripts/test-linux-native-window.py`、`test-linux-xim-fixture.py`、`test-linux-x11-failures.py`。`SIGMA_TEST_BINARY`で`-Dx11=true`の実行ファイルを指定する。XIM fixtureとキーマップ変更は必ずprivate Xvfb上で実行し、`SIGMA_TEST_PRIVATE_XSERVER=1`を付ける。前者はrootのXIM選択をテスト用に設定し、後者はキーマップを変更するため、利用者のデスクトップには適用しない。遅い閉鎖の試験は`SIGMA_TEST_CLOSE_AFTER=6`、キーマップ変更は`SIGMA_TEST_REMAP=1`。

この区切りでは全候補の探索を合わせた5秒予算とTk側の無応答が未受け入れだった。後続の#1004の結果は下記。性能比較、物理マウス、別DPI、XWaylandのコールド起動は未受け入れ。今回のX11単体の期限確認とは分け、#983/#923に残す。これらを満たすまではX11を配布版の既定表示先へ切り替えない。

最終の限定再レビューでは、通常操作の4件（期限、XKB通知、再作成時の状態、特殊キー）への対応を確認された。残ったIMタイマーの起点1件も、最初の未応答forwardで起点を更新するよう修正した。1.2秒の打鍵間隔を置く合成試験では、無応答キーを送った1.002秒後にSYNCが出て、その後の変換・確定も成功した。

XIMの実験用上限は1確定4096 UTF-8 bytes、preedit1024 bytesで、GUI側の小さい受信領域はUTF-8境界で表示を切る。未対応の符号化・輸送・サイズやIM側の異常では、窓を終了させずIMを閉じてraw入力へ戻る。大きさや全文反転を含めた完全なXIM実装ではない。
