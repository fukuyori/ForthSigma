# CATCHの処理負担とRunningの受渡し（2026-11-15）

本書は実装前の調査記録である。その後の[案Aの実験と不採用判断](VM_PERFORMANCE_A_EXPERIMENT.md)は別に記録した。名前領域のコピー削減は実装していない。

## 結果

CATCHの入口には、通常ループのPC参照とは別に、次の定義名を保存する255バイト配列のコピーが3回あった。長さ0でも実行され、1回の正常CATCHで合計765バイトをコピーする。THROW時は復元用のコピーも加わり、今回のケースでは計6回・1,627バイトとなった。

正常復帰はループ内で完結する一方、THROWは外側のドライバーによる復元とループ再開を通る。CATCH成功用の0を積めない場合は、通常復帰でもBYEでも、呼出し元Runningの復元後に失敗することを確認した。案Aではこの状態と失敗PCを維持する必要がある。

改善実装は行っていない。コピー削減による改善率や、案Aの性能を測った結果ではない。[通常VMの調査記録](VM_PERFORMANCE_INVESTIGATION.md)の続きとして、CATCH自身の負担と状態の境界を分けて調べた。

## 対象と方法

HEAD `257504759fd22e7453f9e96798e755f1ea589f79`のLinux fast・baseline CPU・シンボル付き実行体を使用した。SHA-256は`d7c8c88e0dd175231f1c35cf37a7c71358e2e595924e7b6b9a02d93d99b2a028`。以前の時間測定用strip版と、実行体全体の配置が同一とは扱わない。

- 既に校正したCATCH専用9カーネルを各100／200反復でCallgrind測定し、差を100で割った。全18ケースでネイティブ実行とチェックサム・DEPTH・後続の計算結果が一致した。
- `--collect-atstart=no --toggle-collect=forth.State.runOperations__func_180`を使用。ループだけでなく、その外側にあるTHROW復元処理を含めて収集した。
- 各関数の自己命令数を集計し、その合計と収集範囲全体の命令数が一致することを検査した。呼出し先を含む累積値を重ねて足していない。
- GDBで実際のmemcpy入口の第3引数と呼出し元を読み取り、コピー長を確認した。別に、状態復元・バックトレースの入口・名前の復元を観測した。

以下の命令数・メモリー参照数はシミュレーターの計数である。実CPUのサイクル数や、実時間に占める割合を示すものではない。GDBで停止させた実行から速度を判定していない。

[生データ](measurements/2026-11-15-catch-vm-cost.json)に、命令列、関数別計数、呼出し回数、コピー長とアドレス、境界ケースの入力・出力・状態を保存した。調査用スクリプトとログは`.work/vm-investigation-20261115/`にある。リポジトリ本体の実装・ビルド設定・VERSIONは変更していない。

## 経路別の負担

| 1反復のケース | 命令数 | データ読込み | データ書込み |
| --- | ---: | ---: | ---: |
| 正常CATCH | 639 | 189 | 144 |
| EXECUTE経由 | 719 | 214 | 156 |
| DEFER経由 | 757 | 216 | 152 |
| SYNONYM経由 | 704 | 204 | 152 |
| THROW 77を捕捉 | 1,200 | 331 | 275 |
| FAST-THROW 77を捕捉 | 1,220 | 338 | 280 |
| CATCH-NOBTでTHROW 77を捕捉 | 1,202 | 332 | 277 |

いずれも外側のループ制御・結果の加算等を含むカーネル1反復の差分であり、CATCH単体の命令数ではない。

GDBでBENCH-RUNの実際のVM命令列も確認した。通常CATCHはcall_builtin、EXECUTE経由はCATCHのexecution_tokenとexecute、DEFER／SYNONYMはそれぞれのB-CATCHを指すcallだった。ソース上で別名を付けただけで同じ直呼出しになったケースを、動的経路として数えたわけではない。

通常CATCHは`runOperationsLoop → builtinInLoop`を1回通る。EXECUTE／DEFER／SYNONYMは`runOperationsLoop → wordInLoop → builtinInLoop`を1回通り、名前のコピー3回は共通だった。DEFER経由では、保存したcall_depthの補正もある。

深さ64では1反復あたり65回のCATCHと64回のTHROW 0があり、名前のコピーは195回だった。深さ256は257回のCATCH、256回のTHROW 0、コピー771回だった。これらのTHROW 0では外側の復元ドライバーへ移らず、ループ再開も反復に比例して増えなかった。

非0のTHROWでは、1反復につき外側からループへの再入力が1回、CatchContext.handleErrorが1回増えた。FAST-THROWもこの復元経路を通った。現在のwords_diagnostics.zigではFAST-THROWが非0を確認してthrow_nobtを設定し、通常のTHROWへ委譲するため、このカーネルで復元処理を省略する形ではない。今回の命令数だけから実時間の優劣や、他の例外処理全般の性能を結論しない。

## 名前領域のコピー

### 正常CATCHの入口

GDBで1反復ずつ観測した通常／EXECUTE／DEFER／SYNONYMの全ケースで、次の3回があった。アドレスは今回のシンボル付き実行体のmemcpyから戻る位置。

| 戻り位置 | コピー長 | 観測した用途 |
| --- | ---: | --- |
| 0x1108d55 | 255 | CatchContext.initの名前保存 |
| 0x1108dc6 | 255 | enterCatch内の別の一時領域への名前コピー |
| 0x1109535 | 255 | 保存した名前をCATCH継続領域へ格納 |

最初の2回はコピー元が同じState.next_nameで、3回目のコピー元は最初のコピー先だった。全ケースでnext_name_lenは0だったが、各memcpyの長さは255だった。765バイトはコピー長の合計であり、別々の765バイトの状態を保持することや、765バイトのヒープ割当てが発生するという意味ではない。

この正常CATCHカーネルでは、memcpy関数自身の命令数が268、カーネル全体が639だった。これは命令数の内訳であり、「実行時間の約42%がコピー」という判定には使わない。

### THROWの復元

上の入口3回に、以下の3回が追加された。THROW、FAST-THROW、CATCH-NOBT中のTHROWで同じコピー長だった。

| 戻り位置 | コピー長 | 観測した用途 |
| --- | ---: | --- |
| 0x110187a | 352 | resumeCatchから返すCatchContext |
| 0x11019ed | 255 | CatchContext.handleError内の名前領域 |
| 0x1101dab | 255 | restoreCatchFrameによる名前の復元 |

合計は`3×255 + 352 + 2×255 = 1,627`バイト。THROWカーネルでmemcpy自身の命令数は555、全体は1,200だった。Running自体は16バイトであり、このコピー量をそのままRunningの受渡しコストとして扱わない。

### 保持する必要がある名前の意味

名前領域はNEXTNAMEで指定した次の定義名をCATCHの失敗後に復元するために使われる。Stateの定義処理とquotationsはnext_name_lenまでを名前として読み、library_loadingにも名前領域全体を退避・復元する経路がある。CATCHだけを見て状態の保存項目を削除しない。

実際のcompiled CATCHで、長さ4と最大長255の名前を設定した後、捕捉される側で名前をTemporaryへ上書きして-123をTHROWするケースを追加観測した。どちらも元の名前が復元され、その名前で定義した語が10を返し、Temporaryは未登録、最後のDEPTHは0だった。このときも入口の3コピーは各255バイトだった。

中間コピーを減らせるかは、CATCH限定の独立した検討事項となる。全255バイトと関連フラグの意味を保ったまま同じ保存先へ構築できるか、生成コードで確認する必要がある。長さ0なら無条件に保存を省略できる、あるいはprefixだけのコピーへ変えられるとは、今回の調査だけでは決めない。案Aと同時に変更して効果を混ぜない。

## 成功用0の容量不足と失敗PC

Linux fast実行体を`-d 16`で起動し、16個の値を残すFULLと、それをCATCHするINNERを用意した。FULLが通常復帰する場合と、16個の値の後にBYEする場合を調べた。それぞれ外側CATCHの有無とcounted／非countedを組み合わせ、計8ケースをネイティブとGDBで確認した。

| FULLの終了 | 外側CATCH | ドライバー退出時のデータ | halted | 未捕捉時の失敗位置 |
| --- | --- | --- | --- | --- |
| 通常復帰 | なし | 元の16個の値 | false | INNER内CATCHの直後、PC 19 |
| 通常復帰 | あり | -3 | false | 外側で捕捉 |
| BYE | なし | 元の16個の値 | true | INNER内CATCHの直後、PC 20 |
| BYE | あり | -3 | true | 外側で捕捉 |

counted／非countedで上の結果は一致し、ドライバー退出時のcatch_depthは全ケース0だった。これはexecuteOperationsの後処理が終わる前の観測なので、その時点のframe_depthやcall_depthが0とは主張しない。

外側CATCHがないケースでは、recordBacktraceへ渡されたPCとState.failed_pcが一致し、その直前の命令はINNER内のCATCHを呼ぶcall_builtinだった。ネイティブ出力でも`BACKTRACE: INNER`を確認した。FULLの最後の命令を失敗位置として報告していない。

通常復帰の外側CATCHありでは、ネイティブ出力は`-3 0`（捕捉コードと、結果を取り出した後のDEPTH）。BYEの外側CATCHありではhaltedが維持されるため、その後の`.`は実行されず、データが-3になったことはGDBで確認した。

## 案Aに必要な受渡しの条件

| 境界 | 現在の処理と、局所Runningに必要な条件 |
| --- | --- |
| CATCH入口 | 呼出し元Runningをframesへ保存してから、同じRunningを対象語へ切り替える。ヘルパーはループ内の正しいローカルを更新する |
| 正常復帰・EXIT・DOES>終端 | returnToCallerが呼出し元を復元し、CATCH継続を消費してから0を積む。容量不足のfailed_pcは復元後の位置を使う |
| BYE巻戻し | ループ内resumeCatchが呼出し元を復元して0を積む。途中のエラーでも復元位置を失わず、haltedを保つ |
| THROW | ループ退出時にfailed_pcを記録する。外側resumeCatchが外側Runningを保存済みフレームから復元し、handleError成功後、その値で次のループを開始する |
| QUIT・StepLimit | CATCHによる復元を通さず外へ返す。実行状態の受渡し用の偽エラーを追加しない |
| countedの開始時TRACE | 外側の開始状態を参照する |
| countedのCATCH回復後WATCH | 外側resumeCatch後の復元状態を参照する |

外側Runningの読取りは開始時TRACEと、例外回復後WATCHにある。正常なループ終了後の最終Runningを読んで続行する処理はない。recordBacktraceはfailed_pcとframesを使う。このため、今回の範囲では外側へ終了時Runningを常に書き戻す必要性は見つからなかった。

ただし、値渡しへ変えた候補はまだ存在しない。上の境界確認は現行コードの観測であり、候補の正しさを検証したものではない。ホスト再入、例外フォーマッター、TRACE・WATCH・ステップとの全組合せ、Windows／Debugの実行確認も今回の追加調査の範囲外である。

## 現時点の判断

通常VMではPC・終端PCへのメモリー参照が増えており、案Aの単独実験を行う根拠は維持される。CATCHには別に名前領域の中間コピーがあり、処理負担の内訳として記録した。どちらも実CPU上の寄与率や改善率は未測定である。

例外ヘルパーが通常ループの複数箇所へ大規模展開されているというA2の条件は、今回の測定でも確認できなかった。ヘルパーの非インライン化だけで名前のコピーが減るという根拠もない。追加の改善実装や候補の採用は行っていない。
