## B. 不採用と早期打ち切りの妥当性

- **停止は手順どおりです。** `protocol.json` の stop 条項は「完了した条件でいずれかの系列が据え置きの悪化上限を超えたら自然停止、両系列超過だけを再現と呼ぶ」です。stacks は +5.155%／+3.093% で両系列とも 3% を超え、`performance-audit.json` の stop 記録と一致します。
- **閾値は結果を見て動かしていません。** δ=0 なので上限は max(3%, 2δ)=3% の床で、事前規定どおりです。
- **比較回数と順序は worker のコード上で規定どおりです。** `max(7, 採用A/A回数)`、warmup 1回の除外、系列ごとの交互順、worker ごとのハッシュ assert が実装されています。系列2の `orders` は候補先行の8組でした。
- **残り32条件を測らずに不採用とするのは正当です。** 主張は「事前ゲート不通過」で、「普遍的な悪化」ではありません。不採用側の誤りで失うのは小さな最適化機会だけで、本体は無変更です。追加計時は要りません。
- **記録の内部整合は取れています。** 系列ファイル16件、A/A 採用4、比較完了2、`unpaired_comparisons` は空で、棄却した A/A（arithmetic の c0-r15／c0-r31）も残っています。
- **arithmetic は上限内ですが標準条件は未達です。** -1.571%／-1.042% で、10%以上短縮の条件を満たさず、A/A の δ1.571% と同程度です。改善とは読めません。
- **「再現」は protocol 定義の意味に限ってください。** 系列2は刻み1つ未満の余裕なので、統計的再現とは呼べません。文書の現行表現（点推定によるゲート不通過）は適切です。

補助的な観察が1つあります。ゲート指標ではないので、判定根拠にはせず、書くなら参考扱いにしてください。系列2の wall 時間は基準中央値 1,577,037µs、候補 1,658,581µs で約 +5.17% です。外れ値を含めても候補の最小値（1,654,322）が基準の最大値（1,592,895）を上回ります。wall の計測区間の定義は未確認で、系列1は見ていません。

## C. 再試行・コード配置調査の前の任意フォローアップ

1. **計時の分解能を上げる。** 再試行するなら、3%上限が10刻み以上になる反復数（基準5秒以上）にするか、wall を副指標として事前登録してください。今回の結果には遡って適用しません。
2. **δ の床を決める。** 量子化された時計で δ=0 が出たときの扱い（たとえば δ の下限を1刻み相当にする）を、次回の protocol に事前に書いてください。
3. **テストを補強する。** 現行の2件は DO…LOOP 内の経路（`builtinInLoop`）を直接通りません。-ROT のループ内検証は Callgrind 用カーネルの重み付きチェックサムだけです。ループ内 ROT/-ROT の重み付き検査を足すと、今後の試作に共通で使えます。
4. **整形差分を分離する。** 本体の `src/core/words_stack.zig:13-17` は zig fmt で変わる状態のようです（候補側で整形が発生）。次の試作では整形だけのコミットを先に分け、意味差分を分岐だけにすると照合が楽になります。
5. **新テスト2件の本体取り込みは別変更にする。** 基準実装でも通る内容なので、不採用とは独立に判断できます。
6. **コード配置調査は Windows 側の観測から始める。** Windows 計時版の逆アセンブルや命令数は未取得です。Linux Callgrind の 132→55 Ir から Windows の実時間は推定できません。基準と候補の Windows 実行体で、該当ループ周辺のアドレスと整列、インライン化の差を見るのが先です。原因の仮説（レジスタ割付、配置、CATCH との共通性）は、それまで文書に書かない現方針のままでよいです。
