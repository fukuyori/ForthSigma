## 結論
`linux-interrupt.json` からは、「SIGINT が既定の処理（プロセス終了）のまま届いた」ことまでは言えます。どこで届いたかは記録から特定できません。提案された試験用設定は音を変えずに描画の負荷を下げられるので、妥当だと考えます。ただし、物理的な Ctrl+C を wait 中に当てられる確率が上がるだけで、確実にはなりません。ファイルの実行・編集・ネットワークアクセスはしていません。

## 確定している事実
- **終了の状態**: 記録の内容は `stdout` が READY 行だけ、`exit: -2`、`interruption_and_replay_checks_passed: false` です。Python の `Popen.returncode` が負の値になるのは、シグナルで終了したときです。つまり SIGINT（2）で終了しており、Forth 側で `-28` を受け取って `CATCH=` を表示する経路は通っていません。
- **SIGINT ハンドラが入っている範囲**:
  - `waitFor`（`src/core/words_pcm.zig:120`）が `ops.begin` から `ops.end` までの間だけ入れます。呼び出し元は `execution_host_ops` で、`beginExecution` → `beginInput` → `beginNative` の順に進み、`execution_depth` が 0 でないため `SA_RESTART` 付きになります。
  - この範囲に入るのは PCM-WAIT / PCM-STOP / close の待機だけです。ほかに `MS` も、`waitUsing` で別に自分のスコープを持ちます。
  - ZX-RENDER、PCM-WRITE、ふつうの Forth コードを実行している間は、ハンドラが入っていません。
- **ハンドラ外での処理**: `parent_sigint_guard` は Python の親プロセス側でハンドラを捕捉型にしています。捕捉型のハンドラは exec の時点で SIG_DFL に戻るので、Sigma はハンドラ外では SIG_DFL のままです。シグナルの処分はプロセス全体で共通なので、ハンドラが入っていればプロセスは終了しません。したがって、届いた時点ではどの NativeScope にも入っていなかったことが確定します。
- **言えないこと**: 描画中、PCM-WRITE 中、スコープの切り替えの合間など、どこで届いたのかは記録から特定できません。

## 原因の可能性（※推測です）
LONG を実行している間は、ほとんどの時間を 512 フレームの描画と WRITE に使っていると推測されます。1 ブロックの実時間は約 10.7 ms です。描画の速さが実時間に近ければ、waitFor に入る時間の割合は小さくなります。

Windows で同じヘルパーが合格した理由は、時間の割合の差か Ctrl ハンドラの仕組みの差と考えられますが、未確認です。

## 試験の設定の評価
- **ほかのチャンネルは音に影響しない（コードから確認済み）**:
  - R7=62 は tone B/C と noise A/B/C を無効にし、tone A だけを有効にします。
  - `ZX-CHANNEL`（`examples/zx-spectrum-audio.fs:130`）を見ると、B/C は R7 の無効ビットがあるので常に通過し、音量は R9/R10=0 です。A の noise ゲートも R7 bit3 で常に通過します。
  - したがって、A の出力は B/C の周期・noise の周期・LFSR の状態に依存しません。
- **区切りを変えても A は変わらない（コードから確認済み）**: `ZX-STEP-LIMIT` は A の残りステップ数も最小値の候補に含めます。区切り方を変えても、A がトグルする位置は変わりません。
- **今の設定の負荷**:
  - B/C の周期 0 と noise の周期 0 は、`1 MAX` で 1 になります。このため、`ZX-FAST-STEPS` は 1〜2 ステップずつしか進みません。
  - 1 サンプルは約 4.6 ステップ（3546895/48000/16）なので、1 サンプルごとに `ZX-ADVANCE-STEPS` が数回回ります。
  - 包絡線はリセット時に HOLDING なので、制約になりません。
- **提案の設定**:
  - tone B/C=4095（R2=255、R3=15、R4=255、R5=15）と noise=31（R6=31）にすると、ほぼ A の周期 252 だけで区切られます。描画の負荷が下がり、wait の割合が上がると推測されます。
  - 変わるのは試験のソースだけで、ネイティブ側のシグナル処理の範囲は広がりません。
- **残る課題**: 確実にはならないので、物理的な Ctrl+C の試験は確率的なままです。

## 決定的な診断の提案（すべて無音）
1. **PCM が同一であることの確認**: 今の設定と提案の設定で、`ZX-RENDER` を同じフレーム数だけ実行し、バッファがバイト単位で一致することを確認します。デバイスは使いません。
2. **wait の外では SIG_DFL であることの確認**:
   - PCM を使わずに ZX-RENDER だけを繰り返す Sigma を外から見張り、`/proc/<pid>/status` の `SigCgt` の bit1（0x2）を繰り返し読みます。一度も立たないことを記録します。
   - 次に、無音の `FALSE ZX-STREAM` を実行中に同じように見張り、bit1 が立つ時点があることを記録します。
3. **wait 中に SIGINT を送る試験**:
   - 2 と同じ無音ストリームで `SigCgt` の bit1 が立った時点を検出し、すぐ `os.kill(pid, SIGINT)` で SIGINT を送ります。`CATCH=-28 handle=0`、REPLAY、`DEPTH=0` になることを確認します。
   - 検出してから送るまでの間に wait を抜ける競合が残ります。`-2` になった場合は、再試行で上書きせず、その回の結果としてそのまま記録します。
4. **wait の割合の目安**:
   - 両方の設定で、短い無音ストリームの `PS-WAITS` / `PS-WRITES` / underrun を比べます。
   - この値は実行速度に左右されるので、時間の測定に当たります。実行する前に、レモンさんに確認します。

## 失敗の記録を残すために
`interrupt.py` は `{platform}-interrupt.json` と `.fs` を固定の名前で上書きします。次に実行する前に、出力先を別の名前（例: `linux-interrupt-r2.json`、`linux-interrupt-diag.json`）に変えてください。今の `linux-interrupt.json` は、失敗したときの記録として残してください。
