## 所見

### 1. 【中・今回の回帰】全画面に戻らなかったとき `normal_rect` が古いまま残る
- **場所**：1070行 `if (!self.refullscreen) self.normal_rect = null;`。1072〜1077行では、`fullscreen_wanted` が偽なら全画面に入り直しません。
- **起こし方（ソースから確実）**：全画面中に `FALSE FULLSCREEN 1 WINDOW-ON` と続けて書くと、同じループの回で次の順に処理されます。
  1. applyModes が解除を送り、`state_asked=false` にする。
  2. applyPlace は `fullscreen_on` がまだ真なので全画面用の分岐に入り、`normal_rect` に移動先を入れて `refullscreen=true` にする。
  3. 状態の通知が来ると、移動先へ動かす。このとき `refullscreen` が真なので `normal_rect` を残す。続いて `fullscreen_wanted` が偽なので入り直さない。

  結果として、窓は通常表示なのに `normal_rect` が残ります。次のどれでも同じになります。
  - `1 WINDOW-ON` のあと、WMが通知する前に Alt+Enter を押す
  - 同じく、WMが通知する前に `FALSE FULLSCREEN` を実行する
  - WMが解除の要求を無視したあとで解除する
- **影響**：
  - 次に `TRUE FULLSCREEN` を実行しても、1084行の `normal_rect == null` が偽なので、今の位置を取り直しません。
  - そのため、利用者が手で窓を動かしたあとで全画面にして解除すると、窓は昔の WINDOW-ON の移動先へ跳んで戻ります。
  - 全画面中の WINDOW-ON（1255行）も、古い w/h で中央を計算します。
  - 差分の前は1070行で必ず null にしていたので、この状態は起きませんでした。
- **修正案**：入り直すかどうかを、ロックの中で読んだ `fullscreen_wanted` で決めてから null にします。
  ```zig
  lock(); const again = self.refullscreen and fullscreen_wanted; unlock();
  if (!again) self.normal_rect = null;
  ```

### 2. 【中〜高・仕様と合わない】全画面経由では、通常サイズが移動先に入らなくても縮めない
- **場所**：1259〜1266行では、作業領域に収まるように縮めた `client_w/h` を `normal_rect` に入れます。一方、1060〜1066行の復元では、フラグが `3<<8`（x,y だけ）なので大きさを送りません。通常表示用の分岐（1273行、`15<<8`）は大きさも送ります。
- **起こし方（送る内容はソースから確実。最終的な大きさはWMしだいの推測）**：今の記録の配置（画面1は 1920×1080 で左側）なら、`2400 1300 WINDOW-SIZE SHOW TRUE FULLSCREEN` のあと `1 WINDOW-ON`、続いて `FALSE FULLSCREEN` とします。
  - 中央の計算は縮めた大きさで行うので、`left` は作業領域の左端になります。
  - WMは元の 2400×1300 を復元するので、窓は右の画面へ約480px、下へも作業領域からはみ出します。
  - これは仕様文書の「入らなければ作業領域の大きさにする」（`GRAPHICS_AND_SOUND.ja.md` の WINDOW-ON の行）と合いません。
- **連続 WINDOW-ON への影響**：全画面のまま続けて WINDOW-ON すると、1255行は縮めた後の `normal_rect.w/h` を「通常サイズ」として使います。そのため、実際に復元される大きさとの差の半分だけ中央からずれます。
- **修正案**：
  - `normal_rect` に「縮めた」印を持たせ、印があるときだけ大きさを後から送ります。
  - 検証記録の24行によると、通知の直後に大きさを送ると高さが3に縮んだとのことです。そこで、送るのは全画面解除後に最初に来た「全画面でない大きさの ConfigureNotify」を受けてからにします。
  - 少なくとも文書には「全画面からの移動では縮めない」と書いておくべきです。本体側で予定している「大きい通常ウィンドウ」の検証は、ちょうどこの点を確かめるものになります。

### 3. 【中】窓を全画面で開いてから WINDOW-ON すると、左上に寄る不具合が残る
- **場所**：`create` の736行（`fullscreen_on = true` を先に立て、`normal_rect` は null）、728行（`place_dirty`）、1255〜1258行。
- **起こし方**：`1 WINDOW-ON TRUE FULLSCREEN SHOW` のように、全画面を指定したまま開くか、開いたあとで WINDOW-ON します。
  - ソースから確実：`normal == null` なので、`self.width/height` と、今の `_NET_FRAME_EXTENTS` をそのまま使います。
  - 推測：MapNotify を待つ間（757行）に全画面の ConfigureNotify がもう来ていれば、幅は画面の大きさです。すると作業領域いっぱいに縮められ、`left/top` は作業領域の左上になります。そのあと `FALSE FULLSCREEN` すると、窓は左上へ寄ります。来る順番によって結果が変わります。
- **修正案**：
  - `normal_rect` がないときは `desired(frame, room())` の大きさを使い、枠は0のままにする。
  - または、新しい窓は CreateWindow の x,y を移動先の画面に置き、WMに位置の指定（USPosition）を伝える。こうすれば、いったん全画面を解いて入り直す手順そのものを省けます。

### 4. 【中・時間しだい】入り直しや解除が終わっていないうちの WINDOW-ON
- **場所**：1242〜1280行は `state_asked` を見ていません。また、1611〜1612行は同じ回で applyModes → applyPlace の順に動きます。
- **起こし方**：
  - (a) 全画面中に `1 WINDOW-ON 30 MS 0 WINDOW-ON` とします。2回目は、解除の通知と入り直しの通知のあいだに入ります。
    - ソースから確実：`fullscreen_on=false` かつ `state_asked=true` なので通常表示用の分岐に入り、`normal_rect` は1回目の移動先のまま更新されません。そのため、あとで全画面を解除すると画面1へ戻ります。
    - 推測：全画面への要求のあとに MOVERESIZE が届くので、WMが無視すれば2回目の移動は消えます。
  - (b) `TRUE FULLSCREEN 1 WINDOW-ON` を同じ回で処理すると、全画面への要求の直後に通常表示として移動を送ります。推測ですが、元の画面で全画面になり、移動先には行かない可能性があります（これは差分より前からある問題です）。
  - (c) `FALSE FULLSCREEN` の通知が来たあと、ConfigureNotify が来る前に WINDOW-ON すると、全画面の大きさで計算してしまいます。1068〜1069行のコメントにある競合と同じものが、通常表示用の分岐でも起きます。
- **修正案**：`state_asked != null` の間は `place_dirty` を落とさずに return し、WMの状態が落ち着いてから配置します。(c) は所見2で提案した「最初の通常サイズの ConfigureNotify」を待つ仕組みとまとめて扱えます。

### 5. 【問題なし】閉じて開き直す間の状態は良くなった
- 710行で `refullscreen = false` を足したので、開き直したときに前の窓の入り直しが残らなくなりました。`normal_rect` と `normal_extents` も708〜709行でリセットしています。
- 通常の FULLSCREEN の入りと解除（1084〜1095行で取り、1070行で null にする）は、`refullscreen` が偽なら差分前と同じです。回帰が起きるのは所見1の、`refullscreen` が真のまま残った場合だけです。
