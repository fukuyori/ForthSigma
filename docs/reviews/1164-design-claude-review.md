## High

**H1. 60Hz 境界で timer を二重に減らすおそれ**（15 行目）
- 問題：文書の順序は「timer を減らす → 予定 event → 即時 write → 標本」です。ところが、`C8-TO b` で境界 b に止まった後に b 時刻の event を足して `RUN0` すると、b での減算がもう一度起きる実装になりえます。
- 決定案：減らす回数は `floor(new/800000) - floor(old/800000)` で決めます（上限は現在の timer 値）。RESET 時の tick 0 は処理済みの境界とみなします。こうすると `RUN0` は減算を起こさず、event だけを適用します。
- 決定案：tick b で値1を即時 write した場合は、b+800000 で 0 になります。境界の1 tick 前に値1を書いた場合は 1 tick だけ鳴ります。どちらも宣言どおりの挙動としてテストに入れます。

**H2. RENDER が途中で失敗すると原子的でない**（21 行目）
- 問題：「既に生成した部分を巻き戻さない」としているため、時刻 overflow の -24 で buffer と状態が途中まで進んだままになります。他の語は「失敗したら何も変えない」ので、それと揃っていません。
- 決定案：書き込む前に、`frames` が負でないこと、および `frames <= (MAX - cycle) / 1000` であることを調べます（`frames*1000` 自体の overflow も防げます）。満たさなければ何も変えずに -24 を返します。
- 出力 buffer が不正なときの -9：Forth 側で事前に全域を検査するのは難しいです。そこで「出力先 buffer が -9 になった場合だけは途中まで進む」と明記するか、先頭と末尾の byte を事前に試し読みするかを決めます。試し読みで足りるのは、VM のメモリ検査が連続領域を単位にしている場合だけです（※推測です。VM の実装を確認する必要があります）。

**H3. -9 の出どころが決まっていない**
- 問題：examples の中に `-9 THROW` はありません。そのため、-9 は VM が不正アドレスの `C@` を検出したときに出るものと推測されます（※推測です）。
- 決定案：pattern は 16 byte を**まず作業用 buffer に読み込み**、その後で queue の回収（compact）と書き込みを確定させます。tick 検査 → 値検査 → 16 byte の読み込み → 満杯検査 → compact → 確定、の順です。即時の `C8-PATTERN!` も同じで、読み込みを `C8-TO` より前に行います。-9 が本当に VM から返ることは、独立検証の項目に加えます。

## Medium

**M1. Q32 位相の overflow 対策が書かれていない**
- 問題：step の上限は pitch 255 のとき約 2^22.4 です。step と経過 tick の総数をそのまま掛けると、長い TO で 64bit を超えます。
- 決定案：位相を進めるのは timer>0 の区間だけにします。区間は timer が 0 になる境界で必ず区切り、1 区間は最大でも 255×800000 tick（約 2^27.6）です。積は約 2^50 に収まります。
- 決定案：XO の位相は `mod 2^39`（128 bit × Q32）、classic の位相は `mod 2^32` と明記します。

**M2. 標本の値の定義が足りない**
- classic：位相 < 2^31 なら +4096、それ以外は -4096。timer=0 なら 0。
- XO：`idx = phase >> 32`、`byte = idx >> 3`、`bit = 7 - (idx & 7)` とし、bit が 1 なら 4096、0 なら 0。
- 位相 0 の最初の標本がどちらの値になるかを固定してテストします。classic は ±で、XO は 0/4096 なので DC の扱いが違います。この差もはっきり宣言に入れます。

**M3. 同じ値の MODE を書いたときの扱い**
- 問題：17 行目の「MODE変更だけ」が、値が変わったときだけを指すのか、書き込みのたびを指すのかが曖昧です。
- 決定案：「MODE の write は値が同じでも毎回位相を 0 に戻す」を勧めます。ホストの設定操作として単純で、検証も楽です。どちらにするかはレモンが決めてください。

**M4. queue のレコード（1024 件 × 40 byte）の中身**
- 構成：tick / kind / value の 3 cell（24 byte）に pattern 16 byte で計 40 byte。kind は 0=TIMER、1=PITCH、2=MODE、3=PATTERN と固定します。PATTERN の value は 0 にします。
- 受付の条件は `ym2149.fs:84-90` と同じにします。未消化が 1024 件以上なら -528。tick が現在時刻より前、または最後に入れた予定より前なら -24。全体が 1024 件以上なら compact。
- 同じ tick の予定は追加した順に適用します。`C8-TO t` は tick ≤ t の予定をすべて適用します。

**M5. `C8-TIMER@` は読み取りなのに時刻を進める**
- `YM-READ` と同じ流儀ですが、名前の `@` から「状態を変えない」と誤解されやすいです。公開語の表に「時刻を tick まで進める」と書き足します。

## Low

**L1. Q32 丸め誤差の記録**
- classic の 440Hz は step = floor(39370.5…) = 39370 で、相対誤差は約 1.3e-5 です。XO の全 256 pitch の floor 誤差と合わせ、検証結果に数値で残します。

**L2. 宣言範囲と主張の整理**（7–11 行目）
- 宣言している範囲は、レモンの承認（原型/SUPER-CHIP のブザーと XO の pattern/pitch）と一致しています。
- 次の 2 点は資料から引いた主張ですが、原文と照合していないので**未確認**です。照合した日付を文書に残すことを勧めます。

**L3. pitch / pattern の範囲**
- pitch と pattern は classic mode でも保持します。`C8-RESET` で pattern は 16 byte すべて 0 にします。このとき XO mode で timer>0 なら無音（0）が出ます。この挙動もテストに入れます。

**L4. 受け入れの区別**
- 42 行目の「1165/1166/1167 を代用しない」は、方針（CPU と OS ごとの受け入れは別）と一致しています。CPU adapter 側の時刻変換をこの作業で検証しないことも、38 行目に書かれていて十分です。
