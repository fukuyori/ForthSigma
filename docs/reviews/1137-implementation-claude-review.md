## 確認した内容

**fast と reference の境界**
- `PA-STEP-LIMIT`（`paula.fs:87`）は、動いている声のうち一番短い残り時間で区切ります。動いている声の残り時間は、次の理由で必ず1以上です。
  - 開始時は1にする。
  - それ以外は PER の実効値（123 以上か 65536）を入れる。
- 期限が来たかどうかは、先に4声分まとめて決めてから voice0→3 の順に処理します（`:80-86`）。1tick 版も同じ処理を通ります。
- attach が変えるのは次の声の PER（field 7）だけで、残り時間には触れません。そのため、まとめて進めても期限の判定は変わりません。
- 時刻 t の書込みと読出しは、t までに期限が来た処理と予定表の分を先に済ませてから行います（`:150-157`）。Python の `tick`/`to`（`verify-paula.py:56-87`）も同じ順序です。

**同じ tick の attach**
- 4声とも tick 1 に初回の fetch が重なります。全256通りの mask テスト（`verify-paula.py:139-143`）では、voice0 の attach と voice1 の再設定が必ず同じ tick に起きます。
- このとき voice1 は新しい PER で再設定されます（文書 `:47` と一致）。

**DMA の LC/LEN 再読込・IRQ・無効化**
- `PA-START` と `PA-RELOAD` は、DMAEN と AUDxEN の AND が立ち上がった時に動きます（`:126-133`）。
- IRQ の動きはコード上、文書の規則どおりです。
  - IRQ を立てるのは、有効化後の最初の fetch と、ブロック最後の word を fetch した時です。
  - LEN1 では、最初と最後が同じ fetch になります。その場合も同じ bit が立つだけです。
- LEN1 の場合は手計算テスト（`verify-paula.py:129`）にあります。
- 無効化すると、その場で mode と残り時間を 0 にし、DAC の値と IRQ の pending は残します（`:132`）。
- ブロック最後の word を fetch した時に、次ブロックの LC/LEN を写します。attach の交互の位置もこの時に volume 側へ戻ります（`:35`、`:60`）。

**手動 DAT の1word latch**
- 書込みは `:118-122`、状態の進め方は `:62-79` です。
- IRQ を立てるのは word を出し終えた時です（これはモデル上の近似で、実機の pipeline ではありません）。同じ tick に latch の上位バイトを出します。
- latch が空なら idle に戻り、DAC の値を保持します。
- `verify-paula.py:130` の手計算と一致しています。

**mask・アドレス・エラーと状態の原子性**
- `PA-CHECK`（`:96-106`）は、時刻や状態を変える前に検査します。対象は次のとおりです。
  - 値、アドレス、mask、PER 1〜122、過去の時刻
- `PA-EVENT!` は、容量と時刻順も変更前に確かめます。予定表の詰め直しは、検査をすべて通った後だけです。
- `PA-MEM!`、`PA-READ`、`PA-RUN` も、状態を変える前に検査します。
- テストは、エラーの前後で全状態を比べています（`verify-paula.py:153-161`）。

**ステレオの部分書込みと後始末**
- 1 frame = 4 byte の扱いは次のとおりです。
  - 書込み位置は `PS-SENT @ 4 *`（`paula-play.fs:8`）。
  - `PCM-OPEN` は2ch（`:18`）。
  - ゼロで埋める範囲は 2048 byte（`:20`）。
- `PCM-WRITE` は frame 数で数えます（`GRAPHICS_AND_SOUND.md:554` で確認）。
- エラー時の後始末（`CATCH`、`PS-SAFE-CLEANUP`、本体のエラーを優先）は、`PS-STREAM` と同じ形です。

**PCM 全体と各負荷の検証**
- 各負荷は、計時しない別のプロセスで、32768 frame の全 PCM と IRQ・丸め回数・fetch 数を Python と比べています（`:208-209`）。
- 計時する側（`:210-213`）の warm-up 後の `PA-RESET` は、状態を残さず初期化します。
- 8kHz の書込み予定について、Python と Forth は境界の式が違います。Python は `i ≤ end*8000//CLOCK`、Forth は `floor(i*C/8000) ≤ end` です。8192 frame と 32768 frame の場合は、手計算で同じ件数になることを確かめました。件数そのものも `:177` で assert しています。
