## 結論

マイルストーンの大枠は、10節の決定（本体に置かずForthで合成してPCMで流す）と8節（「999はForthで音源を合成してPCMへ流す例を先に作る」）に合っており、進めてよいと判断します。ただし、このまま実装すると次の9点で検証が成り立たないか、結果を誤って読むおそれがあります。それぞれの決め方を下に示します。

## 案の欠陥と足りない検証

1. **単調時計を読む語がありません。**
   - `UTIME` と `NTIME` は実時計で、システム時刻が変わると飛びます。`NS` は待つだけで、時刻は読めません。
   - **決定**：経過時間は `NTIME` の差で測り、同時に `CPUTIME` の差も記録します。差が0以下になった回は無効として、捨てたことも記録します。
   - `CPUTIME` は全スレッド分を合計します。このため、合成だけを測る実行では AUDIO の語を一切使わず（`REQUIRE-AUDIO` も使わない）、音のスレッドを起動しません。※`REQUIRE-AUDIO` だけで音のスレッドが起動するかは確かめていません。安全側として使わない方針にします。

2. **「エンジンの消費に合わせた計測」で合成した波形を流すと、音が出ます。**
   - **決定**：合成した結果はバッファAに置いてハッシュの照合だけに使い、`PCM-WRITE` には同じフレーム数の無音バッファBを渡します。`PCM-WRITE` は中身によらず同じだけコピーするので（`sound_stream.zig:46-58`）、書込みの費用は同じになります。
   - 合成した音そのものをPCMへ流す経路は、聞こえる形のデモ（後で、明示的に有効にしたときだけ）まで確かめないことになります。このことを記録に書きます。

3. **消費の速さが、音を出すバックエンドで変わります。そしてどのバックエンドかは、Forthから分かりません。**
   - Windowsは waveOut の480フレーム×8個のバッファで消費します。装置がないときは、5 msごとに休んで時刻に追い付く無音の消費になります（`host_audio.zig:283-297`）。WSLでは、どちらになるか分かりません（未確認）。
   - **決定**：各回で `AUDIO?` の値を記録し、実行環境（WSL、WSLgの有無）はハーネスの外側で記録します。消費に合わせた計測の結果は「その環境のバックエンドに合わせた値」とだけ書き、装置の遅れや聞こえ方には触れません。

4. **待つフレーム数が容量を超えると、`PCM-WAIT` が -24 で THROW します**（`words_pcm.zig:91`）。
   - 「残りの全部が空くまで待つ」と書くと、容量を超える部分書込みのときに -24 で失敗します。
   - さらに `free()` は、エンジンが出力中のフレーム（held frame）を除いた数です（`sound_stream.zig:38-43`）。再生が続いている間は、空きが容量いっぱいにはまず届きません。
   - **決定**：待つ数は `min(残り, 512)` とします。消費に合わせた計測では容量を4096フレーム（約85 ms）にして、512フレームより十分大きくします。

5. **部分書込みが起きるかどうかが、偶然に任されています。**
   - **決定**：PCM-OPENを `48000 1 2048` で開いた直後に、2560フレームを書きます。リングは空で、容量は2048なので、戻り値は必ず `2048 0` になります。これを固定の検査にします。
   - 続けて、`addr + written*2` から残りを書き直します。受け付けたフレーム数の合計が、渡したフレーム数の合計と一致することを確かめます。`frames=0` の書込みが `0 0` を返すことも確かめます。
   - 消費に合わせた計測でも、書けたのが0の回数（満杯）、途中までの回数、待った回数、期限切れの回数を数えて記録します。

6. **レジスタを書く時刻が決まっていません。**
   - 512フレームのブロック単位でしか書けないと、分割しても同じになるかの試験が、境界の上でしか効きません。
   - **決定**：書込みの予定は絶対フレーム番号で持ちます。ハーネスは書込みのあるフレームの直前で描画の呼出しを分け、`SYN-REG!` を挟みます。合成する側は時刻を持ちません。

7. **照合するPythonの側が、仕様の曖昧な点まで同じ読み方をしてしまうおそれがあります。**
   - 例は、位相を進めるのが出力の前か後か、マスクの幅、ノイズを何回シフトするかです。
   - **決定**：下の仕様で計算の順序まで決め、周波数から増分への変換（浮動小数点）はなくして整数の増分を直接与えます。
   - さらに、手で計算した値（下のG1〜G3）をPythonにもForthにも持たせます。
   - Pythonの側には、規則を1つわざと変えた版（位相を出力の前に進める）を作り、ハッシュが一致しなくなることを確かめる試験を入れます。

8. **計測した処理と、正しさを確かめた処理が別物になるおそれがあります。**
   - **決定**：計測する実行でも、計測の区間が終わった後でバッファのハッシュ（またはチェックサム）を取って照合します。最後にデータスタックの深さが0であることも確かめます。

9. **後片付けの方針がありません。**
   - **決定**：本体の処理を `CATCH` で囲みます。例外が起きたら、必ず `0 0 P PCM-STOP`（すぐ捨てる）を呼び、続けて `PCM-CLOSE` を呼びます。
   - CLOSEが -528 か -516 を返したら3回まで再試行し、それでも閉じられなければ終了コードを0以外にして、そのiorを出力します。
   - 期限切れ（`false 0`）が3回続いたら、失敗として打ち切ります。

## 試作のレジスタ仕様（決定案）

この仕様は特定のチップのエミュレーションではありません。

- **出力の形式**：48 kHz、モノラル、s16LE、`W!` で書きます。値は0..28800の範囲に収まり、飽和はしません（Pythonの側で値の範囲を確かめます）。
- **語の案**：
  - `SYN-RESET ( -- )`
  - `SYN-REG! ( value reg -- )`：値かレジスタ番号が範囲外なら、何も変えずに -24 で THROW します。
  - `SYN-RENDER ( addr frames -- )`：`frames=0` ならメモリを参照しません。
- **SYN-RESET 後の状態**：全レジスタは0、矩形波の位相とノイズの積算値は0、三角波の位相は 0x800000、LFSRは1です。

| reg | 名前 | 範囲 |
|---|---|---|
| 0/4 | P0/P1-EN | 0..1 |
| 1/5 | P0/P1-INC | 0..2^24-1 |
| 2/6 | P0/P1-DUTY | 0..3（しきい値は 2^21, 2^22, 2^23, 3·2^22） |
| 3/7 | P0/P1-VOL | 0..15 |
| 8 | T-EN | 0..1 |
| 9 | T-INC | 0..2^24-1 |
| 10 | N-EN | 0..1 |
| 11 | N-INC | 0..2^27（1標本で最大8回シフト） |
| 12 | N-MODE | 0..1（帰還をビット1から取るか、ビット6から取るか） |
| 13 | N-VOL | 0..15 |

標本ごとの計算は、どの声部も「今の状態から出力を作り、その後で状態を進める」の順です。

- **矩形波**：EN=1 なら、出力は `PHASE < しきい値` のとき VOL、そうでなければ0です。その後 `PHASE = (PHASE+INC) AND $FFFFFF` とします。EN=0 なら出力は0で、位相は止まります。
- **三角波**：`step = PHASE >> 19`、出力は `step<16 ? 15-step : step-16` です。EN=1 のときだけ位相を進めます。EN=0 のときは今の段の値を保ちます。
- **ノイズ**：出力は EN=1 かつ `LFSR AND 1 = 0` のとき VOL、そうでなければ0です。その後 EN=1 なら `ACC += INC` とし、`ACC ≥ 2^24` の間は次を繰り返します。
  - `ACC -= 2^24`
  - `fb = (LFSR XOR (LFSR >> (MODE ? 6 : 1))) AND 1`
  - `LFSR = (LFSR >> 1) OR (fb << 14)`
- **混合**：`s = (P0+P1)*512 + TRI*512 + N*384`
- **セルの幅**：セルは64ビットです（`memory_map.zig:6`）。マスクは必ず明示します。LFSRの周期は、本からの値を断定して書かず、Pythonで実測した値を両方の実装で照合します。

**手で計算した値**：

- G1：P0 を EN=1、INC=2^22、DUTY=2、VOL=15 にし、他は SYN-RESET のままにします。出力は `7680 7680 0 0` の繰り返しです。
- G2：G1 の DUTY を 0 にすると、`7680 0 0 0` の繰り返しです。
- G3：T を EN=1、INC=2^19 にすると、TRI の出力は SYN-RESET 直後の0から1ずつ増えます。s は `0 512 1024 …` と続きます。

## 予定表と分割の試験

- **S1**：手で書く短い予定表です。INC は0と最大値、DUTY は4種類すべて、VOL は0と15、ノイズは両方のモードとINC=2^27を含めます。ENの切替えは、フレーム 0、1、511、512、513 に置きます。
- **S2**：Pythonが固定のシードで作る1000ブロック分の予定表です。ブロックの中の任意の位置で、ブロックあたり約4回書き込みます。ファイルとして固定し、そのハッシュを記録します。
- **S3**：最初に設定した後は書き込まない予定表で、合成だけの費用を見るためのものです。
- **分割の試験**：S1とS2を次の4通りで描画し、全部の出力が同じバイト列になることを確かめます。一致しないときは、最初に違うバイトの位置を出力します。
  - 512フレームずつ
  - 1フレームずつ（S1）
  - `1, 7, 256, 511, 512, 1023` の繰返し
  - 1回で全部
- 予定表はPythonでForthのデータ表に変換します。合成の処理そのものは、ForthとPythonでそれぞれ仕様から別々に書きます。

## 計測の条件

- 対象は Windows GNU と Linux musl（WSL）です。ビルドは ReleaseFast、cpu=baseline です。
- 1回の計測ごとに新しいプロセスを起動し、7回繰り返します。各プロセスでは、100ブロック分を1回空回ししてから計測します。
- 本計測は1000ブロック（512000フレーム、約10.667秒分の音）です。中央値、最小、最大と、7回分の生データを記録します。
- **合成だけの計測**：S2とS3の両方で、1フレームあたりのns、実時間に対する倍率（音の秒数÷実際にかかった秒数）、余裕（1−かかった時間÷音の時間）を出します。
- **消費に合わせた計測**：S2を使います。全体にかかった時間、そのうち合成に使った時間、待った回数、期限切れの回数、部分書込みの回数、`PCM-UNDERRUNS`、`AUDIO?` を記録します。最後に `1 2000 P PCM-STOP` でエンジンが取り込み終えるまで待ってからCLOSEします。アンダーランが0でなくても隠さずにそのまま記録し、装置で音が切れたとは解釈しません。
- **時間の測定はレモンの確認を得てから行います**（保存してある記憶の方針どおりで、他のアプリを止めてから測ります）。実装と、正しさ・部分書込みの試験は、確認を待たずに進められます。
- **結論として書かないこと**：どの機種を本体（ネイティブコード）へ移すか、移さないかは、この結果からは決めません。NES、SID、Paulaの実機の負荷を表す値とも扱いません。装置で音が聞こえることや、ハードウェアで確かめたことも主張しません。
