# S-DSP ネイティブ実装レビュー(読み取りのみ)

ご指定のファイルを読み、Python の検証スクリプト `tests/scripts/verify-snes-dsp-audio.py` と、Zig のテスト `src/tests/snes_dsp_test.zig` も参照しました。ビルド・テスト・計測・git コマンドは実行していません。ファイルの変更もしていません。

結論として、High の不具合は見つかりませんでした。Medium は、テストの網羅不足が1件です。

## 結論

- **High: なし。** Zig の算術と演算順序は、Forth 版および Python 版と一致しています。
- **Medium: 1件。** ネイティブ版のテスト網羅が、設計書で要求されている範囲に届いていません(M1)。
- **Low: 5件。** 性能、レジストリ通知の意味、記録、文書に関するものです。

- Zig の演算子優先順位(`*` は `>>` より強く結合する)、符号付きの右シフト、`@divTrunc` を使う箇所(引数がすべて非負)を確認しました。Forth と食い違う箇所はありません。
- FIR の計算と ARAM への書き込みは、ループの位置が Forth と異なります。ただし、FIR は履歴だけを読み、履歴は先にまとめて読み込まれているので、結果は変わりません。
- `snes_gauss.zig` と `snes-gauss.fs` の 512 個の値は、目視で一致を確認しました。Zig 側にはハッシュのテストもあります(`snes_dsp_test.zig:138-147`)。
- 検証範囲と、Forth の正しい操作で到達できる状態を突き合わせました。Forth で到達できる状態を、ネイティブ側が誤って拒否するケースは見つかりませんでした。

## Medium

**M1: ネイティブ版のテスト網羅が不足している**

- `verify-snes-dsp-audio.py --native` の個別テストは、次の Forth の語を直接呼んでいます(`:172-232`)。
  - `SD-BRR`、`SD-GAUSS-SAMPLE`、`SD-ENV-STEP`、`SD-RATE?`、`SD-ECHO`
- そのため、ネイティブモードで実行しても、これらのテストは Forth 実装を検査しています。Zig の `brr`、`gaussian`、`envelope`、`fir`、`echo` を確かめているのは、2048 フレームの9シナリオだけです。
- その結果、ネイティブ版では次のケースが Python や Forth と比較されていません。
  - BRR: ヘッダ全256種 × ニブル16種、極端な履歴値
  - エンベロープ: 全32レート、GAIN 4モード、直接指定の128通り
  - FIR: 8タップそれぞれのインパルス応答
  - エコー: 帰還の飽和、ミュート
- Zig 側のテストも、Gauss は1点の確認だけです。`envelope` は `pub` で公開されていますが、テストがありません。
- 設計書(`SNES_DSP_NATIVE_DESIGN.md:27`)は「native coverage for BRR/Gaussian/envelope branches」を要求しており、これを満たしていません。
- `error_cases` もすべて Forth 側の事前チェックで例外になるため、ネイティブの -24 の経路を Forth から通すテストはありません(Zig のテストだけが通しています)。
- 対応案: `brr`、`gaussian`、`envelope` などを Zig のテストから直接呼び、Python の期待値と比較します。あるいは、`SD-STEP` だけを1フレーム実行して比較する仕組みを作ります。

## Low

- **L1(性能): 毎フレーム全セルを書き戻している。**
  - `commit` は毎フレーム、138 セルを `writeCell` で書き戻しています(`words_snes_dsp.zig:63-68`)。
  - 検証が済んだ後は、`commit` は失敗しません。例外が起きうるのは `checkWorkBlock` だけです。
  - したがって、書き戻しを「終了時」と「`checkWorkBlock` の失敗時」に限っても、外から見える状態は同じになります。
  - また、予算を指定した RUN の中では、`.native` 単位の charge が毎フレーム `ops.poll` を呼びます(`execution_control.zig:49`)。
  - どちらも、次の計測結果に影響する要素です。
- **L2(レジストリ): 全セルを毎回、完全な書き込みとして通知している。**
  - Forth では書かれないセルも、ネイティブでは毎回書き込みとして通知されます。そのため、damaged の記録が修復されたり、分類し直されたりします。
  - 設計書(`:33`)で決めたとおりの動作ですが、Forth とは意味が異なります。この点を設計書の注記として明記しておくことを推奨します。
- **L3(記録): ハッシュ記録の対象からネイティブ関連のファイルが漏れている。**
  - 検証スクリプトの `files`(`verify:288`)に、次のファイルが含まれていません。
    - `sound_snes_dsp.zig`、`words_snes_dsp.zig`、`snes_gauss.zig`
    - `snes-dsp-native-backend.fs`、`snes-dsp-audio-native*.fs`
  - バイナリのハッシュは記録されていますが、ソースとの対応は記録に残りません。
- **L4(文書): 数字と単語の間の空白が抜けている。**
  - 例: 「at most256」「then by32」「all65536」「32ticks」(設計書)、「Layout1 … :128bytes registers,65536bytes」(`help_text.zig:1660`)。
- **L5(ABI): 一部を未確認として残しています。**
  - `snd_snes_frames` は enum の末尾に追加されており(`defs.zig:1171`)、AUDIO の登録順でも末尾です(`words_audio.zig:44`)。既存の ID は動きません。
  - イメージのシグネチャが実際に変わるかどうかは、読んで確認していないため未確認です。
  - `snes_dsp_test.zig` は `forth_test.zig:98` に登録されています。git に追跡されているかどうかは、git を実行していないため未確認です。

## 以前の B1〜B3 の解決状況

- **B1: 解決済み。** 両方のバックエンドで、1フレームごとに `32-div` を加え `div=0` にしています(`snes-dsp-audio.fs:188`、`sound_snes_dsp.zig:232-233`)。トークンのスタックは `( frames -- )` で、0 フレームでも呼ばれます(`:187`)。端数の tick は、ディスパッチが成功した後で反映されます(`:194`)。
- **B2: 解決済み。** ネイティブでは `checkWorkBlock` をフレームの間でだけ呼んでいます。検証後は `commit` が失敗しないため、途中までのフレームが外に見えることはありません。Forth 側では途中の状態が見えることがありますが、これは設計書に明記されています。
- **B3: 解決済み。** 状態の検証は、0 フレームの場合でもループの前に実行されます(`words_snes_dsp.zig:60`)。検証が失敗したときは、スタックとメモリを変更せずに -24 を返します。

M1 は、tque に登録すべき後続作業です。ただし、今回のご依頼は読み取りのみだったため、tque への登録はしていません。
