**結論:** High に当たる誤りは見つかりませんでした。Medium は9件で、どれも仕様の書き方が曖昧なため、Forth と独立 Python の実装が別々の解釈をする恐れがあるものです。演算の結果に影響します。

## 資料と一致していることを確認した項目
- **BRR**（`:34`）
  - shift 0..12 の floor 式と、13..15 で負なら -2048 / それ以外は 0 になる扱いは、fullsnes の「shift=12・nibble SAR 3」と同じ結果です。
  - filter1〜3 の floor 式は、fullsnes の SAR 式と一致します。
- **ENV**（`:37-38`）
  - attack 2A+1 / +32 / A15 は +1024、2016 で decay へ移る点、decay 16+2D、`ceil(ENV/256)` は、`-(((L-1) SAR 8)+1)` と L=0 を含めて同じ値です。
  - SL 境界 (N+1)*256、bent の 1536 も一致します。
  - 32 個の rate 周期は、fullsnes の表とすべて一致しました。
- **出力と mixer**（`:39`）
  - `floor(s15*ENV/2048)`、ENVX=ENV>>4、OUTX=>>7、voice 音量 /64 を加算のたびに s16 飽和させる扱いは、fullsnes の Output Mixer と一致します。
- **FIR**（`:40`）
  - LE16 で読んで /2、FIR0 が最古、先頭7項を wrap して最終項で飽和、`AND FFFEh`、EDL の `max(4, low4*2048)` を offset 0 で latch する扱いは、fullsnes の FIR 式と EDL 注記に一致します。
- **KON/KOFF/FLG.7 の順序**（`:33`）
  - fullsnes の手順 1〜3 と同じです。KOFF 中に KON すると、2 frame 後に release されて無音になるという帰結も、この設計から再現します。
- **Gauss の加算規則**（`:36`）
  - 「最初の3項を wrap、最終項で飽和、/2」は fullsnes の記述と同じです。1回目の加算は overflow しないので、3項をまとめて wrap しても1項ずつ wrap しても結果は同じです。

## Medium（仕様を確定すべき点と推奨値）

1. **Gauss の係数と履歴の対応が書かれていない**（`:36`）
   - 推奨: 文書に次を明記します。`oldest×g[255-i]`、`older×g[511-i]`、`old×g[256+i]`、`new×g[i]`。加算順はこの順、i=(phase>>4)&255。
   - この対応では、phase=0 のとき主に older の値が出ます。KON 後の最初の BRR 値が聞こえるのは delay が終わってから約2 frame 後です。宣言にこの遅れを書き添えるとよいです。

2. **BRR の END をいつ処理するかが曖昧**（`:35`）
   - 「16値の消費後」が、16個目を履歴に入れた直後なのか、17個目が必要になった時点なのかが決まっていません。pitch=0 で止まっているときに ENDX が立つかどうかが、この解釈で変わります。
   - 推奨: 16個目を履歴へ入れた同じ消費ステップの中で、次の順に処理します。
     1. ENDX を set する
     2. その時点の DIR/SRCN から loop addr を読む
     3. END=1/LOOP=0 なら release にして ENV=0 にする
   - 次の block の header は、その block の最初の nibble が必要になったときに1回だけ読み、block の終わりまで latch します。header が途中で書き換わった場合も、この規則で結果が決まります。

3. **KON delay の数え方が不足している**（`:33`）
   - 推奨値:
     - KON を poll した frame f を delay の1つ目に数え、f..f+4 を無音にします。
     - start addr は f で読みます。
     - delay 中は pitch counter を 0 のまま止め、PMON も加算しません。
     - f+4 の最後に s0 を取り込み、f+5 から ENV と pitch を進めます。

4. **ENV 更新と出力の前後関係がない**（`:37`, `:39`）
   - 推奨: その frame の出力と ENVX には、更新前の ENV を使います。ENV の更新は出力の後に行います。
   - 状態遷移（2016 以上で decay、SL 以下で sustain）は、rate 更新が起きた frame だけでなく毎 frame 判定します。こう決めておくと、Direct GAIN から ADSR へ切り替えた直後の挙動が一つに決まります。

5. **noise の式「bit0 xor1」が二通りに読める**（`:38`）
   - 「xor 1」とも読めてしまいます。正しくは `bit0 XOR bit1` を bit14 に入れる式です（fullsnes 3109行）。
   - 推奨: noise の更新は、voice 処理の前に1回だけ行うと明記します。

6. **volume の乗算 overflow の扱いがそろっていない**（`:39-40`）
   - MVOL/EVOL の積は s16 で wrap しますが、`FIR×EFB/128` は wrap せずに飽和加算しています。どちらも -32768×-128/128 = 32768 になり得るので、扱いを分ける根拠がありません。
   - fullsnes には MVOL=-128 で overflow するという記述しかなく、EVOL と EFB については実機の挙動が未確認です。
   - 推奨: 3つの積をすべて s16 で wrap してから加算する規則に統一し、未確認の事実として宣言します。

7. **即時操作の検査をいつ行うかが曖昧**（`:29`）
   - 「全検査してから変更」と書いているのは予定（`-EVENT!`）についてだけです。`SD-REG!`、`SD-REG@`、`SD-RAM@`、`SD-TO` で reg/addr/value/tick を、時刻を進める前に検査するのかが読み取れません。
   - 推奨: すべての語について「全引数を検査してから時刻を進める」と明記します。

8. **エラーの検査範囲と優先順位**（`:22`, `:29`）
   - `SD-RUN` での `now+ticks` の 64bit overflow と、`SD-TO` で tick < now の場合を -24 にすることを明記します。NES 設計（`NES_APU_FORTH.md:47`）はこれを書いています。
   - -24 と -528 が同時に当てはまるときの優先順位も必要です。推奨: 値・対象・時刻の -24 を先に判定し、容量の -528 を後にします。
   - 満杯の判定は、物理的な末尾位置ではなく、未処理の件数が1024件かどうかで行うと明記します。

9. **即時操作の後に追加した同じ tick の予定を、いつ flush するか**（`:29`）
   - 推奨: その tick 以降の read/write/TO/RUN/RENDER の冒頭で flush し、次の frame より前に必ず適用します。

## 推奨する細部（Low）
- **frame 番号の扱い**
  - rate 位相は frame 番号の mod 30720 で持ちます。30720 は全周期の最小公倍数（2^11×15）なので結果は変わらず、cell の overflow を避けられます。
  - `:13` の「frame32」は「tick32 の frame（frame 1）」と書き換えると、`:33` の frame 番号と食い違いません。
- **SD-SAMPLE の初期値**
  - 最初の frame より前に呼んだときは 0 0 を返すと明記します。
- **独立検証での Gauss 表の扱い**
  - Python は Forth の表を使わず、fullsnes の本文から別に表を抽出してください。
  - 照合する項目は次のとおりです。
    - 512個そろっていること
    - 0..1FFh で値が減少しないこと
    - すべての i で4係数の和が 7FFh〜801h に収まること
    - hash が一致すること
  - 追加する試験ベクトル: filter0 で `-8<<12` を3つ以上並べたときに +3FF8h が出ること（fullsnes 2854行）。
