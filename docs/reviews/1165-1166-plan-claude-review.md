# 1165/1166 測定・試聴計画のレビュー（読み取りのみ）

読んだファイルは `.work/1165-1166/plan.md`、`examples/chip8-audio.fs`、`tests/scripts/verify-chip8-audio.py` の3つです。編集・実行・ネットワークアクセスはしていません。native 側の `NTIME`/`CPUTIME` の実装は読んでいないため「未確認」です。

## High

**H1. 古い出力バッファの残りで PCM 検査が通ってしまう**
- 計画では、計時する各プロセスで warmup をしてから reset し、同じ 64KiB の OUT に計時中の描画をします。
- warmup で同じワークロードを描画すると、OUT には期待値と同じ PCM が残ります。このため、計時中の描画が一部抜けても、全バイト比較が通る可能性があります。
- 改善案:
  - reset の後、計時の前（計時の外）に、OUT を期待 PCM に現れない値で埋めます（例: `0xA5` で FILL）。0 は無音と区別できないので使いません。
  - 埋めた後、計時の前に、埋めた値が入っていることを1バイト以上読んで確かめます。
  - 計時後の状態についても、warmup 後の状態と偶然一致して見過ごすことがないよう、reset 直後の SNAP を計時前に記録します。

**H2. 「queue をすべて消費した」と「22値の状態」が一致していない**
- `Model.state()` が返すのは CYCLE/DIV/TIMER/PITCH/MODE/PHASE とパターン16バイトの22値です。EVENT-COUNT と EVENT-INDEX は含まれません。
- このため、計画にある「queue fully consumed」は Model との比較だけでは確かめられません。
- 改善案:
  - 全ワークロードで `EVENT-COUNT == EVENT-INDEX` を確かめます（既存テストの `state[6] == state[7]` と同じ形）。
  - 実行終了コードが 0、stderr が空、`DEPTH` が 0 であることも条件として明記します。
  - 8kHz ワークロードでは、compaction 後の COUNT の期待値も Python 側で計算して照合します。

**H3. Windows の `CPUTIME` の分解能が測定対象に対して粗い可能性がある**
- Windows のプロセス CPU 時間は、クロック tick 単位（典型的には約 15.6ms）でしか進まないと推測されます。forthz の `CPUTIME` の実装は未確認です。
- 1回の計時が数十 ms 程度に収まる場合、CPU 値は量子化されて比較に使えません。
- 改善案:
  - wall 時間（`NTIME`）を主な指標とし、CPU 値は参考値と明記します。
  - 本測定の前に、同じプロセス内で CPU 値が取りうる最小の差を記録し、分解能を数字で示します。
  - 分解能が不足する場合の扱い（その値を使わない、など）を計画に書いておきます。

## Medium

**M1. 計時する範囲に、ハーネス側の処理が入っている**
- 8kHz ワークロードでは、パターン生成（FILL や `I 37 *`）が計時の中に入ります。そのため、測定値は「model のコスト」ではなく「生成を含むコスト」になります。
- 改善案:
  - 生成だけを行い、enqueue と描画をしない対照ワークロードを1つ追加し、差し引けるようにします。
  - それをしない場合は、記録に「生成込み」と明記します。

**M2. ワークロードの細部が決まっていない**
- 32768フレームを6フレームずつ描画すると 5461回で 32766フレームになり、残りが2フレーム出ます。この残りの描画方法が書かれていません。
- 「XO128 timed changes」が queue 経由（`*-EVENT!`）なのか即時書き込み（`C8-WRITE`）なのかが書かれていません。即時書き込みの経路がどのワークロードにも入っていないなら、それを明記するか、ワークロードを追加します。
- 「classic60Hz timer gates」では、timer が有効なフレームの割合によって速度が大きく変わります（`C8-RAW-RUN` は timer が 0 のとき近道をします）。各ワークロードで有効な割合を記録します。
- compaction は描画と交互に行われるため、1回ごとに移す件数はわずかです。これを「compaction のコストを測った」とは主張しない、と書き添えます。

**M3. warmup の範囲と統計の扱い**
- warmup で全ワークロードを1回通すこと（compaction の経路も含む）を明記します。
- 7回を同じ順に並べると、時間に沿った変動が特定のワークロードに偏ります。ワークロードの順序を回すか、交互に並べます。
- 代表値（中央値など）と外れ値の扱いを、測定前に決めて計画に書いておきます。

**M4. 測定の実施手順がレモンさんの方針と合っていない**
- 計画には「Clock frequency/background apps are not controlled」とあります。
- 記録されている方針では、時間を測る前にレモンさんに確認し、レモンさんが他のアプリを止めてから測ります。この確認の手順を計画に入れる必要があります。
- 電源プランと AC 接続の有無も記録します。
- Linux の測定は「WSL2 上の Linux」と明記し、ネイティブ Linux の性能とは主張しません。

**M5. 出所（provenance）の記録が不足している**
- `examples/chip8-*.fs` と `scripts/chip8-pitches.py` は未追跡です（会話開始時の git status による。現在の状態は未確認）。ソースのハッシュに加えて、次を記録します。
  - git HEAD
  - `git status -sb` の結果
  - 既存のバイナリがどのコミットからビルドされたかの根拠（ビルド時刻、または native ソースの manifest ハッシュとの対応）
  - 実際に計時した Forth ソース全文のハッシュ
  - 計時に使ったバイナリの bytes とハッシュ（size 用の8つとは別に、明示する）

**M6. サイズの内訳が出ない**
- HERE の差分のほとんどは、`C8-EVENTS` の 40960B と pitch 表の 2048B になると見込まれます。
- 改善案:
  - 「コードとヘッダ」「pitch 表」「event queue」「パターンとデモパターン」に分けて報告します。
  - 計測の終点は、ハーネスの `CREATE OUT` より前に取ります。
  - `INCLUDED` によって辞書以外に確保される領域は、この数字に含まれないことを書き添えます。

## Low

**L1. Model の独立性の範囲**
- Python の Model は実装としては独立していますが、仕様と pitch の式は Forth と同じものを使います。
- 主張は「同じ仕様を別に実装したものと一致した」に限ります。実機や ROM の正しさは主張しません。
- pitch 表は `chip8-pitches.py` が生成し、検証も同じ式で行います。このため、この検証は式に対して自明に一致するものだと記録しておきます。

**L2. 計時しない検証プロセスの位置づけ**
- 計時する各プロセスも全 PCM を Python の Model と照合します。
- 照合の基準は Python の Model だけとし、計時しない Forth の出力は基準にしないことを明記します。

**L3. 試聴の細部**
- 「classic 2 seconds」をどう作るか（timer 120 を使うのか、2秒経ったら止めるのか）を書きます。
- pitch 247 では、デモパターン（0 が64ビット、1 が64ビット）の基本周波数が約 439Hz、pitch 199 では約 220Hz になると計算しました。この値を記録に書いておくと、レモンさんが聞いて判断しやすくなります。
- bit レートが 48kHz を超えることによる軽い揺らぎは仕様どおりの挙動だと、あらかじめ書いておきます。

**L4. 採用判断の基準**
- 速度に合格の閾値を設けるのかどうかを明記します（設けず報告だけにすることを推奨します）。
- 採用の条件は「全 PCM と状態が一致すること」と「レモンさん自身の試聴報告」の2つに限ります。
