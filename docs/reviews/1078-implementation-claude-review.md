## 結論: 互換性のブロッカーが1件残っています

**B: 保留バイトがある READ-FILE が、通常ファイルでも短い長さを返す**

- 場所: `src/main.zig:755`。保留バイト(prefix)が1バイト以上あると、`fread` を呼ばずにその分だけ返します。
- Forth 2012 の READ-FILE では、u2 < u1 は「途中でファイル終端に達した」ことを意味します。HEAD の実装は `ungetc` を使った後に `fread` していたので、通常ファイルでは要求どおりの u1 バイトを返していました。今回の変更はその挙動からの後退です。
- 影響する場面:
  - CR だけで終わる行を READ-LINE で読む → 次の1バイトが保留に戻る(`LineSource.unget`) → READ-FILE が1バイトしか返さない
  - KEY?-FILE で先読みした直後の READ-FILE
  - 利用者が `BEGIN buf N fid READ-FILE THROW DUP N < UNTIL` のように「u2 < u1 で終了」と書いていると、ファイルの途中で読取りを打ち切ります。残りのデータを失うのと同じ結果になります。
- 内部の呼び出し側(slurp、blocks、graphics_decode)は 0 が返るまで繰り返すので影響しません。影響を受けるのは利用者のプログラムだけです。
- 設計書 `FILE_INPUT_WAIT_DESIGN.md:42` の「呼出し側は通常どおりshort readを繰り返す」は、通常ファイルについての標準の意味と合いません。ここは考え方が違う点として明示しておきます。
- 修正案: prefix を取り出さずにコピーし、残りを `fread` します。
  - `fread` がエラーなら、prefix を保留に残したまま ior を返す
  - 成功したときだけ prefix を消費する

  こうすれば、prefix を失わないことと、u1 バイトをそろえて返すことが両立します。合わせて、2バイトの短い読取りを期待しているテスト `main.zig:3339-3342` を、3バイト(`E3 81 82`)を返す期待に直す必要があります。

## 確認したこと(`src/main.zig:734-766`)

- **解消の根拠**: 先読み済みの prefix をバッファへコピーした後、残りが `!file_eof` の間は `fread` で残り全体を要求しています。`fread` が要求より短く返るのは、EOF に達したかエラーが起きたときだけです。そのため、短く返ったことを途中のデータ切れと取り違えることはなくなりました。
- **エラー時(757-761)**: `decoder.takeByte()` より前に return するので、prefix はデコーダに残ります。`clearerr` も行っています。
- **成功時・EOF 時(764)**: ここで初めて prefix を消費します。`takeByte` は先頭から取り出すので、バイトの順序も保たれます。
- **境界条件**:
  - `prefix == buffer.len` のとき: `fread` は呼ばず、prefix だけを返して消費します。正しい動作です。
  - prefix があり、`file_eof` が立っているとき: prefix だけを返します。正しい動作です。
  - `buffer.len == 0` のとき: 先に return します。
- **テスト(3340-3349)**: 読み取りエラーを注入した後、prefix の `E3 81` が残っていることを確かめています。その後の再試行で `E3 81 82` の 3 バイトが返ることも確かめています。前回のブロッカーに対する回帰テストとして足りています。

## ブロッカーではない指摘

- `fread` が一部のバイトを読んだ後で `ferror` になった場合、読んだ `count` 分は捨てられ、ストリームの位置だけが進みます。READ-FILE の ior が 0 でないとき、データの中身は保証されないので、規格上は許される動作です。
- 障害注入の仕組み(seam)は `fread` の前で return します。そのため、`ferror` が起きたときの `clearerr` を通る経路は、このテストでは通りません。
