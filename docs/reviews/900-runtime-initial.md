# 900 共通部品レビュー(対象: `.work/900-review/initial/` の固定コピー)

レモン、レビュー結果です。ファイルの編集、Git 操作、テストの実行、外部アクセスはしていません。コードを読んで判断した結果で、OS の挙動のうち確認していないものには「※推測」を付けています。

前提として示された条件(通知側は複数で消費者は1つ、deinit の前に全参加者を停止、台帳は所有スレッドだけが操作、epoch は呼出し側が一意に割り当てる)の範囲では、Wake の lost wakeup は見つかりませんでした。理由は次のとおりです。
- 通知側は世代を acq_rel の cmpxchg で増やしてから OS へ通知し、消費側は acquire の observe で世代を読みます。
- OS の待機は最大 20ms ごとに区切られ、そのたびに世代を確認し直します。

以下は、その前提の境目やホスト統合で問題になりやすい点です。

---

### 1. 【高】別の台帳の Handle が、種類の検査をすり抜けて通る
- **対象**: `runtime_base.zig:56`(Handle の定義)、`:86-91`(`entry`)
- **失敗する条件**: Handle は `{epoch, serial}` だけを持ち、どの種類のものかを含みません。`kind` の検査は「呼出し側が期待する種類」と「台帳の項目の種類」を比べるだけです。設計書 `CORE_EXTENSION_DETAILED_DESIGN.md:48` は「実行時epoch」と書いており、1つの実行時に1つの epoch と読めます。この方針で、例えば process 台帳と task 台帳に同じ epoch を渡すとします。どちらの台帳も serial は 1 から始まるので、process 台帳の `{E,1}` を task 台帳に `kind=.task` で渡すと、task 台帳の `{serial 1, kind .task}` と一致して別の資源を返します。
- **修正案**: 次のどれかにします。
  - (a) Handle に `kind` か台帳の識別値を持たせ、`entry` で照合する。
  - (b) 1つの実行時の中で serial の採番器を全台帳で共有する。
  - (c) 「epoch は台帳ごとに一意(実行時ごとではない)」と契約に明記し、設計書の「実行時epoch」の記述と揃える。

  あわせて、「同じ epoch・別の台帳」の誤用を拒否する試験を追加することを勧めます。

### 2. 【中】owner の番号を再利用すると、古い所有者の資源を引き継いでしまう
- **対象**: `runtime_base.zig:74-75`、`:91`
- **失敗する条件**: owner は `u64` の比較だけで判定しています。終了した task の番号を新しい task に再利用し、終了時に台帳の項目を回収し残すと、新しい task が古い Handle で `get`/`remove` を通せます。serial は再利用しないよう守っていますが、owner には同じ保証がありません。
- **修正案**: 1061 の契約に「owner の識別値は再利用しない(または世代付きにする)」「owner の終了時にその owner の項目をすべて回収する」を加えます。台帳側に owner 単位で列挙・回収する関数を用意するのも有効です。

### 3. 【中】Wake のコピーや deinit 後の notify で、再利用された fd/HANDLE 番号へ書き込む
- **対象**: `host_wake.zig:29-30, 52`(値で返す `init`)、`:55-69`、`:76, 94-96`(`isOpen`)、試験 `:151-152`
- **失敗する条件**:
  - `init()` は値で返すので、共有する前に誤ってコピーし、両方を deinit すると二重 close になります。2回目の close は、その間に同じ番号を割り当てられた別の資源を閉じます。
  - deinit 中や deinit 後の notify は、`isOpen` が非原子的に `native` を読むためデータ競合です。close の直後に別のファイルが同じ fd 番号を得ると、`write` がそのファイルへ `0x01` を書き込みます。
  - 試験 `:151` は「deinit 後の notify は HostFailed になる」ことを契約のように固定しています。この結果は単一スレッドの場合しか成り立ちません。
- **修正案**:
  - `pub fn init(self: *Wake)` のように、その場で初期化する形にする。
  - deinit 後の利用は「エラーが返る」ではなく「禁止(未定義)」と明記し、試験は単一スレッドでの誤用検出にとどめる。
  - 安全側に倒すなら、原子的な状態フラグと参加者の参照数で close を守る。

### 4. 【中】POSIX: SIGPIPE を防ぐ手当てがない。deinit で読み取り側を先に閉じている
- **対象**: `host_wake.zig:61-66`(fds[0]→fds[1] の順で close)、`:86-90`
- **失敗する条件**: deinit は読み取り側 `fds[0]` を先に閉じます。統合後に後片付けの順序を誤り、通知側(パイプ受信スレッドなど)が残っていると、`write` で SIGPIPE が発生します。このプロセスは SIGPIPE を既定の処理のままにしているため、エラーとして返る前にプロセスが終了します。既存コードは SIGPIPE を個別に防いでいます(`host_window_macos.zig:615` の `F_SETNOSIGPIPE`、`host_x11.zig:230` の `MSG_NOSIGNAL`、`host_pipe_signal.zig`)。Wake だけがこの手当てを持っていません。
- **修正案**:
  - close の順序を書込み側→読み取り側に変える。残った通知側は EBADF/HostFailed になりますが、それでも 3 の fd 番号再利用の危険は残ります。
  - macOS では書込み側に `F_SETNOSIGPIPE` を設定する。
  - Linux では `eventfd`(SIGPIPE が発生しない)にするか、`socketpair` と `MSG_NOSIGNAL` の組合せを検討する。※eventfd に SIGPIPE がない点は推測です。採用する前に man ページで確認してください。

### 5. 【中】取消しでは OS 待機が起きず、無期限の待機でも 20ms ごとに起き続ける
- **対象**: `host_wake.zig:105, 109-111`、`runtime_base.zig:44-53`
- **失敗する条件**:
  - `Cancellation.request()` は OS オブジェクトを起こしません。そのため取消しへの応答は最大で約 20ms 遅れます。Windows では `WaitForSingleObject` のタイマー分解能によって、さらに伸びる可能性があります(※推測)。
  - 期限なしの待機でも毎秒約 50 回起きて時計を読むので、待機中の task が増えるほど CPU と電力を消費します。
  - 記録には「即時の起床が必要な接続側は notify も行う」とありますが、型の上では強制されていないため、notify を忘れても検出できません。
- **修正案**: 取消し印に起床先(`?*Wake`)を持たせ、`request` の中で notify します。取消しも Wake 経由で届くようにすれば、期限なしの待機は OS が知らせるまで眠り続けられ、20ms ごとの区切りは安全のための上限として、より長い値にできます。

### 6. 【低〜中】POSIX: 通知のたびに1バイト書くため、消費側が空回りする
- **対象**: `host_wake.zig:85-90`、`:124-131`
- **失敗する条件**: 通知1回につき必ず1バイト書きますが、消費側は1回の確認につき 256 バイトしか読みません。通知が N 回続くと、消費側は約 N/256 回、眠らずに poll→read→時計の読み取り→世代の確認を繰り返します。pipe が満杯(Linux の既定で 64KiB、※推測)のときは最大約 256 周です。論理的な取りこぼしはありませんが、通知側を止められない状況では、消費側が待機中に CPU を使い続けます。また、EAGAIN の分岐は 1000 回の通知では pipe が満杯にならないため、試験で一度も通っていないと考えられます(※推測)。Windows の自動リセット Event は OS 側で通知がまとまるので、この問題はありません。
- **修正案**: 原子的な `pending` フラグを持たせ、false→true に変わった通知側だけが書き込むようにします。消費側は「pending を落とす→EAGAIN まで読み切る→世代を確認する」の順にします。読み切りの量は pipe の容量までなので、取消しの確認を止め続ける心配はありません。あわせて、EAGAIN を起こすほど大量に通知する試験を追加します。

### 7. 【低〜中】macOS: CLOEXEC の設定が原子的でないことが、統合後の Wake 生成時期と衝突する
- **対象**: `host_wake.zig:27-28, 37-49`
- **失敗する条件**: 契約は「並行した子プロセス作成より前に初期化する」です。しかし設計では Wake をキューや task ごとに作る可能性があり、そうなると実行中にも生成されます。その間に別のスレッドで SYSTEM や macOS のウィンドウ子プロセスを生成すると、Wake の fd が子プロセスへ漏れます。害は主に fd の漏れで、長く動く子プロセスでは fd を保持し続けます。
- **修正案**: 1061/1063 で次のどれかを決めます。
  - (a) Wake の生成を起動時の1か所に集約する。
  - (b) 子プロセスの生成と同じロックで直列化する。
  - (c) macOS の `posix_spawn` で `POSIX_SPAWN_CLOEXEC_DEFAULT` を使い、継承する fd を明示する。※この Apple 拡張の挙動は推測です。採用前に公式資料で確認してください。

### 8. 【低〜中】時計が統一されておらず、スリープ中の進み方も OS ごとに違う
- **対象**: `host_clock.zig:15-25`。別系統の時計として `host_audio.zig:162-169`、`host_input.zig:238`、`main.zig:1809`、`host_window_macos.zig:690`(いずれも作業中のコード)
- **失敗する条件**: 共通時計は失敗すると HostFailed を返しますが、既存の時計は失敗すると 0 を返し、`host_audio.zig:162` は QPC の結果を確認していません。統合の際にこれらの Instant を混ぜて期限を計算すると、0 が混じって期限を誤ります。また、システムのスリープ中に時計が進むかどうかは OS によって異なると考えられます(※推測: Linux の `CLOCK_MONOTONIC` はスリープ中に止まり、macOS と Windows QPC の扱いは要確認)。スリープ・復帰をまたぐ期限の挙動が OS ごとにずれる可能性があります。
- **修正案**: 1061 で期限計算に使う時計を `host_clock` に統一します。スリープ中の扱いを OS ごとに公式資料で確認し、仕様に書きます。

### 9. 【低】台帳のエラーの違いから、他の所有者の資源の存在と種類が分かる
- **対象**: `runtime_base.zig:89-91`
- **失敗する条件**: 種類を所有者より先に検査し、`WrongKind`、`WrongOwner`、`InvalidHandle` を区別して返しています。そのため別の task が serial を順に試すと、他の所有者の資源があるかどうかと、その種類を調べられます。設計が掲げる task 間の分離と、方針が合いません。
- **修正案**: 所有者を先に検査し、他の所有者のものは `InvalidHandle` に統一します。詳しい理由はデバッグ用の診断にだけ残します。あわせて、`insert` が失敗したとき(ResourceFull/IdentityExhausted)は payload の OS 資源を呼出し側が回収する、と契約に明記します。

### 10. 【低】期限と時計が結び付いていない。NS 互換性は今回確認していない
- **対象**: `host_wake.zig:98-100`、`runtime_base.zig:16-24`、`host_wait.zig:102-120`
- **失敗する条件**: `Deadline` は時計を持たない絶対時刻です。`wait()` は内部で `host_clock` を使うので、別の時計(差し替えた時計や既存の 0 を返す時計)で作った期限を渡すと、即座にタイムアウトするか、ほぼ無期限に待ちます。型の上ではこの誤用を防げません。
- **修正案**: `wait` に相対ミリ秒を渡して内部で一度だけ期限を計算する入口を用意するか、`Deadline` に時計の識別を持たせます。
- **NS 互換性**: 固定コピーの `host_wait.zig` では、`now()` が `clock.now()` を呼ぶだけで、型は `i128` で一致しています。ただし、変更前の NS の時計の式や、失敗時の結果と同じかどうかは、Git 操作をしない条件のため比べておらず「未確認」です。
