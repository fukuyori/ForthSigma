## 結論

**High はありません。Medium が2件あり、どちらも試験の弱さです。** Forth のコードは、読んだ範囲では正しく動きます。

## Medium

**M1. 不正なレジスタ値で状態が変わらないことを、試験が見分けられていない場合があります**（`verify-pcm-synth.py:53-59`）
- この試験は、声部0の2つ目の標本だけを見ています。そこでは440 Hz、duty 64、gain 2000 なので、位相は307582、しきい値は4194304、LFSRは1のままです。
- 次の4件は、もし値が書き込まれても出力が同じ `+2000` になるため、見分けられません。
  - `(-1,0,0)` と `(4,0,0)`：kind が -1 や 4 になると、ノイズの分岐に入ります。LFSR の最下位ビットが1なので、出力は `+2000` のままです。
  - `(256,0,3)`：しきい値が 2^24 になり、`+2000` のままです。
  - `(-1,0,1)`：floor で step が -350 になります。位相は153441 で、`+2000` のままです。
- 声部番号が範囲外の2件 `(1,-1,0)` と `(1,4,0)` は、配列の外への書込みになります。これは何も観測していません。
- 53行目のコメント「Compare complete rendered state」は、実際の内容と合っていません。
- **修正案**：拒否の前と後で、`PS-KIND`、`STEP`、`GAIN`、`DUTY`、`PHASE`、`NOISE` の 4×6 セルをすべて出力して比べます。範囲外の声部を見るため、配列の前後のセルも比べます。

**M2. 書き残しの続きを渡すアドレスとカウンタが、決まった結果の試験で確かめられていません**（`verify-pcm-synth.py:69,78`）
- 模擬の `PCM-WRITE` は、最初の `DROP NIP` でアドレスを捨てています。このため、`PS-SEND` が2回目以降に `PS-BUFFER + sent*2` を渡しているかは、どの試験でも分かりません。この試験で期待されるのは `PS-BUFFER+10` です。実機での統合試験も、無音のフレーム数を見るだけです。
- `partial-full-retry` は `PS-PARTIAL`、`PS-FULL`、`PS-WRITES`、`PS-WAITS`、`PS-FRAMES` を確かめていません。期待値はそれぞれ 1、1、3、2、512 です。実機の実行でもフレーム数以外は記録するだけなので、部分書込みと満杯の分類はどこでも検証されていません。
- **修正案**：模擬の側で、渡されたアドレスから `PS-BUFFER` を引いた値を記録して確かめます。あわせて、上の PS-* カウンタも出力して比べます。

## 確認して問題がなかった点

- **スタック**
  - `PS-REG!`、`PS-VOICE`（`2 PICK` を含む）、`PS-LE!`、`PS-RENDER`、`PS-SEND` を1語ずつ追いました。どれもデータスタックの出入りが合っています。
  - `PS-SEND` は、ループを抜けるときに残り数を `DROP` しています。
  - `PS-STREAM` は `>R` と `R>` が同じ定義の中で対になっています。`PS-RUN` の DO ループは CATCH の中で終わるので、リターンスタックも合っています。
- **検証してから書き込む**：声部、レジスタ番号、値をすべて確かめてから `!` しています。位相とノイズの状態はリセットしません。
- **floor 除算**：`/` は floored です（`integer_math.zig:66-70`）。Python の `//` と同じ結果になります。Hz と三角波の負の値でも食い違いません。
- **位相の連続性と LFSR**
  - 1標本で回り込むのは最大1回です（step < TURN/2）。
  - LFSR の更新は逆にたどれるので、0 には落ちません。
  - 途中でレジスタを変える試験（4096 の位置）も、oracle の event を適用する時刻と合っています。
- **s16LE と値の範囲**
  - 出力の絶対値は最大 4×8191=32764 です。三角波の最小値も -8191 なので、範囲を超えません。
  - `RSHIFT` は論理シフトですが、`255 AND` を取るので上位のバイトも正しくなります。
  - Python の `struct.pack('<h')` は、範囲外の値でエラーになるので、範囲の検査も兼ねています。
- **後片付け**
  - 本体を実行したときのエラーを優先し、閉じるときのエラーは本体が成功したときだけ THROW します。
  - CLOSE に失敗したら ID を残し、`PS-CLEANUP` で閉じ直せます。
  - ID は正の値なので、0 を「なし」の印に使えます（`PCM_STREAM_DESIGN.md:15`）。
  - STOP の後も `PCM-UNDERRUNS` を呼べます（同 23行）。
- **模擬の分離**：`REQUIRE-AUDIO` は最初の1回しか読み込まないので、先に定義した模擬が上書きされずに使われます。実機の最初の書込みが容量と同じになることは、どこでも前提にしていません。
- **時間の測定**
  - 合成だけを測る実行では、AUDIO を読み込んでいません。
  - CPU 時間を測る区間は、経過時間を測る区間を外側から包んでいます。
  - 2回分のループの後で、最後のバッファのチェックサムを、1,024,000 フレーム分の oracle の値と照合しています。
  - 範囲の説明文は、実際に測っている内容と合っています。

## Low

- **L1. 聞こえる出力を選んでも無音になります。** `pcm-synth-play.fs:2-3` の使い方には `PS-DEMO-SETUP` がありません。読み込んだ時点では `PS-RESET` で全部の声部が mute なので、`96 TRUE PS-STREAM` を実行しても無音のままです。
- **L2. 待ち時間切れの -528 が、OPEN の busy と同じ値です。** ior を見ても、どちらで失敗したのか区別できません。
- **L3. `median_realtime_headroom_at_48000` の中身は実時間比です。** 設計で「余裕」と呼んだ `1−t/T` ではありません。

## 残る限界

- oracle は同じ仕様から書いた Python なので、仕様の読み違いが両方に入っていても見つけられません。手で計算した値や、わざと規則を変えた版での試験はありません。
- 計測のチェックサムは、最後の1バッファのバイトを足しただけです。並び順の違いは見つけられません。
- 実機での統合試験は無音で流すだけです。バックエンドの種類、装置での遅れ、聞こえ方は確かめていません。
- 計測は Release ビルドを前提にしています。各プロセスは30秒で打ち切られるので、遅いビルドでは時間切れになるおそれがあります（※推測です）。
- Mac 実機での PCM 1130 の受け入れは、まだ済んでいません。この試作の結果から、本体（ネイティブコード）へ移すかどうかは決めません。
