レビューの結論として、High・Medium に当たる不具合は raw440 フィクスチャ側には見つかりませんでした。Medium は、記録の扱いと結果の解釈について 2 件です。ファイルを読んだだけで、実行・編集・計測はしていません。

**確認できた点（`channel-check.py` と生成された `silent.fs` / `preflight.json` / `silent.json`）**
- **フレーム数**: 最初に 4096 フレームを送り、その後 512 フレームを 117 回送ります。4096 + 117×512 = 64000 です。
- **バイトオフセット**: `RAW-ADDRESS @ 4096 I 512 * + 4 * +` で、送る位置は「先頭 + (4096 + I×512) × 4」バイトです。最後のブロックは 255,999 バイト目で終わり、`ALLOT 256000`・`READ-FILE` の長さ・ファイルの大きさ（64000 × `<hh`）とすべて合っています。
- **波形**: `(32000-|2·phase-32000|)·2·849//32000-849` で、値の範囲はちょうど ±849 です。周波数は 3 段とも 440Hz で同じです。
- **左右の分離**: L は右が常に 0、R は左が常に 0、B は L=R です。バッファもファイルも別々で、それぞれのハッシュが記録されています。
- **後片付け（cleanup）**: `PS-SAFE-CLEANUP` による後片付けは、`SD-STREAM` と同じ書き方です。
  - 本体の処理を CATCH し、必ず後片付けしてから、本体のエラーを優先して投げ直します。
  - `PCM-OPEN` が失敗したときは `PS-HANDLE` が 0 のままなので、閉じる処理は何もしません。
  - 入口の `PS-HANDLE @ IF -528 THROW` で、前の段のハンドルが残っていないことも確かめています。
  - `SD-ACCEPT-DONE` は後片付けの後に呼ばれ、handle=0、underruns=0、frames=64000 を確かめます。
- **S-DSP を通らないこと**:
  - 生成されたソースに `SD-RENDER`、`SD-STREAM`、`SD-NOTE` の実行はありません（`SD-NOTE` は定義だけです）。
  - `silent.json` の標準出力は `frames=64000` が 3 回と `S-DSP-FRAME=0 DEPTH=0` です。
  - preflight の標準出力も `0 0` を確かめています。
- **`--play` まで音が出ないこと**:
  - `--verify` のソースには PCM のワードがなく、デバイスを開きません。
  - 引数なしで実行すると、読み込んだ後で 3 つのバッファを 0 で埋めてから送ります。デバイスは開きますが、送るのは 0 だけです。
  - `--play` と `--check-ready` は、preflight.json と silent.json の両方で次の 3 点を確かめます。
    - バイナリの SHA が一致すること
    - ソースと PCM の LF 正規化ハッシュが一致すること
    - `checks_passed` が true であること
  - 2 つの JSON の値は互いに一致しています。
- **未確認**: 今ディスクにある `sigma.exe` が `9946…538a` と一致するかは、実行していないため確かめていません。この照合はスクリプトが毎回 assert します。

**Medium 1: `windows-stereo-sent-capture.json` を物理出力の証拠として扱えない**
- `PCM-OPEN`、`PCM-WRITE`、`PCM-STOP`、`PCM-UNDERRUNS`、`PCM-CLOSE` を Forth のモックに置き換えてから `snes-dsp-audio-native-play.fs` を INCLUDED しています。そのため `SD-SEND` はモックの `PCM-WRITE` に結び付いています。
- つまりこの記録で分かるのは、Forth 側がフレームを `<hh` の L/R の位置に正しく書いていることだけです。Zig 側の `PCM-WRITE`、OS のオーディオ API、ミキサー、再生機器は通っていません。
- フラグ `capture_is_RAM_callback_not_physical_output: true` の書き方自体は正しい表記です。
- ただし、この記録には `binary_sha256` もソースハッシュもありません。そのため、試聴に使ったバイナリやソースと同じものだと、記録からは結び付けられません。
- 証拠として使うなら、「RAM 上の L/R 配置は正しい」とだけ書くことを勧めます。

**Medium 2: raw 試聴の結果の解釈**
- 元の S-DSP 試聴では、左は pitch 451（低い音）、右は pitch 901（高い音）で、周波数が違いました。raw の試聴は 3 段とも同じ 440Hz・peak 849 です。
- raw の LEFT が聞こえた場合、元の「右しか聞こえない」は、左右の割り当ての問題ではないと考えられます。低い音と小さい音量（約 -32dBFS）が再生機器で聞き取りにくかった可能性があります。※推測です
- 逆に raw の LEFT が聞こえない場合は、問題は S-DSP より後ろ（Zig の PCM 出力から再生機器まで）にあります。
- 結論を書くときは、この 2 通りを分けて書く必要があります。

**Low（参考）**
- 各段の最初のサンプルが -849 から始まるため、始めと終わりにわずかなクリック音が出ます。小さく、判定には影響しません。
