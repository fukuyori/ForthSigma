## 状態遷移の所見

### A.【中】`state_asked` に期限がなく、WINDOW-ON がずっと保留されたままになる
- **場所**：1293行 `if (self.state_asked != null) return;`。`state_asked` が null に戻るのは、1054行で求めた状態が届いたときだけです。また 1082行は `state_asked` と比べるので、そのあとの全画面の要求も送られません。
- **起こし方**：`_NET_WM_STATE_FULLSCREEN` を無視するWM（twm など。EWMH対応が部分的なタイル型WMでも起きる）で `TRUE FULLSCREEN` のあと `1 WINDOW-ON` とします。
  - ソースから確実：プロパティが変わらないので PropertyNotify が来ず、`state_asked=true` のまま残ります。`place_dirty` もずっと保留されます。
  - さらに 1093行で取った `normal_rect` も消えません（全画面に入らなかったので、解除の処理を通らないため）。
  - 変更前は、こういうWMでも通常表示用の MOVERESIZE は送っていたので、**後退**です。
  - 「各段階1000ms上限」という説明は、この段階には当てはまっていません。
- **修正案**：
  - `state_deadline` を持たせ、1000msを過ぎたら `state_asked=null` にし、`fullscreen_wanted = fullscreen_on` にそろえます（拒否として扱う）。
  - 全画面に入っていなければ、`normal_rect=null` と `refullscreen=false` にもします。

### B.【中・回帰】解除するたびに、全画面前の位置へ戻す移動を必ず送る
- **場所**：1064〜1069行で、`normal_rect` があれば必ず `restore_pending` を作ります。1173〜1179行で、その位置へ MOVERESIZE を送ります。
- **起こし方**：
  1. 画面0で `TRUE FULLSCREEN`。
  2. GNOME の Super+Shift+→ で、全画面の窓を画面1へ移す。
  3. Alt+Enter か `FALSE FULLSCREEN` で解除する。
  - 推測：Mutter は通常の矩形を画面1に置き直して戻します。それを 1173行が画面0の古い座標へ動かし戻します。
  - 同じことは、全画面のあいだにモニタ構成が変わった場合にも起きます。今回の混在倍率スクリプトで倍率を変えた場合がちょうどそれで、古い座標へ強制的に動かします。
  - 変更前は、ふつうの解除で移動を送っていませんでした。
- **修正案**：`normal_rect` に、どこから来た値か（`captured` か、WINDOW-ON の `placed` か）を持たせます。
  - `captured` のときは移動も縮小も送らない。大きさが戻ったのを待つだけにして、`normal_rect=null` にする。
  - 少なくとも、WMが報告する窓の画面が全画面に入ったときと違うなら、移動しない。

### D.【低〜中・タイミングで変わる】遷移中に続けて WINDOW-ON すると、縮めた大きさを元の大きさとして扱う
- **場所**：1305〜1308行は `normal_rect.w/h` を元の大きさとして使います。`restore_pending` の途中では、この値は前回の WINDOW-ON で縮めた後のものです（1316〜1317行）。
- **起こし方**：画面0（2560×1440）で 2200×1200 の窓を全画面にし、`1 WINDOW-ON 3 MS 0 WINDOW-ON` とします。
  - 2回目は縮めた 1920×1011 をもとに計算するので、画面0に入るはずの窓が 1920×1011 に縮みます。
  - 1回目の縮小がまだ送られていないうちでも、同じことが起きます。
- **修正案**：全画面・`refullscreen`・`restore_pending` のときは、`self.normal_before`（WMが実際に戻す大きさ）を元の大きさとして使います。

### E.【低〜中・推測】完了の判定が厳密すぎて、全画面に入り直さなくなる
- **場所**：1187〜1188行は位置と大きさの**完全一致**を求めます。合わないまま1000msたつと、1193行で `fullscreen_wanted=false` にします。
- **起こし方（推測）**：
  - XWaylandで小数倍率（1.25 / 1.5）だと、座標の丸めで1pxずれる可能性があります。
  - 最大化した窓で `TRUE FULLSCREEN 1 WINDOW-ON` とすると、解除したとき最大化に戻り、移動要求が無視される可能性があります。
  - どちらも、利用者は全画面を解除していないのに、全画面が勝手に解けます。
- **修正案**：
  - ±1px までは一致とみなします。
  - 1000msたったとき、窓が目的の画面上にあれば（`monitorOn`）、全画面に入り直します。
  - 最大化の状態は、移動の前に外します。

### F.【低】全画面で開くと、いったん元の画面で全画面になってから移る
- **場所**：1668行と1669行の順序のため、作成直後の最初の回で、`applyModes` が配置より先に全画面の要求を送ります。
- **起こし方**：`WINDOW-CLOSE 1 WINDOW-ON TRUE FULLSCREEN SHOW` とすると、初めに置かれた画面で全画面 → 解除 → 移動 → 入り直し、と3回切り替わります。結果は正しいものの、目に見えて1〜2秒ちらつきます。
- **修正案**：新しい窓で `place_dirty` が立っていて、まだ全画面でないなら、全画面の要求を1回分遅らせ、通常表示のまま先に移動します。

### G.【低】その他
- 遷移中は `fullscreen_on=false` なので、1021行の判定により Alt+Enter が全画面の解除にならず、INKEY に漏れます。そのあと窓は全画面に入り直します。
- 遷移中に WINDOW-ON をくり返し呼ぶと、そのたびに1319行で期限が延びるので、いつまでも終わりません。
- WM自身が全画面にした場合（キー割り当てなど）は `fullscreen_wanted` が真になりません。そのため WINDOW-ON すると、作業領域いっぱいの通常窓で終わります（変更前からある問題）。

## 混在倍率スクリプト（`verify-linux-mixed-scale.py`）

**良い点**：
- 一時的な適用（method=1）しか使わず、永続化しません。
- 候補の構成を、変える前に確認だけの呼び出し（verify、117行）で確かめています。同じリスト形状の Variant を使うので、PyGObject がリストを受け付けない場合もここで止まります（安全）。
- 監視プロセスが準備できてから構成を変えます（135〜137行）。
- 監視プロセスは `start_new_session` で動くので、端末の Ctrl-C や SIGHUP の影響を受けません。
- 書き込み側のfdは子プロセスに引き継がれないので（Python 既定の `close_fds`）、親が死ねば EOF が届きます。
- 復元計画をファイルに書くのは変更前です（120行）。また `--restore-plan` をfdなしで渡すと即座に復元するので、手で戻すこともできます。

### C1.【中】監視プロセスの待ち時間90秒（80行）が、親の最悪の所要時間より短い
- 親の最悪値は次の合計で、約103秒です：準備の待ち8秒（135行）＋ apply 5秒 ＋ 待ち8秒 ＋ 2秒 ＋ inspect 15秒（142行）＋ テスト55秒（148行）＋ 終了待ち10秒（152行）。
- 90秒を過ぎると、**テストの途中で元の構成に戻されます**。
- そうなると、そのあと親が書く `os.write(write_fd, b'R')`（165行）は BrokenPipeError になり、元の例外を上書きします。
- 合格の経路でも遅ければ、元の倍率のままテストが通る可能性があります。そのとき `report['status']='pass'`（159行）は先に入っているので、report.json に pass が残ります。
- **修正案**：
  - 親に全体の期限（例：75秒）を持たせ、テストの timeout は残り時間から計算します。
  - 監視プロセスの待ちは、親の期限＋十分な余裕にします。
  - 合格と書く前に `watchdog.poll() is None` を確かめます。
  - status は、復元を確かめてから書きます。

### C2.【中】親が SIGTERM や SIGHUP を受けると、後始末の `finally` が動かない
- Python の既定では、SIGTERM を受けると後始末なしで終わります。
- 構成は監視プロセスが戻しますが、次が起きます。
  - report.json が書かれない。
  - 子の window-on テストは同じセッションのまま、孤児として最後まで走る。構成が戻った後なので、失敗する。
- 端末を閉じた場合（SIGHUP）、window-on 側にも処理がなく、`SigmaSession.__exit__` が動きません。sigma は別セッションなので残る可能性があります。
- **修正案**：両方のスクリプトで、SIGTERM と SIGHUP を `SystemExit` に変えます（window-on の26行と同じ方式）。さらに、子は `start_new_session` で起動し、例外のときは `killpg` します。

### C3.【低〜中】復元の確実さ
- 元の構成は、method=0 で確認していません。候補だけを確かめています。`original` も確認の呼び出しで確かめてから変えるべきです。
- 監視プロセスは失敗すると1回で終わります（86〜87行）。30秒ほど、間をあけて再試行するべきです。
- 各モニタの属性は `{}` で送り直します（49行）。確認しているのは underscanning と color-mode だけです。推測ですが、新しいMutterの他の属性（rgb-range など）が既定以外だと、既定に戻ります。知らない属性が既定値以外なら止めるほうが安全です。
- 無効なモニタがつながっていると、46行の `next()` が StopIteration になります。構成を変える前なので、安全側です。

### C4.【中】テストとしての妥当性
- XWaylandの倍率の扱い（`org.gnome.mutter experimental-features` の `xwayland-native-scaling` など）を記録していません。そのため、X座標が論理単位なのか物理単位なのかが記録からわかりません。
- 2秒待ったあと（140行）、RandR の値が新しい配置になったかを確かめていません。window-on の202行で途中の変化は検出できますが、反映される前の値で始まる可能性はあります。RandR が期待した幅になるまで待つべきです。
- 中の window-on.json に `limitations=['...mixed scale not tested']`（208行）が残ります。混在倍率で実行したときと記録が矛盾します。
- 利用者の他の窓は、構成を変えたときに Mutter が動かし、戻したあとも元の位置に戻るとは限りません。そのことを文書に書いておくべきです。

## window-on テストの妥当性

### H.【低〜中】
- 各段階は終わったあとの状態しか見ず、1000ms待ってから一度だけ確かめます（129行）。実装の上限は段階ごとに1000msなので、遅いけれど正しい遷移は失敗扱いになって不安定です。拒否の経路（2秒後に `fullscreen_wanted=false`）も見分けられません。期限までくり返し確かめる形のほうがよいです。
- 所見A、B、D、E を突く段階がありません。追加を提案します。
  - 大きい窓のまま `rapid-place`（所見D）。
  - 全画面中にWMの操作で画面を移して解除（所見B。`_NET_WM_FULLSCREEN_MONITORS` か、Mutter のキー操作で）。
  - 最大化してから全画面にして WINDOW-ON（所見E）。
- large の縮小が確かめられるのは、画面0のほうが大きい配置のときだけです。172行で `normal_size` を毎回切り詰めて引き継ぐので、画面0が小さい配置だと、所見2の経路は通らずに合格します。期待値は、元の大きさから毎回計算し直すべきです。
- `user-move`（138〜140行）は送り元を1（アプリ）として送っています。利用者の操作に近づけるなら、2（pager）にするべきです。
- 記録の `source_sha256` が、このスナップショットのソースと同じものかは確かめていません（私はハッシュを計算していません）。
