## 最小化からの復元経路（`host_window.zig:981-1082, 1864-1874`）

### ソースで確定していること
- **DPI 換算は正しいです。**
  - `restore_size` は `rcNormalPosition` の外枠の大きさです。`dpiScaledFrom`（`:1561-1571`）は、古い DPI の枠を引いてクライアント領域を換算し、新しい DPI の枠を足します。
  - 176x139 から dpi96 の枠（16x39）を引くと 160x100 です。これを 1.25 倍すると 200x125 になり、診断値と一致します。
  - 換算の元は、毎回保存した値（`restore_size`/`restore_dpi`）です。今の枠からは換算しないので、換算が重なってずれることはありません。
- **SetWindowPos を2回呼ぶ理由も正しいです。**
  - 1回目の `SetWindowPos`（`:1062`）の中で `WM_DPICHANGED` が同期で届くと、`:1974` が Windows の提案矩形を当てます。
  - 2回目（`:1067-1070`）は、最終 DPI での保存サイズで上書きします。
  - 最後に中央からずれていないかを確かめます（`:1074-1077`）。
  - 目標の矩形は作業領域の内側に収まるので、DPI が行ったり来たりすることはありません。
- **再入は安全です。**
  - `restore_place_pending` は、`SetWindowPos` の前（`:1055`）に false にしています。そのため、`placeOn` の中で同期で届く `WM_SIZE` が `wm_place` を投げ直すことはありません。
  - 最小化の分岐では、`SetWindowPlacement` の後（`:1050`）で true にしています。この順序も正しいです。
  - 関係する変数はすべてウィンドウスレッド専用です。`windowPlace` は `PostMessageW` しか呼ばないので、ロックは要りません。
- **取り消しも正しく動きます。** `-1 WINDOW-ON` では `GetMonitorInfoW` が失敗し、`place_device` が0になります。その結果 `:1016` で pending が false になります。`id==0` の場合と `wm_destroy`（`:2030`）でも false になります。
- **前回 L3 の影響は小さくなりました。** 復元すると `wm_place` が `info.work` を基準に中央へ置き直します。そのため、作業領域座標の変換（`:1045-1047`）が誤っていても、ずれるのは復元直後の一瞬だけになりました（これはソースから導いた推論です）。
- **L2 の無限再帰は防がれています。** `:1025` の `IsZoomed` による確認で止まります。

### 低
**R1. 「最大化に戻る」最小化窓（`WPF_RESTORETOMAXIMIZED`）の経路（ソースで確定、テストなし）**

ソース上の流れは次のとおりです。
1. 復元すると `WM_SIZE(SIZE_MAXIMIZED)` が来て、`wm_place` が投げられます（P1）。
2. P1 の最大化の分岐で `ShowWindow(SW_SHOWNOACTIVATE)` を呼ぶと、`WM_SIZE(SIZE_RESTORED)` が来ます。pending はまだ true なので、P2 が投げられます。
3. 再帰した呼び出しが pending を false にし、再び最大化します。
4. P2 が、最大化解除と最大化をもう一度繰り返します。

処理は止まり、最終状態も正しいです。ただし、解除と最大化が2往復してちらつき、`SW_SHOWMAXIMIZED` による活性化も2回起きます。
- **修正案:** `:1869` を `wparam == 0`（`SIZE_RESTORED`）のときだけにする。または、最大化の分岐に入った時点で、すでに目標のモニター上にあり pending が true なら、pending を false にして戻る。

**R2. 全画面の分岐（ソースで確定。影響は仮説）**
- `:1030-1035` は `restore_place_pending` を false にしません。最小化中に `WINDOW-ON` を実行し、そのまま最小化中に全画面に入ると、pending が残ります。この場合、全画面を解除したときに `restore_size` で一度上書きされます。
- 最小化された全画面窓に `WINDOW-ON` を実行すると、`IsIconic` の確認より先に全画面の分岐を通り、最小化中の窓に `SetWindowPos` を掛けます。Windows はこれを最小化中のアイコン位置の変更として扱い、復元すると元のモニターに戻る可能性があります（仮説）。これは今回の変更以前からある経路で、テストもありません。
- **修正案:** 全画面の分岐で `IsIconic` なら、`SetWindowPlacement` で戻り先の矩形を目標のモニターに置き、pending を true にする。または、最小化中は全画面の分岐を後回しにする。

**R3. 最小化中に、DPI の違うモニターへ2回移動したとき（ソースで確定。まれ）**
- 2回目は、`restore_size` を `placement.normal` から読み直します（`:1041`）。この値は、1回目に作業領域へ収めた（`centered` で切り詰めた）サイズかもしれません。
- 一方、`restore_dpi` は窓の DPI のままです。そのため、切り詰めが起きた場合だけ、目標側のピクセル数が元の DPI の値として換算されます。
- **修正案:** pending が true の間は、`restore_size`/`restore_dpi` を上書きしない。

**R4（仮説）:** `restore_dpi` は、最小化中の窓の `GetDpiForWindow` で取っています（`:1042`）。これが `rcNormalPosition` を測ったときの DPI と常に一致するとは、ソースだけでは確かめられません。診断（dpi96 で保存）は一致した例です。dpi120 のモニターで最小化し、dpi96 のモニターへ移す逆向きの場合は未確認です。

## スクリプト

### `verify-windows-refresh-watchdog.py`: 偽陽性は見つかりませんでした
- 親は表示の変更を確かめてから（`measure-…:117-121`）報告を書き、`os._exit(0)` で `finally` を飛ばします。`restore` ファイルを書くのは `finally` だけなので、残る復元の経路は watchdog の5秒の期限だけです。
- 検証側も独立に照合しています。`restored.json` の `restored` に加えて、`snapshot()` の完全一致と、`EnumDisplaySettingsW` の `dmDisplayFrequency` を確かめています。
- **低:**
  1. `restore` マーカーがないこと、つまり期限で復元されたことを assert していません。`os._exit` が退行すると、親は測定に進み、`child.wait(15)` のタイムアウトで失敗します。偽陽性にはなりませんが、失敗の理由が分かりにくくなります。
  2. 5秒の期限は `ready` の時点から数えます。一方、親は表示を変えた後、反映を最大5秒待ちます。モードの切り替えが遅い環境では、watchdog が親の確認より先に元へ戻し、親の assert が失敗します。これは偽陰性や不安定さの側の問題です。期限を10〜15秒にするのが安全です。
  3. `.work/1037/mixed-refresh-*` は残ります（記録としては有用です）。
- **mixed-refresh:** 前回の低 #3（HMONITOR まで比べる）は `topology` を使うことで解消しました。#1（ジョブからの切り離し）と #2（watchdog が失敗したときに親が最後の復元を試みない）は残っていますが、低のままです。
