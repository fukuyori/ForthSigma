## 結論

## Medium

**M1. 標本時刻の契約が、RENDER 以外で時刻を進めたときに成り立たない**（`docs/YM2149_FORTH.md:63`、`examples/ym2149.fs:127-130`）
- **文書の記述**: 「n番目の標本は floor(n*2000000/48000) まで処理した後の状態」。
- **実装の動き**: `YM-RENDER` は、その時点の `YM-CYCLE` から持ち越した `YM-FRACTION` を使って相対的に `YM-RUN` します。このため `YM-WRITE`、`YM-READ`、`YM-TO`、`YM-RUN`、`YM-BUS@` で先に時刻を進めると、標本の格子がその分ずれます。その間の PCM は作られません。
- **最小再現**（読んだ結果からの予想値です）:
  ```
  YM-RESET 15 8 1000 YM-WRITE CREATE B 2 ALLOT B 1 YM-RENDER YM-CYCLE @ .
  ```
  文書をリセット起点の絶対格子と読むと 41 になりますが、実装では 1041 です。
- **修正案**（どちらにするかはご判断ください）:
  - (a) 文書を「各 `YM-RENDER` は現在の `YM-CYCLE` から始まり、`YM-FRACTION` を持ち越して相対的に進む。即時 write/read/TO で進めた区間の標本は作らない」と直す。
  - (b) 絶対格子が要るなら、フレーム番号から目標 tick を計算する方式に変える。
- テストは queue 経由の書込みだけで RENDER と組み合わせているので、この差は検出されません。

## Low
1. **同じ tick の未適用 event が見えない**: `YM-PORT@`、`YM-PIN@`、`YM-SAMPLE` は時刻を進めないため、現在 tick に予定した event がまだ適用されていません。
   - 例: `0 0 0 YM-INPUT-EVENT! 0 YM-PIN@ .` は 255 を返します。
   - `YM-READ` や `YM-BUS@` は内部で `YM-TO` を呼ぶので適用されます。
   - 対応案: 文書に「適用済みの event だけを反映」と追記する。
2. **filter の減衰を消さないことがテストされていない**（`src/tests/sound_test.zig:611-617`）: テストが確かめているのは、source=0 と、11ブロック後の PCM=0 だけです。停止で filter state を消す退行が入っても通ってしまいます。停止直後の最初のブロックに非0の標本があることを assert すると防げます。
   - 係数 0.9985 とレベ​ル 1/3 からの計算では、停止直後は約 -0.32 に跳ぶので非0になります（※推測です。実行して確かめていません）。
3. **RESET 直後の envelope が最大音量**: RESET 直後は step31/attack0/holding なので、R13 を書く前に envelope モードにすると level31（32767）が出ます。
   - 文書（`:34`）で宣言されていて、native とも一致しています。
   - ただし Python oracle も同じ規則を写しているので、共通の誤りとしては検出できません。「レジスタは全0なのに shape0 の終了状態（0）ではない」点を、宣言として明記しておくとよいと考えます。
4. **ベンチマークの計時実行の検証が部分的**（`verify-ym2149.py:182-185`）:
   - 全 PCM の照合は、warmup→reset の手順を通らない別プロセス（`YM-VERIFY`）で行っています。
   - 計時する方は、最後の 1024 byte の和と5つのスカラー値しか見ていません。
   - `YM-RESET` で初期化漏れがあっても見逃す可能性があります。計時実行の最後にも SNAP の37項目を比べると防げます。
5. **`YM-BUS@` の R14/15 経路を直接試すテストがない**: I/O の読出しは `YM-READ` でしか照合していません。テスト1行で補えます。
   - ついでに: `YM-STEP-LIMIT` に未使用のローカル `distance` があります（`ym2149.fs:41`）。

## ご指定の観点ごとの確認（問題なし）
- **まとめ進め・divider**: `DIV+clocks /MOD 8` で step は tick 8k（k≥1）に起きます。加算の overflow は CYCLE≡DIV (mod 8) なので起きません。slow 版と同じ境界で発火します。
- **noise の位相**: `(steps+1-half)/2` と上限 `2k-1+half` が、奇数番の step だけ数える規則と一致しています（half=0 と 1 の両方で手計算しました）。
- **period を短くした場合**: `1 MAX` で次の step に発火し、count は0に戻ります。slow 版と一致します。
- **全16 shape**: 0-3/9 は下降→0、4-7/15 は上昇→0、8/10/11/12/13/14 の繰返し・交互・保持を手で追いました。期待値の手書き表（`:94`）も正しいです。
- **mixer**: `(tone OR 無効)` AND `(noise OR 無効)` を `0<>` で論理値にしてから AND しているので正しいです。
- **32段の対応**: 固定0→0、固定L→2L+1、envelope→0..31。表は 184…32767 で、Decimal 計算と double 計算の両方で検算されます。
- **I/O**: `YM-PORT@` のスタックの動き（latch, mask）、`YM-PIN@` の output 時の `latch AND pins`、input 中の latch 更新は文書どおりです。
- **bus**: select は raw 1byte。上位 nibble が非0なら読出しは FF、data は無視。予定した data は適用時の select に従います。
- **queue**: 容量判定（未処理1024件）→順序判定→回収（`MOVE` は重なりがあっても安全）→追加、の順です。同じ tick は追加順です。
- **不正入力時の原子性**: すべての公開語が、状態を変える前に検査しています。RENDER 途中の overflow だけは、宣言どおり巻き戻しません。
- **native 修正**（`sound_psg.zig:174-175`）: YM の固定0だけ index0 になり、envelope level1（0.005623）は残ります。AY は `>>1` なので以前と変わりません。追加テスト（`:109-137`）は、2モデル×64 mixer×tone/noise×未使用の上位bit を網羅しています。ST-SOUND の初期無音テストは、修正前の値（約36 LSB の AC）を検出できる構成です。
- **ベンチマーク**: 6種類の負荷すべてで、32768 frame の全 PCM と37項目の状態を Python と照合してから計時しています。warmup と初期 queue は計時に含めず、8kHz の enqueue と回収は計時に含めています。比較として意味のある構成です（Low 4 の補強を推奨します）。
- **oracle**: 第三者のエミュレーターや ROM は使っていません。ただし Python は同じ宣言規則を独立に書いたもので、共通の読み違いは検出できません。これは文書（`:79`）に書かれているとおりです。
