## 1. 根拠と設計の境界

## 2. 所有と内部データ

所有ホストスレッドは一本である。登録、全対象の検査、入力decoderの進行、公開台帳の更新、RELEASE受理、返却確定をこのスレッドに直列化する。OSのI/O補助・描画スレッドとForth workerは存在し得るが、ホスト台帳や登録配列を書き換えない。既存ResourceTableも単一所有スレッドの契約である（`src/core/runtime_base.zig:70`〜`72`）。同じWakeの消費者を複数作らない。既存Wakeは単一消費者・複数生産者で、共有後の移動と利用中の破棄を禁じる（`src/host_wake.zig:1`〜`3`）。

共通登録を次の論理データで表す。これはForth ABIではない。

| データ | 内容と規則 |
|---|---|
| 登録ID | 所有者、再利用しない登録世代。解除済み登録への遅延通知を識別する |
| 対象記述 | 呼出し内の対象番号、kind、資源IDとその世代、要求条件。I/Oは読取・書込を別条件、描画はwindow世代と固定した目標番号を含む |
| 保持参照 | 検査済み対象の内部参照。外部IDが無効になっても解除まで内部実体を保持する |
| 通知先 | ホストの共通Wake。生産者は待機呼出しのスタックや返却配列を参照しない |
| 状態 | 準備中、登録中、解除中、解除済み。登録済み部分を記録して失敗時に戻す |
| 期限 | 呼出しの絶対期限Dと、次回の内部処理期限S。いずれも同一ClockのInstantで表す |
| 返却用記録 | 全対象の観測結果と、待機側中断、呼出し期限到来、ホスト障害を保持する領域 |

対象一覧と返却領域は登録開始前に容量を確保し、返却時に容量不足で成立条件を捨てない。同じ資源の重複指定は内部保持・監視を共有してよいが、返却は元の対象番号ごとに対応させる。上限超過・無効ID・別所有者・別種・能力不足は、全件の事前検査で拒否する。正常対象だけの部分待機にはしない。具体的な待機対象数・確保量は1369で有限上限として示し、追加128 MiBの全体予算へ算入する。台帳16件を待機対象数の上限へ読み替えない（資源ごとに上限を設ける要求：`docs/CORE_EXTENSION_DETAILED_DESIGN.md:845`、全体条件：`docs/TASK_CONTROL_USAGE_CONDITIONS.md:163`）。

## 3. 成立条件と返却

成立結果は先頭の対象一件だけでなく、照会巡回で成立を確認した対象番号の集合として返す。各要素は「対象番号・kind・検査済みの識別値・成立理由・補助情報」を持つ。内部表現は配列とし、公開表現は別判断とする。

| 対象 | 成立理由・補助情報 |
|---|---|
| 入力 | 意味上のイベントあり、EOF、入力障害。イベント本体は既存入力取得経路に保持し、この待機で消費しない |
| I/O | 読取可用、書込可用、EOF、障害、close。可用量は観測値であり後続操作の全量成功を予約しない |
| タスク | ホストが確定したsucceeded・failed・cancelled、または対象解放。結果を取得・消費せず終端と識別値を記録する |
| 時計 | 登録した絶対時刻への到達。呼出し全体のDへの到達とは別の対象番号で返せる |
| 描画 | 固定した目標番号以上のbackend描画完了、window close、対象世代失効、能力喪失。物理提示の完了とはしない |

集合と独立に、待機側中断印、D到来印、ホスト障害を返却記録へ残す。同時に観測された入力・終端・期限・中断を一つの理由に潰さない。単一の終了区分が必要な内部呼出し先では、障害→待機側中断→成立集合あり→D到来の順で選ぶが、集合と各印は保持する。公開値への写像は確定しない。

全対象の事前検査後、既に成立した条件はOS待機せず返す。Dが既に到来、または0待ちでも一度は全対象を照会し、成立集合と期限印を併記する。取消し要求があるだけのタスクは終端成立にしない。確定終端なら即時返却する契約は状態機械に従う（`docs/TASK_CONTROL_STATE_MACHINE.md:92`、`:97`〜`99`）。

返却集合は一巡の観測結果であり、異なるOS資源の同一瞬間のスナップショットではない。各対象の検査はその供給元のロックまたはacquire公開境界で行う。集合形成中に到来した後続条件は、検査で拾えば含め、検査後なら保持状態から次回取得する。返却したreadyは取得操作による予約ではない。

## 4. 登録から解除までの手順

### 4.1 準備と起床世代の観測

所有者・対象世代・能力・要求条件・容量を検査し、内部参照を保持する。この段階では意味上の入力や結果を消費しない。Clock.nowで開始時刻を取り、Dを一度だけ作る。負の待ち時間は無期限、加算の範囲超過は失敗とする既存Deadlineを使う（`src/core/runtime_base.zig:23`〜`35`）。

共通Wake以外の自動リセットのWake・イベントを複合待機の対象にすることを禁止する。file_wakeとpainted_eventも対象へ加えず、供給元から共通Wakeへ通知する経路を要追加とする（6.2節・6.5節）。共通Wakeの消費は本手順の所有ホストに一本化する。共通Wakeの世代gを**対象状態の照会より前**に観測する。既存observeはacquire loadである（`src/host_wake.zig:73`〜`74`）。既に稼働中の供給元が登録前に通知していても、次段の状態再確認で回収できるようにする。

### 4.2 対象の登録

供給元ごとにregister、非消費probe、unregisterの内部操作を設ける。registerは保持済み対象へ通知経路またはOS監視対象を接続し、接続が有効になった境界を返す。供給元の状態公開と接続が並行する場合は、同じロックで直列化するか、接続後probeと持続する状態で補う。登録成功時点から後の変更は共通Wakeまたは同時に待つOS対象で必ず観測可能にする。

途中失敗なら接続済み項目を逆順に解除し、実行中callbackの参照終了を確認して保持を戻す。既存readerを開始した場合も、それが資源本来の所有物なら待機解除だけを理由に破棄しない。呼出しが新規取得した登録用資源と、継続するI/O資源を分けて記録する。

### 4.3 条件の再確認

ホストへ届いた完了報告をacquireで受領し、状態機械の終端を確定する。待ち中取消し・キュー期限超過についても、ホストが原子的な取り出しに成功した項目の終端を、その巡の全対象probeより前に反映する。このホスト内の終端反映にnotifyは不要である（6.3節）。その後に全対象をprobeする。入力側は非待機のdecoder進行、I/O側は保持済みバイト・EOF・障害・可用性の照会、描画側は固定した世代・番号の照会を行う。途中の一件で打ち切らない。

その後、待機側取消し、所有者終了・RELEASE等の無効化、Clock.nowによる期限を採取する。成立集合、解除理由、中断、D到来があれば4.6へ進む。内部処理が残る、または巡回予算を使い切った場合はホストの処理巡回へ戻す。未処理を残したまま眠らない。

### 4.4 単一期限まで待機

眠る直前に世代を照合する。gから変化していれば眠らず4.5へ進む。変化がなければ共通待機へgと絶対期限を渡す。世代比較とOS待機の間に到来した通知もOS対象に残ることを必要条件とする。

OS待機の期限Eは、D、対象時計の最早期限、次フレーム・入力decoderの確定時刻、キュー滞留期限、取消し・回収処理の次回期限、通知障害回復用の巡回期限の最小値とする。無期限Dでも内部処理期限をなくさない。内部期限への到達は再巡回の理由であり、D到来を偽造しない。再起床のたびにDを現在時刻＋元の相対時間へ作り直さない。

既存WakeOps.wait_fnは一つのWakeを期限まで待てるが、任意の入力・I/OのOS対象を受け取れない（`src/core/runtime_base.zig:16`〜`20`、`src/host_wake.zig:125`〜`139`）。したがってホスト内部に、共通WakeとOS入力・I/O対象を同時に待つ多重待機操作を追加する。すべての供給元が共通Wakeへ橋渡し済みの場合だけ既存wait_fnを直接使える。

POSIX側は共通Wakeの読取端と入力・I/Oのfdを同じ待機集合へ入れる。通知消費には、①Wakeのパイプを一巡につき有限量だけ読み出す、②pending.swap(false, .acq_rel)を行う、③保存したgと世代を照合し直す、という順序を必須の不変条件とする（`src/host_wake.zig:148`〜`155`、`:129`）。別のfdの発火を契機にWakeのパイプを読み出した場合にも、この順序を守る。pendingをtrueのまま残すと、後続notifyが書込みを省略し、空のパイプで期限Eまで眠り得る（同`:104`）。読取りのINTRは再試行へ戻し、EOF・障害はホスト障害として扱い、そのまま眠らない。

Windows側は共通Wakeイベントと監視可能な入力・I/O対象を同時に待つ。ウィンドウのメッセージ処理は専用スレッドにあり、ホストの待機では汲み上げない（`src/host_window.zig:1290`、`:1727`〜`1729`）。描画完了・close・窓入力はロックで保護された状態を公開してから共通Wakeへnotifyする経路を要追加とする。既存painted_eventは自動リセットであり、既存frameWait向けの通知として残すが、複合待機には加えない（同`:528`、`:772`〜`782`、`:1786`〜`1790`）。既存I/O workerから共通Wakeへの通知接続も要追加であり、6.2節の起動時統合案を採る。非待機の子プロセス入力排出も巡回処理へ含める。native待機対象を取得・待機する操作はホスト内に閉じ、OSポインターをForthへ公開しない。Wake内部のOS対象を安全に借用する操作と上記の通知消費手順を追加する。別消費者で共通Wakeを排出する構成にはしない。

### 4.5 条件の再取得と再武装

notified・timeout・cancelledは再取得の契機であり、そのまま対象成立の答えにしない。既存Wakeの判定順は取消し→世代変化→期限であるため、単一Outcomeだけでは同時成立を表せない（`src/host_wake.zig:128`〜`134`）。

登録を保持したまま、まず新しいgを観測し、その後に4.3の全対象probeを行う。この順序を各再試行で繰り返す。再取得後にgだけ新しく取り直して直ちに眠ることは禁止する。probe直後の通知を新しいgへ吸収してしまうためである。無関係な通知・古いOS信号・restartだけなら再試行し、Dは維持する。

### 4.6 返却確定と解除

ホストが返却記録を封印した点を返却の境界とする。その直前までにホストが受理したRELEASEは対象解放として反映し、同じ対象の終端成立として返さない。封印後の外部操作は次の処理として扱う。他の対象の成立は保持する。

封印後は解除中へ移し、通知先を外し、進行中callbackの参照終了を同期してから登録参照を解放する。供給元ロックを持ったままcallback完了・worker終了を待たない。解除中に新しい状態が成立しても、供給元のキュー・終端・完了番号・EOF等に保持し、次回照会から取得できるようにする。解除は供給元状態やWake世代を初期化しない。

解除に失敗した場合は残る参照と対象を保持してホスト障害・回収未完了を記録する。解除成功と装わず、残るcallbackが参照するメモリを解放しない。

## 5. 取りこぼしを防ぐ条件と競合の論証

論証の前提は、供給元が状態を先に公開し、状態を取得するまで保持すること、probeが適切な同期を行うこと、登録後の変更が起床経路へ接続されること、消費者が単一であることである。既存Wakeも状態更新後のnotify・状態照会前のobserveを要求する（`src/host_wake.zig:1`〜`3`）。以下はこの前提を後続実装が満たす場合の設計上の論証であり、実機検証済みの証拠ではない。

| 成立・競合の位置 | 観測と処理 |
|---|---|
| 最初のg観測より前 | 世代差がなくても、保持状態を登録後probeが読む。既成立条件で眠らない |
| g観測後、対象登録より前 | 通知先がまだなくても保持状態がprobeで見つかる。登録前の瞬間的なパルスだけを供給元契約にしない |
| 登録直後、probe前 | probeで成立を読む。通知が併合されても答えは変わらない |
| probe後、OS登録前 | gとの差で即座に再取得するか、OS対象の残存信号が眠りを解除する。状態と通知の順序を逆にしない |
| OS待機中 | 共通Wakeまたは同時監視対象で復帰し、全対象を再取得する |
| 複数条件が同時成立 | 全対象を走査して集合へ入れる。OSが返した最初のハンドルや通知の回数で件数・対象を決めない |
| 取消しとD到来 | 最後の再取得で両印を残す。対象readyも保持する。対象タスクへCANCELを送らず、タスクの終端も変えない |
| タスクCANCELと正常完了 | 完了公開を受領して状態機械の終端を返す。要求印trueだけでcancelledを作らない（`docs/TASK_CONTROL_STATE_MACHINE.md:76`〜`81`） |
| 封印前のRELEASE | 対象解放として返す。workerの内部完了受領・回収は継続する |
| 封印後・解除中の成立 | 現返却集合へ遡って追加しない。状態を残し次回照会へ渡す。通知callbackは保持参照の同期解除後にのみ破棄する |
| 同じ通知の重複・併合 | 世代は変化の有無だけを示す。保持状態の全件probeで復元する。通知回数を仕事数とみなさない |
| 無関係通知の連続 | Dを延ばさず、上限付き巡回で時計・取消し・他対象へ進む。通知排出だけの無限ループを作らない |

POSIXの既存Wakeはpendingによって通知を併合する。新しい多重待機でも、パイプ読出し→pending.swap(false, .acq_rel)→保存世代との再照合の順序を必須とする。既存実装も読取後にpendingを戻し、次のループで世代を照合する（`src/host_wake.zig:103`〜`113`、`:145`〜`156`）。Windowsはauto-resetイベントであり、世代は別のatomic値として残る（同`:26`、`:34`〜`35`、`:98`〜`101`）。どちらもOS信号だけを消して条件確認を省くことは許されない。

別のホスト経路が自動リセットイベントを消費すると、probe不成立→供給元の通知→別経路の消費→複合待機がEまで眠る、という順序が生じ得る。既存fileWaitFilesもfile_wakeを待つ（`src/main.zig:1719`〜`1721`）。本設計は共通Wake以外の自動リセットオブジェクトを待機対象から除外し、この競合を避ける。既存fileWaitFilesのobserveは現在のソースでは1684行であり、probeより前に置かれている（同`:1683`〜`1685`）。

I/O可用性はOS側の事情で消える場合がある。これは通知の欠落とは分ける。到着済み入力はホスト所有キューへ保持し、EOF・障害・終端・描画番号は持続させる。書込可用のprobeは現在値を返し、後続WRITEの部分受付・再待機を許す。外部の別消費者が同じ入力を読む契約は本設計の保証対象外である。

通知のOS操作失敗と世代枯渇は正常な併合ではない。既存notifyは世代上限でResultOutOfRange、OS操作失敗でHostFailedになり得る（`src/host_wake.zig:93`〜`111`）。生産者は独立した障害ラッチと完了状態を保持し、ホストは有限の内部巡回期限で必ず再取得する。notify失敗を黙殺して無期限待機しない。枯渇時は通知基盤を障害扱いにし、利用中のWakeをリセット・周回・移動しない。置換は全利用者の停止・解除後に行う。

## 6. 供給元別の接続と追加実装

### 6.1 638：入力

既存のevent_input.readyはmodern(self, 0, true)で照会し、legacyでは取得した内容をpendingへ保持する（`src/core/event_input.zig:55`〜`68`）。standard.readのpeekは意味状態を確定せずに入力を保持するが、Ctrl+CのUserInterruptやEOFも持つ（`src/core/standard_event.zig:129`〜`159`）。modernのリダイレクト分岐はpeek引数を渡さずFileOps.event_waitを呼ぶため、この分岐を共通probeへそのまま流用しない（`src/core/event_input.zig:155`〜`164`）。

追加する入力adapterは、通常入力では既存decoderを所有ホストで非待機進行させ、イベント・EOF・障害・中断を区別して保持する。リダイレクト入力では639の非消費probeを使い、バイトを取得した場合は同じ入力源へ順序を保って戻す。ESC等の確定待ち時刻も内部期限として取得できる操作を追加する。既存decoderはESC開始から50 msの期限を作る（`src/core/standard_event.zig:164`〜`167`）。

WindowsコンソールはGetNumberOfConsoleInputEvents/ReadConsoleInputWでポーリングしており、入力通知を担う専用スレッドはない（`src/host_input.zig:534`〜`545`）。複合待機用probeでは、フォーカスやキー解放など、待機の成立に結び付かないレコードもOSからホスト所有の待ち行列へ移し、decoderで順序を保って処理する機能を要追加とする。意味上のイベントを消費することとは区別する。これらをOSに残すとコンソールハンドルのシグナル状態が続き、複合待機が空回りして管理1 ms/巡の制約を満たせなくなり得る。キュー容量・巡回予算に達した場合は未処理としてホストへ制御を戻し、OS待機へ進まない。

OS入力対象とホスト内の先読み・unread・pending・decoderを両方見る。窓入力・子入力はホスト所有キューへ排出し、キューの空→非空、EOF、障害、入力モード変更を共通起床へ接続する。供給元のcallback中に同じdecoderを再照会せず、必要なら後続巡回へ保留する。modern_depthの共有境界をworkerへ広げない（`docs/TASK_CONTROL_AUDIT_SHARED_STATE.md:564`〜`574`）。

### 6.2 639：I/O可用

既存FileOpsにはio_check、wait_files、read_available、write_available、event_waitがある（`src/core/host_interface.zig:55`〜`60`）。fileWaitFilesは全IDの事前検査後にreader/writerを準備し、writableProbe、保持バイト、stdinProbeByte/filePollByteと戻し処理でreadyを調べる（`src/main.zig:1660`〜`1671`、`:1685`〜`1708`）。そのprobe部分を内部adapterへ分離して再利用する。READ/WRITEによるデータ消費を待機条件の照会に使わない。

WindowsのreaderはioWakeが返すfile_wakeへ通知し、既稼働中のstartは別Wakeへの変更を拒否する（`src/main.zig:1222`〜`1224`、`:1304`、`src/host_file_reader.zig:50`〜`68`）。従って待機ごとに通知先を差し替えない。本書では「資源寿命を持つ共通Wakeへ起動時に接続する案」を推奨し、採用する。共通Wakeをreader等の初回起動より前に確保し、ioWakeと既存I/O待機経路の通知先・消費手順を統合する変更が要追加である。稼働済みreaderのstartへ別Wakeを渡して移行しない。移行が必要な資源は、既存利用者の停止・参照終了と保持データの保全を確認してから再接続する。「既存file_wakeを多重待機へ加える案」は採らない。通知世代と消費者を一本化でき、別経路による自動リセットイベントの消費を追跡する必要をなくせるためである。具体的な起動・移行と既存待機との統合は1369の追加実装とする。

POSIXでは既存fileWaitFilesのfd/POLL.IN・OUTの構築を同時待機へ移す（`src/main.zig:1723`〜`1725`）。ホストのstdio先読み・decoder保留もprobeする。EOF・障害・closeはready解除理由として保持する。既存のWindows queue・POSIX pollと先読みの記録は`docs/ASYNC_IO_IMPLEMENTATION.md:7`〜`9`にある。

### 6.3 タスク終端

workerは完了領域を封印しrelease公開して共通Wakeへ通知する。ホストはacquire受領し、内部ID・所属を検査して一度だけ台帳へ終端を確定する（`docs/TASK_CONTROL_STATE_MACHINE.md:73`〜`79`）。probeは確定終端と外部有効性を読む。workerのnotifyだけをsucceededとしない。

待ち中の取消しは、ホストとworkerが原子的に取り出しを競い、ホストが取得した場合に未実行の終端を一度だけ確定する（`docs/TASK_CONTROL_STATE_MACHINE.md:67`）。キュー期限超過も排他的な取得と終端公開が必要であり、具体的な終端表現は1366で定める（同`:71`）。これらのホスト側終端はnotifyなしで、その巡の全対象probeより前に台帳へ反映する。WAIT自身のD到来では対象タスクを終端にしない。

1366の完了領域へホスト共通Wakeの接続を追加し、1369で完了排出→終端確定→全対象probeを結合する。RELEASE済み内部タスクの完了も排出し、外部ID無効を理由に報告を捨てない。WAITは結果を消費しない。台帳そのものをworkerのcallbackへ渡さない。

### 6.4 単調時計・取消し・信号

Clock.now、Deadline.expired、remainingMillisecondsを再利用する（`src/core/runtime_base.zig:6`〜`47`）。同じRuntimeの時計に統一し、OS待機へ変換するときだけ残時間を丸める。偽時計でも同じ手順を注入できるようにする。個別時計対象の絶対期限を保持し、最早期限をEへ反映する。

待機側取消しは対象タスク固有のCancellationと別に用意する。Cancellation.requestは印をrelease storeするだけであり、単独ではOSを起こさない（`src/core/runtime_base.zig:52`〜`59`、`src/host_wake.zig:132`〜`134`）。必ず要求公開→共通notifyの経路を追加する。Runtime全体の終了は既存beginShutdownの印→notifyを利用できる（`src/host_runtime.zig:71`〜`75`）。Runtime.waitはRuntime自身のトークンを固定使用するため、待機固有トークンも扱うadapterが必要である（同`:56`〜`59`）。

host_waitは信号・端末状態の復旧経路を使うが、そのwaitWithRuntimeを複合待機の代用品にしない。現行loopは最大20 msのSleep/nanosleepであり、waitUsingは入れ子を拒否する（`src/host_wait.zig:330`〜`367`）。既存Wakeも最大20 msで取消しを再検査するだけである（`src/host_wake.zig:132`〜`139`）。この値から10 ms条件の達成を主張しない。POSIXの現行ハンドラーは中断印を立てるだけである（`src/host_wait.zig:108`〜`111`）。ハンドラーからWake.notifyを呼ぶことの非同期シグナル安全性は未確認であり、直接呼び出さない。1369でハンドラーに許す処理は、非同期シグナル安全性を確認した印の設定と、事前に用意した非待機セルフパイプへの書込みだけとする。セルフパイプを多重待機へ接続し、通常のホスト巡回で印を受領して必要な共通通知を行う経路が要追加である。有限の内部期限も維持し、信号所有を一つのscopeで管理する。復旧失敗は隠さず、既存の復旧優先順を維持する（`src/host_wait.zig:363`〜`367`）。

WAIT自身のD、キューの滞留期限、取消し要求から停止までの期限、回収期限、フレーム期限は別々に保持する。キュー期限はG1 50 ms、G2/T1 100 ms、I1 200 msであり、遷移は1366の担当である（`docs/TASK_CONTROL_STATE_MACHINE.md:71`）。WAITのtimeoutによってキュー期限超過や停止完了を作らない。

### 6.5 1043：能力のあるbackendの描画完了

既存windowWaitはLinux・macOS・Windowsへ分岐する（`src/host_window.zig:122`〜`127`）。Windows frameWaitは開始時のframes_shownを目標に取り、frames_paintedとwindow有無を調べるが、描画と同じロックの取得時間を含む（同`:774`〜`798`）。Linuxはsharedの番号を参照して1 msごとに再照会する（`src/host_window_linux.zig:163`〜`177`）。macOSはreadChildInputを進め、PAINTEDから番号を更新して待つ（`src/host_window_macos.zig:585`〜`603`）。これらは共通登録の実装ではない。

1370では能力照会、window寿命世代、登録時に固定する目標番号、非待機完了照会、完了・close・能力喪失の通知接続を追加する。後続SHOWの番号へ目標を追随させない。後の画像が目標以上の番号として描画済みなら目標達成とする。古いwindowを閉じて再表示しても、新しいwindowの番号で古い登録を成立させない。

Windowsは完了番号更新とcloseの公開後に共通通知を行い、描画を長く占有するロックから、短い状態照会・登録用の同期境界を分離する。Linuxもsharedの更新に通知を接続する。macOSは子のPAINTEDを読むI/O自体を共通待機・巡回へ接続し、待っているホスト自身が入力を排出しないために止まる循環を作らない。

未対応backend、窓なし、存在しない目標は登録時に識別して拒否する。登録後closeは対象解放、能力喪失は能力喪失として解除する。最小化は描画完了にせず、再描画またはDまで待つ。能力のないbackendでタイマーを描画完了として返さない。実提示とbackend描画完了は別である（`docs/CORE_EXTENSION_DETAILED_DESIGN.md:549`）。

## 7. 逐次の既存待機で代用できない理由

WAIT-FILESは最初に見つかったI/O対象で戻り、その内部ではI/O用のWakeまたはfdだけを待つ（`src/main.zig:1685`〜`1725`）。WINDOW-PAINT-WAITの操作口はkind・msからboolを返す形で、明示的な登録対象番号・解除操作を持たない（`src/core/host_interface.zig:332`〜`338`）。描画待ちにはキーやCtrl+Cで止まらない既存契約もある（`docs/CORE_EXTENSION_DETAILED_DESIGN.md:552`）。

したがってWAIT-FILES→描画待ち→タスク待ちの順に呼ぶと、先の待機中に成立した別条件へ即応できない。各呼出しに元の相対時間を渡すと総期限も延びる。0待ちで順にprobeする部分は利用できるが、すべて未成立の後は一つのOS待機集合とEへ移す必要がある。これは詳細計画の逐次呼出し不可の要求に対応する（`docs/TASK_CONTROL_DETAILED_PLAN.md:274`〜`280`）。

## 8. 対象の寿命と回収

登録の保持参照を得てから解除完了まで、対象実体・通知先・token・登録記録を解放しない。公開IDにはepoch/serialと所有者・種別の検査を使い、slot位置だけを保存しない（`src/core/runtime_base.zig:63`〜`68`、`:97`〜`108`）。I/O等の既存整数IDには登録adapter側で寿命世代とpinを追加し、close後に同じslotへ別対象が入っても追随しない。

close/RELEASEはまず外部有効性を失効させ、対象解放を公開して起床し、登録参照が外れてから物理解放する。ホストが自分の待機解除を必要とする対象を同期closeして永久待機しない。close要求を処理し、待機解除と参照消滅を進めて回収する。

タスクのRELEASE後に新規WAITを出した場合は無効IDとして無副作用で拒否する。既存登録は対象解放で解除するが、実行中のVM・完了領域・Snapshot等は別の実行側参照で保持する（`docs/TASK_CONTROL_STATE_MACHINE.md:94`、`:105`〜`115`）。待機解除を停止・join・結果コピーの完了とみなさない。既存removeもpayloadを停止・破棄する操作ではない（`src/core/runtime_base.zig:71`、`:110`〜`116`）。

所有者終了は新規登録を止め、すべての登録を解除し、callback参照終了後に通知先を破棄する。workerやreaderが通知先を借用中なら先に停止・joinまたは同等の参照消滅を確認する。停止不能・解除失敗では対象と通知先を保持し、回収未完了を診断する。要求から100 ms経過したことだけで保持メモリを解放しない（`docs/TASK_CONTROL_STATE_MACHINE.md:119`〜`127`）。
