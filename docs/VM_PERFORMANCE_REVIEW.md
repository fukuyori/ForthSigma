# VM速度改善計画のレビュー結果と採否

2026-11-15。利用者の依頼により、実測を基に[改善計画](VM_PERFORMANCE_PLAN.md)を作成した後、Claude CodeとAntigravity（agy）へ設計レビューを依頼し、Gforth固定版も参照して計画を改訂した。今回の成果は**計画・レビュー・判断の文書**であり、速度改善を実装した結果ではない。

## 結論

推奨は「測定の揺らぎと生成コードを確認し、Runningの値渡し・局所保持を小さな独立実験で検証する」。外側への無条件の書戻しは不要と判断し、当初案から外した。ヘルパー境界で一時状態を使う場合は、成功時だけでなくエラー時も正しい状態を反映する設計が必要になる。agyの提言で、例外用ヘルパーの過剰な展開を抑えるA2も、生成コードに根拠がある場合の別候補に加えた。

halted検査の移動は、停止状態が変化する全境界と生成コードの根拠を示せる場合だけの別案とする。案Bの境界退出・再開も、Aが改善しないという理由だけで進めず、改めて詳細設計とレビューを行う。VM全体の複製、機能削除、JIT、アセンブラーへ範囲を広げない。

## 依頼・実施したレビュー

- 実施：Claude Code CLI、モデル指定sonnet、実行時表示`claude-sonnet-5-5`。
- 初回対象：改訂前のVM_PERFORMANCE_PLAN.md、forth.zigのCATCH・実行ループ、CatchContextと復元処理、CATCHテストの名前など。全テスト本体・生の測定値・イメージ処理まで読んだレビューではない。
- 制限：safe-mode・restricted、許可ツールをRead/Grep/Globに限定。初回の実際のツール使用はRead/Grepの10回で、コマンド実行・編集はなかった。
- [初回報告の原文](VM_PERFORMANCE_CLAUDE_REVIEW.md)を保存し、下表で採否を分けた。初回報告が改訂後の全内容を確認したとは扱わない。
- 改訂案を限定的に再確認し、[再確認報告の原文](VM_PERFORMANCE_CLAUDE_FOLLOWUP.md)も保存。Read/Grep計5回、同じモデル・読取り専用制限で終了した。再確認の結論は「重大な残存問題は見つからず、条件付きで安全な実験計画として成立」。実装の正しさや速度改善の保証ではない。
- 入力文書のスナップショット・ハッシュ・JSONLは`.work/vm-performance-review-20261115/`。共有用の判断と報告はdocsへ保存した。

## 初回指摘の採否

| 指摘 | 判断 | 計画への反映・根拠 |
| --- | --- | --- |
| A-1：全退出で外側Runningへ書き戻す必要性 | 一部採用 | 外側は例外時にresumeCatchで保存フレームから全体を上書きし、正常終了・QUIT・StepLimitではRunningを再使用しない。値渡し・ループ内保持へ変更。ヘルパーが外側の古いポインターを使い続けないことを必須化 |
| A-1：書戻しdeferが復元済み状態を必ず壊す | その断定は不採用 | 現行ではループ関数の退出処理が終了してから外側のcatch節とresumeCatchへ進む。不要な書戻しを除く理由と、deferの実際の寿命は別に扱う |
| A-2：ローカル化だけでは最適化が変わらない可能性 | 採用 | 仮説のまま維持。アドレスが逃げる境界を逆アセンブルで調べる。一時コピー案は独立実験とし、エラー時の反映漏れも検査 |
| A-3：halted検査移動を先に試す | 条件付きで候補化 | 直前版にもwhile (!self.halted)がある。新設された検査とは扱わず、全副作用境界を保証できる時だけ別実験。無条件でAより安い・速いとは認めない |
| A-4：Bの引渡し条件が不足 | 採用 | WATCHのran、deferred CATCHのcall_depth補正、抑制状態とhanded、再入のentry_frames/entry_catches、countedイベント順を必須設計項目に追加。遷移を偽のRuntimeErrorで表さない |
| A-5：CATCH関連のテスト不足 | 一部採用 | 既存P09aにCATCH-NOBT/FAST-THROW/NOTHROWと抑制状態、catch_testにcounted切替の深いCATCH回復があることを確認。重複追加せず、BYEと容量不足、実際の診断イベント、再入などの組合せを補う計画へ変更 |
| A-6：CATCH専用の性能測定がない | 採用 | 通常成功、入れ子、動的CATCH、THROW/FAST-THROWを採否前に別々に測る。専用カーネルの追加は現時点で未実施 |
| A-7：差分時間の基準が曖昧 | 採用 | 「現在版とf1140c7直前」の差と明記。現在版・直後版・保存済み旧版を区別し、80%回復は参考値に限定 |
| A-7：3%判定の前にA/Aが必要 | 採用 | 項目別の観測揺らぎδ_iと独立2系列を定義。δ_iが2%を超える項目は測り直し。信頼区間を算出したとは主張しない |
| B節：旧版にはframesがなかった | 不採用・訂正 | 00d234bのreturnToCallerもself.framesを使用する。f1140c7は既存の呼出し枠へCATCH継続を統合した変更であり、frames自体を初めて追加したものではない |

採否の確認は現在のsrc/forth.zig、src/core/words_system.zig、src/tests/catch_test.zig、src/tests/p09a_test.zigと、ローカルに展開した00d234bのソースに基づく。原文の「他ファイルでの有無は未確認」を、「既存テストが存在しない」という事実へ置き換えない。

## 判定基準の整理

以下は今後の実験に使う暫定値で、達成した性能ではない。

| 項目 | 改訂後の判断 |
| --- | --- |
| 小規模なA/A0 | 整数演算とLOOPを各10%以上短縮し、それぞれ2δ_iも超える。初案15%から緩和する代わりに、サイズ・意味・他項目は緩めない |
| より大きいB | 各15%以上短縮を維持。根拠と詳細設計の別レビューが必要 |
| 他の通常カーネル | max(3%, 2δ_i)超の時間増を独立2系列で再確認し、両方で超えれば不採用 |
| CATCH専用カーネル | 正常成功・入れ子・動的CATCHは時間増5%以内、THROW/FAST-THROWは10%以内。同じ2系列で確認 |
| 測定の安定性 | 同一実行体A/Aで項目別δ_iを測り、2%超なら反復・環境を見直す。異なるCPUやビルド条件を再現性の根拠に混ぜない |
| サイズとメモリー | Windows/Linux通常版の実行体増加各1%以内。State・CallFrame・スタック容量・ヒープ割当てを増やさず、ループ命令数も記録 |
| 80%回復 | 参考目標として残す。別の反復数や版の絶対時間を合否に用いない |

Claude Codeはmax(3%,2δ)を提案した。こちらで揺らぎ2%の上限を加え、測定が不安定なほど許容悪化を広げる運用を防いだ。同一ソースの独立ビルドの再現性もハッシュで記録するが、同一バイナリーのA/Aだけで異なるコード配置の影響を校正できたとは扱わない。

## 改訂案の再確認結果

再確認では、外側への通常の書戻しが不要であること、deferの寿命についての訂正、A0の条件付け、Bの偽エラー回避・状態引渡し条件が妥当とされた。初回報告の誤りもそのまま残さず、原文と採否で明示している。

条件付きの指摘は4点で、すべて実装時・測定時の確認事項へ反映した。

1. 外側Runningを読む開始時TRACE、CATCH復帰後WATCHと、それ以外の全参照を実装時に検索する。開始値と復元値を使い分ける。
2. failed_pcはループ内の正しいローカルから、命令取得後に進んだPCという既存の意味で記録する。
3. 同一ソースの再ビルドサイズ・ハッシュを照合し、非countedループの命令数・バイト数も記録する。実行体全体の1%上限は維持する。
4. CATCH専用カーネルでもδ_iを個別に測り、通常カーネルの揺らぎを代用しない。

再確認も、旧版ソース・テスト本体・生成コード・実測結果の全面検証ではない。最後の追記は上記条件を明文化したもので、性能測定を追加したものではない。

## Antigravity（agy）レビューの採否

agy CLI 1.5.9へ、現行の計画・Claudeの採否・Gforth参照調査を読取り専用でレビューするよう依頼した。[報告本文](VM_PERFORMANCE_AGY_REVIEW.md)を保存。実際の履歴はread_file計14回・13ファイルでSUCCESS。モデル名は結果に明示されていない。計画、測定JSONの一部、Sigmaの実行ループ・CATCH・関連テスト、Gforthの参照範囲を読んだ。コマンド実行、ビルド、テスト、編集のツール呼出しはなかった。アプリケーションソースのハッシュも照合した。

CLIではplan指定とslash展開禁止の併用に対する警告があったため、plan強制のレビューとは記録しない。実際のpermission_modeはrequest-reviewで、読取り範囲は依頼文、実際のツール履歴とソースハッシュで確認した。CLIログ・入力スナップショット・監査結果は`.work/agy-vm-performance-review-20261115/`に保存した。

| 指摘・提言 | 採否 | 反映した内容 |
| --- | --- | --- |
| P1：CATCH成功用0の容量不足で復元状態を失う危険 | 採用 | 一時Runningを用いる追加実験では、returnToCallerが呼出し元を復元し継続を消費した後にpush(0)で失敗する経路を明記。failed_pc記録前の反映を必須化。外側CATCHありに加え、外側なしでのバックトレースを追加検証候補にした |
| P2：外側の例外復帰と内側のBYE復帰の接続 | 採用 | 外側resumeCatchは次の値渡し入力へ、内側resumeCatchはループ内ローカルへ反映する。ポインター引数を両経路で維持する最小変更方針を追記 |
| P3：BYEで単純にreturnしてはいけない | 採用 | entry_catchesまで各CATCH継続を解除し0を積む既存動作へ合流する。途中の容量不足も扱う。通常の命令を再開するという意味ではないことも明記 |
| P4：項目ごとの速度差からH2を重視 | 一部採用 | インライン展開・分岐配置・状態の生存区間を調査項目へ追加。ただし項目差だけでH1を否定できるとはしない |
| H1a：pc/end_pcのスカラー化 | 既存案を具体化 | 既存のA・一時Running案の生成コード確認へ対応付けた。SROAやレジスター保持が実際に改善するとは未断定 |
| H2a：例外ヘルパーの非インライン化・cold配置 | 条件付き採用 | A2を追加。過剰な展開を確認した場合だけ、一つずつ試す。coldヒントはnoinlineの保証ではなく、汎用ヘルパーを常にまれな経路と扱わない。calls・CATCH速度とサイズで判定 |
| フォーマッター中のBYE／再THROW・抑制状態 | 採用 | 既存テストと照合した上で不足する組合せを検証候補へ追加。既存の復元処理を勝手に変更しない |
| A/Aのδの分母を固定する | 採用 | 100×中央値の絶対差÷小さい方の中央値を各系列で計算し、2系列の最大とする。候補の改善・悪化は現在版を分母とする |
| 片方だけ大きく改善した時の閾値緩和 | 一部採用 | 部分改善を保存・報告して別の採否判断に回す。通常の合格条件（両方各10%、Bは各15%）は自動的に緩めない。callsも主要観察項目とした |
| 配置による変動と処理コストを分ける | 採用 | 第0段階の生成コード・サイズ・独立測定で切り分ける。命令数だけで配置効果を特定したとはしない |

原文の「直後版比で+59.0%」という表現は基準が曖昧なので、根拠データの区間に従う。整数演算の+59.0%は直前→直後、直前→現在は+61.2%、直後→現在は約+1.4%。原文の「計10ファイル」は実履歴の13ファイル・14読取りとは一致しないため、ここでは監査値を使う。

## Gforth参照の反映

[参照調査](GFORTH_VM_REFERENCE.md)は固定コミットc479e1eのengine/engine.c、engine/threaded.h、primの例外プリミティブ、except.fsを根拠にした。agyも指定範囲を読み、参照の区別を妥当と評価した。速度比較に使ったGforth 1.0.2と同じビルドだとは扱わない。

採るのは、通常実行の局所状態と例外境界の責任を明確にする設計上の材料。採らないのは、生のリターンスタックへの例外フレーム埋込み、TOS/SP/FPの全面キャッシュ、computed goto、機械語方式の移植、GPLコードの転用。SigmaのFAST-THROWの安全な0処理など、参照プリミティブと異なる既存の条件も維持する。A2を含めた効果は仮説であり、Gforthとの差を何倍改善できるという約束はしない。

今回のagy指摘反映後の追記全体を、もう一度外部レビューしたとは主張しない。新候補の実装と生成コード・ベンチマークは未実施で、今後の検証条件を具体化した段階である。

## 実施したこと・残ること

実施済みは実測根拠の保存、初期計画の作成、Claude Codeレビュー、指摘のソース照合と計画への反映、改訂案の再確認、Gforth参照調査、agyレビューと指摘反映。新しい生成コード調査、A/A校正、A/A0/A2/Bの試作、改善後の速度・サイズ測定は未実施。両レビュアーともコマンドやテストを実行していない。

実装を進める場合は、改訂計画の第0段階から開始する。CATCHのホスト再帰回避、容量境界後の回復、デバッグ・保存互換を維持できない候補は、速度にかかわらず採用しない。今回の検討で実装コード・ビルド設定・版番号・tqueの変更はない。
