## 2. 状態と独立した管理情報

初期版の計算タスクでは次の状態を定める。既存案のcreated・runnable/queued・running・waitingを出発点とするが、createdは内部だけとし、waitingはタスクの実行状態として公開しない（元の案：`docs/TASK_CONTROL_DETAILED_PLAN.md:215`〜`217`、`docs/CORE_EXTENSION_DETAILED_DESIGN.md:785`）。WAITは呼出し側の待機登録であり、対象タスクをwaitingへ変えない。

| 内部状態 | 意味 | 有効な外部ハンドルからの公開状態 |
|---|---|---|
| created（作成） | 入力コピー・検査・台帳とキューの予約を準備中 | 公開しない。SUBMITはまだ成功していない |
| queued（投入済み） | 投入を受理し、実行側への引渡しを待つ | 投入済み |
| running（実行中） | 実行側が仕事を取得し、開始前検査・実行・完了データの封印を担当する | 実行中 |
| succeeded（成功） | 正常帰還と必要な結果コピーの成功を実行結果として確定した | 成功 |
| failed（失敗） | 取消し以外の実行失敗を実行結果として確定した | 失敗 |
| cancelled（取消し） | ホストが未実行の待ち項目を排他的に取り出した、または実行側が取消し専用結果で帰還したことを確定した | 取消し |

終端はsucceeded・failed・cancelledである。RELEASE後の「無効ハンドル」、回収中、回収済み、停止不能は、この列の追加終端ではない。終端状態と物理的な停止・回収完了は分ける。

状態とは独立して次を保持する。

- `cancel_requested`：ワーカーと共有するタスク固有の原子的な取消しトークンに置き、ホスト側の台帳にはその写しを持つ。workerは台帳の写しを読まない。現行Cancellationと同じく要求はrelease store、確認はacquire loadとする（`src/core/runtime_base.zig:52`〜`60`）。falseからtrueへのラッチだけを許し、実行中に解除しない。Runtime全体の終了印と混用しない（所有分離の根拠：`docs/TASK_CONTROL_DETAILED_PLAN.md:174`〜`175`）。
- 外部ハンドルの有効性、所有者、内部タスク識別子、Snapshot版、入力・結果・診断の所有参照。
- キュー・実行側・完了領域・待機登録・コピー中処理が保持する内部参照、および停止確認と回収進捗。
- 封印した実行結果と、その受領済み印。要求印や通知回数から実行結果を作らない。

初期版では同一ハンドル値の複製を独立した外部所有参照とは扱わない。RELEASEはそのIDへの以後の外部操作を全て無効にする。複数の外部所有参照を作る操作は本書では導入しない。内部待機参照や実行側参照は別に管理する。

## 3. 状態遷移と終端確定

| 遷移前 | 事象・成立条件 | 遷移後 | 必須処理 |
|---|---|---|---|
| 未作成 | SUBMIT開始 | created | 入力を所有コピーし、入口・Snapshot・許可条件を検査する |
| created | 台帳登録とキュー登録が共に成立 | queued | 一つの受理境界で公開する。成立後だけハンドルを返す |
| created | 検査・確保・登録の失敗、所有者終了 | 公開なしで破棄 | 部分取得を戻し、呼出し側の入力所有を変えない。公開タスクの失敗終端を生成しない |
| queued | 実行側が取得 | running | ホストの取り出しと排他的な原子的取得でキュー参照を実行側参照へ引き渡す。既に要求済みなら入口の実行前に確認する |
| queued | CANCEL、RELEASE、所有者終了によりホストが待ち項目の取り出しに成功 | cancelled | 要求をラッチし、未実行の取消し内容を封印して一度だけ確定する。入力・Snapshotの当該参照を解放する |
| running | CANCEL、未終端のRELEASE、所有者終了（ワーカー受取りが先行した場合を含む） | 同じ状態 | 原子的な要求印を立て、必要な起床を行う。ここでは終端を生成しない |
| running | 正常帰還・必要な結果コピー成功 | succeeded | 封印した成功報告を所有ホストが受理し、一度だけ確定する |
| running | 取消し専用結果 | cancelled | 封印した取消し報告を所有ホストが受理し、一度だけ確定する |
| running | その他の実行エラー | failed | 封印した失敗報告を所有ホストが受理し、一度だけ確定する |
| 終端 | CANCEL、RELEASE、重複完了通知、回収 | 同じ終端 | 結果を別の終端へ変更しない。外部有効性・回収進捗だけを更新する |

queuedでは、ホストの取り出しとワーカーの受取りを原子的に取り合い、一方だけが所有を取得する。ホストが勝てば、一度も実行していないことが確定するため、要求印だけで実行結果を置き換えることなくcancelledにできる。次のメイン処理巡回、かつ要求から10 ms以内に終端を公開し、実行開始を待たずに入力・Snapshotの当該参照を解放する。待ち中の所有者終了・RELEASEも同じ経路を使う。ワーカーが勝てばrunningの要求処理と実際の帰還結果に従う。取り出した事実の確認・終端確定・参照解放を省いて、単にキューから消しただけで処理済みとしてはならない（[利用条件5節・10節問5](TASK_CONTROL_USAGE_CONDITIONS.md#5-native処理量と取消しの案)、[判断記録問7・問9](CORE_EXTENSION_DESIGN_DECISIONS.md#利用者の決定2026-11-24)）。

現行`runtime_base.zig`にはタスクキューとTaskManagerの実装はなく、上記の取得競合・終端公開は後続実装への仕様である。CancellationとResourceTableの既存契約を、キュー実装済みの証拠として扱わない。

待ち期限超過の具体的な遷移と、期限切れまたは再投入可能な失敗としての終端表現は1366へ渡す必須事項である。利用条件3節・10節問2に従い、G1は50 ms、G2・T1は100 ms、I1は200 msの最大滞留を適用し、黙って待ち続けさせない。ワーカー受取りとの排他的な取得、期限の保持・判定・公開方法も1366で具体化する。WAIT自身の期限とは別であり、公開状態・診断から期限超過を識別可能にする（[利用条件3節](TASK_CONTROL_USAGE_CONDITIONS.md#3-利用例別の条件案)）。

実行側が取得したタスクの終端確定の手順を次のように定める。ホストが取り出した未実行タスクも、内容の封印を可視化と通知より先に行い、ホストで一度だけ確定する。

1. 実行側はVMからの帰還結果を保持し、結果・診断を所有バッファへ移す。成功として必要なコピーや出力検査に失敗した場合は、成功を公開する前に失敗報告を作る。
2. 完了データを不変として封印した後に、共有完了領域の公開印をrelease storeする。所有ホストは公開印のacquire loadで公開を確認してから内容を読む。起床通知は公開より後に行う。この順序は本書で定め、1366へ保留しない。取消しトークンの印とは別であり、現行Cancellationのrelease/acquireは取消し要求の同期であって完了データの公開実装ではない（`src/core/runtime_base.zig:52`〜`60`）。通知だけを完了の証拠としない。既存計画も公開後の起床を求めている（`docs/TASK_CONTROL_DETAILED_PLAN.md:177`〜`179`、`:223`）。
3. 所有ホストが内部識別子と報告の所属を検査し、未終端の場合だけ状態・結果・診断を一体として確定する。workerはResourceTableを直接更新しない（`src/core/runtime_base.zig:70`、`docs/TASK_CONTROL_DETAILED_PLAN.md:169`）。
4. 正常帰還なら成功、取消し専用結果なら取消し、それ以外なら失敗とする。確定時に要求印がtrueでも、正常帰還を取消しへ変更しない。確認前に正常帰還すれば成功となる。
5. 確定後の再報告・再通知で結果を上書きしない。同一内容の再通知は再照会の契機だけとし、矛盾する完了報告は内部不整合として診断する。

実行中の失敗と取消しの優先は要求時刻の比較では決めない。実行境界から返された唯一の結果で決める。既に別エラーで帰還した後の要求は失敗を変えない。取消し帰還後の後始末エラーは回収診断として保持し、取消し終端を変更しない。実行中に複数エラーが生じる場合の主診断・副診断の選択は1365へ渡す（引継ぎ根拠：`docs/TASK_CONTROL_METHOD_DECISION.md:121`）。

## 4. 状態別の操作契約

以下は所有者・種別・世代の検査を通った操作の意味である。検査失敗は状態に関係なく拒否し、副作用を起こさない。SUBMITは既存IDを対象としない作成操作であり、既存タスクの再投入操作ではない。

| 操作 | created（内部のみ） | queued | running | 終端 |
|---|---|---|---|---|
| SUBMIT | 準備を継続する。二重受理しない | 既存タスクの再投入は不可 | 同左 | 同左。再実行は新規SUBMITとする |
| STATE | 外部から到達不可 | 投入済み・要求印を非消費で返す | 実行中・要求印を非消費で返す | 確定状態・要求印・結果量等を非消費で返す |
| CANCEL | 外部から到達不可 | 要求をラッチしホストの取り出しで取消しを確定する。受取りに負けた場合はrunningの契約に従う | 要求をラッチし起床する | 終端済みとして受理し、状態・要求印・結果を変えない |
| WAIT | 外部から到達不可 | 終端待機を登録する | 終端待機を登録する | 確定終端を直ちに返す |
| RESULT | 外部から到達不可 | 未完了を返す。コピーしない | 未完了を返す。コピーしない | 取得可能な結果をコピーする。失敗・取消しでは終端種別と診断を区別し、成功結果と混同しない |
| RELEASE | 準備の中止は内部ロールバックで行う | 外部IDを無効化し要求を立てる。ホストが取り出せば取消し確定と当該参照解放、受取りに負ければ実行側参照を保持する | 外部IDを無効化し要求を立て、実行側参照を残す | 外部IDを無効化する。終端は不変であり、参照がなく回収条件を満たした後だけ破棄する |
| 所有者終了 | 未公開部分を戻す | 新規投入を止め、外部IDを無効化する。ホストの取り出しによる取消し・回収を行い、受取りに負ければrunningの契約に従う | 新規投入を止め、外部ID無効化・要求・回収を担当する。停止確認まで責任を維持する | 終端を変えず、待機・結果・所有資源を回収する |

取消し要求の再送は冪等とする。CANCEL成功は要求を受け付けた意味であり、停止完了を意味しない。RELEASE後の同じIDによる再RELEASEは古いIDとして拒否する。

WAITの期限到来は呼出し側の待機結果であり、タスクを失敗・取消しにしない。待機側の中断も対象のCANCELとは別である。複合待機・UI応答を含む登録方式は1368以降へ渡す（既存契約：`docs/CORE_EXTENSION_DETAILED_DESIGN.md:792`、`docs/TASK_CONTROL_DETAILED_PLAN.md:348`）。

RESULTは非消費とし、有効なハンドルで再取得可能とする。呼出し側バッファ不足では必要量を返し、部分結果を確定コピーした扱いにせず、保存結果を残す。RESULTの呼出し失敗でタスク終端を失敗へ変更しない。内部の結果バッファ上限超過とは区別する（出発点：`docs/TASK_CONTROL_DETAILED_PLAN.md:222`、`docs/CORE_EXTENSION_DETAILED_DESIGN.md:793`）。

## 5. RELEASE・所有者終了・停止不能

### 5.1 外部無効化と内部寿命

RELEASEの受理境界で以後の外部操作を拒否する。同じホストスレッドで処理する外部操作は前後に直列化し、workerによる完了報告だけを内部経路で受け付ける。ホストスレッドは1本であるため、この時点で残るWAITはブロックしない待機または複合待機の登録だけである。既に登録されたWAITには「対象の外部参照が解放された」旨を返して登録を解除する。これを対象タスクの取消し終端とは扱わない。先にWAITが終端を受け取った場合、その返却結果は変えない。

既に開始した結果コピーには完了まで内部参照を持たせる。RELEASE後の新しいRESULTは拒否するが、進行中コピーの元バッファを破棄しない。複数スレッドからの外部APIを将来許す場合も、この受理境界と参照保護を維持する必要がある。

実行中RELEASEは、外部ハンドルを無効化してもTaskRecord・VM・Snapshot・入力・取消しトークン・完了領域を破棄しない。停止、必要な結果・診断の所有コピー、待機解除、所有資源の後始末、進行中コピーの完了を確認するまで実行側と回収側の参照を保持する。切離し操作や、所有者のない実行を残す契約は設けない（利用者決定：`docs/TASK_CONTROL_METHOD_DECISION.md:187`）。

外部参照がなくなった結果も、まず完了報告として安全に所有し、終端と回収診断を管理側が受領する。その後、結果コピー中・待機・実行・完了受領の内部参照がなくなった時点で結果を破棄できる。RELEASEを理由にworkerが書込み中の結果領域を即時破棄しない。Snapshotはタスクの参照だけを外し、他タスク等の参照が残る版を破棄しない。

ResourceTableのremoveはpayloadを返してメタデータを除去するだけであり、payloadの停止・破棄機能ではない（`src/core/runtime_base.zig:110`〜`116`）。既存契約は利用者を止めてからのメタデータ除去を要求する（同`:71`）。したがって実行中RELEASEでは、まず外部有効性の印で拒否を開始し、内部回収記録を残す。removeだけで実行中資源を失わない。公開スロットと内部回収台帳の具体構造は1364で定める。内部回収台帳の記録も同じ台帳16件に数え、別枠として増やさない（[利用条件4節・10節問3](TASK_CONTROL_USAGE_CONDITIONS.md#4-同時実行とメモリ予算案)）。

### 5.2 所有者終了の責任

所有者は、新規受理を停止し、未公開createdを戻し、未終端の受理済みタスクへ要求を送り、外部IDを無効化する。既にRELEASE済みでも内部実行が残るタスクを回収対象へ含める。所有者の可視ハンドル一覧だけを走査して終わらない。

完了報告の排出、待機登録の解除、停止の確認、結果・診断コピー、joinまたは同等の実行参照消滅の確認、資源解放までを所有者の責任とする。共有worker方式ならタスク終了とworkerスレッド終了を区別する。具体的なjoin単位は1366・1374で定める。台帳・完了処理が必要なロックを持ったままjoinしない（既存の終了設計：`docs/CORE_EXTENSION_DETAILED_DESIGN.md:834`〜`843`）。

### 5.3 停止不能

取消し要求や期限超過だけで停止済み・取消し終端・回収成功にしない。実行側が取得済みで帰還結果が届いていなければ未終端のままである。ホストが排他的に取り出した未実行タスクの取消しは3節に従う。終端報告後に回収が止まった場合も終端は不変であり、回収未完了を別途示す。

参照され得るStorage・State・Snapshot・台帳・トークン・完了領域等を保持し、所有者、内部ID、要求の有無、最後の状態、停止未確認箇所、保持資源、回収の試行と失敗を診断する。停止不能な仕事を残したまま上限枠を無条件に再利用しない。強制スレッド終了、切離し、保持対象の先行解放で回収成功にしない。最終ホスト終了の独立資源の後始末・期限・OS終了経路は1375へ渡す。要求→停止10 ms、要求→回収100 msを超えた場合は「停止不能・上限超過」として診断し、期限経過だけで停止したとはみなさない。停止不能のVMがworker 1枠を占有している間は、新しい実行を拒否する。台帳16件には実行中・待ち・未回収の終端・RELEASE済みでまだ実行中の内部記録をすべて数える。超過時の扱いの根拠は[利用条件5節](TASK_CONTROL_USAGE_CONDITIONS.md#5-native処理量と取消しの案)、枠と件数の根拠は[同4節・10節問3](TASK_CONTROL_USAGE_CONDITIONS.md#4-同時実行とメモリ予算案)である。有限時間停止は未保証である（`docs/TASK_CONTROL_DETAILED_PLAN.md:243`〜`245`、`docs/CORE_EXTENSION_DETAILED_DESIGN.md:835`、`:843`）。

決定済みの利用条件は台帳16件、全体待ち4件、worker 1、追加メモリ128 MiB、確認点のないnative 64 KiB/回以下、要求→停止10 ms以内、要求→回収100 ms以内である。内訳と費用・応答条件は[利用条件3〜7節・10節](TASK_CONTROL_USAGE_CONDITIONS.md#10-利用者の回答2026-11-24)および[判断記録問9](CORE_EXTENSION_DESIGN_DECISIONS.md#利用者の決定2026-11-24)を引く。値は2026-11-24の利用者決定であり、達成保証・受け入れ合格ではない。64 KiBなら一定時間内に必ず終わるという保証でもない（利用条件5節）。

## 6. ハンドル検査とエラーの分類

現行Handleは`epoch: u64`と`serial: u64`である。epochは台帳の世代を表し、単なるプロセス番号ではない。スロットごとのgenerationフィールドがある実装として説明してはならない（`src/core/runtime_base.zig:63`〜`66`）。

task操作はResourceTableを`kind = .task`で照会する。現行の検査順はepoch不一致またはserial=0の拒否、同じserialの探索、種別検査、所有者検査である。削除済みserialは見つからずInvalidHandleになる（`src/core/runtime_base.zig:97`〜`108`）。本書で追加する外部有効性の検査も操作前に行い、RELEASE後のIDで要求・照会・待機・回収を操作できないようにする。

serialは最大値を発行すると次を0として枯渇させ、周回しない。満杯はResourceFullである。epochとowner IDはホストがプロセス内で再利用せず割り当てる契約である（`src/core/runtime_base.zig:64`、`:85`〜`95`）。Snapshot辞書版の世代と、ハンドルのepoch/serialは別の寿命検査である。辞書版の失効で実行中タスクのハンドルや保持版を勝手に破棄しない（`docs/TASK_CONTROL_DETAILED_PLAN.md:205`〜`209`）。

| 論理的なエラー種別 | 発生条件・効果 | 現行基盤との関係 |
|---|---|---|
| 台帳満杯 | タスク・保持中回収記録の枠不足。SUBMITを不受理とし、部分取得を戻す | ResourceFullがある。キュー満杯へまとめない（`src/core/runtime_base.zig:95`） |
| キュー満杯 | 受理キューの枠不足。SUBMITを不受理とする | ResourceTableにはキューがない。1366で別原因として扱う |
| 停止不能による実行拒否 | 停止不能のVMがworker 1枠を占有しているため、新しい実行を拒否する。台帳満杯・待ち満杯とは別原因とする | ResourceTableだけでは判定できない。利用条件4節・10節問3に従い、保持VMを帳簿外にして代替VMを作らない |
| バッファ不足 | 入力等の所有領域の不足、実行中の結果・診断上限超過、RESULTの宛先容量不足 | フェーズと必要量を分ける。未受理、実行失敗、再取得可能な操作エラーを混同しない |
| 世代・識別子枯渇 | serial・epoch・owner等を再利用なしで発行できない | IdentityExhausted。満杯とは別であり、周回による救済をしない（`src/core/runtime_base.zig:68`、`:87`〜`91`） |
| 別種ID | 有効な別種資源のIDをtask操作へ渡す | WrongKind。種別情報が既に失効したIDまで別種と断定しない（`src/core/runtime_base.zig:101`） |
| 古いID・無効ID | 世代違い、serial=0、削除済み、RELEASE済み | InvalidHandleまたは外部有効性検査による拒否。新しいタスクに適用しない |
| 別所有者 | 有効なtask IDでも呼出し側ownerが一致しない | WrongOwner（`src/core/runtime_base.zig:102`） |
| 未完了・不正な操作 | 終端前RESULT、既存IDの再投入等 | 操作結果として区別し、既存タスクの状態を変更しない |
| 投入条件・実行の失敗 | 旧Snapshotの新規投入拒否、禁止入口、開始失敗、実行エラー等 | 受理前の拒否と受理後のfailedを区別する |

複数条件が重なる場合、現行のハンドル検査順を保つ。SUBMITの資源検査順・主原因の報告順は1364〜1366で定めるが、各原因を識別できる診断を残す。失敗したinsertはpayloadの所有権を取得しない契約であり、準備側が部分取得を回収する（`src/core/runtime_base.zig:72`）。

公開エラー値・状態の数値・診断形式は未確定である。内部TaskCancelled、取消し終端、通常THROW、WAITの期限到来、RELEASEによる待機解除は別の意味である。試作の**-282を公開値として確定しない**（`docs/TASK_CONTROL_METHOD_DECISION.md:133`、`:189`〜`190`、`docs/CORE_EXTENSION_DESIGN_DECISIONS.md:50`）。

## 7. 競合時の最終状態

下表の「帰還」は結果コピー等を含めた封印対象の実行結果を表す。「内部終端」はRELEASE後も回収側が保持する確定状態である。CANCELとRELEASEの呼出し順だけで終端を選ばない。

| 競合 | 再現する順序・条件 | 最終的な内部終端・観測 |
|---|---|---|
| 完了と取消し | 正常帰還→要求→終端確定、または成功確定→要求 | succeeded。要求で成功を変えない |
| 完了と取消し | 要求→確認前に正常帰還 | succeeded。要求印trueと成功は両立する |
| 完了と取消し | 要求→安全境界で確認→専用取消し帰還 | cancelled。正常帰還はこの経路では報告しない |
| 失敗と取消し | 他エラー帰還→要求、または要求→確認せず他エラー帰還 | failed。要求時刻でエラーを取消しに変えない |
| 失敗と取消し | 要求確認→取消し帰還→後始末失敗 | cancelledと回収診断。終端は不変 |
| 完了とRELEASE | 成功確定→RELEASE | succeededのまま外部ID無効。回収条件成立後に破棄 |
| 完了とRELEASE | 正常帰還→RELEASE→成功確定 | succeeded。外部ID無効でも内部報告を受領する |
| 完了とRELEASE | RELEASE→要求確認前に正常帰還 | succeeded。外部ID無効、結果受領と回収は必要 |
| 完了とRELEASE | RELEASE→要求確認→取消し帰還 | cancelled。外部ID無効、停止確認前には解放しない |
| 失敗とRELEASE | RELEASEと他エラー帰還が前後する | failed。外部ID無効、診断と回収責任は残る |
| 取消しとRELEASE | CANCEL→RELEASE | ホストが待ち項目を取り出した場合はcancelled。実行側取得済みなら帰還が取消しでcancelled、正常でsucceeded、他エラーでfailed。外部ID無効 |
| 取消しとRELEASE | RELEASE→同じIDでCANCEL | CANCELは古いIDとして拒否。RELEASE自身の要求は維持する。ホスト取り出し成功ならcancelled、実行側取得済みなら帰還に応じて確定 |
| 取消し確定とRELEASE | cancelled確定→RELEASE | cancelledのまま外部ID無効 |
| ホストの取り出しによる取消し 対 ワーカーの受取り | queuedの項目を排他的に原子的取得する | 勝つのは一方だけである。ホストが勝てばcancelled、ワーカーが勝てばrunningとして実行結果に従う |
| 待ち中のRELEASEとワーカーの受取り（T08） | RELEASE後にワーカーが受取りを試みる | ホストの取り出しが先ならcancelledで受取り不可。ワーカー取得が先なら要求を入口で確認し、その帰還結果に従う。いずれも外部IDは無効 |
| 待ち中の所有者終了 | queuedで終了処理が取り出しを試みる | ホストが勝てばcancelledと当該参照解放。ワーカーが勝てば要求を送り、実行結果の受領と回収まで担当する |
| 実行中の所有者終了 | runningで要求・外部ID無効化 | 帰還に応じた終端を確定する。停止不能なら未終端のまま保持し診断する |
| RELEASE後のWAIT・STATE・RESULT | RELEASE受理後に同じIDで発行 | すべて古いIDとして無副作用で拒否する。内部終端や保持結果を変更しない |
| WAITと終端 | 登録前後に終端確定・通知 | 再照会で確定終端を返す。通知の取りこぼしで永久待機しない |
| WAITとRELEASE | 終端返却より前にRELEASE受理 | 待機は対象解放で解除する。内部終端は3節のホスト取り出しまたは実行結果で確定する |
| RESULTとRELEASE | コピー開始→RELEASE | コピー元を保持して開始済みコピーを完了する。以後の取得は古いIDとして拒否 |
| 所有者終了と完了 | 終了処理中に完了報告 | 帰還に応じた終端を受理し、終了処理が回収まで担当する |
| 所有者終了とRELEASE | いずれが先でも内部参照と回収責任を引き継ぐ | 内部回収対象を失わない。待ち中ならホスト取り出しでcancelled、実行側取得済みなら終端は帰還に従う |
| 停止不能とRELEASE・終了 | 要求後も帰還しない | 終端を新造しない。未終端・停止未確認として保持し診断する |
| 重複完了通知と取消し | 終端確定後に両方が到着 | 最初に確定した終端・結果を維持する |
