# 案Aの単独実験と採否（2026-11-15）

## 結果

**案Aは2通り試し、どちらも不採用とした。** 値渡しだけの版では、整数演算・LOOPで狙ったメモリー参照が減らなかった。ヘルパーとの境界に一時Runningを置く版では参照を減らせたが、実時間は整数演算で約5.5〜6.0%、LOOPで約28.4〜33.2%増えた。

境界コピー版では呼出しとCATCH専用カーネルに短縮があったが、通常カーネルの悪化と「整数演算・LOOP各10%以上短縮」の条件を満たさない。条件を緩めて採用していない。src/forth.zigは実験前の実バイト列へ戻し、追加した回帰テスト4件を残した。

対象はtque 121配下の755〜763。[計画](VM_PERFORMANCE_PLAN.md)、[調査](VM_PERFORMANCE_INVESTIGATION.md)、[CATCHの境界調査](VM_CATCH_COST_AND_BOUNDARIES.md)に基づく実験である。CATCHの名前領域コピー、停止検査、インライン指定、VM命令や保存形式は変更していない。

## 試した変更

### 値渡し版（value）

runOperationsLoopにRunningを値で渡し、ループ内の変数を正とした。returnToCaller、builtinInLoop、wordInLoop、local_execute、BYEのresumeCatchは、そのローカルを参照する。外側のドライバーはエラー時に保存済みCATCHフレームから次の入力を復元するため、通常退出時の書戻しは設けない。

Windowsの既存テストとfreestanding確認はビルド上成功扱いとなった（候補段階のキャッシュ利用と版の記録上の制限は回帰検証節を参照）。しかし生成コードはPC・終端PCをローカルのスタックから毎命令読み、PCを書き戻していた。整数演算とLOOPの命令数・参照数も基準と同じだった。2千万反復・5回・独立2系列の予備測定で、整数演算・LOOP各10%短縮は得られなかった。この版は最終判定候補にしなかった。

値渡し版の予備測定全8項目は次のとおり。正は所要時間増加、負は短縮。

| カーネル | 系列1 | 系列2 |
| --- | ---: | ---: |
| 整数演算 | +0.74% | -0.65% |
| スタック操作 | -8.66% | -9.69% |
| 呼出し | +0.77% | +1.23% |
| 定数・変数 | -9.89% | -7.37% |
| LOOP | +1.60% | -0.63% |
| +LOOP | -0.69% | -0.72% |
| シフト・ビット演算 | -1.63% | -2.58% |
| 浮動小数点 | -0.11% | -0.22% |

スタック操作・定数／変数に部分的な短縮があった。ただし、値渡し版は最終条件（1億反復・7回）とCATCH専用項目では未測定である。スタック操作はCallgrindの命令・参照計数が基準と同じでも所要時間が約9%異なり、同一実行体のA/A校正だけでは別ビルド間の差を説明できない。部分短縮をRunning保持方式そのものの効果と断定しない。

### 境界コピー版（boundary）

計画にある追加実験として、wordInLoop／builtinInLoopを呼ぶ7箇所だけ、ブロック内に一時Runningを作成した。ブロックのdeferで通常・エラーの両方をループ内Runningへ反映する。エラー時の反映は関数側errdeferのfailed_pc記録より先になる。inlineのreturnToCallerや、実際にループ内へ展開されるresumeCatchには不要なコピーを加えなかった。

この版ではPC・終端PCがレジスターに保持され、対象のメモリー参照は減った。予備測定で悪化が見られたため改善を宣言せず、通常8項目とCATCH専用9項目を計画の最終条件で対比較して採否を決めた。

両版の実装差分とソースハッシュは[生データ](measurements/2026-11-15-vm-a-experiment.json)に保存した。ローカルには`.work/vm-a-experiment/value.patch`、`boundary.patch`、`forth-a-value.zig`、`forth-a-boundary.zig`と各実行体を残した。

## 比較条件の固定

基準ソースは、実験前に保存したsrc/forth.zigと、実際の作業ツリーの入力ファイルを別ディレクトリへ複製して作成した。git archiveによる改行変換を比較条件へ混ぜていない。VERSIONと埋込み資源も実バイト列を維持し、入力ハッシュを記録した。

Windows側Zig 0.17.0、fast、baseline CPU、stripを統一し、Windowsはx86_64-windows-gnu、Linuxはx86_64-linux-muslへビルドした。再ビルドしたLinux基準版のSHA-256は既存の校正用HEADと同じ`93e1eefb8a8ed198ab1bd8355d3fd944426992527e1e80d534aef1a63adebd99`だった。

時間測定はWSLのCPU0固定で、基準・候補を交互に起動した。通常カーネルは1億反復、ウォームアップ1回除外後7回、独立したベンチマーク起動で2系列。2系列目は初期順を反転した。起動・コンパイルを除いた子プロセスCPU時間を使用し、チェックサムは全試行で一致した。ビルド・テスト・Callgrindは時間測定と同時実行していない。

## 回帰検証

- PowerShellでWindowsの通常・debug無効・float無効・最小構成のzig build testは成功扱いとなった。ただし、候補段階の保存ログ（windows-debug-test.log等）ではcoreテストが新規実行され、hostテスト・freestandingコンパイル・sigma実行はキャッシュヒットだった。通常構成の新規実行分は1,005成功・5スキップ。ログ単体には試作ソースのハッシュがなく、値渡し／境界コピーのどちらで取得したかを独立に同定できない。キャッシュ元の実行ログもここでは照合していない。復元後の通常構成は全テストを新規実行し、1,064成功・10スキップだった。機能無効化に伴うスキップはログへ残した。
- WindowsでLinux向けDebug／fastのテストをクロスコンパイルし、各2実行体をWSLで直接実行した。両最適化ともcoreは1,005成功・5スキップ、hostは63成功・1スキップ。WindowsのビルドランナーがLinuxバイナリを直接実行できず返す終了コード1と、WSL上でのテスト成功を区別して記録した。WSLのZig 0.14.1は使っていない。
- Windows／Linuxのfast／Debug計4実行体でverify-runtime.pyが各13件、verify-p10.pyが各37件成功した。深いCATCH、容量後の回復、保存・追加読込み・SAVESYS等を含む。
- 4実行体で、容量不足とBYEの8ケースおよびWATCH・TRACE・PROFILEを基準の挙動と照合し、計44比較が一致した。
- Windows／Linuxそれぞれで、基準が保存したイメージを候補が読み、候補のイメージを基準が読む双方向比較を行った。先行定義を置いた追加読込み、SAVESYSで作った両実行体も確認し、計16比較が一致した。

追加した回帰テストは次の4件である。

1. CATCH成功用0の容量不足：通常／BYE、外側CATCH有無、counted／非countedの8組合せ。外側CATCHなしの4組合せかつdebug有効時に、failed_pcとバックトレースのPCの意味を分けて検査する。全8組合せでスタック結果・haltedと各深さを検査する。
2. ホスト出力コールバックからexecuteWordで再入し、内側のCATCH回復後に外側のCATCH・locals・フレーム・counted状態が保持されること。
3. WATCH中のCATCH回復で、変更の順序とBAD／RUNの呼出し位置が維持されること。変更は!の次のループ先頭で検出されるため、失敗した命令自身による変更を外側ドライバーの回復後検査で検出する経路は対象外。
4. DBGでCATCH回復後の最終スタックとCATCH／呼出し深さ、および出力にCATCH・42が含まれること。回復後の呼出し元でステップ表示が再開したことまでは区別しない。

境界コピーのエラー時の反映がfailed_pc記録に先行することはdefer／errdeferとコードの読取りに基づく。現在のヘルパーにはRunning変更後にエラーを返す経路がなく、この反映を省いた版との差を追加テストで実証したものではない。Callgrindの計数は上表の4項目だけで、+LOOP・シフト／ビット演算などは未計数である。

macOS実機検証や、人が操作するステップ画面の受入確認は今回行っていない。

## 最終判断と残したもの

正しさの検証とサイズ条件は通ったが、通常VMの性能条件に明確に反したため、両試作を不採用とした。実験差分を保存した後、src/forth.zigを実験前のバイト列へ戻した。追加した回帰テストを含め、復元後もWindowsの4構成とfreestanding、WSLのDebug／fastのcore・hostテストが成功した。復元後のWindows通常は1,064成功・10スキップ、WSLは両最適化ともcore 1,005成功・5スキップ、host 63成功・1スキップだった。

この結果は、CATCH変更前後にPC参照が増えたという観測を取り消すものではない。一方、今回の保持方法でその参照を除いても高速化できず、参照回数だけで過去の所要時間増加全体を説明する根拠にはならなかった。

案A2、A0、BやCATCHの名前コピー削減へ、自動的に作業範囲を広げていない。実装・検証・採否判断の記録を完了し、性能改善を達成したとは判定しない。版番号変更、パッケージ作成、コミット・タグ・プッシュは行っていない。
