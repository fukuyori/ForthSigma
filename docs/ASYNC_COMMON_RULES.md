## 1. 時計

### 現状

- `UTIME ( -- d )` と `NTIME ( -- d )` は実時刻で、時刻の変更で飛ぶ。
- 単調時計は、調べた範囲でホストの内部に4つある。`monotonicMilliseconds`（`src/main.zig`。Windowsは `GetTickCount64`、ほかは `CLOCK_MONOTONIC`。ミリ秒）、`host_wait.zig` の `now`（Windowsは `QueryPerformanceCounter`。ナノ秒）、`host_audio.zig` の `monotonicNanoseconds`、`host_evdev.zig` の `milliseconds`。macOSのウィンドウにも `monotonicNs` がある。語としては公開していない。失敗したときの動作はそろっていない（`now` はエラーを返し、`monotonicMilliseconds` は0を返す）。
- `FRAME ( ms -- )` は `UTIME` を使い、待つ時間をミリ秒に切り捨てる（`src/graphics/graphics.fs`）。
- Gforthの `deadline ( d -- )` は、1970年からのナノ秒で表した絶対の時刻まで待つ。時計は `ntime`（実時刻）である。調べた名前（`monotonic`、`mtime`、`clock-gettime`）では、Gforthに単調時計を読む語は見つからなかった。ほかの名前であるかは調べていない。

### 案

- **単調時計を読む語を1つ足す。** 起点は決めない（起動ごとに違ってよい）。値は減らない（続けて読んで同じ値が返ることはある）。時刻の変更に影響されない。単位はナノ秒とするが、ナノ秒の分解能は保証しない。ホストの実装は `host_wait.zig` の `now` にそろえる。内部の時計を1つにまとめるかは、失敗したときの動作と、音のスレッドから呼ぶ場合の扱いを決めてから判断する。
- **値は1セルとする。** セルは64ビットなので、ナノ秒で約292年を表せる。`NTIME` は2セルだが、単調時計は差を取る使い方が中心で、1セルのほうがForthの側の計算が軽い。一周は考えない。
- **絶対の時刻まで待つ語を1つ足す。** 単調時計の値を受け取り、その時刻まで待つ。すでに過ぎていればすぐ戻る。フレームの周期は、アプリが「次の時刻」に周期を足して進める。端数（60 Hzの約16.67 ms）は、アプリが周期を分数で持って積み上げる。
- **名前はSigma独自とする。** 調べた範囲で、Gforthに同じ働きの語が見つからなかったためである。候補：`MONOTONIC-NS ( -- n )`、`WAIT-UNTIL-NS ( n -- )`。
- **`FRAME` の意味は変えない。** 新しい語の上に、周期をナノ秒で受け取る語をForthで足すかは、項目12の後で決める。

### 保証すること

- 待機は、ふつうに終わったときは、指定した時刻より前には戻らない。中断とエラーでは、前に戻る。
- 未決：負の値の期限、時刻に周期を足したときのあふれ、OSが休止している間に時計が進むか。
- 戻るのがどれだけ遅れるかは保証しない。OSのスケジューリングによる。Windowsの `Sleep` はミリ秒の単位で、`NS` はいまも正の待機をミリ秒に切り上げている。

## 2. 待機

### 現状

| 待機 | 期限 | 中断の受け方 | 戻り方 |
|---|---|---|---|
| `NS` | 単調時計の1つの期限。20 msごとに区切って待つ | 待つ間だけ信号のハンドラーを置き、端末の信号を有効にする | 中断は -28 を `THROW` |
| `MS` | Windowsは `Sleep`、ほかは `nanosleep`（信号で切れたら、残りの時間を待ち直す） | ハンドラーを置かない。中断に気づかない | — |
| `EKEY` | 最初の1バイトは期限なし。ESCの続きは全体で50 ms。UTF-8の続きは期限なし | 読んだ値3を -28 に変える | イベント。終端は終端の値 |
| `PLAY`、`SOUND`（キューの空きを待つ） | 期限なし | ホストの `audio_wait_fn` が、信号か、読んだ入力のCtrl+Cを知らせる | 中断は -28 を `THROW`。`PLAY` は入れた音符を取り消す |
| `KEY`、行入力 | 期限なし | 端末の行入力に戻すので、信号で届く | — |

`NS` の正の待機は、プロセスの中で同時に1つだけである（入れ子は `HostFailed`）。0以下の待機は入口で戻る。

### 案

**適用する範囲**

この節と3節の取り決めは、今回足す待機の語（`EKEY-WAIT`、`WAIT-FILES`、書込みの空きの待機、絶対の時刻まで待つ語、PCMの空きの待機）に適用する。既存の語の動作は変えない。既存の語のうち、取り決めと違うものは次のとおりである。

| 既存の語 | 取り決めとの違い | 扱い |
|---|---|---|
| `MS` | 中断に気づかない | 変えない。変えるなら、動作の変更として別に決める |
| `SHOW`（ウィンドウの作成待ち） | キーを先読みせず、Ctrl+Cですぐにはやめない。最大5秒の期限で終わる（#909の契約） | 変えない |
| `KEY`、行入力 | 期限なし | 変えない |
| `READ-FILE` などの同期のファイル操作 | 期限なし、中断の確認なし | 変えない |
| Tclのプログラムの応答待ち | 今回は読んでいない | 変えない |
| `PLAY`、`SOUND` | 空きができるまで待つ | 変えない |

**期限**

- 1回の呼出しに、単調時計の期限を1つだけ持つ。途中で何かを受け取っても、期限は延ばさない。
- 時間を受け取る語の引数は、相対のミリ秒とする（`EKEY-WAIT`、`WAIT-FILES`）。0は待たない。負の数は期限なしとする。
- ミリ秒より細かい周期が要る用途は、1節の「絶対の時刻まで待つ語」を使う。

**結果の区別**

待機する語の結果は、次の4つを区別できるようにする。

| 結果 | 伝え方 |
|---|---|
| 得られた | 値と、真のフラグ |
| 期限が来た | 偽のフラグ。エラーにしない |
| 終端・切断 | フラグか専用の値。エラーにしない |
| OSのエラー | ior（0でない値）。`THROW` しない |

- **中断（Ctrl+C）は -28 の `THROW` とする。** iorでは返さない。いまの `NS`、`EKEY`、`PLAY` と同じである。
- **ホストに機能がないときは `HostUnavailable`（-21）、実行の基盤が失敗したときは `HostFailed`（-265）** を `THROW` する。いまの `NS` と同じである。
- **iorと `THROW` の境目は、失敗が起きた場所ではなく、失敗の種類で決める。** 操作の対象について、ふつうに起きる失敗はiorで返す（ファイルがない、相手が閉じた、権限がない、子プロセスを起動できない）。機能がない、時計が読めない、端末の設定を戻せないといった、アプリが対処できない失敗は `THROW` する。
- **既存の語の戻り方は変えない。** `EKEY` は終端を専用の値で返し、ホストの読取りの失敗は `HostFailed` になる。`KEY-IOR` はホストの失敗をiorに変える。この表は、今回足す、iorを返す語に適用する。
- 未決：語ごとの具体的なスタック効果、1回の呼出しで複数の結果が重なったときの優先の順（例：読めるデータがあり、期限も過ぎている）。

**途中まで進んだ待機**

- 期限か中断で戻るとき、読んだ途中のバイト（ESCの列、UTF-8の列）は保留して、次の呼出しへ持ち越す。捨てない。
- 入力を待つ語が待っている間に読んだほかの入力（`INKEY` のキー、物理キー、マウス）は、それぞれのキューに残す。
- いまの音の待機（`graphics_input.readPending`）は、キューに空きがある範囲で残す。コアのキーのキューが満杯なら、新しいキーを捨てる。ウィンドウの確定した文字は、UTF-8の全部のバイトが入らなければ、その文字を捨てる。満杯でも読み続けるのは、Ctrl+Cとマウスを読むためである。
- 端末の文字を捨てない（4節の種類A）なら、満杯のときに読むのをやめても中断に気づける仕組みが要る。いまの `readPending` を使うだけでは両立しない。この仕組みは未決である。

**書く側**

- **書く語は待たない形を基本とする。** 書けた数を返す（部分書込み）。満杯は、書けた数が0で、エラーではない。相手が閉じた場合（切断）は、満杯と区別して返す。一部を書いた後にエラーが起きたときは、書けた数とiorの両方を返す。
- 空きの待機から戻った後でも、書けた数が0や一部になることがある。アプリは、書けた数を見て繰り返す。
- **空きを待つのは、別の待機の語で行う。** 読む側の「読める分だけ読む語」と「待機の語」の組と同じ形になる。項目3（子プロセスへの書込み）、項目9（PCM）がこれに従う。
- いまの `PLAY` と `SOUND` は変えない（空きができるまで待ち、中断で -28）。

**入れ子と同時の待機**

- 待機は入れ子にしない。Forthを実行するスレッドは1つなので、同時に待つ語は1つである。
- 信号のハンドラーと端末の設定を変える待機は、`NS` と同じ入口（`host_wait.zig`）を通す。ハンドラーを置く場所を1つにする。いまは、音の待機が3 msの待機ごとに自分でハンドラーを置いて外している（`src/host_audio.zig` の `wait`）。
- 未決：数える実行（5節）の中で待機の語を呼んだときの、ハンドラーの保存と復元。

## 3. 中断

### 現状

Ctrl+Cの届き方は、端末の状態で変わる。次の表は、待機の語がハンドラーを置いていない間の、ふつうの動作である。

| 端末の状態 | Ctrl+Cの届き方 | 気づく場所 |
|---|---|---|
| 行入力（Raw modeでない） | 信号（Windowsはコンソールの制御ハンドラー） | ハンドラーを置いている間だけ。`NS` と音の待機が置く。それ以外では、信号の既定の処理でプログラムが終わる |
| Raw mode（`INKEY` や `EKEY` を使った後） | キーの値3 | 入力を読んだとき。読まなければ気づかない |
| ウィンドウ | ウィンドウのキーとして届く | `INKEY` などが読んだとき |

- Raw modeでも、`NS` の間は端末の信号を有効にするので、Ctrl+Cは信号で届く。
- すでにOSのバッファにある値3は、後から信号を有効にしても信号にはならない。

### 案

- **中断は -28 の `THROW` の1つの形にそろえる。** `CATCH` で受けられる。
- **今回足す待機の語は、どれも中断に気づく。** 既存の語は2節の表のとおりで、変えない。入力を読む待機は、読んだ値3で気づく。入力を読まない待機は、`NS` と同じ方法（待つ間だけ信号を有効にする）か、音の待機と同じ方法（区切りごとに入力をのぞく）を使う。気づくまでの遅れは20 msを目標とする（`NS` の区切りと同じ）。保証ではない。
- **計算の途中の中断は、数える実行の入口（5節）から実行したコードだけで起きる。** 通常の実行ループには確認を足さない（決定済み）。
- **中断は、待機をやめるだけとする。** キューにある入力、鳴っている音、開いている資源は変えない。後始末はアプリが `CATCH` で行う。いまの `PLAY` の「入れた音符を取り消す」は変えない。
- **貼り付けの間の値3は中断にしない**（項目2で決定済み）。貼り付けを見分けられる経路に限る。Windowsの初期版は貼り付けの印を出さないので、見分けられない。
- 未決：貼り付けの間の値3を残す案と、`NS` の方法（信号を有効にする）を同時に使うときの扱い。計算の間（5節）に信号のハンドラーを持つものと、待機の語が置くハンドラーとの関係。

## 4. キュー

### 現状

| キュー | 容量 | 満杯のとき |
|---|---|---|
| 端末の入力 | OSのバッファ | 読まなければOSに残る |
| ウィンドウのキーの押下（Windows） | 64 | 新しいものを捨てる。解放は状態の差から作る |
| ウィンドウのマウスのボタンとホイール（Windows） | 64 | 古いものを捨てる。移動は最新の位置だけを持つ |
| コアのキー（`graphics_input.zig`） | 64 | 新しいキーを捨てる。ウィンドウの確定した文字は、UTF-8の全部のバイトが入る場合だけ受け付ける |
| コアのマウスのイベント | 64 | 最も古いイベントを捨てて、新しいものを入れる |
| `KEY-HELD?` の保持 | 16 | 最も古いものを外す（#909で決定済み） |
| Tclからのイベント（`TCL-EVENT`） | 64 | 新しいイベントを捨てる。Tkのウィンドウのキーとマウスは、このキューを通らず、コアのキューへ届く |
| 音の声部ごとの音符 | 32 | `PLAY` が空きを待つ |
| 音のコマンド | 64 | `SOUND` などが空きを待つ |

ゲームパッドはキューではない。最大8台の状態を読むだけで、SDLの経路はイベントの通知を止めて状態を読み、静的なLinuxの経路はevdevの `ioctl` で状態を読む（`src/host_gamepad.zig`、`src/host_evdev.zig`）。読取りの間に終わった短い押下は取れない。

### 案

キューを4つの種類に分け、種類ごとに満杯のときの扱いを決める。

| 種類 | 例 | 満杯のとき |
|---|---|---|
| A 読まなければ元に残る入力 | 端末、パイプ、子プロセスの出力 | 読まない。OSの側に残し、相手を待たせる。捨てない |
| B1 元に残せず、状態を読み直せる入力 | 物理キー、マウスのボタン | 有界のキューに入れる。あふれたら捨て、あふれたことを知らせる。状態（押している・いない）は、状態の表から読み直せるようにする |
| B2 元に残せず、読み直せない入力 | ウィンドウの文字、ホイールの量 | 有界のキューに入れる。あふれたら捨てる。失ったものは戻らない |
| C まとめてよい入力 | マウスの移動、端末の大きさの変更 | 最新のものだけを持つ |
| D 出力 | PCM、音のコマンド、子プロセスへの書込み | 書く語は書けた分だけ書いて戻る。空きは待機の語で待つ（2節） |

- **「キーと文字は捨てない」（企画書と[項目2](ASYNC_CORE_PLAN.md)）は、種類Aについての約束とする。** これは今回の案で、項目2の文面（条件なしの「捨てない」）を限定することになる。採るなら、項目2の文書も同じ日に直す。
- **ウィンドウの入力は種類Bで、#909の契約に従う。** #909の次の点は引き継ぐ。文字はUnicodeのスカラーの単位で、全部のバイトを受け付けるか、全部を捨てる。Ctrl+Cは満杯でも失わないように、入力のキューと別に持つ。マウスのボタンの状態は、あふれた後も実際の状態に収束させる。#909は、種類Bの全部に「あふれたことを知らせる」ことを求めてはいない。知らせるのは、今回足す物理キーである。
- **ゲームパッドは、いまは状態を読むだけである。** イベントを足すなら種類B1とする。
- **物理キー（項目8）は種類Bとする。** イベントのキューは256個を候補とする（全部のキーの押下が一度に入る数）。あふれたら新しいものを捨て、「あふれた」印を立てる。印を読んで消す操作と、状態の表を読む操作の間に入った変化を取りこぼさない手順（印を消してから状態を読む、など）を、項目8の仕様で決める。
- **PCM（項目9）は種類Dとする。** リングの長さは、始める語で指定する。上限は1秒分を候補とする。
- **Windowsのパイプの読取りスレッド（項目3）は種類Aとする。** 受信のキューが満杯なら、スレッドは読むのをやめる。

## 5. 実行制御の仕様（項目7）

### 現状

- 数える実行ループは、デバッグ機能のビルドにだけある。どちらのループを使うかは、実行ループに入るときに決まる（`src/forth.zig` の `runOperations`）。
- 上限に達したときの `StepLimit` は、`CATCH` に渡さずに外へ返す。
- ネイティブの処理の中の反復は、256回ごとに1と数える（`checkWorkBlock`）。上限がないときは何もしない。中断の確認はしない。
- 予算は `step_limit` と `steps_left` の1組だけである。`in_counted` は設定と復元をしているが、どちらのループを使うかや予算の消費の判断には使っていない。各 `runOperations` は、終わるときに `catch_depth` を入口の値に戻す。

### 案

- **入口の語**：`EXEC-LIMITED ( i*x xt u -- j*x ior )`。xtを、数える実行ループで実行する。uは実行数の上限で、0は上限なし（中断の確認だけを行う）。
- **戻り方**：ふつうに終われば ior は0。上限に達したら、入口まで戻り、0でない ior を返す。スタックの深さは、`CATCH` が `THROW` を受けたときと同じ扱いにする（入口の深さに戻す。中身は決めない）。xtの中の `THROW` は、そのまま外へ伝える。
- **予算を区別する。** 入口ごとの予算と、コマンドラインの予算を別に持ち、どの予算が尽きたかを内部で見分ける。いまの `StepLimit` 1つを入口で受けるだけでは、`--max-steps` が尽きたときまで入口がiorに変えてしまう。
- **入れ子**：内側の実行は、外側のすべての入口の予算と、コマンドラインの予算からも引く。内側の予算が尽きたら、内側の入口へ戻る。外側の予算が先に尽きたら、内側の入口では止まらず、その外側の入口まで戻る（案。内側の入口で一度iorを返す形もあり、未決）。
- **入口へ戻るときに戻すもの**：データスタックの深さだけでは足りない。リターンスタック、浮動小数点スタック、呼出しのフレーム、ローカル変数、`catch_depth`、バックトレースを抑える状態を、`CATCH` が `THROW` を受けたときの処理（`src/forth.zig` の `enterCatch`）と照らして決める。
- **コマンドラインの `--max-steps`**：いまのまま、プログラムを終わらせる。入口の語の予算とは別に数える。
- **中断の確認**：数える実行ループが、一定の実行数ごとに確認する。間隔は、速度を測って決める。20 msは目標で、保証ではない。1つの操作が長いネイティブの処理やOSの呼出しを含むと、同じ実行数でも時間は変わる。確認の方法は、音の待機と同じにする。信号の印を見て、Raw modeなら入力をのぞき、値3があれば -28 を `THROW` し、ほかのキーは空きのある範囲でキューに残す（2節）。
- **上限なし（uが0）の中断の確認**は、予算の仕組みとは別に要る。いまの `checkWorkBlock` は、予算が0なら何もしない。
- **計算の間の信号**：行入力の状態で計算の途中のCtrl+Cに気づくには、計算の間ずっと信号のハンドラーを置くものが要る。だれが置き、待機の語のハンドラーとどう入れ子にするかは未決（3節）。
- **ネイティブの処理**：ネイティブのループが呼ぶ共通の確認に、予算の消費と中断の確認の両方を持たせる（いまの `checkWorkBlock` を広げる）。項目11と12で足す大きな転送と変換のループは、これを呼ぶ。待機する語は、数える実行ループの確認に頼らず、2節と3節に従って自分で中断を確認する。
- **デバッグ機能を外したビルド**：語群ごと外す（決定済み）。

### 取り決め

- **資源は、作った語と対になる語が閉じる。** 閉じる語は、何度呼んでも同じ結果にする。
- **別のスレッドが触る資源は、スレッドを止めて `join` してから解放する。**
- **いまの終了の順序**（`main` の `defer`）：Tclのプログラムを止める → 端末を戻す（`leave`）→ ゲームパッド → ウィンドウ → 画像 → ディレクトリ → ファイル。その後に、コンソールの復元と出力の書出しなどが動く。
- **終了のときの順序の案**（いまの順序を変える）：(1) 子プロセスを止める（下の手順）。(2) 読取りスレッドを止めて `join` する。(3) ファイルとパイプを閉じる。(4) ウィンドウと音を止める。(5) 端末の状態を最後に戻す。端末を最後にするのは、ほかの片付けの出力や失敗が、戻した後の端末を乱さないようにするためである。
- **子プロセスを止める手順**：終了を求める → 出力を読み捨てながら、期限を付けて終わるのを待つ → 終わらなければ強制的に止める → 回収する。読取りスレッドを先に止めると、子が出力を書けずに止まり、回収が終わらないおそれがある（設計上の懸念で、確かめていない）。期限の長さは未決。
- **既存の `OPEN-PIPE` は別に扱う。** `pclose` で閉じるので、新しい子プロセスの表には入れない。
- **音のスレッドを止められるようにする作業が要る。** 止める通知、出力装置の待ちの解除、コールバックの停止、`join`、資源の解放を足す。終了の順序に「音を止める」と書くだけでは実現しない。項目9の作業に含める。
- **`QUIT` へ戻るエラーでは、資源を閉じない。** 端末の表示の状態だけは、行入力の前に一時的に解除する（項目1）。
- **新しく足す資源のハンドルは、プロセスの中で番号を使い回さない。** 閉じた後の番号を使ったら、エラーにする。これは追加の要件である。いまのファイルIDは表の位置から作り、空いた位置を使い回す。ディレクトリの列挙の番号はプロセスの中では増えるだけだが、起動のたびに同じ値から始まる（`src/host_directories.zig`）。既存のファイルIDの作りを変えるかは未決。標準入出力の固定のIDは例外とする。

## 7. 辞書イメージに含めない状態

`SAVE` と `SAVESYS` は、6節の資源とその状態を保存しない。いまも、画素、カーソルの位置、エディタの状態は保存していない。表示先などの利用者の設定（保存するもの）と、キューや接続先などの実行時の状態（保存しないもの）は分ける。

次の表は、保存したイメージから新しく起動したときの値である。

| 状態 | 起動した直後の値 |
|---|---|
| 端末の表示の状態 | すべて解除 |
| 保留中の入力、キュー | 空 |
| 物理キーの状態 | すべて離している。「あふれた」印はなし |
| 子プロセス、開いているファイルID | なし |
| PCMのストリーム | 止まっている |
| 単調時計の値 | 起動ごとに違う。保存した値と比べない |
| 数える実行の予算 | なし |

- **資源を開いたまま保存してよい。** 資源は保存されない。エラーにしない。
- **実行中の読み込み（完全な復元）と辞書の追加は、別に決める。** いまの完全な復元は、ホストの側のファイルの状態とブロックのバッファを残し、画像を解放し、Tclのヒープへの参照を忘れる（`src/core/image_restore.zig`）。「保存しない」ことと、「復元のときに開いている資源を閉じる」ことは別である。新しい資源（子プロセス、読取りスレッド、PCM、端末の表示の状態）を復元のときに残すか閉じるかは未決。
- **保存したイメージの変数に残ったハンドルは、新しい資源を指すことがある。** イメージは変数をただのセルとして戻すので、起動の後に開いた資源と番号が同じになりうる。「使ったら必ずエラー」は、いまの番号の付け方では保証できない。保証するには、ハンドルに起動ごとの世代を入れるなどの設計が要る。足すかどうかは未決。どの場合も、落ちないことは保証する。

## 8. 語群の依存関係

いまのビルドのオプションは、`float`、`files`、`help`、`tools`、`image`、`graphics`、`audio`、`debug` の8つである。組み込み語を足すと辞書のABIが変わり、以前のイメージは読めなくなる（既存の方針）。

### 決定（2026-11-18、利用者）

**拡張機能は、ビルドのときに選んで切り離せなければならない。サウンド、グラフィックス、拡張モジュールの3つに分けて作る。**

| 語群 | オプション | 含む項目 |
|---|---|---|
| サウンド | `audio`（既存） | 9 PCMストリーム、10 音源のレジスタ書込み（本体に移す場合） |
| グラフィックス | `graphics`（既存） | 8 物理キー、11 直接色の画素転送、12 描画の補助 |
| 拡張モジュール | 新しいオプションを1つ足す | 1 ターミナル制御、2 イベントキュー、3 非ブロッキングI/O、4 Unicode処理、5 子プロセス管理、6 ファイルシステム、7 実行制御、時計の語（1節） |

### 案（決定を受けた細部。未決）

- **オプションの名前**：`-Dextension` を候補とする。既定は入れる。
- **3つの語群は、公開する語の上で互いに依存しない。** どの組合せで外してもビルドが通り、残した語群は働く。サウンドとグラフィックスの新しい語とForthのライブラリは、拡張モジュールの語を呼ばない。内部のZigの部品は語群をまたいで共有してよい。待機と時計の内部の処理は、語群によらず本体に置く。いまも、音の待機は中断の確認に `graphics_input` を使っている。
- **時計の語は拡張モジュールに入れる。** 拡張モジュールを外したビルドでは、エミュレータは `UTIME` と `FRAME`（ミリ秒）で動く。これは代わりの手段で、単調であることと、細かい周期の精度は同じにならない。1 ms未満の周期が要るエミュレータは、グラフィックスと拡張モジュールの両方を入れたビルドで動かす。
- **拡張モジュールの中で、ほかの語群が要る語**：項目3、5、6のファイルIDを扱う語は `files` が要る。項目7は `debug` が要る（2026-11-17の決定）。要る語群を外したビルドでは、その語だけを外し、ビルドはエラーにしない。組み込み語の除外の表（`src/core/defs.zig` の `excluded_builtins`）は語群ごとの集合の和なので、重ねられる。ただし、ライブラリを読み込む処理（`src/core/library_loading.zig` の `loadWords`）は、語群の定義を全部足し、除外の表を見ない。条件ごとに定義とForthのライブラリを選ぶ処理を足す。外した語をForthのライブラリが参照して、読み込みの全体が失敗しないことも確かめる。
- **読み込み方**：サウンドとグラフィックスの語は、起動時の辞書になく、`REQUIRE-AUDIO` と `REQUIRE-GRAPHICS` で読み込む。拡張モジュールも同じ形（例 `REQUIRE-EXTENSION`）にするか、起動時の辞書に入れるかを決める。同じ形を第1候補とする。拡張を使わないプログラムの、辞書の項目の数と語の番号への影響を抑えられるためである。イメージのABIの署名には、読み込んでいない語も含めて組み込み語の列挙の全体が入る（`docs/IMAGE_FORMAT45.md`）ので、組み込み語を足せば、読み込み方によらず署名は変わる。実装の版をまたぐイメージの互換は保証しない（既存の方針）。
- **`WAIT-FILES` に渡す端末の入力**：端末の入力そのものは、いまも語群によらず読める。拡張モジュールの中では、`files` を外したビルドでも、端末だけを対象にした待機は働くようにする。
- **ホストの機能がないビルド（freestandingなど）では、語は `HostUnavailable`（-21）にする。** いまの `NS` と同じである。
- **外したビルドの確認**：3つの語群の8通りの組合せでビルドが通ることを、既存の機能除外の検証（`tests/scripts/verify-feature-matrix.py`）に足す。

## 検証の方法

この文書は仕様だけで、実装はない。各項目の実装のときに、次を確かめる。

- 待機：期限より前に戻らないこと、期限・終端・エラー・中断を区別できること、途中まで読んだ列が次の呼出しで続くこと。ホストの入力と時計を差し替える既存の方式で試す（`src/tests/xchar_test.zig` の `EKEY` の期限の試験と同じ形）。
- 中断：行入力の状態、Raw mode、ウィンドウのそれぞれで、待機と数える実行がCtrl+Cに気づくこと。対話的な確認は利用者の操作が要る。
- キュー：満杯、あふれの印、読み直しの後の状態。
- 資源：閉じる語を2回呼ぶ、閉じた後のハンドルを使う、開いたまま終了する、開いたまま `SAVE` する。
- 語群：サウンド、グラフィックス、拡張モジュールの8通りの組合せでビルドが通り、残した語群が働くこと。`files` か `debug` を外したビルドで、拡張モジュールの該当する語だけが外れること。
- 通常の実行ループの速度が変わらないこと（時間の計測は利用者に確認してから行う）。
