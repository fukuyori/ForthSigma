# PC分離実装レビューへの対応（2026-11-15）

対象はtque 764配下の765〜767。[レビュー原文](VM_PC_SCALAR_CLAUDE_REVIEW.md)を残し、対応と実測をここへ記録する。レビューでは意味の違いや採用を覆す具体的不具合は見つからなかった。静的読解による評価であり、実行検証の代わりとは扱わない。

## 指摘への対応

- B-1：局所runningのpc/end_pcは境界間で古くなるため、他フィールドだけを使い、完全なフレームを渡す前にframeWithLoopPCsを使うことをコメントに明記した。型を分ける変更は行っていない。
- B-2：回帰テスト3件を追加した。DEFER経由組込み／local_execute／DOES>のエラーで外側failed_pcと最内バックトレースPCをcounted両方で検査する。コード上端end_pc=65535で分岐し、明示EXITと暗黙終端の両方から低アドレスの呼出し元へ復帰する。DEFER／SYNONYM経由CATCHのcounted TRACEをENTER/LEAVEの全文・最終スタック・深さで検査する。現在のヘルパーにはRunningを書き換えた後にエラーを返す経路がないため、その将来の経路でdeferの有無を区別する保証までは追加していない。
- B-3：旧案Aの不採用記述に、PC分離版の採用前の記録であることを追記した。コードのExperimentというコメントも更新した。
- B-4：[実験報告](VM_PC_SCALAR_EXPERIMENT.md#linux最終測定のばらつきレビュー補足)に、通常8項目・両系列の基準／候補の最小〜最大と、整数演算の大きい試行の存在を追記した。ばらつきの原因は未特定であり、中央値だけから再現性を過大に主張しない。

## 再検証

レビュー対応後の製品ソースの変更はコメントのみ。テストと計測器も変更したため、関連検証を行い、結果を以下に記録した。保存先は`.work/pc-review-validation-20261115/`。

## Windows測定の事前条件

タスク765の対応・再検証後に766を実施する。基準版とPC分離版をWindowsネイティブで同じZig 0.17.0・x86_64-windows-gnu・baseline CPU・fast・strip・同一資源バイト列から作る。旧基準／測定済み候補との実行体のバイト一致も確認する。

計測器はGetProcessTimesのkernel+user時間をREADY/DONE間で読み、起動・コンパイル・終了処理を除外する。FILETIMEの100ns単位は実際の分解能を意味せず、この環境では短い試行で刻みが見られたため、基準の各項目が少なくとも約1秒になる反復数へ校正する。runnerと継承する子プロセスをCPU0へ固定する。APIの根拠はMicrosoftの[GetProcessTimes資料](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/processthreadsapi/nf-processthreadsapi-getprocesstimes.md)と[SetProcessAffinityMask資料](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winbase/nf-winbase-setprocessaffinitymask.md)。OS全体の設定・権限・タイマー設定は変更しない。

通常8項目・CATCH9項目ごとに、同一基準実行体のA1/A2を交互に測るA/A校正を5回・独立2プロセスで行う。δは2系列の中央値比の絶対値の最大。δ>2%なら、その項目だけ反復数を増やして両系列を取り直し、旧結果も残す。以後は確定した反復数を固定する。

本比較は7回・独立2プロセス、各系列でウォームアップ1回除外、交互順、2系列目の初期順は反転。チェックサム一致を必須とし、ビルド・テスト・レビューやCallgrindと同時実行しない。通常項目の最低反復数は1億とし、校正で必要なら増やす。LinuxとWindowsで反復数が異なる場合は、OSを跨いで絶対時間を比較しない。

Windowsでも従来の整数演算・LOOP各10%以上短縮かつ2δ超、他項目max(3%,2δ)以内、CATCH成功等5%／THROW等10%以内で評価する。未達の場合は採用確定を保留し、勝手に基準を緩めたりOS別の実装を追加したりしない。サイズ条件は引き続き両OS各1%以内。

結果と最終判断は[Windows記録](VM_PC_SCALAR_WINDOWS.md)にまとめた。マージ・コミット・タグ・プッシュ・リリースはこの計画に含めない。

## Windows校正手順の見直し

最初のA/A校正では17項目中12項目を取り直した。反復数を2倍にして独立2系列を取り直しても、9項目（スタック操作とCATCH系8項目）にδ>2%が残り、最大は深さ256の約16.38%だった。反復数増加だけでは、この時点の校正は改善していない。CPU時間と経過時間の全試行値を保存した。原因をCPU・ASLR・計測API等のどれかに特定したという意味ではない。

ここで全系列を終了させ、次の反復数増加の前に意図したチェックポイントで止めた。calibrate pass 2の終了コード75はこのための制御であり、その反復数で測定した結果ではない。`cases.json`のpass 2対象値は提案値で、実測条件は`cases-before-aa-0.json`／`cases-before-aa-1.json`と各A/A記録から区別する。

校正が済んだ必須2項目（整数演算・LOOP）を先に7回・独立2系列で比較するよう順序を変更した。δ上限・性能の合格値を緩めた変更ではない。CATCH等の未校正項目を合格と見なさず、これらの状態を結果へ明記する。

校正判定の数値上の補足：初回のスタック操作は比を引く計算で2.0000000000000018%となっていたが、記録した中央値の差を分母で割り直すと正確に2.0%で、上限以内だった。丸めを含む元の結果と、補正した判定を別ファイルに残した。合格値を緩めたものではない。

必須2項目の先行比較は7回・独立2系列で、整数演算−17.39%／−18.31%、LOOP−19.05%／−17.68%だった。元の通常・CATCH全項目の確認は未完了のため、これだけで採用を確定していない。

反復数の2倍化で改善しない項目があったため、最初に約1秒以上へ校正した反復数を使い、独立プロセスの試行数を15回へ増やす校正を追加する。まず最大の揺らぎがあった深さ256で、独立2系列を確認する。元の5回系列と2倍反復数の系列は捨てず、測定条件の違いを記録する。

15回の追加校正でδ>2%が残る項目は、31回・独立2系列まで試行数を増やして再確認する。上限値は変えず、この追加校正の後も残る項目は未校正として扱う。各段階の全試行を保存し、合格した系列だけを抜き出して合成しない。

## 最終的に採用したWindowsの校正条件

15回・31回の独立プロセス試行による追加校正で、CPU0の16項目はδ≤2%になった。正常CATCHだけは31回でも最大約3.49%が残ったため、同じ基準実行体をCPU4へ固定して対照条件を調べた。CPU4では15回・独立2系列のδが約1.19%となった。CPU0の不安定さの原因をCPU・ASLR・API等のどれかに特定したものではない。

正常CATCHの最終的な比較条件はCPU4、ほか16項目はCPU0とする。正常CATCHのCPU0での速度評価が成立したという意味ではない。CPU4を選ぶ時点では、この項目のWindows候補版の時間を測っていない。候補の有利な結果を見てCPUを選び直したものではなく、基準版A/Aの再現性に基づく条件の変更である。各項目の基準・候補は同じCPU・反復数で比較する。

採用したA/Aの試行数は項目により5／15／31回で、いずれも独立2系列。反復数と試行数、CPU割当、δ、過去の不採用校正系列をすべて保存した。先行比較した整数演算・LOOPの7回×2系列を使用し、残る15項目も7回×2系列で測定する。後続比較は項目・系列ごとに新しい計測プロセスを起動する。
