# 呼出し経路分離のレビュー対応

2026-11-15。[受領原文](VM_DATA_CALL_ROUTE_CLAUDE_REVIEW.md)への対応。VMコードの意味上の欠陥は指摘されていない。採否前の必須事項は測定の来歴と文書の修正で、回帰テスト3件も追加した。本体への反映と最終検証も完了した。

## B-1：実際に比較を実行したworkerと回数

実装欠落という見立てには相違があり、Windowsの`focused.py`とLinuxの`focused-linux.py`に、既に実装がある。親driverは最低回数7をCLIで渡し、workerが`accepted-aa.json`から採用したA/A回数を読み、`a.rounds = max(a.rounds, accepted[slug]['rounds'])`としてから実行する。最初のレビューではworkerは未読だった。

親driverだけでは追いにくかったため、[実行経路・実バイト列のハッシュ・回数監査](VM_ALL_VALIDATION_METHOD.md)を追加した。全29追加条件で、両比較系列の実回数と配列長がmax(7,採用A/A回数)以上であることを照合した。重点5条件の実回数も保持する。主JSON内のソース文字列はLF正規化されるため、別の方法監査JSONには元ファイルのCRLFを含むバイト列をbase64とSHA-256で保存した。

実行済みの親driverを書き換えて7を別の値に見せる対応はしていない。CLIの7は最低値、出力JSONのroundsは実回数である。最終比較driverの正常終了、34条件、179個の系列データと期待チェックサム・中央値・最小最大を照合した。意図した校正途中のチェックポイント75は旧履歴に残し、未完了の片系列は校正確定に使っていない。

## B-3：Windowsの量子化と境界の余裕

保存されたWindows比較CPU時間が15.625ms刻みであることを全比較値で確認し、[限界と全試行範囲](VM_ALL_VALIDATION_METHOD.md)へ記録した。APIの一般的な分解能と断定せず、今回の観測として扱う。

Windows LOOPの小さい側の短縮率は約10.12%。最低条件10%に対する余裕は約0.119ポイントで、この系列の基準中央値に対する1刻み約0.595ポイント未満である。点推定として条件を満たしたが、十分な余裕や再測定時の通過を保証しない。δ=0の項目も揺らぎゼロとは扱わない。Windows THROWの最大約7.79%悪化、SYNONYMの系列差、Linux CATCH-NOBTの増減方向の違いも残した。

## B-4：回帰テストの追加

以下の3テストを追加した。4種類のデータ語を対象とし、基準版にも同じテストを適用した。

- `core_words_test.zig`：コンパイル済みデータ語のpushが満杯で失敗したとき、通常／counted経路でスタック内容と深さを維持し、debug有効時のfailed_pcと先頭バックトレースPCが呼出し位置を指す。
- `core_words_test.zig`：実行中のFORGETで対象と呼出し元が削除された後、残ったデータ語呼出しが通常／counted経路でInvalidExecutionTokenとなる。
- `debug_words_test.zig`：データ語の呼出しを含むDATAが、9操作を各1回計数し、TRACEがDATAの開始・終了のみを示し、終了後のprofile/trace深さが0となる。

debug無効ではcounted経路とPC診断が選択されないため、その構成でcounted経路の検証済みとは主張しない。TRACE/PROFILEテストもdebug無効時はskipする。

## 軽微な指摘の判断

既存switchの重複する単純データ語アームは、測定したコード生成形状を維持するため今回は整理しない。本体反映時に「Experiment」を外し、fallback switchを維持する理由をコメントに記した。zig fmtによる字下げ1か所とこのコメント2か所以外に、測定したVMソースとの差分はない。両OSの最終実行体は測定済み実行体とバイト単位で一致した。機能上の未修正不具合ではなく、整理を別の変更に分ける判断である。コメント表現だけで実装を実験中と判断せず、最終状態は計画・採否記録を参照する。

レビューは静的評価であり、Claudeがテスト・ハッシュ計算・性能測定を独立に実行したとは主張しない。必須事項を再確認し、既定の点推定による採用と本体反映を確定した。

## 再確認後の対応

[Claude Codeの再確認原文](VM_DATA_CALL_ROUTE_REVIEW_FOLLOWUP.md)ではB-1〜B-3は解消、コード面の採用阻害事項はなしとされた。追加の必須事項として、計時本体scripts/benchmark-runtime.pyの同一性を明示した。前段の重点項目記録、初回試作記録、今回の全項目記録、現在のファイルのSHA-256が一致することを照合し、方法記録に実バイト列・ハッシュと、workerに実行ごとの検査はないという限界を追記した。測定時期の異なる保存ハッシュの前後照合であり、実行ごとの検査を遡って実施したと扱わない。

非先頭のデータ語での失敗PC検証は任意の追加候補として残す。今回の新テストは各データ語が先頭であるという識別力の限界があり、ステッパー・WATCH全組合せも追加3テストだけで検証したとは主張しない。既存のPC・ヘルパー・境界回帰テストは引き続き維持する。

## 採否判断

全34条件が既定の点推定による性能条件を満たし、実行体増加は両OSとも1%以内、同一VMソースの構成別回帰テストと独立再ビルドも確認できたため、PC分離＋データ語の呼出し経路分離を採用する。レビューの必須事項は来歴・文書・計時本体の同一性の追記で解消した。実機上の普遍的な性能保証や、CPU内部の原因特定を意味しない。本体へ反映し、Windows Debugの1070成功・10skip、両OSの最終ビルド、実行体の完全一致とCLIの期待値26を確認した。[最終反映記録](measurements/2026-11-15-vm-data-route-adoption.json)を参照。最終src/forth.zigのSHA-256は`d2c101033474ba348c6cd148249bd81afb6ae4e7656ae5bb0c40326806182195`。
