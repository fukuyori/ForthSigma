## 中程度の指摘（採否記録の前に対処を推奨）

1. **採否式が片側だけで、未達時の扱いが書かれていない**
   - `run.py` の判定は「両群で変化率 ≤ −10% かつ |変化率| > 2δ」のみで、`decision.json` には `integer_screen_passed` しか残りません。
   - 未達が「同等」なのか「悪化」なのかが記録上区別されません。`VM_PERFORMANCE_PLAN.md:179` の悪化基準 max(3%, 2δ) との対応もありません。
   - 文書も「打切り」とだけ書き、打切りが「速度施策として不採用」を意味するのか、サイズ目的の採用を別判断に残すのかが未記載です。
   - `protocol.json` と `run.py` はSHA凍結済みなので変更せず、文書側に解釈を結果確定前に追記するのが安全です。

2. **2δ条件は今回実質的に効いていない**
   - 確定済みのA/Aはδ=0.2315%、最小中央値5.716秒で通過しています。2δは約0.46%なので、効いている条件は −10% だけです。
   - δはA/A段階の値で、A/B中のドリフトは事後に検査されません。A/B後のA/A再確認もありません。
   - 文書の「独立環境や信頼区間ではない」に、この点を一言足す価値があります。

3. **画像互換性の根拠が薄い**
   - 同じOS内でもfastとsmallの画像SHAが異なります（Windows 1519…/d9dc…、Linux c727…/7ba8…）。原因は記録されておらず、画像サイズや差分位置も `images.json` にありません。
   - プローブはリテラルと `-` だけのコロン定義1個です。VARIABLE/CREATE-DOES、文字列、浮動小数、ボキャブラリは通っていません。
   - 4SAVE・8LOADの成功は「読める」ことの確認で、「同等」の根拠ではありません。文書の限界記載は正しいですが、「SHA不一致の原因は未調査」と明記すべきです。

4. **root `BYE` の由来の証拠が弱い**
   - 現在rootに `BYE` は無く、`initial-save-wrong-filename.sigma` と記録（87,341 bytes、290f4c…）は残っています。
   - ただし、どの実行体が作ったか、時刻、移動前に未追跡の新規ファイルだったことの確認は記録されていません。
   - 初回スクリプトの構造上、作成したのはwindows-fastの最初の1回だけと読めます。直後に期待ファイル不在で止まるためです。その旨を追記すると「今回作成」の主張が閉じます。
   - `.gitignore` は `BYE` を無視しないため、会話開始時のgit statusに `?? BYE` が無いことは弱い傍証になります。

## 任意の指摘

- **ソース同一性の範囲**: `source_hashes` のroot照合は5ファイルだけです。全体の同一性は、fastが採用済みSHA（379d…/bdb6…）を再現したことが実質的な根拠なので、文書でそちらを主根拠と書くと正確です。
- **テスト時のstrip**: `test.py` は `-Dstrip=true` を渡していませんが、small既定でtrueです。Linux CLI 9件の `binary_sha256` はすべて配置済みsmall（6bd1…）と一致しており、同一実行体で検証されています。この一致を文書に書くと強い根拠になります。
- **Linux unit testの実行条件**: ELFを引数なしで直接実行しており、build runnerの `--seed` は付いていません。結果は1,011/5skip、63/1skip、各exit 0で文書どおりです。
- **pilotの見積もり**: pilotは暖機なしの1回（0.776秒/100M）で、N=773,361,863は目標6秒に対し実測約5.72秒でした。5秒の下限で守られており問題ありません。
- **先行順の偏り**: 群内の先行回数は3対2（A/A）、4対3（A/B）で、群2の反転により2群合計では均等です。
- **計時スクリプトの堅牢性**:
  - 実行体のSHA検査は開始時のみ。
  - チェックサムassertで失敗した場合は `stop.json` が残らず、partialだけが残る。
  - 「再試行しない」は運用上の約束で、スクリプトは強制していない。
- **smokeの範囲**: N=100の8カーネルで、CATCH/THROW、文字列、ファイルI/Oは含みません。文書の「short smoke」という表現で足ります。
- **C側への影響**: `-Doptimize=small` はcore-mathなどCソースにも及びます。機能は同じでも浮動小数の経路は別コードになるので、根拠はunit testであってsmokeのfloat 1件ではない、と分けて書くと明確です。
