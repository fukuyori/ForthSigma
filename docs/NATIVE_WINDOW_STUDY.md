## 2. ねらい

macOS の具体案を起点とし、Linux への拡張は9章で扱う。Linux も Tcl/Tk を必須にせず既存の語で表示することを目標とするが、X11 と Wayland の対応範囲は未決定。

- Tcl/Tk を入れなくても、macOS でウィンドウに表示できる。
- `SHOW` が軽くなる（PNG にせず、画素をそのまま渡す）。※推測
- 拡大率が整数倍に限られない。Windows 版と同じく、縦横比を保って入る最大の大きさで描ける。
- `TCL` の語と `DISPLAY-TK` は残す。Tk の部品を使うプログラム（`examples/calculator.fs`、`examples/graphs-tk.fs`）はそのまま動く。

## 3. 現行設計との整合とメインスレッド

### 3.1 維持する既存の決定と境界

[決定事項](DECISIONS.md)の「グラフィックス機能の設計方針」「G3」の記録と、現在のコードを基準にする。

| 条件 | 根拠・扱い |
|---|---|
| OS 固有処理はホスト側に置く | `src/core/host_interface.zig` の `window_fn` と `InputEvent` を境界にする。AppKit や通信の処理をコアへ持ち込まない。`src/freestanding_check.zig` による OS 非依存の確認を維持する |
| 描画の基盤は Zig、図形は Forth | 新しい C ライブラリをグラフィックスのために追加しない、という既存の決定を維持する。Objective-C の橋渡しを追加するなら、その方針との関係を先に確認する |
| 表示先の選択は既存の Forth ライブラリ | `src/graphics/graphics.fs` の `SHOW`、`DISPLAY-WINDOW`、`DISPLAY-TK` の利用者向けの語を維持する。自動選択の実装と `GFX-WINDOW?` の判定は変更が必要かを別途決める（4.1 節）。`FRAME` は待機して `SHOW` を呼ぶ定義であり、macOS 専用のイベント処理を直接追加しない案とする |
| 画像の受け渡し | `window_fn` は上から順の行、32bit の `0xAARRGGBB` と表示領域のサイズを受け取る。色変換、縦横比、黒い余白、画像座標への入力変換を既存仕様に合わせる |
| 端末のフォーカス | Windows 版は表示時にフォーカスを奪わない決定。macOS も端末で入力を続けられ、クリック後はウィンドウでキーを受け取れる動作を基準に検証する |
| OS 資源を辞書に保存しない | ウィンドウ、子プロセス、パイプ、フレームワークの参照はホストが持つ。`SAVESYS` の実行ファイルでも実行時に作り直す |
| 機能を除いたビルド | 通常、`-Dgraphics=false`、`-Dfiles=false`、freestanding を確認する。現在の `window_fn` 登録、`poll`、`close` は graphics の条件なしなので、macOS バックエンドと内部起動の有効条件を明示し、無効版に内部引数を渡した場合も確認する |
| 終了と再表示 | `host_window.close()` で後始末する。利用者がウィンドウを閉じても Forth は終了せず、次の `SHOW` で開き直す |

SDK なし、単一実行ファイル、最初の表示までの遅延初期化は、既存実装や配布を維持する候補条件として扱う。すべてが正式な設計決定であるとは断定しない。`main` が `std.Io` を使わない点は、実行ファイルの大きさを抑える既存の決定である。

`docs/ASYNC_OVERVIEW.md` は未確定の企画であり、現在の実装仕様とは区別する。そこにある入力の一元管理、イベントキュー、非ブロッキング I/O、子プロセス管理の候補と重複するが、今回それらを確定しない。「Forth はメインスレッドで実行」はワーカーで Forth を実行しない文脈であり、OS のメインスレッド要件と同一視しない。GUI 操作をメイン VM に集約する案との関係も、案 A を再評価する際に確認する。将来案の「キー・テキストを無断で破棄しない」と現行 Windows 版の有界キューの差も未解決の調整事項とする。既存の入力境界を維持し、今回だけの新しい公開イベント API は追加しない案とする。

既存の段階的な方針は「macOS は画像ファイルと端末表示を先にする」「Linux は X11 のソケット通信を直接実装する方式を調べる」である（`docs/DECISIONS.md` の同設計方針）。macOS の次の段階の候補に加え、Linux は既存の X11 調査方針を起点に9章で検討する。方式の採用を決めたものではない。

### 3.2 メインスレッドの制約

Apple の資料ではイベント処理はメインスレッドが担当し、`NSView` の作成・破棄・サイズ変更もメインスレッドで行う。2014 年の資料には `NSWindow` を副スレッドで作れる例外もある。一方、現行リファレンスの Swift 宣言は `NSWindow` と `NSView` を `@MainActor` としている。古い例外の現在の適用範囲は未確認であり、これに依存せず AppKit の操作をメインスレッドへ集約する案とする。Swift の宣言から Zig 経由の実行時制約までは断定しない。[NSWindow](https://developer.apple.com/documentation/appkit/nswindow)、[NSView](https://developer.apple.com/documentation/appkit/nsview)。[Apple の資料](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/ThreadSafetySummary/ThreadSafetySummary.html)

Sigma のメインスレッドは Forth のインタープリターが使っていて、行の入力を待つ間は止まっている。そのため、Windows 版の「ウィンドウ専用のスレッド」の作りは、そのままでは使えない。

作り方の案は、この制約をどう扱うかで分かれる。

## 4. 作り方の案

### 案 A: Forth を別のスレッドで動かす

macOS では、起動時に Forth のインタープリターを別のスレッドで始め、メインスレッドはウィンドウの処理のために空けておく。ウィンドウが要るまで、メインスレッドは待つだけにする。

- **よい点**: Forth が入力を待っていても計算していても、ウィンドウは動かす・大きさを変える・閉じることができる。Windows 版と同じ使い勝手になる。
- **負荷**: 大きい。`src/main.zig` の起動と終了に手が入る。
- **危険**: 端末の入力、Ctrl+C、終了の処理、ネイティブスタックの大きさに回帰の恐れがある。別スレッドのスタック容量を確認し、必要な大きさを明示する（深い再帰でネイティブスタックを使い切る不具合を過去に直している。CHANGELOG の `CATCH` の項）。
- **終了経路**: nib を前提にする `NSApplicationMain` をそのまま使わず、`sharedApplication` と `run` を候補とする。ただし `terminate:` も `main` の後始末を通らないと Apple は説明している。Cmd+Q、Dock の終了、ログアウトを含め、端末の復帰・出力の書き出し・子の停止と Forth の終了を調停する必要がある（5.1 節）。
- **影響の範囲**: macOS の全利用者。ウィンドウを使わない端末だけの利用でも、起動の経路が変わる。

### 案 B: メインスレッドのまま、語の中でイベントを処理する

スレッドの構成は変えず、`SHOW`・`INKEY`・`MOUSE`・`MS` のホスト処理で、たまっているイベントを処理する。`FRAME` は既存の `MS` と `SHOW` を通じて間接的に処理する案で、直接は変更しない。

- **変更範囲**: `SHOW` と `poll` だけの試作ならホストのウィンドウ処理を中心にできる。`MS` や入力待ちにも処理を入れる場合は、ほかのホスト処理も変更する。
- **負荷**: 小さい。
- **欠点**: Forth が行の入力を待っている間と、これらの語を呼ばずに計算している間は、ウィンドウが固まる（動かせない、描き直されない）。対話しながら描く使い方では、Windows 版や Tk 版より使い勝手が落ちる。ゲームのように毎コマ `FRAME` を呼ぶプログラムでは問題にならない。※推測
- **緩和**: 行の入力の待ちの中でもイベントを処理すれば、固まるのは長い計算の間だけになる。ただし端末の入力の処理（`src/host_line.zig`、`src/host_input.zig`）に手が入る。未確認

### 案 C: ウィンドウを別のプロセスにする

ウィンドウは子プロセスが持ち、Sigma は画素を送ってイベントを受け取る。Tk の表示と同じ形で、相手が `wish` でなくネイティブのプログラムになる。子プロセスは、同じ実行ファイルを特別な引数で起動したものにできる（配るファイルは増えない）。

- **よい点**: インタープリターのスレッドの構成は変えない。子プロセスのメインスレッドはウィンドウ専用なので、親が入力を読まない間も、子が通信で待たない設計なら操作を継続できる（成立は未検証）。`src/host_process.zig` の起動・パイプ処理を参考にできる。ただし Tcl 用の単一のプロセス状態を持つので、そのまま共用せず、ネイティブ表示の状態は独立させる。
- **実装規模**: 未見積もり。画素とイベントの通信、待ち時間の制限、異常終了と再起動まで含めて評価する。
- **欠点**: `SHOW` のたびに画素をパイプで送る（480×300 の画像で約 0.6 MB）。PNG の符号化は不要になるが、Tk や案 A・B との実測比較はしていない。大きな画像では共有メモリが要るかもしれない。※推測
- **未確認**: 子プロセスが異常終了したときの後始末、Dock に出るアイコンの扱い、署名と公証への影響。

### 案 C の構成候補（採用未決定）

- 親は現在どおり Forth を実行し、`show / poll / close` を通じて子を管理する。
- 子は AppKit と表示画像だけを持つ。内部モードへの分岐は `run` の冒頭など、`forth.State` の確保、端末判定、リサイズ監視、コンソール初期化より前に置く。通常の引数解析や埋め込み辞書の読み込みも行わない。
- 専用引数が利用者プログラムの引数と衝突しないよう、継承した通信用記述子による初回応答などと組み合わせる。初回応答で通信の版番号を照合し、実行ファイルの置き換えも検出できるか検討する。`SAVESYS` の実行ファイルで同じ経路を確認する。
- 入力を既存の `InputEvent` に変換し、端末入力に続いて `host_window.poll()` から返す。親はプロンプト待ちや `INKEY`／`MOUSE` を呼ばない計算中には入力を読まず、端末入力が続く場合もウィンドウの読み取りが遅れる（`src/main.zig` の `inputEvent`）。通信の受信と Forth による消費を区別する。
- 子のメインスレッドは AppKit のイベント処理を担当する。画像の受信を副スレッドか実行ループの入力源で処理し、描画状態の更新をメインスレッドへ渡す方式を試す。SDK なしでの通知、画素の所有権、自動解放プールの寿命も確認する。
- 起動には `posix_spawn` を比較する。`std.Io` を使わない既存方針を維持し、標準ライブラリの起動 API を使う場合は依存とリンク範囲を先に調べる。子へ渡す記述子は通信と明示的に必要な標準入出力だけに限定する。`POSIX_SPAWN_CLOEXEC_DEFAULT` と file actions、close-on-exec を比較し、Tk・ファイル・`OPEN-PIPE` との相互継承を防ぐ。既存 Tcl の `pipe()` には close-on-exec が付いていない（`src/host_process.zig`）。
- 子のプロセスグループ、シグナルの既定動作とマスクを指定する方針を決める。端末の Ctrl+C、Ctrl+Z、SIGHUP と、親の異常終了を区別する。SIGPIPE のプロセス全体の一時変更を新しい送信スレッドへそのまま流用せず、macOS の `F_SETNOSIGPIPE` も比較する（5.1 節）。
- 通信ではメッセージの種類・長さ・サイズの上限・画素形式・版番号を定義する。部分的な読み書き、途中切断、不正なサイズを処理する。
- 子は入力送信でメインスレッドを止めない。親が読まない間も、移動・リサイズ・終了を処理する。Windows 版ではキー押下は64個で満杯なら新しいものを捨て、マウスのボタン変化とホイールは64個で古いものを捨て、移動は最新位置を持つ。通信も含め、集約・破棄の規則と上限を定義する。
- キー解放はイベントの送達だけに頼らない。Windows 版は現在の押下状態とコアへ伝えた状態の差から解放を生成する。案 C では状態の同期方法を決め、フォーカス喪失・切断・子の終了・ウィンドウ終了時に、親が伝達済みのキーを解放できることを確認する。
- 親の送信待ちと初回応答待ちには上限を設ける。期限超過を `HostFailed` とする案では、子の停止・回収にも上限を持たせる。古いフレームを捨てるなら、送信途中のフレームを破棄する規則も決める。
- `SHOW` の初回と再表示は、子がフレームワークを読み込みウィンドウを作ったという応答を期限付きで待つ案とする。以降は、画素を全量パイプへ渡すか、親が所有するバッファへコピーして送信処理に引き渡すかを決める。後者には送信スレッド等の処理が必要になる。どちらも戻った後に Forth が元の画素を変更してよいことを保証する。
- 比較の基準となる Windows 版は初回・再表示の `open()` で作成完了を待つ。以降は全画素のコピーと再描画依頼を行い、依頼失敗はエラーにする。毎回の描画完了まで待つわけではない（`src/host_window.zig` の `show`、`open`）。
- 色変換を親で済ませるかを決める。Windows 版にも表示用コピーが1枚あるため、それを比較基準に、親の送信バッファ・子の保持・描画用画像の枚数と最大メモリーを明示する。確保失敗を `MemoryExhausted` とする範囲と、前の表示を保持できる条件を定義する。

以上は設計案であり、試作による成立確認はしていない。

### 案の比較（構成からの評価・※推測）

| | 案 A（別スレッド） | 案 B（語の中で処理） | 案 C（別プロセス） |
|---|---|---|---|
| 入力待ちの間のウィンドウ | 動く | 固まる | 動く |
| `main.zig` の変更範囲 | 起動・終了・実行スレッド | 入力待ちも処理するなら変更 | 早期分岐・登録判定・ビルド条件（規模未見積もり） |

| 採用前の中心課題 | Forth の実行スレッド変更 | 計算中・入力待ちの操作性 | 通信停滞・異常終了・大画像 |

### 4.1 自動表示先と保存済み辞書（未決定）

`GFX-WINDOW?` は現在 `window_fn != null` だけを調べる（`src/core/words_graphics.zig`）。`SHOW` は真ならネイティブ表示へ進み、失敗を `CATCH` しない（`src/graphics/graphics.fs`）。コールバックを macOS で常時登録するだけでは、GUI 不可時に Tk／端末へ落ちない。また、ネイティブを有効にしたまま既定だけ Tk にすることも、現在の自動選択ではできない。

次を分けて評価する。

1. 起動時に GUI を使えるかを判定し、不可なら `window_fn` を登録しない案。既存の `__CFBundleIdentifier` は手掛かりであり、GUI 利用可否の保証ではない。古い `SHOW` でも使えるが、起動後の子の失敗は扱えない。
2. 自動 `SHOW` に限ってネイティブ表示の失敗を捕捉し、Tk／端末を試す案。これは Forth ライブラリの変更で、既に保存された辞書の古い `SHOW` には反映されない。明示的な `DISPLAY-WINDOW` の失敗を隠すかどうかとは区別する。
3. `GFX-WINDOW?` の意味を実行時の利用可否へ変える案。問い合わせの副作用・初期化費用と、ほかの OS や保存済み辞書との互換性を調べる。

Linux でも同じ登録とフォールバックの問題が生じる。起動時に `DISPLAY`／`WAYLAND_DISPLAY` 等の有無だけで登録する案では接続失敗を検出できず、実接続を試す案では起動時間と待ち時間の上限が問題になる。コンソール、SSH、WSL、古い辞書で従来の Tk／端末への経路を失わないか確認する。環境判定、接続確認、自動 `SHOW` の失敗処理を別々に決める。

`(TRY-TK)` は `(DISPLAY)` を端末または Tk に書き換える。この後の辞書保存では選択済みの値が残るため、自動のまま保存した場合と区別する。OS を移した辞書、明示選択、自動選択後の保存・復元を試す。既存の決定にある「別の OS ではその環境の表示先になる」は、値が自動のままの場合と、選択結果を保存した場合を分けて説明する必要がある。

## 5. どの案でも要る作業

- **Objective-C の呼び出し**: Zig から AppKit を実行時に読み込んで呼ぶ。キーやマウスのイベントを受けるには、クラスを実行時に作ってメソッドを足す必要がある。arm64 と x86_64 の両方で動かす（構造体を返す呼び出しの扱いが違う）。音と同じ手法が AppKit でも使えるかは未確認。
- **描画**: 画素から画像を作り、縦横比を保って拡大して描く。余りは黒にする。Retina の画面と `WINDOW-SIZE` に対応する。`DISPLAY-COLORS` と `DITHER` の色数も、Windows 版と同じに扱う。
- **キー**: キーコードを `K-UP` などの番号に対応づける。文字は UTF-8 のバイトにする。`KEY-HELD?` のために、押したとき、離したとき、フォーカスを失ったときを追う。Ctrl+C は `USER INTERRUPT !` にする。
- **マウス**: 拡大した画像のうち、マウスの下にある画素を返す。ボタンとホイールを `MOUSE` と `MOUSE-EVENT` に渡す。
- **ウィンドウの管理**: 閉じたウィンドウは次の `SHOW` で開き直す。コマンドラインから起動しても端末のフォーカスを奪わずに表示し、クリック後にキーを受け取れるようにする（未確認: アプリのバンドルなしでの振る舞い）。
- **文書**: 利用者の手引き、グラフィックモードのマニュアル（英語と日本語）、実装ノート、互換性一覧、CHANGELOG、決定事項。
- **テスト**: キーの対応づけや画像の収め方の計算に加え、通信の分割、不正なサイズ、切断、子の終了・再起動も自動テストの対象にできる。表示、キー、マウス、閉じる操作は、実機で人が確かめる必要がある。確かめる対象には、既存のサンプル（`paddle.fs`、`runner.fs`、`hopper.fs`、`shmup.fs`、`klondike.fs`、`graphs.fs` など）を含める。

以前の 600〜900 行という見積もりには検証の根拠がないため、採用判断には使わない。通信・異常終了・両アーキテクチャ対応を含め、試作後に見積もる。

### 5.1 公式資料から確認した注意点

2026-11-14 に公式資料と公開ソースを確認し、Claude Code の追加レビューでも再確認した。資料上の根拠と Sigma での実証を区別する。追加レビューでは一部のリファレンス本文を通常ページから取得できず、Apple の `tutorials/data/documentation/` の公式 JSON から確認した。`NSWindow`、`NSView`、`NSApplication` は取得範囲が途中までで、未取得部分に記載がないとは断定しない。以下の公開ソースの `main` ブランチは macOS 11 での提供を保証するものではなく、最低 OS と両アーキテクチャで検証する。

- **Objective-C ABI**: Apple の公開ヘッダーは適切な関数ポインター型での呼び出しを要求し、`objc_msgSend_stret` を arm64 では使用不可としている。構造体の戻り値を一律に扱わない。x86_64 の構造体ごとの呼び出し規則は ABI 資料で別に確認し、Zig の C 呼び出し規約で実証する。構造体の値渡し・戻り値・`drawRect:` のコールバック登録を試作に含める。[message.h](https://github.com/apple-oss-distributions/objc4/blob/main/runtime/message.h)
- **動的クラス**: クラスの生成とメソッド追加の API は公開されている。SDK なしで Sigma から AppKit の表示まで成立するかは未検証。[objc_allocateClassPair](https://developer.apple.com/documentation/objectivec/objc_allocateclasspair(_:_:_:))、[class_addMethod](https://developer.apple.com/documentation/objectivec/class_addmethod(_:_:_:_:))
- **起動と終了**: `NSApplicationMain` は終了時にプロセスを終了させる。`NSApplicationMain` はバンドルの nib を読む。`sharedApplication` と `run` の構成でも、`terminate:` の資料は `main` の後始末が実行されないと説明する。案 A は終了通知と Forth の後始末を調停し、案 C は子の終了を切断として回収する。`stop:` での復帰は今回未確認。[terminate:](https://developer.apple.com/documentation/appkit/nsapplication/terminate(_:))。[NSApplicationMain](https://developer.apple.com/documentation/appkit/nsapplicationmain?language=objc)
- **Dock と入力**: `regular` は通常の Dock 表示、`accessory` は Dock・メニューバーなしでクリック等によるアクティブ化が可能、`prohibited` はウィンドウを作れない。バンドルなしの Sigma での実際の動作は未確認。[ActivationPolicy](https://developer.apple.com/documentation/appkit/nsapplication/activationpolicy-swift.enum)
- **前面化**: macOS 14 以降のアクティブ化は要求であり成功は保証されない。macOS 14 のリリースノートは `activate(ignoringOtherApps:)` を非推奨として使わないよう説明する。追加レビューでは個別リファレンスの availability 表示と時期の不一致が報告されたため、正式な非推奨バージョンはここで断定しない。毎回の `SHOW` で前面化しない既存方針と区別する。配布スクリプトの最低 OS は既定で macOS 11.0 なので、新 API だけに依存しない。[AppKit macOS 14 Release Notes](https://developer.apple.com/documentation/macos-release-notes/appkit-release-notes-for-macos-14)
- **非アクティブ表示**: `orderFrontRegardless()` はアプリが非アクティブでもキー／メインウィンドウを変えずに前へ表示すると説明される。候補 API とし、端末のフォーカスを保つか、初回・更新・サイズ変更の各経路で検証する。クリックによるアクティブ化と最初のクリックのマウス通知も別に確認する。[orderFrontRegardless](https://developer.apple.com/documentation/appkit/nswindow/orderfrontregardless())
- **Retina**: ビューの座標と backing store の画素は別で、変換 API がある。既存文書の `WINDOW-SIZE` は画素という説明なので、ポイントとして実装してよいとは判断しない。単位、画面間の移動、非整数倍の補間、マウスの逆変換を決める。サイズ用と点用の変換を使い分け、`backingScaleFactor` を単純に掛ける実装は避ける。奇数の物理画素サイズも検証する。[backingScaleFactor](https://developer.apple.com/documentation/appkit/nswindow/backingscalefactor)。[convertToBacking](https://developer.apple.com/documentation/appkit/nsview/converttobacking(_:)-4ra9y)
- **描画領域**: macOS 14 のリリースノートは、リンクした SDK により `clipsToBounds` の既定が変わり、dirty rect がビュー外まで広がりうると説明する。黒い余白は `bounds` 基準で扱い、クリッピングを明示する案とする。SDK なしのビルドがどの SDK として扱われるかは未確認。
- **文字入力**: UTF-8 への変換と IME による文字入力は別の処理。ゲーム向けのキー取得と、IME の確定文字列対応の範囲を明記する。`NSTextInputClient` は範囲・候補位置などのメソッドを持ち、構造体の受け渡しも必要になる。プロトコルなしで確定文字列を受けられるかは未確認。Windows の `WM_CHAR` による UTF-8 入力との互換性を調べる。[interpretKeyEvents](https://developer.apple.com/documentation/appkit/nsresponder/interpretkeyevents(_:))、[NSTextInputContext](https://developer.apple.com/documentation/appkit/nstextinputcontext)
- **スクロール**: `NSEvent` は精密なスクロール差分を提供する。精密差分と行単位の差分を区別し、トラックパッドの差分を Sigma の整数ホイールイベントへ変換する規則が必要。Windows 版は120を1刻みとして端数を蓄積するが、その定数を macOS に流用しない。慣性と方向の扱いは未確認。[NSEvent](https://developer.apple.com/documentation/AppKit/NSEvent)
- **記述子とシグナル**: Apple の `posix_spawn` 資料は close-on-exec のない記述子、無視設定、シグナルマスクの継承を説明する。公開 xnu のマニュアルには `POSIX_SPAWN_CLOEXEC_DEFAULT`、`SETPGROUP`、`SETSIGDEF`、`SETSIGMASK` がある。`fcntl` の `F_SETNOSIGPIPE` は記述子ごとに SIGPIPE 生成を抑止する。最低 OS での利用可否、file actions の適用と記述子の重複を試す。[posix_spawn](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/posix_spawn.2.html)、[setflags](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man3/posix_spawnattr_setflags.3)、[file actions](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man3/posix_spawn_file_actions_addclose.3)、[fcntl](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/fcntl.2)
- **署名・公証**: コマンドラインの実行ファイルも対象で、Hardened Runtime が必要。既存の `scripts/sign-and-notarize-macos.sh` は `--options runtime` を使う。Apple 署名のライブラリはライブラリ検証で許可されるが、AppKit の動的読み込み・クラス生成に追加権限が不要とまでは今回の資料で確認していない。公証要件の SDK バージョンと SDK なしビルドの関係、`SAVESYS` の追記後の署名状態も未確認。単体バイナリーにはステープルできず、既存手順は pkg に行う。[Library Validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)、[Customizing notarization](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)。[Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

## 9. 3 OS 共通の条件と Linux の検討

2026-11-14 追記。Windows・macOS と同じ利用者向けの語で Linux のウィンドウも扱う検討。実装、実機検証、性能測定は未実施。以下の推奨順序と構成は設計上の提案であり、採用決定ではない。

### 9.1 共通化する境界

`SHOW`、`DISPLAY-WINDOW`、`WINDOW-SIZE`、`INKEY`、`KEY-HELD?`、`MOUSE`、`MOUSE-EVENT` の利用者向けインターフェースと、`window_fn`／`InputEvent` のホスト境界を基準にする。OS ごとに実行スレッドやプロセスの構成を同じにする必要はない、という設計案とする。

| 環境 | 表示方式・候補 | 検討上の位置づけ |
|---|---|---|
| Windows | Win32、専用スレッド | 既存実装を維持し、動作比較の基準にする |
| macOS | AppKit（候補: 案 C の表示専用の子プロセス） | 案 C を先に検証する提案。採用未決定 |
| Linux の X11 環境 | Zig による X11 の直接通信 | 既存の調査方針を起点にする |
| Linux の Wayland＋XWayland 環境 | 同じ X11 バックエンドで XWayland に接続 | 互換経路として別に検証する |
| Linux の Wayland のみの環境 | Wayland の直接通信 | X11 と分けた後続の調査候補 |

共通の検証条件案は次のとおり。語の契約と未決定事項は10章で具体化する。Linux のフォーカスは下記のとおり環境別の評価目標として区別する。

- 初回の作成完了、以降の画像受け付け、表示先切断の検出について、成功・失敗の意味を定義する。`SHOW` から戻った後は元の画像を変更できる。
- Forth の入力待ち・計算中も、ウィンドウの移動・サイズ変更・終了・再描画を継続できる。
- 初回表示・更新・サイズ変更で端末のフォーカスを奪わず、クリック後はウィンドウのキーを取得できることを目標とする。X11 のフォーカス付与はウィンドウマネージャーにも依存するため、クライアントだけの保証や一律の合否条件にせず、要求方法と環境別の結果を記録する。キーを受け取らない設定で回避しない。ICCCM の入力モデルと EWMH の手段を調べる（EWMH は今回未取得）。[ICCCM](https://xorg.freedesktop.org/archive/current/doc/xorg-docs/icccm/icccm.html)
- 閉じても Forth を終了せず、次の `SHOW` で再表示する。フォーカス喪失と切断時はキーの押下状態を解放する。
- 画素の意味、色変換、補間、縦横比、余白をそろえ、`WINDOW-SIZE` の物理画素と論理座標の関係を明記する。
- 自動表示先、明示的な `DISPLAY-WINDOW`、GUI 不可時、保存済み辞書を4.1節と合わせて扱う。
- OS 資源を辞書に保存せず、`SAVESYS`、graphics／files 無効ビルド、freestanding の境界を維持する。

### 9.2 Linux の既存方針と X11

`docs/DECISIONS.md` の「G3: LinuxのX11の調査（#368）」には、libX11／libxcb を使わず、ソケット上で X11 と直接通信する候補が記録されている。配布の静的 musl 方針は `docs/DECISIONS.md` の「S5: Linux の出力層」に記録され、`.github/workflows/release.yml` は x86_64／arm32／arm64 の musl ターゲットを指定する。`src/host_gamepad.zig` も静的 musl では依存する共有ライブラリを解決できないため、動的読み込みを無効にしている。ターゲット名だけを静的リンクの検証結果とは扱わない。※設計上の判断: この配布を保ち、新しい共有ライブラリを必須にしない方式として、X11 の直接通信を最初の検証候補にする。

X11 の公式プロトコルは接続時の画素形式・バイト順・visual の色情報と、要求の長さの上限を定義している。24bit の色が必ず32bitで格納されるとは仮定せず、サーバーの情報から変換する。[X.Org: X11 Protocol](https://xorg.freedesktop.org/releases/current/doc/xproto/x11protocol.html)

主な調査・試作項目は以下。

- `DISPLAY` の解析、接続先と認証情報の選択、`XAUTHORITY`、接続失敗と時間制限。認証情報の値はログに出さない。明示的な認証情報なしで接続できる経路も調べる。`.Xauthority` のファイル形式と項目選択は今回未確認。[Xsecurity](https://xorg.freedesktop.org/archive/current/doc/man/man7/Xsecurity.7.xhtml)
- Unix ドメイン、ホスト名付き `DISPLAY` の TCP、SSH の転送で対応範囲を分ける。MIT-MAGIC-COOKIE-1 は接続時に暗号化されずに送られるので、TCP 対応を追加する場合は接続範囲を明記する。初期試作をローカルの Unix ドメインに限定する案もあるが、SSH 転送の対応を含むとは扱わない。OpenSSH の詳細は未確認。[X](https://xorg.freedesktop.org/archive/current/doc/man/man7/X.7.xhtml)
- ウィンドウと描画資源の生成、`Expose` の再描画、サイズ変更、`WM_PROTOCOLS`／`WM_DELETE_WINDOW` による終了。
- `PutImage` の要求分割、行のパディング、depth と最大要求サイズ。コアの最低保証は要求全体で16384バイトだが、最大幅16384画素の32bit画像は1行65536バイトになる。横方向の分割と BIG-REQUESTS の利用を比較し、ヘッダー分も含めて上限内にする。送信中もイベント・応答を読み、サーバーと相互待ちしない。[X11 Protocol](https://xorg.freedesktop.org/releases/current/doc/xproto/x11protocol.html)、[BIG-REQUESTS](https://xorg.freedesktop.org/archive/current/doc/bigreqsproto/bigreq.html)
- 拡大縮小の実行場所を決める。`PutImage` 自体には拡大率の引数がない。※設計案: クライアント側で表示サイズに変換して送る方式と、拡張を使う方式を比較する（RENDER は未確認）。補間、リサイズ時のバッファと追加コピーを検証する。クライアント側で変換して送る場合は転送量が表示領域に依存し、8.1節の元画像の転送量を X11 の見積もりに流用できない。
- キーボード配列・修飾キー・押下と解放・リピート・フォーカス喪失。物理キー番号を文字に固定対応させない。日本語 IME を含む入力方式、追加依存を避ける範囲は未確認。keysym から Unicode への変換で扱う範囲、表の容量、ライセンスを調べる。リピート中に `KEY-HELD?` が一瞬解放にならないことも検証する。追加レビューでは XKB の既定リピートが解放・押下の対で、DetectableAutorepeat の対応が任意であることを確認した。※設計案: 検出可能リピートを要求し、非対応時の対の判別・解放抑止を調べる。[XKB Protocol](https://xorg.freedesktop.org/archive/current/doc/kbproto/xkbproto.html)XIM はコアとは別のプロトコルとして評価する。[XIM Protocol](https://xorg.freedesktop.org/releases/current/doc/libX11/XIM/xim.html)
- マウスとホイール、ウィンドウマネージャーごとのフォーカス、DPI・拡大率の違い。高 DPI での XWayland の扱いは実機確認する。
- X サーバーの停止・切断、受信と送信が停滞した場合の上限、終了時の回収。接続失敗で Forth のプロセス全体が終了しないこと。
- 切断済みソケットへの送信時の SIGPIPE 抑止と、close-on-exec による `wish`／`SYSTEM` 等へのソケット継承防止。送信スレッドでプロセス全体のシグナル設定を一時変更する既存処理をそのまま流用しない。Linux の `MSG_NOSIGNAL` 等を候補として公式資料で確認する（今回未確認）。Tk 起動の前後どちらの順でも切断と資源回収を試す。

※設計案: Linux ではまず、接続・描画・入力をホスト側の専用スレッドで所有する方式を比較候補にする。Forth の実行スレッドを変更せず、macOS 案 C の親子間通信を追加しない構成を評価する。ただし、専用スレッドだけで停止回避が保証されるわけではなく、X サーバーとの通信にも待ちの上限と有界キューが必要。macOS と共有するのは公開仕様とホスト境界で、IPC を必須の共通基盤にはしない。

### 9.3 XWayland と Wayland 直接対応の区別

XWayland は Wayland のクライアントとして動く X11 サーバーである。同じ X11 バックエンドを使える互換経路だが、Wayland の直接対応とは区別して表記する。Wayland 環境に XWayland が必ずあるとは仮定しない。[Wayland 公式: X11 Application Support](https://wayland.freedesktop.org/docs/book/Xwayland.html)

Wayland の公式資料では、Unix ドメインソケット上の非同期オブジェクト型プロトコル、インターフェースの版交渉、通常のメッセージとは別の付随データによるファイル記述子の受け渡しが定義されている。[Wayland 公式: Protocol](https://wayland.freedesktop.org/docs/book/Protocol.html)

共有メモリー方式では `wl_shm` のバッファを描画に使えるが、コンポジターが使用中のバッファを書き換えない寿命管理と、`wl_buffer.release` による再利用が必要である。[Wayland 公式: Protocol Specification](https://wayland.freedesktop.org/docs/html/apa.html)

Wayland 直接対応では、さらにデスクトップウィンドウ用の xdg-shell、configure とサイズ変更、バッファ更新の通知、キーボード配列と文字入力、カーソル、装飾、拡大率の扱いを調べる必要がある。xdg-shell の公式 XML は今回の取得で失敗したため、詳細な手順と対応バージョンは未確認。`wl_keyboard.keymap` は `xkb_v1` のキーマップを記述子で渡すため、配列と文字入力を扱う方法も評価する。※推測: 外部ライブラリを使わない場合はキーマップの解析を自前で担う範囲が大きくなる。XKB の全仕様と対応範囲は未確認。装飾をどちらが描くか、タイトルバーなしでも移動・サイズ変更・終了を提供できるかも調べる（装飾の仕様は未取得）。libwayland 等を利用する方式は、外部 C ライブラリを追加しない既存方針と静的配布への影響を別に評価する。静的 musl で共有ライブラリの実行時読み込みを一般的な解決策とせず、静的リンク時の依存・ライセンス・クロスビルド、または配布方式の変更を比較する。

※設計上の判断: 外部ライブラリなしで X11 と Wayland を同時に実装する範囲は広いため、Wayland 直接対応を独立した検討段階にする。実装規模・性能・対応可能なコンポジターはまだ見積もらない。

### 9.4 可用性と検証順序

`DISPLAY`／`WAYLAND_DISPLAY` や継承記述子の `WAYLAND_SOCKET` を手掛かりとし、環境変数があることと、接続・認証・ウィンドウ作成が成功することを区別する。SSH でも X11 転送を使う場合があるため、「SSH なら GUI 不可」と一律には判定しない。ローカル接続と転送経由を分け、後者の認証・通信方式・性能と対応範囲は未確認として調査する。

## 10. Forth から見える3 OS 共通仕様案

2026-11-14 追記。Forth の語の構成と、Windows／macOS／Linux で同じプログラムを動かす条件を整理する。以下は仕様案であり、利用者による採用決定、実装済み、3 OS での検証済みを意味しない。現在のネイティブウィンドウは Windows のみである。

### 10.1 語の設計と責務

※設計上の評価: 小さな語をスタック効果で組み合わせ、Forth で描画や `FRAME` を定義し、OS 固有の処理をホストへ分ける構成は、Sigma の既存設計に沿う。これらのグラフィックス語は Sigma 独自のものであり、標準 Forth のウィンドウ仕様への適合を意味しない。

- 利用者は通常の描画・入力プログラムで OS 名による分岐やネイティブハンドルの操作を必要としない。
- 要件案: `SHOW` 等を呼ぶために利用者が OS の初期化やイベントループを実行する必要はなく、Forth の入力待ち・計算中も表示側が応答する。この要件を採用すると案 B は適合しないため、7章の方式選択と合わせて決める。
- コアとホストの境界は `window_fn` と `input_fn`（`InputEvent` を返す）とする。`show / poll / close` はホスト内の窓口で、`close` は CLI の終了処理から直接呼ばれる。Forth の公開語とこれらの責務を共通にする。ホスト内部のスレッド・プロセス・通信方式は OS ごとに選べる。
- エラーは既存の `CATCH`／`THROW` の経路で扱う。ホスト処理の失敗で Forth 全体を終了させない。
- Windows の既存実装も共通仕様に照合する。既存動作をすべて無条件に採用せず、変更する場合は互換性への影響を記録する。

### 10.3 自動選択と明示選択

※仕様案: 表示先を指定していない `SHOW` は利用可能な表示先を選び、明示した `DISPLAY-WINDOW` は利用不可なら既存のエラーを返す。明示選択を黙って端末へ切り替えない。`DISPLAY-TK` と `DISPLAY-TERMINAL` の既存用途も維持する。

自動選択の順序は4.1節と合わせて決める。ネイティブがない・GUI を使えない場合に Tk／端末へ進むことと、初期化後の故障を隠すことを分ける。メモリー不足・不正な入力・通信規約違反等を、すべてフォールバックで隠す案は採らない方向で検討する。接続失敗・作成失敗・切断のどれを捕捉対象とするかと、選択状態を変更する時点は未決定。

`GFX-WINDOW?` は現在コールバックの有無を返すだけなので、この案を現在の実装で保証できるとは扱わない。`DISPLAY-WINDOW` は選択時にも利用不可なら `-21` を投げ、`SHOW` では画像生成や作成・更新が別に失敗しうる。選択時と表示時のエラーを分けて定める。

現行の `(TRY-TK)` は全エラーを捕捉し、`(DISPLAY)` を1か3へ変更する。したがって失敗時の状態不変や、メモリー不足を隠さない案は現行との差分である。新しい規則の適用範囲と変更が必要な語を明記する。

※設計案: 明示した表示先の意図と、自動選択で解決した表示先を分離する。自動時は辞書の `(DISPLAY)` を0のまま保ち、解決結果はイメージ保存対象外のホスト／実行時状態へ置く案を比較する。`State` に置く場合も保存・復元・初期化の規則を確認し、公開語から操作する既存の責務との整合を調べる。

古い辞書では自動と明示選択の区別が既に失われており、復元時に推測して書き換えない。古い `SHOW` はネイティブ失敗を捕捉しないので、保証可能な範囲は4.1節のホスト側の登録判定に依存し、それでも作成時の失敗まで救済できない。ソースから再構築する等の移行方針と既知の制限を記載する。自動へ戻す語（仮称 `DISPLAY-AUTO ( -- )`）の追加も未決定の候補とする。これは新しい表示選択 API の案で、3.1節の「新しい公開イベント API は追加しない」とは対象を分ける。

### 10.4 入力の同等性と保証範囲

OS のイベントを同じ名前の語へ渡すだけでは同等性を保証できない。次の入力列と状態を共通にする範囲を決める。

- 特殊キー、文字、修飾キーと配列、リピートを Sigma の値へ変換する。OS が予約してアプリへ渡さないキーの組み合わせは、共通入力を保証する対象から分ける。
- UTF-8 の複数バイト文字をキュー境界でも壊さない扱いと、IME の確定文字列・合成中の状態の範囲を調べる。現行 Windows の `pushCharacter` は1文字をバイト単位で `pushKey` し、ホストとコアの `pushKey` は満杯なら個別に破棄する。このため残り容量より長い文字の一部だけ入る経路がコード上にある（実機未検証）。※契約案: 各段で1文字を全バイト単位で受け付けるか破棄し、途中で切らない。現在のバイト単位の `InputEvent` で実現するための文字境界の保持・再構成も設計する。IME の範囲候補は確定文字列のみ、容量超過は文字単位で破棄、合成中の状態は対象外とするが、採用未決定。日本語入力を3 OS 同等と表記するのは対応範囲と検証結果がそろってからにする。
- キー押下列、実際の押下状態、Forth が既に読んだ状態を区別する。キューがあふれても解放状態を復旧できるようにする。
- キーとマウスそれぞれの順序、端末とウィンドウの優先順、キーとマウスの間の順序をどこまで保証するかを決める。現行は端末入力が続くと窓の入力を読まず、Windows の `poll` もキー押下、解放、マウスの変化、最新位置を優先順に返す。※契約案: 保持したキー押下同士とマウスイベント同士の順序を保つが、両者の間と端末／窓の間の厳密な時刻順は保証しない。あふれにより押下のない解放が読まれうるが、`MOUSE` の buttons は最新状態へ収束させる。解放通知は状態同期と区別する。
- `MOUSE` 等が入力を更新したときも、キーが `INKEY` で読める既存の性質を保つ。キュー容量・破棄・移動の集約はホストとコアの両段階を含めて確認する。
- 現在の端末の `KEY-HELD?` は解放通知がないため押下後0.6秒を保持とみなす。ネイティブ表示の実状態追跡と同じ保証ではない。ネイティブ同士、Tk、端末を別の適合範囲として記録し、フォールバック後に完全同等と表記しない。

### 10.5 OS に委ねる部分

タイトルバー・装飾、画面上の配置、フォーカスの最終決定、描画時刻、リフレッシュレート、ウィンドウの物理的な外観は OS／ウィンドウマネージャー／コンポジターへ依存する。同じ意味の要求と、環境別に観測した結果を記録し、完全同一を保証しない。キーリピートの有無と間隔も OS の設定に依存するため、共通契約は不要な解放を発生させないことと、受信した入力の変換に限定する案とする。

ネイティブバックエンドが提供されない環境もある。例えば XWayland のない Wayland 環境は、X11 の実装だけではネイティブ表示の適合対象にできない。「Windows／macOS／Linux 対応」という表記には、バックエンド・動作確認環境・既知の制限を添える。

### 10.6 同じ Forth プログラムによる検証案

採用前に、各語のスタック効果だけでなく、状態変化・失敗後の状態・入力列まで具体化する。Windows を含む各バックエンドに、同じ Forth の描画と入力の検証プログラムを使う案とする。

| 検証 | 比較する内容 |
|---|---|
| 表示と更新 | 基準画像、色数と dither、連続 `SHOW`、戻った直後に元画像を書き換えても表示側の保持画像が壊れないこと |
| サイズと座標 | 縦長・横長、奇数サイズ、整数倍・非整数倍、黒い余白、端と画像外、DPI の異なる画面への移動 |
| キーと文字 | 特殊キー番号、UTF-8、押下・解放、リピート、フォーカス喪失、IME、キュー上限付近での状態 |
| マウス | ボタン番号、短いクリック、ドラッグ、ホイール、移動の集約、入力を読むまで長時間待った場合 |
| ライフサイクル | 入力待ち・計算中の操作、閉じて再表示、接続切断、終了、切断後のキーとボタン状態 |
| エラーと表示先 | 未生成画像、無効サイズ、利用不可、確保失敗、期限超過、自動選択と明示選択、失敗後の再試行 |
| 配布と辞書 | 機能無効ビルド、`SAVESYS`、保存済みの表示先と古い辞書、GUI を利用できない環境 |

純粋な計算とコアの契約は、`src/tests/support.zig` の偽ホスト等で入力列と `-21`／`-265`／`-257` の失敗を注入して自動確認する案とする。Windows の DPI、無期限待ち、UTF-8 の欠落も基準側の不適合候補として検証対象にする。`WINDOW-SIZE` は辞書内の変数とは別の実行時状態なので、`SAVESYS` のアプリで再指定が必要かを復元処理まで確認する。OS のイベントと接続・フォーカス・実画面は実機試験を組み合わせる。同じ Forth プログラムの実行だけで、描画時刻や OS の挙動まで証明したとは扱わない。結果は適合・不適合・未確認に分け、画像・入力ログ・エラー番号と環境を残す。

共通仕様案の採用、未決定事項の確定、Windows の変更を含む実装は、この文書更新には含めない。


### 10.7 共通仕様を確定する前の重点判断

**サイズと DPI**

今回の `src`、`build.zig`、`scripts`、`.github` の検索では、Windows の DPI awareness 宣言・設定は見つからなかった。外部から適用されるマニフェストや実行環境の設定は未確認。Microsoft は既定の DPI 非対応アプリがビットマップ拡大されることを説明している。※推測: 現行の要求値が高 DPI 画面で物理画素数と一致せず、OS の拡大で補間結果も変わる可能性がある。[High DPI Desktop Application Development](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows)

候補は、物理画素を契約にして Windows の DPI 対応を調整する案と、OS の論理単位を契約にする案。前者は既存プログラムの見かけの大きさが変わる可能性、後者は「1画素を整数倍で表示」の物理的な一致を保証できない可能性がある。採用前に互換性を実機確認する。7章の `WINDOW-SIZE` の判断と結び付け、単位が確定するまでは3 OS 同等と表記しない。

描画は要求値・実領域・配置矩形を分ける。※設計案: 配置矩形と逆変換の純粋な計算を共通化し、矩形内の補間を統一する。整数倍での画素一致と非整数倍でのサンプリングを別々に検証する。`StretchDIBits` の端数規則は未確認。画面表示ではアルファを無視する案も、画像操作全体のアルファ規則と分けて検討する。

**受け付け、待ち、失敗後の状態**

Windows の `open()` は旧スレッドの終了と作成完了を無期限で待つため、待ちに上限を設ける共通仕様は Windows にも変更を要する。`SHOW` の待機中にはグラフィックスの Ctrl+C を消費できない経路も考慮し、終了・キャンセル・期限超過を設計する。正常に受け付けた後の描画が遅いだけなら、最新画像へ集約する案とする。未送信・切断・期限超過まで成功として隠さない。

※失敗時の契約案: 明示表示の `SHOW` が失敗しても Forth の元画像と選択意図は変えず、次の呼び出しで再試行できる。表示済み画像のロールバックまでは保証しない。Windows はコピー後に再描画依頼が失敗すると、エラーの後にも新画像が表示されうる。自動選択は、許可した利用不可のエラーを内部で処理し、次の表示先が成功した場合に解決結果を更新する。全候補失敗時の状態も定める。

※エラー分類の候補: バックエンドなし・初回の接続先なし・初回の利用拒否を `-21`、確立後の切断・規約違反・期限超過を `-265`、確保失敗を `-257` とし、自動フォールバックは `-21` のみ捕捉する。認証拒否や子の起動失敗をどちらへ分類するかはログと具体例で決める。これは現行の分類を確認済みとする表ではなく、実装ごとの対応を照合すべき候補である。

**入力と互換性**

UTF-8 の文字単位での受け付けにはホストとコア両段の見直しが必要で、macOS／Linux のバックエンドだけでは解決しない。画像外マウスの `-1 -1` と未取得の重なりを既知の制限として残すか、状態を調べる語を追加するかは未決定。新語を加える場合は必要性・スタック効果・辞書互換性を別途検討する。自動表示先の保存と復元も、古い辞書へ推測で新仕様を適用しない。

### 10.8 今回のレビュー範囲と残る未確認事項

Claude Code の追加レビューと現行コードの照合を反映した。Microsoft の DPI の説明と `WM_IME_CHAR`、XKB のリピート仕様の一部は取得されたが、Apple 資料は今回再取得していない。Wayland の xdg-shell は非公式の閲覧サイトを参照した結果が報告されたが、公式 XML の確認に置き換えず、9章の未確認を維持する。
