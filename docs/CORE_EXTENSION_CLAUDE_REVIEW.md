# 613 詳細設計のレビュー結果

## 総合評価

全体の方向は既存の決定と合っています。3語群の分割、652 は debug 専用、通常実行ループを変えない方針、PCM は 900 だけに依存すること、の4点です。待機の手順（世代の記録→登録→再確認）、型付きハンドル、終端の扱いの考え方も妥当です。

ただし、タスク制御（1048）の中心である次の2点は、ソースと照らすと設計がまだ成立していません。このままの承認はできません。

- **通常ビルドの取消し経路**：Forth コードを動かすワーカーを debug なしで止める手段が定義されていません（R01）。
- **独立 VM の隔離**：State には辞書本体とホスト資源へのポインターが含まれます。Writer のコールバックはプロセス全体のグローバル変数につながっています。そのため、記述されている「独立 Storage＋辞書スナップショット」だけでは隔離になりません（R02・R03）。

工程にも欠けている点があります。共通の内部基盤（時計・起床・台帳・信号の所有）を実装するタスクがありません（R04）。信号の所有の決定（未決18）が debug 専用の 652 に割り当てられています（R05）。

## 指摘

区分は2つです。
- 【設計修正】：設計段階で直せる矛盾や欠落
- 【実装時検証】：試作・実測で確定する項目

### R01 重大【設計修正】通常ビルドで Forth を動かすワーカーを取り消す経路が未定義

- **対象**：11.4、11.1、7
- **根拠**：
  - 数えるループは `defs.debug_enabled` のときだけ選ばれます（`src/forth.zig:1815`）。
  - debug なしでは `checkWorkBlock` が何もしません（`words_numeric.zig:85-92`）。
  - 設計は「タスク用入口と許可したネイティブの境界に限定」「debug なしでも使える専用経路を設計する」とだけ書いており、方式を示していません。
- **失敗例**：debug なしのビルドで `BEGIN AGAIN`（または長い Forth の計算）を投入すると、TASK-CANCEL は確認点に一度も届きません。11.4 の「未完了・利用不可を明示」になったまま、BYE でも join できなくなります。
- **補足（ソースの事実）**：通常ループも毎回 `self.halted` を確認しています（`forth.zig:1878`）。しかし `halted` は BYE 用の非 atomic な bool です。CATCH がある場合は 0 を積んで再開するので（`forth.zig:1878-1890`）、取消しに流用すると、タスク内の CATCH が「成功」に見えます。そのままでは使えません。
- **修正提案**：1049 の比較ゲートで、次の候補を明記して比べてください。
  - (a) 初期版はワーカーで Zig ネイティブのジョブだけを動かす（ASYNC_OVERVIEW の「今回案」。R14 も参照）
  - (b) ワーカー専用に、comptime で3つ目のループ（取消し確認つき）を作る。メインのループは変えないが、通常ビルドのコードは増える。`executeOperations` での選び方が、メイン側の分岐を増やすかどうかを測る必要がある
  - (c) プロセスで隔離し、kill で止める
  - (d) 取消しできないことを仕様にし、許可するのは上限のあるネイティブだけにする

  「通常の実行ループを変えない」が「通常ビルドに別のループを足さない」まで含むのかは、決定の範囲の解釈になります。設計書だけで決めず、利用者の判断事項として示してください。

### R02 重大【設計修正】State/Storage を分けても隔離にならない状態の一覧が欠けている

- **対象**：11.3、2、1の表（`src/forth.zig` の行）
- **根拠**：
  - State の中に、ホスト資源やホストのメモリへのポインター・スライスがあります（`forth.zig:199-460`）。
    - `gfx_images`（ホストの `image_alloc_fn` が返した画素）
    - `gfx_pixels`、`tcl`、`capture_sink`、`wrap_guard`、`profile`、`lint`、`sh_get_result`
    - `source_line`、`embedded_source`
    - `audio_samples` など
  - Writer の `context` は1つだけで、`load_fn`、`save_fn`、`file_ops`、`input_fn`、`sleep_ns_fn` などを持ちます（`host_interface.zig:148-260`）。
  - それらの実装は、プロセス全体のグローバル変数を使っています。
    - `main.zig` の `open_files`、`file_peeked`、`lookahead`、`output_buffer`
    - `host_input.zig` の12個、`host_wait.zig` の `active`/`interrupted`
- **失敗例**：
  - State をコピーしてワーカーを作ると、`gfx_images` のスロットが同じ画素バッファを指します。
  - ワーカー側で `image_restore.apply` → `graphics_images.releaseAll` が動くと、メインの画像を解放してしまいます（`image_restore.zig:98`）。
  - ワーカーの `.` や `TYPE` が `write_fn` を通り、メインの `output_buffer` と競合します。
  - ワーカーの NS は `active` の衝突で、メインの NS を HostFailed にします。
- **修正提案**：
  - ワーカーは `State.init` から新しく作ってください。コピーはしないでください。
  - 権限表は、**ワーカー専用の Writer**（許可しない callback は null にし、その語は -21 で失敗させる）として実装すると明記してください。
  - 省略できない `write_fn` の扱いを決めてください（捨てるか、結果バッファに取り込むか）。
  - State の各フィールドについて、ワーカーで「初期化／コピー／禁止」のどれにするかの一覧を、1053 の成果物にしてください。

### R03 高【設計修正】「辞書世代」ではデータ空間の変更を検出できず、スナップショットの費用と意味も決まっていない

- **対象**：11.3（辞書は世代別に固定）、12（辞書の追加）
- **根拠**：
  - 辞書の本体は State の中にあります（`words[max_words]`、`code[65535]`、`names`。`forth.zig:203-214`）。
  - 変数や CREATE のデータは Storage.memory にあります。
  - 既存の `image_generation` は、復元のときにしか増えません（`image_restore.zig:24`）。
  - ASYNC_OVERVIEW の「辞書が更新された場合だけ同期」の案には、更新を検出する手段がありません。
- **失敗例**：
  - メインが `X !` で変数を書き換えても、世代は変わりません。後から投入したタスクが古いスナップショットの値を読みます。
  - 逆に、`!` に世代の更新を足すと、通常ループの変更になります。
- **修正提案**：
  - スナップショットは「投入時に毎回コピーする」か「アプリが明示して取る」かのどちらかにしてください。
  - ワーカーが読む変数は投入時点の値で、ワーカーが書き込んだ内容はメインへ返らない、という意味を仕様に書いてください。
  - 作り方は、既存の `encodeImage` → `restoreFresh`（新しく `init` した State へ）を候補として比べてください。辞書の relocation、`specializeCall`、`inline_calls.restore` を正しく再構成できる既存の経路だからです。
  - コストは「State（数 MB。`forth.zig:462` のコメント）＋メモリ全体」を基準に、1049 で測ってください（測るときは利用者に確認します）。

### R04 高【設計修正】共通の内部基盤を実装するタスクがない

- **対象**：2（RuntimeServices）、4、PLAN の依存表
- **根拠**：
  - 900 は仕様だけで完了します（PLAN:188）。
  - 内部基盤（時計の統一＝未決24、起床、型付き台帳、信号の所有）を使う最初のタスクが、互いに依存していません。
    - 998：900 のみに依存
    - 1038・1044：1056 のみに依存
    - 638：900・1056 に依存
- **失敗例**：998 と 638 が並行して、それぞれ別に待機と起床を実装し、時計が5つ目・6つ目と増えます。1038 の `DISPLAYS-OPEN` と 643 で、ハンドルの形式がずれます。
- **修正提案**：
  - 1055 の配下に「内部基盤の実装」タスクを足してください（または 1056 の範囲に明記してください）。
  - 998、1038、638、643、1050 は、そのタスクに依存させてください。

  PCM が 900 に「だけ」依存するという決定は、公開機能の依存（639 を待たない）についてのものです。内部基盤に依存させても、その決定とは矛盾しないと考えます（※解釈です。利用者の確認が必要です）。

### R05 高【設計修正】信号ハンドラーの所有（未決18）を 652 に割り当てている。既存のスコープ型 sigaction はスレッドが増えると競合する

- **対象**：13の表「10、18、20 → 652・900」、4.3
- **根拠**：
  - 652 は debug なしでは除外されます（決定9）。
  - 一方、EKEY-WAIT（638）、PCM-WAIT（998）、1043、1051 は通常ビルドで中断を検出する必要があります。
  - 既存のコードは、プロセス全体の sigaction を一時的に差し替えて戻しています。
    - `host_pipe_signal.zig`（SIGPIPE）
    - `host_resize.zig`（SIGWINCH）
    - `host_wait.zig`（SIGINT）
  - 音のスレッドは SIGPIPE だけを block しています（`host_audio.zig:435-438`）。
- **失敗例**：パイプの受信スレッドやワーカーが書込み中に SIGPIPE のスコープを張っている間に、メイン側のスコープが前の値へ戻すと、受信スレッドの書込みで SIGPIPE によりプロセスが終了します。
- **修正提案**：
  - 18 の担当は 900・638 にし、652 は「入れ子での利用」だけを担当してください。
  - 新しく作るスレッドはすべて、SIGINT・SIGWINCH・SIGPIPE を `pthread_sigmask` で block すると規定してください。
  - SIGPIPE はプロセスの開始時に一度だけ ignore にし、EPIPE で判定する方式を比べてください。この方式は SYSTEM の子プロセスへの継承に影響します（`host_process.zig:583` のコメント）。そのため【実装時検証】とします。

### R06 中【設計修正】1036 を基本語群に置く案では、1056 の縦通しにならない

- **対象**：3「OS判別 所属の提案は基本語群」、PLAN の 1036
- **根拠**：PLAN は 1036 を「1056 の基盤を使う最初の縦通し」と位置付けています。基本語群に置くと、`REQUIRE-EXTENSION`、files/debug の条件による選択、ライブラリの選択、HELP の機能表を、どれも通りません。
- **修正提案**：次のどちらかにしてください。
  - (a) 1036 は extension に置く
  - (b) 基本語群に置くなら、1056 の完了条件に「extension の最小の語（例：MONOTONIC-NS の雛形）による縦通し」を別に加える

  どちらにするかは、1056 で利用者に示して決めてください。

### R07 中【設計修正】入力の「消費位置を別に設ける」は、既存の EKEY と INKEY を混ぜたときの意味を変える

- **対象**：5（2段落目）
- **根拠**：
  - いまは EKEY と INKEY がどちらも `host_input.zig` から読み、1つの入力は一方だけが消費します（ASYNC_CORE_PLAN 2節）。
  - 既存の語は変えないことになっています（COMMON 未決14の案）。
- **失敗例**：
  - EKEY と INKEY を混ぜて使うアプリで、同じキーが二重に処理されます。
  - INKEY を一度も読まないアプリでは、共有バッファの INKEY 側の位置が進まず、満杯になると種類A（端末）の読取りが止まります。
- **修正提案**：
  - 端末の入力は、既存どおり一度だけ消費すると明記してください。
  - 「別の消費位置」は、ウィンドウの物理キーと既存の INKEY・マウスの関係（997 の決定）に限ってください。
  - 位置の遅れた消費者がある場合の扱いを、キューの種類ごとに表に加えてください。

### R08 中【設計修正】起床の手段が OS ごとに具体化されていない

- **対象**：4.3、6.1、11.3
- **根拠**：
  - Windows のウィンドウはウィンドウスレッドで動き、メインは `input_fn` でポーリングしています（`host_window.zig` 冒頭、`mouseMoved` の SRWLock）。
  - macOS は子プロセスとパイプのプロトコルです（`host_window_macos.zig:1-3`）。
  - Windows の `WaitForMultipleObjects` は、待てるハンドルが64個までです（OS の仕様です。今回のレビューでは文書を確認していません）。
- **失敗例**：メインが EKEY-WAIT で端末を待っている間にウィンドウの閉じる要求やタスクの完了が届いても、起こす手段がないため、期限まで待ち続けます。
- **修正提案**：
  - 起床の手段を、OS ごとに1つ決めて明記してください。
    - POSIX：self-pipe（または eventfd）＋poll
    - Windows：起床用の Event 1個＋コンソールのハンドル
    - macOS の子プロセス：その fd を poll に加える
  - 待機できる対象の上限を、この制約から決めてください。
  - スレッドからの通知は「状態の更新→世代の増加→起床」の順と規定してください。

### R09 中【設計修正】余白でのマウスの扱いが既存の契約とぶつかる可能性がある

- **対象**：9.3
- **根拠**：
  - 既存の処理は、画像の外では範囲外の座標を返します。余白でのボタンの変化もキューに入ります（`host_window.zig:521-543`、`window_layout.imagePixel`）。
  - Linux にも「letterbox coordinates preserve outside」というテストがあります（`host_window_linux.zig:1122`）。
- **失敗例**：「クリックを生成しない」を既存の MOUSE-EVENT に当てると、余白のクリックで UI を閉じるような既存アプリが動かなくなります。
- **修正提案**：
  - 既存の MOUSE と MOUSE-EVENT は変えないと明記してください。
  - outside は新しい API の付随情報に限ってください。
  - 変換には `window_layout` を再利用すると書いてください。

### R10 中【実装時検証】画面情報の取得能力が OS ごとに大きく違う

- **対象**：9.1、9.4
- **根拠**：
  - **Windows**：DPI 認識は、ウィンドウスレッドだけに Per-Monitor v2 を設定しています（`host_window.zig:851-868`）。メインスレッドから列挙すると、仮想化された座標になるおそれがあります（※推測です）。
  - **Linux**：Xinerama で矩形を取るだけです（`host_window_linux.zig:552-568`）。libX11 を使わない自前のプロトコル実装（`host_x11.zig:1`）なので、DPI・リフレッシュレート・主画面・作業領域・安定した ID を取るには、RandR などを手で実装する必要があります。
  - **macOS**：子プロセスとのプロトコルに FRAME/FRAME-ACCEPTED がすでにあり、presented を確認するにはプロトコルの拡張が必要です。
- **修正提案**：
  - 列挙はウィンドウスレッドで行うか、スレッドの DPI コンテキストを一時的に切り替えると規定してください。
  - 対応表に、Linux の初期能力（矩形だけ）、`-Dx11=false`、Tk を入れてください。
  - macOS は実機での確認が利用者の作業になる、と明記してください。

### R11 中【設計修正】premultiplied RGBA8 は既存の画素の意味と合わない

- **対象**：10（画素アルファ）
- **根拠**：
  - 既存の描画は `opaque_black` でアルファを 0xFF に固定しています。
  - 色キーは RGB で比べています（`rgb_mask`）。
  - copy モードは、元の画素の u32 をアルファバイトごと写します（`graphics_images.zig:262-293、433-453`）。
- **失敗例**：
  - premultiply で RGB が変わると、半透明の画素が色キーや既存の画素取得と一致しなくなります。
  - 色キーを「alpha=0 に変換」すると、画像そのものを書き換えるのか、転送するときだけなのかが曖昧です。
- **修正提案**：
  - 次の2案を比べてください。
    - (a) 保存はストレート（非 premultiplied）のままにし、合成するときだけ premultiply する
    - (b) 画像ごとに形式のフラグを持つ
  - 色キーは「転送するときの判定であり、画像は変えない」と明記してください。
  - `window_fn` へ渡すときにアルファを無視するかどうかは【実装時検証】です（未確認）。

### R12 中【設計修正】非ブロッキングの書込みが、既存の C ストリームと同じ fd を共有する

- **対象**：6.1
- **根拠**：ファイルは C ストリームで扱っています（ASYNC_CORE_PLAN 3節）。
- **失敗例**：WRITE-AVAILABLE のために fd へ O_NONBLOCK を付けると、同じ fid への既存の WRITE-FILE（fwrite）が EAGAIN で途中まで失敗し、既存の語の意味が変わります。
- **修正提案**：
  - 監視モードへ切り替えた fid では、同期の語を拒否するか、FILE* を flush してから fd だけで扱う、という移行規則を FileRecord に加えてください。
  - SIGPIPE は R05 にまとめます。

### R13 中【設計修正】直接依存の不足と、語群の独立性との関係

- **対象**：PLAN の依存表、3
- **根拠と問題点**：
  - 1046 は依存が「なし」になっています。同じ graphics の 1044・1000 は 1056 に依存しているので、1046 で語を足すなら 1056 が必要です。
  - 1039 は作成後に actual の更新を待ちます（9.2）。そのため、900（待機）と 1041（サイズの通知）が必要です。
  - 997・1041・1042 は 638（extension）に依存しています。しかし `-Dextension=false` の graphics 単独構成でも、これらは動く必要があります。
- **修正提案**：
  - 1046→1056、1039→900・1041 を追加するか、追加しない理由を記録してください。

### R15 中【設計修正】止められないワーカー・異常終了と、資源の回収

- **対象**：11.4、12
- **失敗例**：
  - BYE のとき、止まらないワーカーを join できません。その後、`main` の defer で Storage や画像を解放すると、解放後の参照になります。
  - 行入力の状態では、Ctrl+C の既定の処理でプロセスが終わります（COMMON 3節）。このとき、新しく足す子プロセス・代替画面・PCM は後始末されません。
- **修正提案**：
  - 止まらないワーカーについて、「そのスレッドが参照する Storage は解放せずにプロセスを終了する」と規定してください。
  - 子プロセスの回収や端末の状態を戻す経路として、SIGINT の既定終了を「保証しない」と、終了経路の表に明記してください。プロセスグループの扱いは 643 と合わせてください。

### R16 低【実装時検証】ネイティブの境界での取消し確認は、通常ビルドのコストを変える

### R17 低【実装時検証】EXEC-LIMITED で u=0 のときのループ選択

### R18 低【設計修正】Windows のウィンドウスレッドへの同期呼出しによるデッドロック
