## 確認できたこと

定数と変数の語を混在させると悪化し、単独では改善した。メモリー更新を含まない混在でも再現したため、`+!`単独が原因とはいえない。同じ値の変数アドレスを定数で返す対照条件では悪化が消えた。ただし、CPU内部で何が起きたかは未特定。

数値は候補版のCPU時間の増減。負数は短縮、正数は悪化。

## 測定条件

保存済みのWindows baseline/candidate実行体を使用。CPU0に固定し、起動とコンパイルを除くGetProcessTimesのCPU時間を測定。baselineが1秒以上になるよう反復数を校正した。各ケースはウォームアップ1回を除き5回の中央値。独立した親プロセスで2系列を実行し、初回順序を逆転、各回の実行順も交替させた。全チェックサムを照合し、小反復でSEEとスタック残数も確認した。各分割条件の正式なA/A校正はしていないため、小さな差の採否判断には使わない。

`mixed-sum`は定数と変数アドレスを参照してDROPと加算を行い、ループ内のメモリー読み書きを除いた。`constant-address`は元の混在更新と同じ本体で、変数アドレスを同じ値の定数として返す。`both-variable`は両方を変数とし、定数相当の値を@で取得する。`reversed`は変数と定数の参照順を逆転する。これらはVM命令列全体が同一と証明した対照ではなく、複数の条件差を含む。

## 生成コードの確認

対応するPDBを持つ別ビルドから関数を特定し、実測したstrip済みPEの逆アセンブルで処理を確認した。シンボル付きとstrip済みの関数は命令数とオフセットで対応するが、外部参照のRIP相対変位は異なり、バイト一致とは扱わない。

通常VMループはbaselineの8743バイトから候補の9553バイトへ増え、スタック予約量も56から200バイトへ増えた。baselineでは定数と通常変数のpushが別の経路にあり、候補では同じpush経路を共有して保存したPCを読み戻す。通常の+!では両方とも直接メモリー加算する経路があり、アドレス登録数が0の場合にwriteCellを呼ぶコードではなかった。

これらのコード形状の差と混在時の悪化は確認できたが、PCの保存、分岐予測、コード配置など個別の寄与は分離できていない。ハードウェアカウンターは取得していない。原因を特定した修正として新しい実装を入れる根拠はまだ不足している。

## 次の検証

小さな試作で、定数・通常変数の呼出し経路だけを変更し、混在ケースの悪化が消えるか確認する。これは原因を確定した修正ではなく、コード形状の対照実験として扱う。良好でもWindows・Linuxの通常8項目、CATCH9項目、回帰テストとサイズ条件を再確認するまで採用しない。

本調査ではVM本体を変更せず、コミット・タグ・プッシュは実行していない。
