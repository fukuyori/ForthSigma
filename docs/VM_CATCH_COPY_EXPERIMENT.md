# CATCH名前領域の中間コピー削減（2026-11-16）

**結果：第1候補は不採用。本体は維持した。Linux fastのmemcpy＋memmove呼出しで観測したコピー長の合計は減ったが（総メモリー転送量やWindowsの観測ではない）、Windows整数演算とスタック操作の悪化が既定上限を超えたため、全項目の比較を打ち切った。**

## 基準と範囲

tque #781〜785。基準VMは採用済みPC分離＋データ語経路分離のコミット`7b1295fc9c79d3d90db0a56d1408a68004c7b5b1`。本体と作業用コピーを分離し、`.work/catch-copy-20261116/`に基準・候補・入力ハッシュを保存した。検証用の基準コピーにはこのコミットに新テスト1件だけを加えた。新テストは基準・候補で共通の別保存テストで、性能差を生む変更には含めない。runtime 3ファイルのcandidate-current.patchだけでは新テストは再現できず、観測JSONのnew_test_patchを別に適用する。コミット・プッシュは今回の依頼に含めない。

旧調査の3×255バイトという観測は旧版Linuxの結果であり、現行版の測定として転用しない。現行の両生成物を作り、コピー長と呼出し元を再観測する。

## 第1候補の設計

`CatchContext.init`の構造体返却を、呼出し元のローカル変数へ初期化する`initInto`にする。`handleError`と`restoreCatchFrame`はconst参照を受け取る。保存する255バイト全体と全フィールド、処理順は変えない。長さ0でも全体を保存する。

| 経路 | 保存先と寿命 |
| --- | --- |
| compiled CATCH入口 | enterCatchのローカルcontextへ構築。エラー処理・defer終了まで生存 |
| 継続開始 | 従来どおりcontextをcatches配列へ値コピー。ローカルへのポインターは保持しない |
| compiled THROW | resumeCatchは従来どおり値を返す。呼出し元ローカルがhandleError完了まで生存 |
| interpreted CATCH | runCatchのローカルcontext。対象語・ホスト再入・deferをまたいで生存 |
| 復元 | handleErrorからそのcontext.frameへのconst参照を渡す。参照を保存せず同期処理内で使う |

pop済みcatchesスロットを参照する設計は今回採らない。継続への直接構築も、入口の容量判定より前に配列を参照する変更を避けるため第1候補には含めない。State/CallFrame/CatchContextのレイアウト、容量、ヒープ割当ては変えない。

## 検証の順序

1. 同条件のLinux fast・シンボル付き生成物でコピーを観測。削減がなければこの候補は打ち切る。
2. 削減があれば既存の境界テストを照合し、名前領域の全255バイトの復元など不足分を検証する。
3. 両OS・構成別テスト後、時間測定用の実行体を固定。A/A校正後、全17項目を独立2系列で比較する。ビルド・テストと性能測定を重ねない。
4. 標準採用条件を変更せず、CATCHだけの改善は部分改善として扱う。レビュー・採否は結果を見て記録する。

## 現在の状態

第1候補はコピー削減と回帰テストを通過したが、Windowsの対比較で悪化上限を超えたため不採用。CATCH自体とLinuxの候補比較は打切りにより未測定。本体未反映。

整数演算の2系列で打切りを判断した。制御を確認してチェックポイントを設置する間にスタック操作の2系列も完了していたため、この結果も保持する。続く呼出しの系列1は完了したが、系列2の開始前にworkerが意図した終了75となり、親controllerが終了1になった。プロセスの強制終了ではなく、VMの失敗を示す終了コードでもない。この未完了ペアは採否・安定した悪化の判定に使わない。

[選定文書の「第一候補の実施順と打切り条件」箇条6](VM_ADDITIONAL_MEASURES_SELECTION.md#第一候補の実施順と打切り条件)は通常処理や他CATCHの悪化上限を超える場合に見送るとしている。その条件に従った早期不採用であり、残る32条件の候補比較は完了させなかった（呼出しの片系列を除き未着手）。CATCHの部分改善としても、通常処理の悪化を許容する新基準は設けない。今回のコード・配置で悪化した根本原因は未特定。命令配置やCPU内部の理由を断定せず、別の修正を推測で重ねない。

## レビュー対応と残件

[Claude Codeレビュー原文](VM_CATCH_COPY_CLAUDE_REVIEW.md)では、不採用と早期打切りは支持され、現在の呼出し元に寿命違反は見つからなかった。これは静的レビューであり、Claudeがテストや性能測定を再実行したという意味ではない。

必須の文書指摘は、古い「現在の状態」の修正、Linuxコピー観測の限定、完了2条件と残る32条件の区別、打切り条件・上限式の出典、基準コピーへの新テスト追加と別パッチの所在、基準・候補ともmemcpy＋memmove捕捉であることの追記で対応した。

CPU列の制御文字という指摘は現ファイル・保存入力の実バイト列で再確認したが、該当行のCPU値はASCIIの4（0x34）で制御文字はない。実測系列のcpu_affinityも[4]で、他33条件は[0]。数値の書換えはせず、[レビュー対応記録](VM_CATCH_COPY_REVIEW_RESPONSE.md)に照合結果を記した。

新テストの保証範囲は上記のとおり限定した。全域を異なる値で上書きするケース、noname_nextの反転、名前が異なる入れ子やCATCH-NOBT・入口エラーと組み合わせた復元は、この試作を再検討する場合の追加検証として残す。今回は不採用なので、弱いテストを十分な安全性証明として扱ったり、本体へ新テストを追加したりしない。

runtime参照APIを将来再利用する場合は、pop済み継続スロットの参照を渡さず、同期利用中のcontext/frameの寿命を呼出し元が保証する契約を明示する。今回の呼出し元ではローカル保存領域だけを渡している。

通常処理の悪化原因は未特定。CATCH案を再試行する、又はこの結果から共通の最適化原因を導く場合は、同じ条件のWindows生成物で通常ループ・スタック操作の生成コードを比較してから判断する。次のROT/-ROT評価は、この候補の原因仮説を根拠にせず独立した実験として行う。LinuxやCATCHの残る候補比較は、不採用判断のための必須作業とはしない。
