## 583：例外構文5語

| 語 | 対応案 | 確認すべき違い |
| --- | --- | --- |
| TRY | 例外領域を開始するコンパイル専用の即時語 | 正常時にCATCHのような0を自動追加しない |
| IFERROR | 例外時の分岐を作り、THENで閉じる | ENDTRYまでハンドラーが有効で、処理中の例外も再び捕捉する |
| RESTORE | 正常・例外の両経路が通る後処理 | 再例外時は後処理を再開する。暗黙に元の例外を再送出する語ではない |
| ENDTRY | 領域を閉じる | 正常・例外双方で継続状態を解放する |
| ENDTRY-IFERROR | 領域を閉じてから例外分岐へ進む | 分岐内の再例外は外側へ伝える |

特にRESTOREは、一般的な言語のfinallyと同一だと説明しない。Gforthの例でも、正常経路で0を用意し、後処理後のTHROWで再送出の有無を決めている。後処理が常に例外になると再開を繰り返すため、試験時にはステップ上限が必要になる。

### Sigmaへの接続案

現状の`CatchContinuation`は呼出し元フレームを保存し、被呼出し語の終了または例外時にCATCHの直後へ戻る。TRYには、同じ定義の途中の例外分岐へ戻り、宣言済みローカルを保つ別の継続先が必要になる。

実装案は、既存の例外コンテキストを共有しつつ、継続を「語呼出しのCATCH」と「定義内のTRY」に区別する方式とする。TRY開始・解除のVM命令と分岐先を持たせ、通常のデータ／浮動小数点／利用者リターン／ループの深さ、呼出し、ローカル領域を整合させる。Gforthのハンドラーフレームの生のメモリー配置は再現対象にしない。

無名引用へ機械的に変換する方式は推奨しない。Sigmaの引用・ローカルのスコープ、EXIT、ループ制御を別の定義へ移してしまわないことを、先に保証する必要があるためである。

### 実装前に比較して確定する項目

- TRY中のEXIT、LEAVE、ループ分岐、RECURSEと、対応するENDTRYを通らない経路。残ったハンドラーを別の呼出しが誤利用しない設計を必須とする。
- ローカル宣言をTRYより前・中・後に置いた場合のスコープと例外後の寿命。保存されるスタックの深さと、内容が復元されるという誤解も区別する。
- IFERRORとRESTOREで一度だけ再例外を起こす場合と、ENDTRY-IFERROR内で再例外を起こす場合。
- CATCH／CATCH-NOBT／FAST-THROW／NOTHROW、入れ子TRY、バックトレース、プロファイルとの相互作用。
- 現在CATCHを通過するQUIT・StepLimitの扱いを維持する案。BYEを例外と同一視しない。
- 即時属性、POSTPONE、制御構造の不整合とコンパイル失敗時の巻戻し。
- 命令の追加が保存・復元・追加読込み・SAVESYSへ与える影響と、旧イメージの扱い。

5語を一組の機能として仕上げる。内部の作業順はVM継続基盤、構文、境界・保存・デバッグ検証とし、TRY/ENDTRYだけを先に「互換対応済み」としない。

## 584：ブロック拡張9語

| 語 | 対応案 | 実装時の重点 |
| --- | --- | --- |
| +LOAD | BLKからの相対読込みを追加 | 符号付き加算の範囲、入れ子後のBLK復元 |
| +THRU | BLKからの相対範囲読込みを追加 | 基準BLKの保持、逆順・空範囲・上限 |
| --> | 即時のブロック継続として追加 | 現ブロックの残りを捨てて次へ進む。REFILLとの共通化 |
| OPEN-BLOCKS | 名前付きファイルの選択を追加 | 旧ファイルの変更保存、新ファイルを開けない場合の状態 |
| USE | 解析したファイル名をOPEN-BLOCKSへ渡す | 空名、空白、パス検索と作成先 |
| GET-BLOCK-FID | 現ファイルの借用IDを公開 | 未選択時の既定ファイル、外部CLOSE-FILE後の扱い |
| UPDATED? | 比較対象に合わせた変更状態問い合わせを追加 | 参照版ではBUFFERを呼ぶため、純粋なメタデータ参照とは限らない |
| BLOCK-OFFSET | 初期値0の番地取得語を追加 | 物理位置は番号からoffsetを引いて1024倍。変更前後のdirtyバッファー |
| BLOCK-INCLUDED | 別ファイルのブロック1を読み、元へ戻す機能を追加 | 入れ子、正常終了、例外、保存・閉じる処理の失敗 |

GforthがTRYを使ってOPEN-BLOCKSを実装していても、Sigmaの584を583に依存させない。Zig側のエラー処理と既存CATCH基盤で、独立に実装できる構成を提案する。

### 先に必要な基盤

現在は`blocks.fb`を遅延オープンする単一`Storage`であり、バッファー識別はブロック番号だけである。ファイル切替を名前の置換だけで追加すると、旧データの誤読や、変更した内容を別ファイルへ保存する危険がある。

選択ファイルとその世代、読取り専用属性、ファイルに対応するバッファーを一体で管理する案とする。切替時は旧dirtyデータの保存が成功するまで破棄しない。新ファイルのオープン失敗、旧ファイルのflush失敗・close失敗を別々に扱い、どのIDを所有するか、再試行できる状態かを明示する。close失敗後も必ず元どおり利用できる、という保証はホストの動作確認なしに置かない。

BLOCK-OFFSETは通常の`!`で変更されるため、変更の検出なしに現在値で古いdirtyバッファーを書き戻さない。バッファーに元の物理対応を保持し、アクセス時に対応変更を検出・整理する案を推奨する。負の物理位置や乗算のオーバーフローを検査する。厳密なエラーコードはGforth比較後に確定する。

BLOCK-INCLUDEDは外側の入力スナップショットだけでなく、ファイルの所有権、offsetの扱い、バッファーの対応も保存・復元する設計が必要である。参照版の手続き列をそのまま写さず、例外時の復元と保存失敗時に未保存データを失わないことをSigmaの要件とする。参照版と差が出る場合は互換性文書へ明記する。

GET-BLOCK-FIDは借用として説明し、ブロック基盤が閉じる責任を持つ案とする。利用者が閉じた場合の不正ID検出、ID再利用、外部からの書込みによるキャッシュとの不整合は、公開前の確認項目に含める。

### 推奨する作業順

1. ファイル選択・所有権・失敗時状態を整理し、OPEN-BLOCKS／USE／GET-BLOCK-FIDを追加。
2. +LOAD／+THRU／-->／UPDATED?を追加。UPDATED?のアクセス副作用も比較する。
3. BLOCK-OFFSETとBLOCK-INCLUDEDを追加し、番号変換・一時切替・復元を統合検証。

相対読込みを先に試作することは可能だが、584全体としては切替基盤の設計を先に固める。9語が揃うまで未対応分を一覧に残す。
