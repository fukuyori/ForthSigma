- A2：未比較32条件＝非予備30条件＋校正のみ実施したLinux予備2条件、と明記した。
- A3：全Windows比較CPU値が15.625ms刻みであることを実データで照合した。系列2の上限3%は約2.91刻み、中央値差3刻み。A/A δ0%は分散ゼロや信頼区間ではなく、比較の基準試行は1,375.000〜1,578.125msに広がることを記録した。

**A4の「中央値に影響せず」という指摘には相違がある。** 元の7試行の中央値は1,562.500ms。この最終試行を外した6試行の参考中央値は1,554.688msとなり、基準に対し約2.577%になる。除外すると判定が変わり得るため、影響なしとは記さない。今回の判定は事前手順どおり元の7値すべてから計算し、除外後の値を採否に使わない。統計的に普遍的な悪化と断定せず、保守的な点推定ゲートの不通過に限定する。

新テスト2件はcore_words_testの無条件testで、全実行構成に含まれ、これら2件にskip分岐はない。debug有効構成ではcompiled呼出しのkeep_counting false/trueを実行し、debug無効・最小構成ではどちらも非counted経路になる。この区別を追記した。checkpoint.jsonは今回存在せず、workerの終了75機構は使用していない。controller自身が予定した上限判定で自然終了0となった。

任意指摘C3の「DO...LOOP内の反復を新テストが検証していない」は正しい。ただしbuiltinInLoopはDO...LOOP専用ではなく、compiled -ROTもsrc/forth.zigのcall_builtinフォールバックから通る。builtinInLoop自体が未検証という解釈には相違がある。ソース上の呼出し経路と動的な網羅率の測定は区別し、今後のループ内重み付きテスト追加は別の強化項目として残す。

時計量子化に対する再試行条件は今後の測定前に固定する。既存の閾値を遡って緩めたり、wallを新たな合格指標にしたり、δの床を勝手に採用したりしない。次のコード配置調査で予備タイミングを追加する場合は、基準を5秒以上に伸ばして刻みの比率を小さくする案を検討する。
