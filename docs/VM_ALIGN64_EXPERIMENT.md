# VMループ関数の64バイト配置対照（2026-11-16）

**最終判断：標準改善候補として第1試作は不採用。追加ログ版のWindows整数演算で約11.98%/15.00%悪化し、既定の第1ゲートを満たさなかった。本体は維持した。悪化のハードウェア原因は未特定。**

## 選定の根拠と範囲

#789でWindows計時版と生成コードを対応付け、ROT試作では通常ループ入口のPC保持と入口SP減算が同じであり、ROT側の呼出し・データ移動と配置が変わることを確認した。その差のどれが時間へ寄与するかは分からない。[調査と時間指標の追加ログ](VM_WINDOWS_DISPATCH_INVESTIGATION.md)を参照。

次はアルゴリズムと配置を混ぜないため、採用済み7b1295fのrunOperationsLoopだけにalign(64)を指定する対照を選んだ。64は今回あらかじめ決めた1条件で、最適な値・ハードウェア原因・改善率を推測で決めたものではない。悪化したROT/CATCH試作やそれらの新テストは混ぜていない。根拠のない新ライブラリー挙動も組み込まない。

Zig 0.17.0のローカル標準ライブラリーに関数宣言のalign指定の実例があり、同じツールチェーンで実際に両OSのビルドを通して構文・対象での対応を確認した。runtime差分はprivate関数宣言1か所の属性だけで、VM操作、保存形式、PC/CallFrame、スタック容量、ヒープ割当ては変更しない。

## 回帰検証と第1判定の手順

Windows Debug/fastは各1,070成功・10skip、debug無効1,003成功・77skip、float無効1,005成功・49skip、最小構成589成功・462skip。Linux Debug/fastは各core1,011成功・5skip、host63成功・1skip。これらは前の未採用試作の新テストを含まない基準共通テストで、件数差をテスト削除による通過とは扱わない。freestandingはコンパイル検証。WindowsからのLinux直接起動終了1と、WSLでのELF各終了0は区別した。

[回帰・ビルド・入力](measurements/2026-11-16-vm-align64-validation.json)を保存した。Windowsの計時版でもPDB版の先頭32バイトが一意に対応し、両ループのVAが64で割り切れることと、外部参照を抽象化した全命令列の維持を確認した。Linux計時版の全命令列を同じ方法で照合したとは主張しない。

実測前に第1標準ゲートを固定した。Windows整数演算N=629,508,196（以前の同一基準版の約3秒の縮尺を2倍）、新規A/Aを各5回×独立2系列、全中央値5秒以上・δ最大2%以内が条件。ここで未達なら自動的な反復数探索や候補比較を行わない。通過時だけ対比較を各7回×独立2系列で行い、整数演算の既定標準条件（各10%以上短縮かつ2δ超）と悪化上限を判定する。標準条件未達なら残る候補比較へ進まず、未測定範囲を記録する。この配置対照にはROT専用のような別の部分改善合格率を設けない。第1条件だけの通過で本体へ採用することもない。

すべてPEのイメージ上VA。今回の計時コマンドにはtrace/profile/step等を付けず、既定の非counted経路を測る。counted側は基準から既に64バイト整列済みで、今回64バイト移動しただけ。非counted側は48バイト動き、入口だけでなく同一相対位置にある全内部ラベルもmod64で48、mod32で16ずれた。計時版とPDB版の差を混同せず、特定の入口整列だけが遅さの原因とは記さない。

初回の規則ではA/A未達でその走行を終えている。追加ログ版は、候補測定前に別途固定した**プロトコル改定による別走行**で、同じNの2回目の校正機会である。一次CPU式と閾値は変えていないが、追加API読取り・観測負荷がある点は異なる。protocol生バイト列・SHA-256とstartのUTCを保存し、記録上start→最初のA/A→最初の候補比較の順序を照合した。保存記録以上の暗号学的な時系列証明とは扱わない。

参考として初回δ2.089%を今回の増減に代入しても悪化上限2δ約4.178%を超える。ただし初回校正が通過したことにはせず、別走行のデータを初回screenへ転用しない。
