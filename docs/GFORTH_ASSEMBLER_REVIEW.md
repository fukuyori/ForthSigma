# アセンブラー関連8語の対応検討（582）

2026-11-15。Sigma `7b9e4dd`のVM・辞書・ビルド構成と、Gforthの公開仕様を照合した。実装は行っていない。

## 結論

「システムが巨大になるなら見送る」という利用者の方針と、検討結果を記録して完了にする指示に基づき、8語とも今回の対応を見送ると決定した。機械語の実行基盤は、現在のVMへ少数の便利語を追加する範囲を超える。実行体サイズや工数は試作・測定していないため、増加量を数値では断定しない。確認した判断材料は、必要になる仕組みと保守範囲である。

ASSEMBLERやINIT-ASMだけを空の語彙として追加したり、FLUSH-ICACHEを常に何もしない語として登録して、対応済みと数えることもしない。機械語を生成・実行する用途が具体化した時に、対象CPU・OSと利用場面を限定して再検討する。

## 語ごとの判断

| 語 | Gforthでの役割 | Sigmaへの対応判断 |
| --- | --- | --- |
| CODE | VMの実行方式に接続する機械語定義の開始 | SigmaのVMへ戻る規約を新設する必要があり、見送り |
| ;CODE | CREATEで作る語に機械語の実行動作を与える | 作成語・本体番地・機械語の寿命管理まで影響するため見送り |
| ABI-CODE | プラットフォームの呼出規約を使う機械語定義 | 呼出しの橋渡しとCPU・OS別の対応が必要なため見送り |
| ;ABI-CODE | 作成語の動作をABI経由の機械語にする | ABI対応に加え、作成語の本体を渡す設計が必要なため見送り |
| END-CODE | 機械語定義の終了 | 開始・実行基盤と一組の機能であり、単独では追加しない |
| ASSEMBLER | 検索順の先頭をアセンブラー語彙に置き換える | 語彙切替自体は既存基盤にあるが、命令を生成する語群が必要。空の語彙は追加しない |
| INIT-ASM | アセンブラー語彙を検索順へ追加する | 実体となるアセンブラーがないため追加しない |
| FLUSH-ICACHE | 命令キャッシュを同期する | 機械語領域の管理と対象別の保証を伴うため追加しない |

公開仕様の根拠：[Gforth 1.0 Assembler Definitions](https://gforth.org/manual/1.0/Assembler-Definitions.html)。CODE系はGforthのVM実装へ、ABI-CODE系はCPU・OSの呼出規約へ依存し、両者を区別する。[AMD64の説明](https://gforth.org/manual/1.0/AMD64-Assembler.html)でもWindows x64とLinux側の規約を分けている。

従来の比較基準版にある[code.fs](https://github.com/forthy42/gforth/blob/c479e1eec66dd57a2441c3020177267ba70d3bdc/code.fs)も参照した。公開1.0マニュアルと従来の比較版を、同じ版であるかのようには扱わない。Gforth実行体での比較や全CPUのアセンブラー調査は今回は行っていない。

## Sigmaで確認した現状

- [defs.zig](../src/core/defs.zig)のWordKindとOpKindは、辞書語とVM命令を定義する。機械語の利用者定義を扱う種別はない。
- [forth.zig](../src/forth.zig)のwordIdは実行トークンを辞書番号として検査する。executeWordとexecuteOperationsが語種別・VM命令を実行する。実行トークンをホストの関数ポインターとしては扱わない。
- 同ファイルのmemoryAddressは論理メモリーのオフセットを検査する。利用者の番地を、そのままCPUの実行番地に使う設計ではない。
- [dictionary_image.zig](../src/core/dictionary_image.zig)は辞書語・VM命令・論理データの保存と追加時の再配置を扱う。機械語領域の保存・再配置を扱う実装は確認できなかった。
- [build.zig](../build.zig)は通常のネイティブ実行体に加え、Cortex-M0+のfreestandingコアのコンパイル確認を含む。機械語実行を追加する場合も、コアへOS依存を直接持ち込む設計は避ける必要がある。

src配下のZig/C/ヘッダーについて、VirtualAlloc・VirtualProtect・mmap・mprotect・命令キャッシュ同期の代表的な名前を検索し、該当はなかった。これは検索結果であり、依存ライブラリ内部まで含めて一切の関連処理が存在しないという証明ではない。

## 対応した場合に増える設計・確認範囲

以下は現行実装との差から整理した設計上の評価であり、実装済みの仕組みではない。

1. 機械語の格納・実行領域、書込みから実行への移行、解放と命令キャッシュ同期。対象OS・CPUの条件も確認する必要がある。
2. Sigmaのスタック・論理番地とネイティブ呼出しとの橋渡し。Gforthのスタック配置やVMレジスター規約を、そのままSigmaの仕様として採用できない。
3. SAVE・LOAD-DICTIONARY・SAVESYSにおける機械語の扱い。CPU・OS・ABIの識別、移動時の参照、異なる環境のイメージ拒否、または保存自体を制限する方針が必要になる。
4. FORGET・MARKER・辞書復元後の機械語と参照の寿命。作成語が機械語を参照する場合も含む。
5. CATCH・バックトレース・ステップ上限・プロファイルの適用範囲。任意のCPU命令を現在のVM命令と同じ単位で検査・計測できるとは扱わない。
6. 実用的なアセンブラーを同梱するなら、命令・レジスター・分岐などの語群とCPU別の検査。バイト列を直接入力する方式でも、実行と保存の基盤は必要になる。

単一CPU・単一OSだけに限定しても、このうち実行・呼出し・寿命の基盤は必要になる。ビルドオプションで無効化できるようにしても、対応版の実装と保守の負担は残る。このため、今回の規模抑制方針には全面対応も限定対応も合わないと判断する。

## 現在の代替手段と再検討条件

通常の拡張はForth定義・CREATE/DOES>を使う。性能上の問題がある場合は先に計測し、必要な処理だけをZigの組込み語として追加する方法を個別に検討する。これはアセンブラー語の互換実装や、任意のネイティブコードを読み込める機能を意味しない。FFIや外部ライブラリーの読込みを今回の代替実装として追加することもしない。

再検討は、既存語では満たせない具体的な用途、対象CPU・OS、必要な速度や外部接続、保存の必要性が明確になった場合に限定する。語数の互換性を増やすことだけを理由に実装しない。
