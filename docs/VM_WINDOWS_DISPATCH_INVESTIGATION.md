# Windowsディスパッチ・分岐・PC調査（2026-11-16）

#789で計時版の生成コードと計時の揺らぎを調査し、配置だけを変える64バイト関数アラインの対照実験を選定した。#814〜818の記録を以下に残す。悪化原因の特定や速度改善の確定には至っていない。本体は変更していない。

## 計時版への対応付け

ここで示すVAはPEヘッダーImageBaseを用いたイメージ上の値。実行時ASLRロード先は今回取得していない。

前回採用版と不採用ROT試作を、同じfast・baseline CPUでWindows GNUシンボル付きビルドした。PEにはCOFF関数名表がなく、生成されたPDBをllvm-pdbutilで読み、runOperationsLoopのsection:offsetとcode sizeを抽出した。PDBのoffsetは10進表示としてPE section情報からVAへ変換し、llvm-objdumpで命令列を取得した。Linuxのアドレスや関数名をWindowsへ転用していない。

両ループの先頭32バイトは、各計時用strip実行体内でそれぞれ一意に一致した。関数全体の生バイト列は一致しない。命令の相対位置、レジスタ、定数、内部分岐先オフセットを保ち、外部call/branch先とRIP外部参照だけを抽象化すると、シンボル版と計時版の全命令行が一致した。外部参照先すべての意味的一致を証明するものではない。

| 実装 | 基準サイズ／命令行 | ROT候補サイズ／命令行 |
| --- | ---: | ---: |
| 非counted側 | 9,628バイト／1,954行 | 9,605バイト／1,948行 |
| counted側 | 13,081バイト／2,520行 | 13,073バイト／2,517行 |

counted側にはcheckWatches・traceRunning・showStepStackの直接呼出しがあり、非counted側にはない。これらのコードと、sourceのcomptime counted条件との対応から区別した。表は静的行数で、反復当たりの実行命令数ではない。

## 確認した差と、まだ分からない点

通常ループ先頭は両版のシンボル版とも0x14003d650。PC/endをrcx/r12dへ読み込む入口と、sub rsp,0xc8（200バイト）の入口SP減算は同じだった。今回のROT試作で、ループ入口の保持方式やこの入口SP減算量が大きく変わったとは扱わない。プロセス全体の最大スタック使用量を測った結果ではない。

基準のROT側は、深さ3の検査後、3セル・回転量1を指定してrotate__func_139を呼び、通常関数呼出し後に作業値を復元する。候補は関数呼出しがなく、64ビットの読込み・書込みとmovdquの16バイト読込み・書込みになった。そのブロック以降の内部ジャンプ先と命令配置はずれるが、変更した事実だけでは5.155%/3.093%の計時差の原因を説明できない。

[生成物のハッシュ・PDB対応・命令列・照合スクリプト](measurements/2026-11-16-windows-dispatch-code.json)を保存した。LinuxのCallgrindで命令数が減ったことと、Windowsの時間が悪化したことは別の観測であり、CPU内部の因果関係は未特定。CATCH試作と同じ原因という断定もしない。

## 次のログ取得

Windowsの基準版と同じROT候補を固定し、VM実装は変えずにカーネルだけを分ける。ROT単独とROT+SWAPを、それぞれ順序が分かる重み付きチェックサムで確認する。基準のみの100M反復pilotから約6秒を目標に反復数を固定し、新規A/Aの全中央値5秒以上・δ最大2%以内を要求する。校正はウォームアップ1回除外後5回×独立2系列。未達なら自動再試行や都合のよい条件選びをせず、その事実を残して候補計時へ進まない。

校正通過時のみ、候補比較を各7回×独立2系列で行う。すべての試行を保存し、外れた値も除外しない。各子プロセスのPIDと全生存期間のCPU時間も保存し、READY/DONE間のCPU時間・wall時間と区別する。既存の3%閾値やδの定義を過去へ遡って変えず、この分離測定だけで採用やハードウェア原因を断定しない。

測定前の手順と進捗は`.work/vm-dispatch-20261116/`へ保存。ビルド・テスト・他の時間測定を重ねずに実行している。


## 分離測定の校正結果

ROT単独のbaseline-only pilot100M反復はCPU468.750msで、候補を読む前に反復数1,280,000,000を固定した。新規A/Aは全中央値が5秒以上だったが、系列1の差3.107%、系列2の差2.557%で2%上限を超えた。予定した手順に従い自然終了0とし、候補比較もROT+SWAPも未実施。長い値を除外したり、都合よく校正を繰り返したりしていない。

| 系列 | A1 CPU中央値 ms | A2 CPU中央値 ms | δ |
| --- | ---: | ---: | ---: |
| 1 | 5,703.125 | 5,531.250 | 3.107% |
| 2 | 5,640.625 | 5,500.000 | 2.557% |

wallとCPUの揺らぎは同じではないため、ソースの分岐配置が原因と決めず、kernel/user・process cycle・wallの区間値を同じ基準版で追加ログ取得する方針を選んだ。cycle値は診断の生データであり、新しい採用基準にはしない。Processor Information計数も補助ログとして取得する。監視自体の負荷がある診断走行で、採用用のベンチマークとは区別する。

#817では同一基準版・同一NでA/Aを2系列取得し、CPU時間をkernel/userに分け、QueryProcessCycleTimeの生値・PID・UTC・区間境界も保存した。logical0のProcessor Information計数を1Hzで150回取得した。監視負荷を含む診断走行で、候補の採用用ベンチマークではない。

指標ごとの変動率の違いを確認できたが、GetProcessTimesのkernel時間差の根本原因や、過去の候補の長い1試行の原因までは特定していない。候補はこのログで再計時していない。過去の不採用や閾値を遡って変更せず、wall/cycle値を勝手に採用指標へ切り替えない。

## プロセス全体と主スレッドの照合

#824でPython3.14の実際のCreateProcess戻り値からprimary TIDを記録し、同じ区間のGetProcessTimesとGetThreadTimesを照合した。READY時点には2〜3スレッドが存在したが、集計対象の全20試行でプロセスCPU時間と主スレッドCPU時間の差は0μsだった。process/thread cycle差は最大86,860で、約211億の区間値に比べ小さかった。これは今回の診断走行において、背景スレッドCPUの加算が観測差を説明しないことを示す範囲に限る。スレッド照会は同時ではなく逐次API読取りであり、他の過去走行まで原因を否定するものではない。

今回のCPU時間A/A差は1.977%・1.136%、wall差は0.118%・0.245%、process cycle差は0.0080%・0.0026%。前の未達ログをこの別走行で通過扱いへ書き換えない。一次指標を主スレッドCPUへ替えても、この走行では値が同じであり、改善する根拠にはならない。計時の根本原因はまだ未特定。
