# VM_PERFORMANCE_PLAN.md の設計レビュー

方針は妥当で、実装前の計画として大筋で通せます。ただし案Aの書き戻しの必要性と、Aより安い先行実験が抜けています。

## A. 重大度付きの指摘

### A-1【高】案Aの「全退出での書き戻し」は、現行構造ではほぼ不要で、誤読すると危険です（計画61行目）

- **外側のRunningは退出後に使われません。**
  - 外側の`running`が使われるのは、ループへの再入力時と、`resumeCatch(&running)`が丸ごと上書きする時だけです（`forth.zig:1801-1816`）。
  - Quit、StepLimit、通常のreturnでは、`runOperations`は`running`を読まずに戻ります。
  - 例外後の`checkWatches(running.pc -| 1)`（1813行）は、`resumeCatch`で復元済みの値を読みます。
  - したがって、必要なのは入口のコピーだけです。「最後の状態を書き戻す」処理を足すと、復元済みの`running`を古い値で潰すバグを作れます。
- **本当の危険は、外側ポインターの取り残しです。**
  - `enterCatch`（1618-1624）は`running.*`を書き換えて呼び出し先へ切り替えます。
  - `halted`経路の`resumeCatch(running)`（1831）と`returnToCaller`（1682）も`running.*`を書き換えます。
  - これらのどれかがループ外の`running`を指したまま残ると、切替が黙って失われます。
  - 失われるとフレームだけ積まれて本体が走らない状態になり、CATCHテスト群で検出できる種類の不整合になります。
- **failed_pcは現行実装でループ内の`self.failed_pc = running.pc`に記録されます（1823-1825）。**
  - この更新はローカル化しても同じ値を読めます。
  - 注意点は2つです。
    - `try`の各エラー経路で、pcが「取得後に進めた値」であること。
    - ヘルパー呼出しの前にローカルが退避されていること。
  - `executeOperations`のerrdefer（1779）は、`failed_pc`と`frames`だけで`recordBacktrace`を行います。外側`running`は不要です。
- **現行の挙動で、改善後も維持を明示すべき点（仮説）。**
  - Quit、StepLimitで`runOperations`が戻る時、`failed_pc`が更新されない経路があります。
    - たとえば`handleError`が再スローした場合です（1809-1812）。
  - `halted`経路（1829-1833）では`resumeCatch`後に`push(0)`するだけです。
    - `returnToCaller`（1684-1688）と違い、`backtrace_suppression`の復元と`call_depth`の置換がありません。
    - `runOperations`のdeferが最終的に`backtrace_suppression`を戻すため、実害があるかは未確認です。
  - これらはAの対象外なので、「挙動を変えない」の基準にしてください。

### A-2【高】Aの効果が出る前提が、計画の「ローカルコピー」では成立しにくい（計画63行目）

- ローカル`running`のアドレスを`enterCatch`、`builtinInLoop`、`wordInLoop`、`returnToCaller`へ渡す限り、アドレスが逃げます。
  - 現状も外側の変数のアドレスを渡していて、条件はほぼ同じです。
  - 計画の「最適化が変わる保証がない」はその通りです。
- **仮説**：効果を出すには、ホットパスでアドレスを渡さない設計が必要です。
  - `call`／`call_colon`／`execute`／`branch`／`loop`／`exit`は、すでにループ内で直接`running.*`を操作しています。
  - ヘルパーが必要なのは、`builtinInLoop`の`catch_word`と`catch_nobt`、`wordInLoop`、`local_execute`、`does`、`returnToCaller`の`push(0)`だけです。
  - ヘルパーを呼ぶ直前だけ、ローカルを一時変数へコピーし、呼出し後に戻す形で試せます。
  - アドレスが逃げる範囲が冷たい経路に限られれば、SROAが効く可能性があります。
  - ただし`returnToCaller`はinlineなので、アドレスが逃げない形にできます。
- 計画は、この「どのヘルパーにアドレスを渡さないか」を第0段階の逆アセンブル観点に入れるとよいです。

### A-3【高】Aより安い先行実験が計画にありません（H1/H2の補強、仮説）

- **ループ先頭の`if (self.halted)`（1829行）が毎命令実行されます。**
  - 整数演算のような`inline else`のホット命令でも、メモリーロードと分岐が発生します。
  - `halted`が立つのは、ホストコールバックやBYEなどの呼出しの後だけのはずです。
  - 確認できれば、`.builtin`／`.call_builtin`／`wordInLoop`／`execute`の復帰後にだけ検査する案が考えられます。
  - この案はVMの規模をほぼ増やしません。
- **整数演算とLOOPの悪化は、CATCHを呼ばない命令で起きています。**
  - 整数演算は`inline else`経由です。
  - LOOPは`inline .loop`です。
  - したがって、CATCH経路のコードそのものより、ループ頭の共通コストの可能性があります。
  - 具体的には、`halted`検査、`running`のメモリー経由アクセス、`catch_depth`と`entry_catches`の保持、`ran`の更新などです。
- ただし、旧コミットとの差分は未確認です。「`halted`検査がf1140c7で追加された」とは断定しません。
- **A-3の提案**：実験0に、`halted`検査の位置の移動案（A0）を並べてください。AとA0は一つずつ測り、混ぜないでください。

### A-4【中】案Bに欠けている設計条件（計画69〜75行目）

境界退出・再開は、現行の`runOperations`が例外時にすでに行っている構造に近いです。通常呼出しを遅くしないために、次が未定です。

1. **ループのローカル状態の引継ぎ。**
   - `ran`（WATCH用の直前の命令）は`runOperationsLoop`のローカルです（1827行）。
   - 退出・再開で失われます。
   - CATCHへ入る直前の命令でWATCHを検査するか、`ran`を外側へ持つかを決める必要があります。
2. **戻り値の符号化。**
   - 現状の戻り値は`RuntimeError!void`です。
   - 「遷移のための退出」を新しい値で返すには、型の変更が必要です。
   - 呼出し側で比較が増え、ホット経路のコードサイズに効きます。
   - エラーセットへ偽のエラーを混ぜる方式は、`errdefer`の`failed_pc`更新、`defer`、`backtrace`を誤作動させます。
3. **`wordInLoop`のdeferred CATCH後処理。**
   - `catches[..].call_depth = call_depth`の後処理（1655-1657）を、ドライバー側へ移す必要があります。
   - 移さないと、DEFER経由CATCHの`call_depth`が戻りません。
4. **enterCatchの`handed`フラグと`backtrace_suppression`の扱い（1571-1575）。**
   - 引渡し済みかどうかを、境界をまたいで保持する必要があります。
5. **ホストの再入の境界。**
   - 再入した内側の`runOperations`は、`entry_catches`と`entry_frames`で外側のCATCHを越えない設計です（1792-1793、1804）。
   - Bで遷移の責任を移しても、この境界を壊さないことが条件です。
6. **counted時のイベント順。**
   - `traceRunning`、`checkWatches`、プロファイルの`unwind`の順序を保つ必要があります。
- Bは、Aが無効だった理由が「ループ頭の共通コスト」なら、効果が出ない公算が大きいです。
  - CATCH関連の検査は`builtinInLoop`の1比較（1630行）と`returnToCaller`の`catch_depth`検査（1684行）だけです。
  - 昇格の条件に、「Aの逆アセンブルでCATCH経路が原因と特定できた場合のみ」を足してください。

## B. 指摘ではない設計上の限界

- **ループ頭の共通コストは、現行の設計に由来するものが多いです。**
  - `running.pc >= end_pc`、frames経由の呼出し・復帰、`halted`、`catch_depth`は、CATCH安全化とホスト再帰回避の対価です。
  - 完全に回復できる保証はありません。
- **旧版との比較は、構造が違います。**
  - 旧版はCATCHがホスト再帰で、`frames`が無い構造でした。
  - 速度が戻っても同じ機械語にはなりません。
- **A/B/C/Dは、機械語レベルの原因が未特定です。**
  - 「ソースの一部分と性能低下の因果」はH1/H2/H3の仮説です。
  - 逆アセンブル比較で原因が分離できない場合、Aを残さない判断で正しいです。
- **ビルド間のコード配置の差による±数%は、構造的な限界です。**
  - 小さな差の判定には使えません。
- 辞書画像との整合は確認していません（`dictionary_image.zig`は未読）。Aは辞書形式を変えない前提ですが、`CallFrame`を変えた場合は確認が必要です。

## C. 推奨案と具体的判定基準

### 推奨する実験順

1. **A/A基準線の測定。**
   - 同じソースを別ビルドしてA/Aの差を出します。
   - 無関係な変更（未使用関数の追加など）で配置が変わった場合の差も測ります。
   - 揺らぎを`δ`とします。
2. **逆アセンブル比較。**
   - 現在版の非countedの`runOperationsLoop`の、`inline else`ホット命令と`inline .loop`を中心に見ます。
   - 見る点は次の3つです。
     - `halted`ロード
     - pc／end_pc／`running`のメモリー参照
     - ヘルパー呼出し前後の退避
3. **A0：`halted`検査の位置の移動。**
   - 検査位置の移動の効果を、先に測ります（A-3）。
4. **A：ローカル`Running`。**
   - ヘルパー直前の一時コピー方式を試します（A-1、A-2）。
   - A0とAは一つずつ測ります。
5. **A0とAのどちらも不十分な場合のみ、Bの設計レビューへ進みます（A-4の条件を満たす場合に限る）。**

### 判定基準

| 項目 | 計画案 | 推奨 |
| --- | --- | --- |
| 整数演算とLOOPの最低改善 | 各15%以上 | A／A0の小規模案は各10%以上で保持してよい。Bは各15%以上。両方とも`δ`の2倍を超えること |
| 回復目標 | 80%以上 | 参考値として維持。合否には使わない |
| 他カーネルの悪化 | 3%超で2系列再測定 | `max(3%, 2δ)`超で2系列再測定し、再現したら不採用。2系列の中央値が両方とも超える場合を「再現」とする |
| サイズ | 実行体の増加は各1%以内 | 各1%以内で妥当。非countedの`runOperationsLoop`のコード量（逆アセンブルの命令数）も併記する |
| CATCH専用測定 | 未数値化 | 成功・深い入れ子・動的CATCH（EXECUTE／DEFER経由）は現在版比で+5%以内。THROW／FAST-THROWの経路は揺らぎが大きいので+10%以内。Aは通常ループだけの変更なので、基本は±`δ`内を期待する |
| メモリー | 既存容量・割当てを増やさない | 維持。`CallFrame`のサイズ（pc／end_pc／defining_word／locals_frame）も変えないこと |
| 反復数 | 最終判定は1億反復・7回 | 維持。最小・最大・中央値と、同系列の`δ`も併記する |

- 判定値は私の提案で、実測に基づく校正はまだありません。`δ`の測定後に見直してください。

2. A0を先に試すか、Aと同時に準備するか。
3. ヘルパーへ渡す`Running`の扱い（一時コピーか、ホットパスからのアドレス除去か）。
4. CATCH専用カーネルの追加場所（`benchmark-runtime.py`と、期待値の検証）。
5. Aが無効だった場合の撤退基準（保持の最低基準を満たさなければ破棄、とすでに書いてあるのでそのまま維持）。
6. テストの追加範囲（A-5）。
