# VM速度改善の第0段階調査（2026-11-15）

本書は改善実装前の調査記録である。その後の[案Aの実験と不採用判断](VM_PERFORMANCE_A_EXPERIMENT.md)は別に記録した。

続く[CATCHの処理負担とRunningの受渡し調査](VM_CATCH_COST_AND_BOUNDARIES.md)では、名前領域のコピー長、動的CATCHの経路差、成功用0の容量不足とBYEの組合せを追加確認した。この調査時点では改善実装は未着手だった。

## 結果

通常ループのPC保持に具体的な生成コード差を確認した。CATCH変更直前はPC・終端PCをレジスターに保持し、変更直後と現在版は、命令取得ごとにRunningのPC・終端PCをメモリーから読み、進めたPCを書き戻す。この差はシンボル付き調査用実行体だけでなく、以前の速度測定に使ったstrip版でも確認した。

これは[計画](VM_PERFORMANCE_PLAN.md)のH1を支持する証拠である。**この差だけで時間増加の割合や因果全体を確定したわけではない。** ※推測です：PCの更新・再読込みの依存が、整数演算やLOOPの実行時間増加に寄与している可能性がある。案Aの局所保持で生成コードが変わるかを次に確認する根拠となる。

改善実装は行っていない。A/A測定、調査用ビルド、逆アセンブル、VM命令列の読取り、Callgrind計数、埋込み資源の改行を変えた対照実験を行った。追加調査では、埋込み資源の改行差だけでもベンチマーク結果が変わることを確認した。したがって、メモリー参照の増加だけで既存の時間増加率全体を説明しない。

## 生成コード

### 通常ループの識別

counted版は外側からtraceRunningを呼び、ループにもWATCHやステップ用の呼出しがある。以下はそれらを持たない非counted版を対象とした。関数番号は今回のビルド固有である。

| 版 | 通常ループ | バイト数 | 静的命令行数 |
| --- | --- | ---: | ---: |
| 直前 | runOperations__func_112 | 7,677 | 1,505 |
| 直後 | runOperationsLoop__func_116 | 7,961 | 1,539 |
| HEAD | runOperationsLoop__func_181 | 8,550 | 1,647 |

バイト数は`nm -S`のシンボルサイズ。命令行数はobjdumpの命令行を数え、バイト列の折返し行は除外した。nopなどの配置用命令は含む。旧版の表は外側処理も含むため、純粋なループ本体だけの同一範囲比較ではない。動的実行命令数でもなく、この増加率から実行時間を説明しない。

### PCと終端PC

直前の命令取得（シンボル付き`0x10d0ded`、strip版`0x10d0bfd`）は、`cmp r14w,r15w`でPCと終端を比較し、`add r14d,1`でPCを進める。この通常ディスパッチ部分にはRunningのPC書戻しがない。locals_frameもレジスター`r11`に保持される経路を確認した。

直後（シンボル付き`0x10d3030`、strip版`0x10d2e40`）は次の形になる。r14は外側が所有するRunningへのポインターである。

```asm
movzx ecx, WORD PTR [r14+0x8]  ; pc
cmp   cx, WORD PTR [r14+0xa]  ; end_pc
; 終端判定、命令取得
add   ecx, 1
mov   WORD PTR [r14+0x8], cx  ; 更新後pc
; ディスパッチ
```

HEADのシンボル付き`0x1101f90`と、保存済み50e661eのstrip版`0x1101d50`にも同じ読込み・書戻し構造がある。直後ではlocals_frameも必要な分岐で`[r14]`から読み込まれる。すべての命令でlocals_frameを読むという意味ではない。

調査用とstrip版では.textのハッシュが一致しなかったため、シンボル付き全体を測定用と同一の命令配置とは扱わない。上記の共通ディスパッチ差はstrip版自体を逆アセンブルして再確認した。

### ヘルパーと停止検査

直後・HEADともbuiltinInLoopとwordInLoopは通常ループから別関数として呼ばれる。enterCatchの独立シンボルはなく、その処理に対応するXT消費・CATCH状態保存などの命令列はbuiltinInLoop内にある。非countedのbuiltinInLoopは直後1,665バイト、HEAD2,663バイト、wordInLoopはそれぞれ521、510バイトだった。

今回確認したコードでは、例外ヘルパー全体が通常ループの複数箇所へ展開されている形は確認できなかった。したがって、そのような展開を前提としたA2の実施根拠はまだ得られていない。ヘルパー内部の展開や配置の影響全般を否定したものではない。

停止検査は旧版にも存在する。新しいコードでは停止判定からCATCH巻戻しへ分岐するが、その追加だけで性能低下を説明できる計数結果は取得していない。A0の境界証明も未実施であり、停止検査の削除は提案しない。

## SEE比較と限界

初回は同じ8カーネルを3版に入力し、BENCH-RUNのSEE出力が全項目で一致することを確認した。

追加調査では、GDBでseeBodyの機械語上の入口にブレークポイントを置き、State.codeの各命令のPC・OpKind名・数値タグ・valueを読み取った。実行体は変更していない。callsのBENCH-A/B/Cも含めた計11定義で、**CATCH変更の直前と直後のこれらのフィールドが全件一致**した。構造体の未使用パディングを含むバイト単位の比較ではない。

## 保存済み版の完全再現とPC参照の対応付け

### 残る16バイト差はVERSIONの改行

埋込み資源をLFにした50e661eの調査用コピーについて、作業ツリーに合わせてさらに55ファイルの改行を揃えたが、実行体は1,888,016バイト・同じSHA-256のままだった。続いて、507ファイルをバイト単位で同じ内容のまま別のビルドルート`.work/vm16-src/`へ複製してビルドしたが、これも同じ実行体になった。今回の残差について、これらの改行差やビルドルートの違いが原因という証拠は得られなかった。

次にELFの.rodataを比較した。両実行体で4759個ずつある.text内への整列済みポインターをセクション相対値へ置き換えて差分を調べ、VERSIONの生文字列に到達した。保存済み版には`0.10.0\n`、調査コピーの再ビルドには`0.10.0\r\n`が入っていた。main.zigは版表示用の文字列をtrimEndしているが、今回の実行体では末尾改行を含む元の埋込みデータも残っていた。

調査コピーのVERSIONだけを`0.10.0\n`にして再ビルドしたところ、**1,888,000バイト、SHA-256 `5ff80c55b17444d3d091699b61b4552b516cabfa15fc133416aa6736fc0f2592`となり、保存済み版と完全一致した。** 出力は`.work/vm-investigation-20261115/saved-exact/bin/sigma`。VERSIONの1バイト差が、配置・パディングを含む実行体の16バイト差につながっていた。リポジトリ本体のVERSIONや資源は変更していない。

これにより、保存済み版の不明な生成コード差を前提にする必要はなくなった。今後の入力固定では、グラフィックス等の資源だけでなくVERSIONも実バイト列のハッシュ対象にする。バナーに表示される版文字列が同じという確認だけでは足りない。

### 命令アドレス単位でPC参照を数えた結果

Callgrindの`--dump-instr=yes --dump-line=no`を使い、直前・直後・HEADの整数演算・LOOP・callsを各1,000／2,000反復で計18回測定した。全実行でネイティブ実行と出力が一致し、対象ループの命令別Ir合計が収集範囲全体のIrと一致することも検査した。集計対象は前節と同じシンボル付きの非countedループである。

直後版とHEADではr14がRunningを指す。反復に比例するPC参照は次の4箇所だった。回数は前節と同じく反復数の差分から算出した1反復あたりの値。

| 対象命令 | 整数演算 | LOOP |
| --- | ---: | ---: |
| PC読込み `[r14+0x8]` | 7読込み | 5読込み |
| 終端PC比較 `[r14+0xa]` | 7読込み | 5読込み |
| 命令取得後のPC書戻し | 7書込み | 5書込み |
| LOOPによる分岐先PC書込み | 1書込み | 1書込み |
| 合計 | 14読込み・8書込み | 10読込み・6書込み |

直後版の前3箇所は`0x10d3030`、`0x10d3035`、`0x10d304e`、LOOPの書込みは`0x10d4b15`。HEADではそれぞれ`0x1101f90`、`0x1101f95`、`0x1101fae`、`0x1103e05`である。

これは、CATCH直前→直後の整数演算の総増分（読込み69−55=14、書込み27−19=8）、LOOPの総増分（読込み52−42=10、書込み19−13=6）と一致する。これら2カーネルでは、追加されたPC・終端PCのメモリー参照がメモリー参照の総増分に対応することを確認できた。ほかのメモリー参照が命令単位ですべて一対一対応するという証明ではなく、実CPU上の所要時間の増分を算出した結果でもない。

callsでは共通ディスパッチのPC・終端PCを各13回読み、PCを13回書き戻すほか、呼出し・復帰時のRunning全体やlocals_frame等への参照もあった。既存のフレーム参照の生成方法も変わるため、同じ単純な足算でcallsの総増分全体をPCだけに帰属させない。
