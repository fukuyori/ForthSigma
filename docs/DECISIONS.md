# FORTH/Σ移植の決定事項と保留事項

資料に明記された仕様、Zig移植で選んだ動作、資料だけでは決められない点を分けて記録します。ソースページの対応は[FORTH/Σ仕様書](SPEC.md)、実装上の値と未実装機能は[実装ノート](IMPLEMENTATION.md)を参照してください。

## 方針の変更（2026-10-28）

利用者の指示により、Gforthの挙動に近づけ、教材ForthBasicMasterのサンプルが動くことを目標にしました。作業は6段階に分け、段階1（コアの変更）、段階2（浮動小数点）、段階3（文字列・数値書式）を実装済みです。意味が衝突する部分はGforthに合わせ、衝突しないFORTH/Σ固有のワードは残しています。GforthはGPLv3のため、挙動だけを参照し、コードは移植していません。

| 段階 | 内容 | 状態 |
| --- | --- | --- |
| 1 | 64ビットセル、1 MiBメモリ、真=-1、床関数除算、全文字の名前照合、TYPE ( addr u )、基本標準ワード | 実装済み |
| 2 | 浮動小数点スタックとF系ワード（教材Level 17の範囲） | 実装済み |
| 3 | 文字列・数値書式（S"、<# #>、倍長整数など） | 実装済み |
| 4 | ローカル変数 | 実装済み |
| 5 | 例外・ファイル・動的メモリ（Level 14の `$!` などの動的文字列を含む） | 5a（THROWと主なファイル語）、5b（ALLOCATEと動的文字列）、CATCHを実装済み |
| 6 | 語彙・条件付きコンパイル | 実装済み |

### コロン呼び出しの保存フレーム（2026-11-04）

`CallFrame` と実行中の状態は同じ型を使う。ローカル変数フレームのアドレスは `?Cell` から `Cell` にし、0を「ローカル変数なし」とする。ローカル変数領域は0より大きいアドレスから始まることをコンパイル時に確認する。Windows/Linux x86_64で保存フレームは24バイトから16バイトになり、1024個のフレーム領域は8KiB小さくなる。呼び出し・スタック・メモリの上限検査と例外復帰は維持する。実行状態の表現だけの変更で、保存イメージには含まれない。

### 短いコロン定義の展開（2026-11-04）

終端の `EXIT` を除いて1〜4命令のコロン定義を、コンパイル時に呼び出し箇所へ展開する。対象はリテラル、実行トークン、専用命令になった組み込み語、既に展開された呼び出しの検査だけで、即時語・再帰・分岐・ローカル変数・動的呼び出し・`DOES>` は展開しない。展開分と残り1命令分の空きがない場合は通常の呼び出しにする。この判定は、その後に続く定義全体が収まることを保証しない。展開によってコード領域の消費は増えるため、従来は収まった定義でも、後続の命令や終端の `EXIT` で `OUT OF CODE SPACE !` になる場合がある。保存イメージにも展開領域を残すので、従来は収まった複数イメージの `LOAD` が容量不足になる場合もある。

実行ループの命令タグは増やさず、`call_colon` のオペランドに元の語番号、展開の長さ、必要な呼び出し深さを格納する。各呼び出し位置で元と同じ順に深さを検査し、フレームの保存・復元を省く。`SEE` は元の呼び出し名を表示する。保存時には通常の `call` と展開領域を飛ばす `branch` に戻すので、保存形式は `SIGIMG33` のままで旧版でも実行できる。復元時は、領域内へ入る分岐や語の入口がなく、元の定義から正しく展開できる場合だけ再構築する。旧イメージでも、空の `ELSE` や直後へ飛ぶ分岐が展開領域と同じ命令列になる場合は再構築の対象になる。現行版の `SEE` ではその空の分岐が省略されることがある。逆に、展開対応前の旧版で新イメージを読むと、保存用の分岐が余分な `BRANCH` や空の `ELSE` として表示されることがある。これらは表示上の制約であり、`SEE` は元のソースを完全に復元する機能ではない。

| 記録の場所 | 論理メモリ2D0Hのセルに `GRAPHICS` 語彙の語番号、2D8Hのセルに「読み込んだことがある」印を置く。以前の版はこの2つのセルに書かないので、`SIGIMG33` のイメージでは0。2D0Hの語が `GRAPHICS` 語彙で、その次が `GFX-INIT` のときだけ読み込み済みとみなすので、`FORGET` や `MARKER` で消えたあとは、もう一度読み込める。`FORGET GFX-WIDTH` のように `GFX-INIT` より後ろの語だけを消した場合は読み込み済みのままで、`REQUIRE-GRAPHICS` は消えた語を戻さない（制限）。セルにどんな値があっても判定は安全に偽になる。 |
| 復元と追加読み込み | `SIGIMG34` を復元すると、`GFX-` の語はほかの利用者の語と同じく辞書の項目として戻り、読み込み済みになる。復元に成功すると、それまでの画像は使わなくなる（領域はホストのもので、コアは解放しない）。失敗した復元では画像も残る。`LOAD` で `SIGIMG34` を追加すると、読み込み済みの印と `GRAPHICS` 語彙の番号（付け替えた後の番号）を引き継ぐ。フレームバッファ、ウィンドウ、OSの資源は保存しない。復元した辞書では、`GFX-INIT` を実行するまで画像はない。 |
| `SAVESYS` | `SIGIMG33` と `SIGIMG34` のどちらも実行ファイルに入れられる。 |
| `-Dgraphics=false` の版 | `SIGIMG34` も読み込むが、`GFX-` の語の実行は、ほかの除いたグループと同じく `INVALID EXECUTION TOKEN`。 |

#### G1の語と動作

| 語 | スタック | 動作 |
| --- | --- | --- |
| `GFX-INIT` | ( w h -- ) | 新しい画像をホストから受け取り、黒（不透明）で埋める。幅・高さは各1〜16384、1 GiBまで。範囲外は `NUMBER ERROR`（-24）、ホストに確保の機能がなければ `HOST FUNCTION UNAVAILABLE`（-21）、確保の失敗は `OUT OF MEMORY`（-257）で、前の画像を残す。 |
| `GFX-WIDTH` `GFX-HEIGHT` | ( -- n ) | 画像の幅・高さ。`GFX-INIT` の前は0。 |
| `GFX-PSET` | ( x y rgb -- ) | 色は下位24ビットの `0xRRGGBB`（上位は無視）、透明度は常に255。画像の外は何もしない。 |
| `GFX-PGET` | ( x y -- rgb ) | 画素の色。画像の外は-1。 |
| `GFX-HLINE` | ( x1 x2 y rgb -- ) | x1からx2まで（両端を含み、順序は問わない）の横線。画像の端で切る。 |
| `GFX-CLS` | ( rgb -- ) | 画像全体を塗る。 |
| `GFX-SAVE-PPM` `GFX-SAVE-BMP` | ( c-addr u -- ior ) | 2進のPPM（P6）、無圧縮24ビットのBMP（下の行から、各行を4バイトの倍数に詰める、72 dpi）で保存する。ior は開く・書く・閉じるのうち最初の失敗。ファイルはホストを通して書くので、`-Dfiles=false` の版でも使える。 |

画像がないときの `GFX-PSET` `GFX-PGET` `GFX-HLINE` `GFX-CLS` と保存の語は `NO GRAPHICS IMAGE`（-271）。ホストの関数は `Writer.framebuffer_fn`（画素数を受け取り、成功したら前の領域を解放して新しい領域を返し、失敗したら null を返して前の領域を残す）。違う長さの領域が返ったときは `HOST FUNCTION ERROR`（-265）とし、前の領域は解放された前提で画像を使わなくする。ライブラリは `src/graphics/graphics.fs` を `@embedFile` で埋め込み、ファイル番号 -2 の取り込み元としてコアが自分で1行ずつ読む（ソースファイルの表の名前は `*graphics library*`）。G1のライブラリは注釈だけで、描画の語はG2で加える。

2026-11-05、Codexのレビュー（`f182fdc`）で、(1) ライブラリが定義の途中で失敗すると、`report` や `CATCH` の復帰が消した語を戻す、(2) 使用済みの State への `restoreImage` が画像を残す、(3) 2D0Hの値によっては判定の加算があふれる、(4) ホストが違う長さを返すと古い画像を参照し続ける、と指摘された。利用者の指示で4件とも直し、回帰テストを加えた（埋め込みソースの行の読み方、4096バイトを超える保存と書き込み・閉じる失敗、`-Dgraphics=false` での `SIGIMG34` の実行も含む）。一部の `GFX-` の語を消した場合の扱いは、上の制限として記録した。ライブラリの語の `LOCATE`/`WHERE` はG2で扱う。

#### G2: Forthの描画ライブラリ（2026-11-05）

利用者の決定: 色は現在の色を `COLOR ( r g b -- )` で決める方式（`RGB` `COLOR!` `COLOR@` も置く）、`RECT` は左上と幅・高さ `( x y w h -- )`、塗りつぶしは `FILL-RECT` `FILL-CIRCLE`、`PAINT ( x y -- )` を入れる。

| 項目 | 決定 |
| --- | --- |
| 語 | `RGB` `COLOR` `COLOR!` `COLOR@` `PSET` `CLS` `LINE` `RECT` `FILL-RECT` `CIRCLE` `FILL-CIRCLE` `PAINT` `SAVE-PPM` `SAVE-BMP` を `src/graphics/graphics.fs` にForthで書き、`GRAPHICS` 語彙に置く。補助の語は名前を括弧で囲む（例 `(CLAMP)`）。標準の `FILL` と名前がぶつかる語は作らない。 |
| 現在の色 | ライブラリの変数に置き（辞書イメージに残る）、最初は白。`GFX-INIT` では変わらない。`CLS` は黒で塗る。 |
| 線 | Bresenhamの方法。端点が画像の外なら、Cohen–Sutherlandの方法で画像の端まで移してから描く（`*/` の切り捨てで端点が1画素ずれることがあるので、移す回数は8回までとし、残りは `GFX-PSET` が切る）。 |
| 円 | 中点アルゴリズムの画素を、円周をたどらずに行ごとに求める。第1八分円（0 ≤ x ≤ y）で列 x の y は `x² + y² − y < r²` を満たす最大の y、すなわち `(isqrt(4(r² − x²)) + 1) / 2` であり、ほかの八分円はその鏡像なので、各行の画素はこの式から直接決まる。縦横・対角線に対称になる。`FILL-CIRCLE` は各行を円周のいちばん外の画素まで塗るので、同じ引数の `CIRCLE` の画素をすべて含む。描く行は画像の中の行だけなので、半径がどれほど大きくても、1行あたりの手間は同じ。テストでは、八分円をたどる独立した中点アルゴリズムと、半径0〜64、画像の外にはみ出す中心を含めて画素が一致することを確かめる。 |
| 値の制限 | あふれを防ぐため、`LINE` `RECT` `FILL-RECT` の値は ±2^61（差がセルに収まり、`*/` は倍長で掛ける）、円の値は ±2^30（半径の2乗がセルに収まる）に寄せてから描く。 |
| `PAINT` | 上下左右につながる同じ色の領域を、行単位で塗る。まだ塗っていない行の始まりを、ヒープ（`ALLOCATE`）の作業用スタックに2セルずつ積み、足りなければ2倍に `RESIZE` する。エラーのときも `CATCH` でヒープを解放してから `THROW` し直す。非常に複雑な領域ではヒープが足りず、`ALLOCATE`・`RESIZE` の ior（-524、`CANNOT ALLOCATE MEMORY`）を `THROW` し、途中まで塗られる。作業用の変数を共有するので、`PAINT` の中から `PAINT` を呼ぶことはできない（今のライブラリにそうする経路はない）。 |
| 保存 | `SAVE-PPM` `SAVE-BMP` は `GFX-SAVE-*` の ior を `THROW` する。 |
| 画像がないとき | ライブラリの描画の語も、何も描かない場合を含めて `NO GRAPHICS IMAGE`（-271）にする。 |
| `BASE` | `REQUIRE-GRAPHICS` はライブラリを10進で読み、読み終えたら（失敗したときも）`BASE` を元に戻す。 |
| `HELP` | `REQUIRE-GRAPHICS` が加えた語（`GFX-` の語と、ソースファイルが `*graphics library*` の語）は、組み込み語と同じく説明を表示する。同じ名前でも利用者が後から定義した語は、これまでどおり「起動後に定義した語」と表示する。 |
| `LOCATE` `WHERE` | ソースファイルの名前が `*graphics library*` のときは、ファイルを開かずに、その版に埋め込んだライブラリの本文から行を表示する。ほかの版のイメージから復元した語では、行が合わないことがある。 |

性能（2026-11-05、fast、Windows x86_64、1024×768の画像、`UTIME` で計測、1回ずつ）: `GFX-CLS` 0.09 ms、`GFX-PSET` 33 ns、`PSET` 38 ns、`LINE`（768画素）81 µs（1画素あたり約0.1 µs）、`RECT`（1000×700）29 µs、`FILL-RECT`（全体）0.18 ms、`CIRCLE`（半径300）0.97 ms、`FILL-CIRCLE`（半径300）0.73 ms（レビュー対応後の円は0.85 ms・0.93 ms）、`PAINT`（全体）90 ms、`PAINT`（512本の櫛形）187 ms。止まった絵を描くには十分なので、利用者の決定（2026-11-05）でZigへ移す処理はない。

G2の後にCodexのレビューで、半径4などで円が対角線に対称にならないこと（四捨五入した平方根の式が中点アルゴリズムと違った）と、`PAINT` のヒープ不足のエラー名が文書と違うことが指摘され、円を上の方式に直し、文書を直した。`LINE` の端点を移す回数の条件も、記述どおり8回までにした。G1のライブラリ（注釈だけ）を読み込んだ開発中の辞書では、`REQUIRE-GRAPHICS` は読み込み済みと判定するので、G2の語は加わらない（G1は配布していない）。アニメーション（G4）で足りなくなったときは、まずForthのまま（円の行ごとの平方根を減らすなど）速くする。

#### G3: 画面への表示（2026-11-05）

利用者の決定: `SHOW` が現在の表示先へ画像を出し、表示先は `DISPLAY-TERMINAL` と `DISPLAY-WINDOW` で切り替える。端末は半角ブロックを既定にしてSixelも選べるようにする。画像が端末より大きいときは端末の大きさに縮小する。Windowsのウィンドウは専用のスレッドで動かす。

| 項目 | 決定 |
| --- | --- |
| 語 | ライブラリに `SHOW` `DISPLAY-TERMINAL` `DISPLAY-WINDOW` `TERMINAL-BLOCKS` `TERMINAL-SIXEL`、基本語に `GFX-SHOW-BLOCKS` `GFX-SHOW-SIXEL` `GFX-SHOW-WINDOW` `GFX-WINDOW?` を加える（`GFX-` の語は既存の9語の後ろに登録する）。 |
| 表示先 | ライブラリの変数に、0（自動: ホストにウィンドウがあればウィンドウ、なければ端末）、1（端末）、2（ウィンドウ）を持つ。既定は自動なので、別のOSで読み込んだ辞書でも、その環境の表示先になる。ウィンドウのないホストでの `DISPLAY-WINDOW` は `HOST FUNCTION UNAVAILABLE`（-21）。 |
| 半角ブロック | 1文字（上半分のブロック U+2580）で上下2画素を、前景色と背景色の24ビット色のエスケープで表す。色は変わるときだけ出す。高さが奇数の画像の最後の行は、下を端末の背景色にする。行の終わりで色を戻す。 |
| Sixel | 色は6×6×6の色立方体の216色（各画素を最も近い色にする）。色の定義を最初に出し、6行ごとの帯で、使う色ごとに `#色` と6画素の縦の並びを繰り返しの圧縮（`!回数`）付きで出す。幅は4096画素まで（帯をStateに置く）。 |
| 縮小 | 端末の大きさはホストに聞く（ホストが答えないとき、たとえば出力がパイプのときは80桁24行とみなす）。半角ブロックでは、桁数×（行数−1）×2画素に収まるよう、縦横比を保って縮める（拡大はしない。1行はプロンプトのために残す）。Sixelでは、ホストが端末の画素数を知っていればそれに、知らなければ1文字を10×20画素とみなして収める。縮めた1画素は、元の画素の平均の色にする。 |
| UTF-8 | 半角ブロックを書く前後に、ホストの関数 `terminal_utf8_fn` を呼ぶ。Windowsのホストは、標準出力がコンソールのとき、その間だけコンソールの出力コードページを65001（UTF-8）にして、終わったら元に戻す（それまでの出力は先に書き出す）。 |
| ウィンドウ（Windows） | Win32 を Zig から直接呼ぶ（新しいCライブラリは使わない）。ウィンドウは専用のスレッドでメッセージを処理するので、Forthが入力を待つ間も動かす・大きさを変える・閉じることができる。`SHOW` は画像をホストの領域に写し（ロックで守る）、ウィンドウに描き直しを頼む。画像の大きさが変わると、ウィンドウの大きさも合わせる（1600×1200を超える画像は縮めて表示し、ウィンドウの大きさを変えると、それに合わせて伸び縮みする）。ウィンドウは表示してもキー入力の焦点を取らないので、続けてコンソールに入力できる。利用者が閉じたウィンドウは、次の `SHOW` で開き直す。描き直しの依頼は、まだ処理されていない依頼がないときだけ送り（待ち行列があふれないようにするため。処理される依頼が最新の画像を描き、大きさの変更も共有の状態から読む）、送れなかったときは、ウィンドウが閉じる途中なら開き直し、そうでなければ `HOST FUNCTION ERROR` にする（画像は写してあるので、次に描くときに表示される）。利用者がウィンドウを閉じるのと同時の `SHOW` の画像は表示されないことがあり、次の `SHOW` で開き直して表示する。Sigmaが終わるときはウィンドウを閉じ、そのスレッドの終わりを5秒まで待つ（終わらなければ、プロセスの終了に任せる）。 |
| ほかのOS | ウィンドウはない（`GFX-WINDOW?` は偽）。端末の大きさは `ioctl`（`TIOCGWINSZ`）で調べる。 |

G3の後にCodexのレビューで、(1) ウィンドウのスレッドが生きているのに依頼を送れないと、`SHOW` がそのスレッドの終わりを無期限に待つ、(2) 終了時の待ちが時間切れでも終わったものとして扱う、と指摘され、上のとおり直した。`SHOW` を100,000回続けて呼ぶ間にウィンドウを3回閉じても止まらないことを確かめた。端末への出力のバッファが4096バイトを超える1回の書き込みを受けられない点（今の呼び出しでは起きない）も直した。また、`REQUIRE-GRAPHICS` は読み込み済みの辞書を更新しないので、古い版のライブラリを読み込んで保存した辞書には、新しい版で加えた語（G2で保存した辞書の `SHOW` など）は加わらない。必要なら、その辞書をソースから作り直す（0.6.0より前のグラフィックスは配布していない）。

#### G8: スプライトとタイルマップ（#434、2026-11-10、利用者の決定）

利用者の指示で、Forth の設計の考え方から離れないことを方針とした。小さな語を組み合わせる、データは利用者が辞書に持つ、制御はプログラムが持つ（呼び返しを作らない）、ほとんどを Forth で書き Zig は速さの要る最小限にする、の4点。

| 項目 | 決定 |
|---|---|
| 読み込み | `REQUIRE-GAME` で `GAME` 語彙に読み込む。ライブラリは Forth（`src/graphics/game.fs`）で、グラフィックスの語を先に読み込む。語彙の語番号は 0x2F8。 |
| スプライト | 番号で管理する表（MSX の PUT SPRITE、NES の OAM）は作らない。`BEGIN-STRUCTURE` の構造体で、`SPRITE:` か `INIT-SPRITE` で利用者が必要な数だけ作る。フィールドは `@` と `!` で読み書きする。アニメーションのコマは画像の中で横に並べる。 |
| 衝突 | `HIT?`（長方形）と `PIXEL-HIT?`（透明色を除いた画素）の問い合わせだけ。MSX の `ON SPRITE GOSUB` のような呼び返しは作らず、どの組を調べるかはプログラムが決める。 |
| タイルマップ | 地図は1タイル1バイト（0〜255）で、`TILEMAP:` の構造体の後ろに行ごとに置く。`C@` `C!`（`TILE@` `TILE!`）で読み書きする。描くのは `DRAW-TILEMAP` の1語で、ビューの長方形の中だけを計算する。地図の外は描かない（繰り返さない）。 |
| 2枚の背景 | 専用の仕組みは作らない。2つの地図を、2枚目を透明色付きで順に描く。 |

#### KEY-HELD? と WINDOW-SIZE のレビューへの対応（2026-11-06）

`b600afb`〜`b699e15` のCodexのレビュー（`.work/codex-review-g5/review.md`）の R01〜R06、懸念 C01、文書の指摘を、利用者の指示で直した。前回の R01・R02・C01・C02 は対処済みと評価された。

- R01（離した知らせが捨てられる）: Windowsのウィンドウは、離した知らせを待ち行列に入れず、ウィンドウが今押しているキー（`down`）と、コアに押したと伝えたキー（`told`）を仮想キーごとに持ち、待ち行列が空のときに両者の違いから離したことを伝える（待ち行列が一杯でも、フォーカスを失っても失わない）。Tk側は `U` を出力の間引きの対象から外した。Windowsのコンソールはフォーカスを失ったとき、押していたキーを1回に1つずつすべて離す（16個の上限をなくした）。
- R02（押している間に文字が変わる）: 同じキーのコードが変わったら、前のコードを離してから新しいコードを押したことにする（コンソール、ウィンドウ）。Tkは `%K` の名前ではなく `%k` のキーの番号で覚え、同じキーの別のコードは前のものを離す。
- R03（Tcl を止めたあとも Tk のキーが残る）: 押しているキーに入力元（端末、ウィンドウ、Tk）を持たせ、離す知らせは同じ入力元のものだけに効く。Tclのプログラムを止めたとき（`TCL-STOP`、通信の切断、取り決めの違反）と、保存などで `U` の残りを読み捨てるときは、Tkのキーを忘れる。
- R04（Tk で 0 0 のまま画像の大きさが変わる）: Tk側で前の画像の大きさを覚え、0 0 のときは画像の大きさが変わったこともウィンドウを合わせ直すきっかけにする。
- R05（電卓の最も小さい数）: 表示の絶対値を倍長で求め、符号の反転も倍長で行って範囲を調べる（収まらなければ Error）。
- R06（長い SIGMA_WISH）: `SIGMA_WISH` が設定されていて長すぎるときは、ほかを探さず起動の失敗（-265）にする。`PATH` の `wish` が長いパスで見つかったときは、見つからないとは扱わない。
- C01（`WM_KEYDOWN` と `WM_CHAR` の対応）: 1つの変数で覚えるのをやめ、`WM_CHAR` の走査コードから `MapVirtualKeyW` で仮想キーを求める。
- 文書: 利用者マニュアルの「Sigmaが読むのは」に `KEY-HELD?` を加え、`HELP` の `KEY-HELD?` にWindowsのコンソールと端末の違いを書いた。

#### ウィンドウの大きさ（WINDOW-SIZE、2026-11-06）

`examples/paddle.fs` の160×120の画像がウィンドウに小さく出ることから、利用者の決定で、画像を表示する領域の大きさを画素数で決める `WINDOW-SIZE ( w h -- )`（下の層は `GFX-WINDOW-SIZE`、組み込み語の最後に加えた）を加えた。

- 各辺は1〜16384（`GFX-INIT` と同じ）、0 0 は画像と同じ大きさ（初めの値）。それ以外は `NUMBER ERROR !` で、前の値が残る。次の `SHOW` から効き、画像そのものと端末への表示は変えない。値は `State` にあり、辞書イメージには入らない。
- 利用者の決定で、縦横の比が違うときは比を保って入る最大の大きさで中央に描き、余りは黒にする。ウィンドウの端を引っぱって大きさを変えたときも同じにした（以前は全体に引き伸ばしていた）。Windowsのウィンドウは任意の倍率、`MOUSE` は描いた位置から画像の画素に戻す。ウィンドウのクラスに `CS_HREDRAW`・`CS_VREDRAW` を付け、大きさが変わると全体を描き直す。
- 利用者の決定で、Tkのウィンドウにも効かせた。`sigma_show` に大きさを渡す（`sigma_show <w> <h> <base64>`）。Tkの写真の画像は整数倍でしか拡大・縮小しないので、入る最大の整数倍（入らなければ整数分の1）で表示する。そのため余りの黒は、Windowsのウィンドウより大きくなることがある。

#### 押しているキー（KEY-HELD?、2026-11-06）

`examples/paddle.fs` で、キーを押し続けるとパッドが最初の1回の後しばらく止まる（キーボードの繰り返しは最初に約0.5秒待つ）ことから、利用者の決定（案B）で、キーを今押しているかを返す `KEY-HELD? ( key -- flag )`（下の層は `GFX-KEY-HELD`、組み込み語の最後に加え、辞書イメージの互換は保つ）を加えた。

- 離したことを知らせるホストでは、離すまで押しているとする: Windowsのコンソールはキーを離した入力記録（押したときの仮想キーとコードを覚えておく）と、フォーカスを失った記録（押していたキーをすべて離す）、Windowsのウィンドウは `WM_KEYUP` と `WM_KILLFOCUS`（文字のキーは `WM_KEYDOWN` の仮想キーと続く `WM_CHAR` の文字を結ぶ）、Tkのウィンドウは `KeyRelease` と `FocusOut` で、Tcl側が押したキーを覚えて新しい知らせ `U 0 <length>\n<code>` を送る。`InputEvent` に `key_release` と `window_key_release` を加えた。
- LinuxとmacOSの端末は離したことを知らせないので、利用者の決定で、最後に押してから0.6秒は押しているとみなす（多くの端末の繰り返しの待ちより長く、押し続けると繰り返しで続く）。離してから最大0.6秒は押しているとみなすことになる。
- 2026-11-08、Codexのレビューと利用者の決定で、端末では、方向キーを押すと、それまで押していることになっていた別の方向キーを忘れるようにした。端末は最後に押したキーしか繰り返さないので、前のキーの0.6秒が残ると、`examples/runner.fs` の `WANTS`（左を先に調べる）で逆方向へ動けなかった。方向キーでないキーでは忘れない（移動中に Z で掘っても移動が続く）。離したことを知らせるホストは変えない。
- 2026-11-08、利用者の指摘と決定（案A）で、端末でキーを離してもしばらく動くのを減らした。同じキーが0.12秒以内にまた来たら繰り返しとみなし、最後の繰り返しから0.12秒だけ押しているとみなす。最初の1回は、繰り返しまでの待ちがあるので0.6秒のまま。短く1回押したときの0.6秒は残る（直すには kitty keyboard protocol などの、離したことを知らせる方式が要る）。
- 対象は、1バイトの文字（ASCII）と256〜277のキー。覚えるのは16個までで、あふれたら最も前に押したものを忘れる。端末のやり直し（行の入力の後）では、端末のキーを忘れる（その間に離しても知らせが届かないため）。時計が戻ったときも忘れる。
- `KEY-HELD?` はホストの入力を読み、その間のキーは `INKEY` のために残す。

#### macOS の音の出力（2026-11-08）

利用者の指示で、macOS で音を出す。AudioToolbox の AudioQueue（`AudioQueueNewOutput`）で、既定の出力装置に 48 kHz 16ビット ステレオを送る。リリースの macOS 版は Linux でクロスビルドし、macOS の SDK がないので、フレームワークはリンクせず、実行時に `dlopen`（`std.DynLib`）で読み込む。読み込めない・作れないときは、これまでどおり音を出さずに進める。

- バッファは Windows と同じ 10 ms を 8 個（約80 ms 先まで）。AudioQueue には実行ループを渡さず、AudioQueue の自分のスレッドが、使い終わったバッファを埋めて戻す（`refill`）。そのスレッドが音のエンジンのただ一人の読み手で、音のスレッドはその間、待つだけで描かない。
- 戻せなかったときは、音のスレッドが AudioQueue をすぐに止め（`AudioQueueStop` の即時）、その後は音なしで進める。
- Hardened Runtime の署名でも、出力に権限（entitlement）は要らない。

#### macOS のシステムの wish を飛ばす（2026-11-08）

利用者の決定で、macOSでは、`TCL-PROGRAM` も `SIGMA_WISH` もないとき、ホストが `PATH` を自分でたどり（`access` の `X_OK`）、システムの `/usr/bin/wish` は飛ばして、最初に見つかった `wish` を使う。`PATH` にほかがなければ `/opt/homebrew/bin/wish`（Apple silicon の Homebrew）、`/usr/local/bin/wish`（Intel の Homebrew）、`/opt/local/bin/wish`（MacPorts）の順に、あるものを使い、どれもなければこれまでどおり `wish` を起動する（システムのものが起動して失敗する）。`PATH` の空の項目（現在のディレクトリ）は見ない。`SIGMA_WISH` が指すものは、そのまま使う。きっかけは、macOS 27.2 で `examples/calculator.fs` が `HOST FUNCTION ERROR !` になったこと。macOS に付いている Tk 8.5 の `Wish.app` は、端末から直接起動しても `SIGKILL (Code Signature Invalid)`、`Launch Constraint Violation` で止められる。Homebrew の `tcl-tk`（9.x）は keg-only でなくなり `wish` を `PATH` に置くが、`PATH` で `/usr/bin` が先にある場合や、Finder から起動した場合のために、決まった場所も探す。

#### Git for Windows の wish を探す（2026-11-06）

利用者の決定で、Windowsでは、`TCL-PROGRAM` も `SIGMA_WISH` もなく、`PATH` にも `wish.exe` がない（`SearchPathW`）とき、Git for Windows に付いている `wish` を探す。場所は `%ProgramW6432%`・`%ProgramFiles%` の下の `Git\mingw64\bin\wish.exe` と、利用者ごとに入れた場合の `%LOCALAPPDATA%\Programs\Git\mingw64\bin\wish.exe` で、この順に、ファイルがあるものを使う。`C:` のような決まったドライブは書かず、環境変数から作る。`SIGMA_WISH` が指すものがなくても、ほかは探さない（指定を黙って変えない）。Linux・macOSは変えない。きっかけは、`SIGMA_WISH` を設定していない環境で `examples/calculator.fs` が `HOST FUNCTION ERROR !` になったこと。

#### Tcl/Tk の2回目のレビューへの対応（2026-11-06）

`6ea9f2a`〜`b600afb` のCodexのレビュー（`.work/codex-review-tcl2/review.md`）で、受け取りの途中の状態と保存・停止の組み合わせの不具合2件と、懸念2件が指摘され、利用者の指示で直した。

- R01: 受け取りの途中で `SAVE`・`SAVESYS` をすると、境界の情報も消え、残りを次の見出しとして読んでいた。利用者の決定（案A）で、途中の本文の領域は解放し、その残りのバイト数（`skip`）を覚えて、届いたら読み捨てる。そのメッセージ1件は失われ、プログラムは動いたまま。見出しの途中まではヒープの外にあるので、そのまま続きを読む。画像の復元でヒープが置き換わるとき（`forgetHeap`）も同じく残りを読み捨てる。案B（保存の前にプログラムを止める）は、Tclの変数やウィンドウも消えるので採らなかった。

- NaN の座標は描かない。`PLOT` は y が NaN のところで線を切る。画素の位置が ±2^61 を超える値（無限大を含む）は、整数の `LINE` と同じくその限界に寄せる。そのため、両端がとても遠い線は向きが変わる。浮動小数点数のまま切り取っても、そのような値では桁落ちで正確な位置を求められないので、この扱いにした。

#### G4: PNGの保存（#372、2026-11-05）

`GFX-SAVE-PNG ( c-addr u -- ior )` と、それを `THROW` するライブラリの `SAVE-PNG ( c-addr u -- )` を加えた（`GFX-SAVE-PNG` は既存の `GFX-` の語の後ろに登録する）。PNGは、赤・緑・青の各8ビット（色の種類2）、フィルターは各行とも0（なし）、インターレースなし。画像のデータは、zlibの見出し（0x78 0x01）、65535バイトまでの無圧縮（stored）のdeflateのブロック、データのAdler-32を1つの `IDAT` に入れる。チャンクのCRC-32はイメージと同じ `std.hash.Crc32` で、データの長さは先に計算して書く。新しいCライブラリは使わない。圧縮しないので、大きさはBMPとほぼ同じ（200×200で120,273バイト）。Pythonの `zlib` とWindowsの `System.Drawing` で読み、CRC・Adler-32・画素が一致することを確かめた（200×200の画像は2つのブロックになる）。

#### G3: LinuxのX11の調査（#368、2026-11-05）

当初はインターネットの資料を参照せず、私が知っている内容から整理した。2026-11-08 に、X11の通信規約（X11R7.7）、`Xserver(1)`、`Xsecurity(7)`、ICCCMの第4章と照合し、次の項目の、ソケットの場所（`/tmp/.X11-unix/Xn`）、接続時の `pixmap-formats` などの情報、要求の大きさの上限（`maximum-request-length`、4バイト単位）、`PutImage`、`Expose`、MIT-MAGIC-COOKIE-1 と `.Xauthority`（`XAUTHORITY` で場所を変えられる）、`WM_PROTOCOLS`/`WM_DELETE_WINDOW` が記述のとおりであることを確かめた。TCPのポートは照合した文書にない。24ビット色を32ビットに入れるのは実際の多くのサーバーの話で、規約の定めではない。

- X11のサーバーとは、Unixドメインソケット（`DISPLAY` が `:0` なら `/tmp/.X11-unix/X0`）か TCP で通信する。通信規約は公開されており、ライブラリ（libX11/libxcb）なしでも Zig で直接話せる。静的リンクの musl の版とも両立する。
- 必要な手順は、接続の確立（認証は `~/.Xauthority` の MIT-MAGIC-COOKIE-1 を読む）、`CreateWindow`・`MapWindow`・`CreateGC`、画素を送る `PutImage`（1回の要求の大きさに上限があるので、行ごとに分けて送る）、イベントの読み取り（`Expose` で描き直し、ウィンドウを閉じるボタンは `WM_PROTOCOLS`/`WM_DELETE_WINDOW` の取り決めで受け取る）。
- 画素の形式は、サーバーの画面の深さと並び（多くは24ビット色を32ビットに入れる）を接続時の情報から読んで合わせる必要がある。
- Wayland だけの環境では XWayland が必要になる。WSLg には X サーバーがあるので、WSL で試せる見込みがある（※推測です）。
- 作業量は、Windows のウィンドウより大きい（接続・認証・要求の組み立て・イベントの解析を自分で書くため）。G3 の最初の実装の条件にはせず、必要になったら別の段階として作ることを勧める。

#### MSX の MML（2026-11-07）

MSX BASIC の動作は、MSX Red Book（UK 版の MSX1 の ROM の解説）に合わせた。

| 項目 | 決定 |
| --- | --- |
| コマンド | `A`〜`G`（`+` `#` `-`、長さ、`.`）、`O` `L` `T` `V` `R` `N` `S` `M` `<` `>`。小文字は大文字として読む。空白は読み飛ばす。BASIC の変数を使う `X` と `=変数;` は扱わない（Forth では文字列をつないで渡せる）。 |
| 範囲 | `O` 1〜8、`L` と音符の長さ 1〜64、`T` 32〜255、`V` 0〜15、`N` 0〜96（0 は休符）、`S` 0〜15、`M` 1〜65535。範囲外や表にない文字は、何も待ち行列に入れずに `INVALID NUMERIC ARGUMENT` 相当のエラーにする（エラーの番号は S2 で決める）。 |
| 引数を省略したとき | Red Book のとおり既定値にする（`O4` `L4` `T120` `V8` `R4` `M255`。Red Book に既定値の記述がない `S` は `S0`）。msx.org の wiki は「前回の値」と書いており、出典が食い違う。`N` は引数が必須。 |
| 音の高さ | オクターブ1の約数（C = 3421 〜 B = 1812）をオクターブごとに半分にする。`B+` は同じオクターブの `C`、`C-` は同じオクターブの `B` になる（ROM の表のとおり）。`N n` は、n を12で割った商 + 1 がオクターブ、余りが音（`N36` は `O4C`）。 |
| 長さ | 50 Hz の刻みで `12000 / (長さ × テンポ)`、付点ごとに1.5倍し、小数は切り捨て、5刻み未満は5にする。日本の60 Hz の機種での定数は、日本版のROMや実機がないので確かめない（利用者の決定、2026-11-08）。Red Book はUK版のROMの定数を12000と書き、日本版との違いはキーボードと文字の部分に限られ、大部分のコードは同じだと書いている。これに従えば日本の機種でも12000で、`L4 T120` は25刻み×1/60秒で約0.42秒となり、楽譜より約2割速い（推定）。Sigmaは、テンポが楽譜どおりになる50 Hz の式を使う。 |
| 音量 | `V` は固定の音量にし、エンベロープを解除する。`S` はエンベロープを使い、音符ごとに R13 を書いてやり直す。`M` はエンベロープの周期。休符は音量0。 |
| 同期 | 1回の `PLAY` の各声部の終わりに区切りを入れ、3声すべてが区切りに着いたときだけ、次の `PLAY` の音符を同時に始める。 |
| 状態 | オクターブ、長さ、テンポ、音量、エンベロープは声部ごとに `PLAY` をまたいで残り、`BEEP` で初期値に戻る。 |

#### S1: AY/YM の合成と MSX の MML（2026-11-07）

`src/core` に、`sound_psg.zig`（AY-3-8910 と YM2149 のレジスタ、トーン、17ビットの LFSR のノイズ、8種類のエンベロープ、AY の実測の音量と YM の1.5 dB 刻みの音量）、`sound_mml.zig`（MSX の MML の解釈）、`sound_engine.zig`（待ち行列と演奏の進行、`SOUND` と `BEEP` の命令、16ビットのステレオの出力）、`sound_wav.zig`（WAV の見出し）を加えた。まだ Forth の語からは使わない（S2 で加える）。

| 項目 | 決定 |
| --- | --- |
| 周期0 | トーンとノイズとエンベロープは、周期0を1として扱う（MAME のコメントでは、エンベロープの0は1の半分。データシートに記載がないので、ほかと同じにした）。 |
| 長い `PLAY` | 音符がまだ残っている声部がすべていっぱいになったら、入れ終わる前でもその `PLAY` を始めてよいことにし、空くのを待つ（MSX の ROM も、待ち行列がいっぱいになると演奏を始める）。この間に音のスレッドが追いつくと、その声部だけ遅れることがある。 |
| 中断 | 待っている間に中断されたら、入れた音符は残る。呼び出し側が、`BEEP` と同じ初期化（音を鳴らさない版）で捨てる。 |
| `BEEP` | 待ち行列と演奏をその時点までの分だけ捨て、PSG を MSX の BIOS の初期値（R0 = 55H、R7 = B8H、R11 = 0BH）にしてから、周期85（約1316 Hz）、音量7で40 ms 鳴らし、もう一度初期値にする。 |
| `SOUND` の時機 | レジスタへの書き込みは、音のスレッドが次に `render` を呼んだときに反映する（ホストの1回分のバッファの遅れ）。 |
| 出力 | 3チャンネルの和を3で割り、直流分を1次のハイパス（係数0.9985、48 kHz で約11 Hz）で除き、0.6倍して16ビットにする。 |
| freestanding | `src/freestanding_check.zig` から `render` を呼び、OS の機能を使わないことを `zig build freestanding` で確かめる。 |

#### S2: Windows の出力層と音の語（2026-11-07）

利用者は、S2 の案（読み込みの語と語彙、新しい辞書イメージの形式、MML の誤りのエラー、`waveOut`、待っている間の中断）を「進んで」として承認した。案で示した番号 -272 は `FONT ERROR`、-273 は `TCL ERROR` が使っていたので、空いている -274 にした。

| 項目 | 決定 |
| --- | --- |
| 読み込み | `REQUIRE-AUDIO`。`REQUIRE-GRAPHICS` と同じく解析器が扱う語で、最初の実行で Forth 語彙に `AUDIO` 語彙を、`AUDIO` に `SND-` の語とライブラリ（`src/audio/audio.fs`、ソースファイルの表の名前は `*audio library*`）を加える。検索順序と定義先は変えない。定義の中では `DEFINITION ERROR`。2つの読み込みの共通の手順は `src/core/library_loading.zig` にまとめた。 |
| 基本語 | `SND-PLAY ( c-addr1 u1 c-addr2 u2 c-addr3 u3 -- )`（音符のない声部は空の文字列）、`SND-SOUND ( reg value -- )`、`SND-BEEP ( -- )`、`SND-PLAYING ( n -- flag )`、`SND-DEVICE ( -- flag )`。この順で辞書に加える（順は辞書イメージの一部）。 |
| ライブラリの語 | `PLAY` `PLAY2` `PLAY3` `PLAY?` `SOUND` `BEEP` と、音を出せるかどうかを調べる `AUDIO? ( -- flag )`。 |
| エラー | MML の誤りは新しいエラー `INVALID MML`（-274）で、何も待ち行列に入れない。`-Daudio=false` の版の `REQUIRE-AUDIO` は新しいエラー `AUDIO UNAVAILABLE`（-275）。`SOUND` のレジスタ 0〜13 と値 0〜255、`PLAY?` の 0〜3 の外は `NUMBER ERROR`（-24）。ホストが音のスレッドを持たないときは `HOST FUNCTION UNAVAILABLE`（-21）、スレッドを始められないときは `HOST FUNCTION ERROR`（-265）。 |
| 辞書イメージ | 音の語を読み込んだ辞書は `SIGIMG35` で保存する（グラフィックスの語の有無によらない）。`SIGIMG34` までしか知らない版は読まない。読み込んだことは 0x02E0（`AUDIO` 語彙の語番号）と 0x02E8（読み込んだ印）に記録する。 |
| ビルド | `-Daudio=false` で `REQUIRE-AUDIO` と `SND-` の語を除く。 |
| ホストとの取り決め | `Writer.audio_fn`（音のエンジンを返す。最初の呼び出しでスレッドを始める）、`audio_device_fn`（音が装置に届くか）、`audio_wait_fn`（数ミリ秒待ち、待つ間の Ctrl+C を報告する）。音の状態（エンジン）はホストが持ち、MML の声部の設定（オクターブ、長さ、テンポ、音量）は `State.audio_voices` に持つ。 |
| スレッド | `src/host_audio.zig`。最初の音の語でスレッドを始め、プログラムの終わりまで動かす。装置は呼び出した側のスレッドで開き、`AUDIO?` がすぐ正しく答えるようにする。装置がない、または途中で失敗したときは、同じスレッドが実時間に合わせて音を作って捨てる（Windows 以外は S5 まではこの動作）。 |
| `waveOut` | 48 kHz、16ビット、ステレオ。10 ms のバッファを8つ使い、遅れは約80 ms。案の4つでは、Windows 11 の `waveOut` は1秒に80個しか受け取らず（音が途切れ、演奏が1.25倍に遅れた）、5つで88個、6つで100個だった。余裕をとって8つにした。スレッドの優先度は `THREAD_PRIORITY_TIME_CRITICAL`。 |
| 中断 | `PLAY` が待つ3 ms ごとに、その間だけ Ctrl+C を受け取る（Windows は `SetConsoleCtrlHandler`、ほかは `SIGINT`）。待つ時間の外の Ctrl+C は、これまでどおりプログラムを終える。端末が1文字ずつの入力（`INKEY` を使った後）のときは、Ctrl+C はキーとして届くので、core が入力を読む（ほかのキーは `INKEY` のために残す）。中断されたら、`BEEP` と同じ初期化（音なし）をして `USER INTERRUPT`（-28）。 |
| 止めた直後 | `BEEP` と中断は、音のスレッドが命令を受け取るまで待ってから戻る（最大で待ち300回）。直後の `PLAY?` は偽になる。 |
| `PLAY?` | 音符のない声部の区切りも、音のスレッドが受け取るまで（次の 1/50 秒まで）は演奏中と数える（MSX の ROM も、すべての声部に区切りを入れる）。 |

#### S3 の方針（2026-11-07、利用者の決定）

利用者は、S3 の案の8項目を、すべて推奨のとおりに決めた（「おすすめで」）。

| 項目 | 決定 |
| --- | --- |
| 機種の切り替え | `MSX-SOUND` `ST-SOUND` `NES-SOUND`（S3b で `C64-SOUND`、S3c で `SCC-SOUND`）で、`PLAY` が鳴らす機種を1つ選ぶ。切り替えると、`BEEP` と同じく演奏を止めて初期化する（音は鳴らさない）。始めは `MSX-SOUND`。同時に鳴らすのは S4。 |
| 声部の数 | MSX、ST、C64 は3声、NES は4声（矩形波2、三角波、ノイズ）、SCC は5声。`PLAY` `PLAY2` `PLAY3` は残し、`PLAYS ( c-addr1 u1 … c-addrn un n -- )` を加える。 |

| 音色 | `n INSTRUMENT` で変える音色を選び、`SQUARE` `PULSE` `TRIANGLE` `SAW` `NOISE`、`DUTY`、`ADSR` で変える（S3b で `RING` `SYNC` `FILTER`、S3c で波形表）。機種にない値は、その機種の一番近い値にする。 |

| Atari ST | S1 の YM2149 を 2 MHz で使い、MSX と同じ MML と `SOUND` を使う。 |
| 音の品質 | 矩形波とのこぎり波は PolyBLEP で帯域を制限する。 |
| 作る順 | S3a（共通の部品、Atari ST、NES）、S3b（C64）、S3c（SCC）。 |

#### S3a: 共通の部品、Atari ST、NES（2026-11-07）

| 項目 | 決定 |
| --- | --- |
| 部品 | `src/core/sound_parts.zig`: 音色（`Instrument`）、ADSR、PolyBLEP の矩形波、平均律の音の高さ（`O4 A` = 440 Hz）、チップの周期の値への丸め。 |

#### S5: Linux の出力層（2026-11-07）

| 項目 | 決定 |
| --- | --- |

#### S8: 音源の統合（2026-11-09、利用者の決定）

利用者は、機種を音色の属性にする案を選び、この案を「実装して」として承認した。S3 と S4 の「機種を1つ選ぶ」「合計8声まで」「MSX と ST は一緒に使えない」は、この形に置き換えた。

| 項目 | 決定 |
| --- | --- |
| 声部 | 常に8声。`PLAYS` は 1〜8、`PLAY?` は 0〜8（機種によらない）。 |
| `STYLE ( chip -- )` | `INSTRUMENT` で選んだ音色の機種を決める。引数は `MSX` `ST` `NES` `C64` `SCC` `AMIGA` のどれか1つ（0 で外す）。それ以外は `NUMBER ERROR`。`BEEP` と機種の切り替えでは変えない。基本語は `SND-STYLE`。 |
| 音符の機種 | 音色に `STYLE` があればその機種、なければ声部の機種（`MSX-SOUND` などと `CHIPS` の割り当て）。音符ごとに決まる。 |
| 声部の割り当て | `CHIPS` の順に番号を付ける。最後の機種の声部より後ろの声部は、最後の機種の音にする。合計が8声を超えると9声目以降は鳴らない。 |
| 機種ごとの部分 | 各機種の部分（`sound_nes.zig` など）は、PLAY の8声ぶんの場所を声部と同じ番号で持ち、機種ごとのミキサーや共有部分を通す。`active` は、選んだ機種と、`STYLE` で使った機種で、止めるまで鳴らし続ける。 |

## 上限・境界・エラー復帰

- データ領域は14000Hからヒープの先頭（`m`）までを割り当て可能とします。末尾を超えるALLOT、変数、配列、文字列、カンマ、Cカンマ、Fカンマは失敗し、データ領域ポインタを進めません。負のALLOTは14000Hまで戻せます。
- セル・浮動小数点数は8バイトのリトルエンディアンで読み書きします。アドレスが0未満、または読み書きが論理メモリ末尾を越える場合は `INVALID MEMORY ADDRESS !` になります。アドレスの折り返しはしません。配列アクセスは要素数を検査しません。
- スタックのアンダーフロー／オーバーフロー、領域超過、辞書／コード超過、ゼロ除算はエラーです。制御ネスト超過はNESTING ERRORとして報告します。エラー報告時にデータ・リターン・浮動小数点・ループ・制御スタックを初期化します。
- コンパイル中のエラーは、作成中のワード、追加コード、当該定義中に確保したデータ領域を巻き戻します。既に完了した定義は残します。トップレベルのALLOT失敗では、割り当て位置は失敗前の値を保ちます。
- FORGETは指定語以後の辞書語をすべて削除し、削除対象内の最初のコンパイル済み定義までコード位置を戻します。データ位置も指定語の割り当て前へ戻し、その後の定義で領域を再利用します。
