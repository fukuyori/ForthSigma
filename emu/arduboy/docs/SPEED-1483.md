## 対象と再現条件

`avr-bench.fs` と `avr-check.fs` は基準としてそのまま残した。追加コードは独自実装であり、他リポジトリ、Web、ゲームROMは参照・取得していない。Git操作・Σ再ビルドは行っていない。

実行体は `.work/arduboy/fast/bin/sigma.exe`、2,610,688 byte、SHA256 `a341ee9e6b1a979c487d3dfe4eb7d4cc1ac0dc1850189fb84eae702dfe552e8f`。利用者指定の現行ソースからの `zig build -Doptimize=fast` 実行体を使用し、サイズとhashを実測照合した。ビルド自体は本作業では再実行していない。

リポジトリ直下のPowerShellから、条件ごとに別プロセスを順次起動する。warm-upは32,000,000 cycle（2仮想秒）、状態をresetし、160,000,000 cycle（10仮想秒）以上になる最初の命令境界まで計測する。命令・IRQ受付を途中で切らず、端数cycleを捨てない。UTIMEの内側計時にCPU・busアクセス・タイマー同期・IRQを含め、初期化・opcode表構築・検査・出力を含めない。外側はPowerShellの `System.Diagnostics.Stopwatch` でプロセス全体を測るため、warm-up、初期検査、表構築、最終全状態出力も含む。本作業で他の重い処理は並行実行していない。順序は各巡でCPUのみ→timer/IRQ、各負荷でvariant 0→5に固定した。3回の測定から統計的な信頼区間を算出したものではなく、微小な差は優劣の根拠にしない。旧 `avr-bench.fs` 単独の測定と異なり、共通runnerにはcycle期限判定と命令数加算があるため、旧STUDYの値との直接比較には使わない。

```powershell

pwsh -NoProfile -File .work/arduboy/1483/measure.ps1
```

生成コードは `.work/arduboy/1483/generate-1483.py` で再生成できる。新規ファイルの改行はLF。起動時の `SAME NAME WORD EXISTS` は、基準のxtを保存した後で同名語を再定義し、それぞれの結合先を固定するための意図した警告である。

## 比較する実装

| variant | CPU handler | Timer0-like同期 |
|---|---|---|
| 0 B | 既存のlocals使用・opcodeからoperand抽出 | 毎命令 |
| 1 B+E | Bと同じ | 次overflow期限に達した命令境界 |
| 2 L | hot wordのlocalsを語ごとの専用cellへ置換 | 毎命令 |
| 3 L+E | Lと同じ | 次overflow期限 |
| 4 L+P | Lにopcode別handlerを追加 | 毎命令 |
| 5 L+P+E | L+Pと同じ | 次overflow期限 |

CPUのみでは同期処理自体を呼ばないため、0/1、2/3、4/5は同じCPU処理の対照測定となる。

LはFLAGS、ADD-F、SUB-F、ALU、IMM、UNARY、BR、SIGNからlocalsを除き、呼出し元も結び直す。scratchは語ごとに独立し、flag更新などの入れ子呼出しでも衝突しない。単一インスタンス用であり再入可能ではない。

PはROMに現れるLDI、MOV、ADD/ADC/CP/AND/OR/EOR、SUBI/CPI、RJMPのopcode別語を生成する。registerアドレス・即値・命令種別・相対offsetを定数にし、実行時の抽出とALU種別分岐を減らす。他の命令はLのhandlerへfallbackする。表は引き続き全65536 opcodeのxt表であり、PCや測定ループ順を決め打ちしていない。PC fetchやLDS/STSの第2word読出しは省かない。生成済みopcodeは任意のPCから同じ語を使え、未知opcodeは基準同様に停止する。一般ROM用の全opcode特殊化やflash書換え対応は本試作に含めない。

Eは絶対cycleの次overflow期限を持ち、期限を跨いだ命令の完了時にdeltaを同期する。通常命令ごとのタイマー語呼出しと加算を省くが、命令境界の期限判定とIRQ受付判定は残す。計測終端でも同期して同一状態にする。IRQ受付の4cycleもタイマーへ反映する。I/Oからタイマーregisterを読む負荷は扱わず、timer I/Oの同期を飛ばしてよいという設計判断ではない。

## 負荷と適用範囲

CPU負荷は既存の自作手組みROM（34命令・47cycle/周）を使う。算術、論理、shift、比較、branch、SRAM、IN/OUT、PUSH/POP、RCALL/RETを含む。周期的に初期値を再設定する合成負荷であり、実ゲームの命令頻度を代表しない。

第2負荷は同じROMに簡易Timer0-likeのoverflow IRQを加える。normal mode相当、64分周、256カウント、16,384 CPU cycleごとのoverflowとし、maskは固定で有効。vector word 0x2EからhandlerへRJMPし、R0/SREG/R24を退避、R24をINCしてSRAM[0x301]へ書き、復元してRETIする。SREGの自動保存はしない。pendingは1bitで合流し、I=0中もoverflowを保持する。RETI後の1命令遅延を処理する。拡張したAVR命令はRETIだけである。

実Timer0のregister、WGM/compare、他のtimer、SPI、OLED、PCM、ADC、EEPROM、GPIO、USB、UIは未実装である。仕様10章の第2負荷にある毎frameのSPI 1024 byte送信も含まない。したがってこれは「CPU＋簡易timer/IRQ」の段階であり、「全周辺」段階や最終方式判断の測定ではない。

既存試作の64 KiB平坦data、独立したSP/SREG cell等を維持している。SREGのIN/OUT以外の実bus制約、SPのI/O alias、未定義pointer重複形式・stack範囲等の診断を実装した本番CPUではない。本ROMはその未実装領域に依存しない。測定対象の命令・operand・副作用を同じAVRの意味で実行し、最適化のためにflag・cycle・IRQ・メモリ書込みを省略していない。

## 正当性

既存のflag検査を基準とLの両方へ結び直して実行し、ADD/ADC/SUB系262,144ケース、INC/DEC/LSR/ROR 262,144ケース、BRBS/BRBC 4,096ケースと、独立した期待メモリ画像・SREG=2・47cycleの検査に通った。hash方式には衝突の可能性があり、AVR全命令適合の証明ではない。

Pの演算6 opcodeについて全入力byte対×carryの786,432ケースを基準と直接比較し、結果register、SREG、cycleが一致した。特殊化したSUBI/CPI 3 opcodeは全入力byte×全初期SREGの196,608ケースで直接一致した。Pが使用するflag語はLと同じであり、その他はLの既存handlerを使う。

両負荷について320,000 cycleまで全6 variantを実行し、65,536 byteの全データ（全registerを含む）とPC、SP、SREG、cycle、timer残余、pending、RETI遅延、IRQ件数、overflow件数、命令数、次期限、同期済みcycleの12 scalarを完全一致比較した。IRQ側は19回のIRQを含む。RETI遅延、I無効中のoverflow合流、受付4cycleの直接検査にも通った。さらに全6 variantで、既知のPC=12・SP=2815・SREG=229・R0=125・R24=51からIRQを受け付け、stack上のreturn PC byte順、SREG/作業registerの復元、RETI後のPC/SP、受付から復帰まで27cycle・12命令を独立した期待値で確認した。単項演算の結果byteも全入力×全初期SREGの262,144ケースで基準とLを期待式に直接照合した。

生ログは `.work/arduboy/1483/correctness.txt`。測定終了時にも全65,536 byteと12 scalarを各runから出力し、`analyse.py` で負荷ごとに全runをbyte/整数列で完全比較する。rolling hashだけで同一性を判断しない。

## 全測定結果

全36runで、負荷ごとに全65,536 byteと12 scalarが完全一致した。CPUのみは160,000,000 cycle・115,744,685命令、timer/IRQありは160,000,001 cycle・115,671,136命令。後者は全runでoverflow=IRQ=9,765、残余=10,241 cycle。全runでdata stack depth=0、process exit=0。flashは全条件で同じROMを初期化し、実行中の書換えはない。

CPUのみのE列は同期処理を実行しない対照条件であり、その差をbatchの効果とは扱わない。localsを専用cellへ置換する手法は、この試作では速度改善を得られなかった。opcode特殊化は毎回のoperand抽出・命令種別分岐を減らし、timer側では期限による同期省略も改善した。性能差の測定であり、ハードウェアcounterによるhotspot内訳の測定ではない。

timer/IRQ負荷で中央値が最大なのは **L+P+E、5,008,705 cycle/s、16 MHz比31.304%**。残り周辺を加える前でも、実時間到達には **3.194倍**が必要である。CPU単体の高速な値を全周辺込みの値に流用しない。

## 推奨と利用者の判断

※推測です。未実装周辺を追加したときの同じ仮想時間に要するホスト時間が、このtimer/IRQ負荷から25〜100%増えると仮定すると、16 MHz比は25.04〜15.65%、実時間到達に必要な追加高速化は約3.99〜6.39倍になる。この仮定は予測区間や上限ではなく、感度を見るための計画用の値である。実ゲーム・SPI・OLED・PCM等の未測定負荷により外れる。

今回の改善後も実時間には届かない。**実時間動作を目指す場合は、native coreの境界設計と別評価を検討することを推奨する。** nativeでも実時間に届くという実測根拠はまだない。学習・正当性比較を優先し、実時間未達を受け入れるなら、今回のL+P+Eを候補にForthで継続できる。

仕様10章に従い、今回の部分負荷だけで最終方式は決定しない。1484〜1486等の周辺実装後、CPU＋全周辺＋画面展開＋PCM sink、さらにUI＋実PCMの段階を再測定する必要がある。60実秒のUI、underrun、入力応答の実時間合格条件も未検証である。

レモンが判断する事項は、①実時間未達を受け入れて最適化Forthで継続するか、②実時間を目標にnative coreの検討へ進むかである。本作業ではnative API追加・方式変更・タスク完了操作は行っていない。
